# AI Coding 可控治理总纲

防止系统失控

> 适用范围：`hospital_medical_insurance_agent` 项目  
> 当前状态：草案 v0.1  
> 文档定位：项目级 AI Coding 治理原则、准入标准与改造路线说明书

---

## 1. 文档目的

本项目不是一个普通的互联网 CRUD 系统，而是一个面向院端医保场景的智能导办与协同中枢。系统天然具有以下特征：

- 业务后果严肃：涉及结算异常、质控、政策解释、权限边界、高风险动作拦截。
- 运行链路复杂：覆盖 `runtime`、`security`、`knowledge_extension`、`adapters`、`skill_infra`、多前端应用。
- 外部依赖众多：模型服务、知识库、MCP、数据库、缓存、院内系统适配器。
- 长期演进压力大：AI 可以快速生成局部补丁，但也更容易带来架构熵增和隐藏风险。

因此，本项目的治理目标不是“人类逐行审查 AI 写的所有代码”，而是建立一套可以持续复用的**边界控制体系**：

- 人类锁死关键边界。
- AI 仅在受限区域内生成和修改。
- AI 改动必须携带可验证证据，而不是依赖人类通读源码。
- 故障发生时可定位、可回滚、可收敛，避免在核心医保流程中扩散。

## 2. 问题定义

### 2.1 本项目当前面临的真实风险

结合当前仓库现状，AI Coding 风险不是抽象的“模型不稳定”，而是以下四类可观测问题：

1. **控制错位**
   - 规则主要存在于文档与开发约定中，但尚未完全下沉为 CI、目录权限、执行隔离等硬约束。
   - 结果是“原则上不能做”和“实际上做不到”之间存在落差。

2. **Happy Path 偏置**
   - AI 更容易补齐正向业务逻辑，而不是优先处理脏数据、超时、权限拒绝、依赖失败、知识缺失、人工确认等非理想路径。
   - 在医保场景里，这类缺失会比业务小 bug 更危险。

3. **局部补丁驱动的架构熵增**
   - AI 对局部文件进行快速修改是强项，但对跨目录的长期架构收口不具备天然优势。
   - 如果缺少模块边界治理，系统会逐步形成重复逻辑、路径分叉、规范与实现脱节。

4. **伪控制感**
   - 如果把“控制”理解为人工 review 每一行 AI 代码，最终会演化为认知带宽瓶颈。
   - 审查速度无法匹配 AI 产出速度，团队最终会在“看不完”和“看不细”之间被迫妥协。

### 2.2 当前仓库里的典型信号

以下信号说明项目已经具备治理基础，但还没有形成完整闭环：

- 根 `AGENTS.md` 已经明确高风险动作必须拦截为 `waiting_human_confirmation`。
- `src/tests/AGENTS.md` 已经建立了较完整的测试金字塔和模块映射。
- `src/security/risk_control/service.py` 已经具备高风险动作识别与人工确认返回能力。
- `src/observability/` 已有指标和追踪骨架，但 `src/runtime/api/app.py` 尚未完整挂载可观测性中间件。
- `src/skill_infra/skill_loader.py` 已支持动态加载 skill，但目前仍属于“逻辑隔离”，尚不是“物理隔离”。

结论：项目并不缺“规范意识”，缺的是把规范变成**不可绕过的系统卡点**。

## 3. 治理目标

本项目 AI Coding 可控治理的目标分为四层。

### 3.1 第一目标：控制边界，而非控制生成过程

我们不追求观察或理解 AI 的全部生成过程，而追求以下结果：

- AI 碰不到关键红线区域。
- AI 即使写错，故障半径也被控制在局部模块内。
- AI 的输出必须经过客观验证门槛，而不是依赖主观“看起来没问题”。

### 3.2 第二目标：把审代码改成审证据

人类主要审核以下内容，而不是逐行通读：

- 改动边界是否正确。
- 是否触及红区。
- 是否包含异常分支验证。
- 是否补齐日志、审计、指标、追踪。
- 是否给出回滚策略和影响面说明。

### 3.3 第三目标：把“上线标准”前移为“准入标准”

任何改动在进入主干前就必须满足：

- 最低限度的负向测试。
- 最低限度的可观测性。
- 对高风险动作和权限边界的显式处理。
- 与模块职责一致，不引入跨层耦合。

### 3.4 第四目标：以目录和运行时边界对抗架构熵增

通过目录分区、模块边界表、准入策略、定期巡检等方式，持续对抗：

- 同一逻辑在多个文件重复实现。
- 新旧路径并存且未收口。
- 接口契约漂移。
- AI 为了局部修复而破坏整体分层。

## 4. 核心治理原则

### 4.1 原则一：数据与逻辑隔离

核心数据流转、状态机、数据库模式、权限与风险策略属于人类锁定边界。AI 只能在既定输入输出契约内实现计算逻辑，不得任意改写系统真实状态的定义方式。

适用于本项目的解释：

- `domain/`、数据库表结构、核心响应契约、风控策略不应由 AI 自由修改。
- skill、展示层、纯函数转换逻辑更适合交给 AI 生成。

### 4.2 原则二：爆炸半径控制优先于“写得聪明”

AI 写坏一小块可以接受，但写坏一个核心链路不可接受。因此模块边界、目录权限和执行隔离优先级高于“让 AI 更聪明”。

适用于本项目的解释：

- skill 应尽量保持插件化、可替换、可下线。
- 外部系统访问必须继续通过 `adapters/` 防腐层。
- 高风险动作必须继续通过 `security/risk_control/` 和人工确认机制拦截。

### 4.3 原则三：强制防守先行

业务逻辑不是准入的充分条件。没有异常分支测试、没有日志、没有追踪、没有失败路径说明的改动，即使 happy path 正常，也不允许进入主干。

### 4.4 原则四：规范必须变成硬卡点

文档只是表达共识的载体，不是治理本身。真正的治理必须落成：

- 目录级权限与变更范围约束。
- CI 串行验证。
- 变更模板。
- 风险分级准入。
- 运行时隔离。

### 4.5 原则五：优先审“边界合法性”，再审“实现优雅性”

一个边界正确但实现普通的改动，通常优于一个实现优雅但破坏边界的改动。对医保场景尤其如此。

## 5. 本项目的三色治理模型

### 5.1 红区

定义：默认只允许人类直接修改，AI 仅可阅读，不可自由生成补丁。

典型对象：

- 领域模型与通用语言字典
- 状态机与工作流核心状态定义
- 数据库 Schema 与迁移
- 高风险动作策略
- 权限与审计规则
- API 核心契约

治理要求：

- 变更必须先有人类写设计说明。
- AI 如参与，仅能在明确范围内做局部辅助。
- 变更必须附影响面、兼容性、回滚策略。

### 5.2 黄区

定义：允许 AI 参与，但必须通过更严格的验证与证据审查。

典型对象：

- 运行时编排与 API 路由
- 知识服务与扩展注册
- skill 基础设施
- 外部系统适配器
- 前端页面逻辑

治理要求：

- 不要求人工逐行读完代码，但必须审变更边界和验证证据。
- 必须补负向测试或说明为何已有测试足够覆盖。
- 必须补可观测性说明。

### 5.3 绿区

定义：鼓励 AI 快速迭代的区域，以低状态、低耦合、低后果模块为主。

典型对象：

- `skills/` 下的自包含能力包
- 提示词、模板、说明文档
- 纯展示层和低风险管理界面
- 纯函数数据转换与格式化逻辑

治理要求：

- 可采用更高自动化比例。
- 仍需基本测试与边界检查。
- 不得越权访问红区职责。

## 6. AI 改动准入制度

### 6.1 AI 改动的最小证据包

任何由 AI 参与生成的改动，在提交时至少应附带以下内容：

1. **边界说明**
   - 改动涉及哪些目录。
   - 为什么这些目录属于本次允许改动范围。
   - 是否触及红区。

2. **异常分支说明**
   - 本次改动覆盖了哪些失败路径。
   - 哪些失败路径尚未覆盖，为什么。

3. **可观测性说明**
   - 是否新增或影响日志、审计、指标、追踪。
   - 如果没有，需给出理由。

4. **验证说明**
   - 跑了哪些单元测试、API 测试、Flow 测试。
   - 哪些测试未执行，原因是什么。

5. **回滚说明**
   - 失败时如何撤回。
   - 影响范围局限在哪个模块。

### 6.2 一票否决条件

满足以下任一条件，改动不得进入主干：

- 修改红区但没有人类先行设计说明。
- 引入跨层调用，绕开既有 `adapters/`、`model_service/`、`risk_control/` 等边界。
- 涉及高风险动作但未进入人工确认链路。
- 没有异常分支测试且无法给出合理豁免。
- 缺失来源引用、脱敏、权限边界或不确定性声明。
- 通过补丁绕过现有规范，而不是沿既有职责扩展。

### 6.3 审核重点转移

审核者优先看以下内容：

- 目录是否改对。
- 角色和权限边界是否被破坏。
- 人工确认链路是否仍然成立。
- 异常和降级路径是否可证明。
- 证据包是否完整。

审核者不应把主要精力浪费在：

- 全量逐行阅读低风险样板代码。
- 纠缠代码风格上的微小差异。
- 在没有证据的前提下凭直觉判断“应该没问题”。

## 7. 项目当前优先治理事项

以下事项应写入后续治理路线图，作为从“文档约束”走向“系统硬卡点”的第一批改造项。

### 7.1 统一测试口径

当前根 `AGENTS.md` 强调“单元测试 → API 测试 → Flow 测试”，而 `src/tests/AGENTS.md` 已扩展到“单元 → 集成 → 性能 → E2E”。

后续应统一为一套项目级口径：

- 基础准入口径
- 完整回归口径
- 不同风险等级对应的最低验证要求

### 7.2 将可观测性从骨架升级为准入门槛

当前项目已有 `observability/` 骨架，但还未形成“没有可观测性就不准进主干”的强门槛。

后续目标：

- 关键链路强制日志和审计。
- 关键接口强制指标暴露。
- 关键跨服务调用强制 trace。
- 高风险与降级路径可被明确追踪。

### 7.3 将 skill 从逻辑隔离升级为执行隔离

当前 skill 以动态加载为主，适合快速扩展，但不等于真正沙箱。

后续目标：

- 短期：约束 skill 的能力边界和上下文注入方式。
- 中期：将 skill 执行从主进程内直接 import，升级为受限执行单元。
- 长期：对 skill 引入资源、权限、网络访问的细粒度限制。

### 7.4 把高风险动作治理提升为全局范式

当前高风险动作拦截已经存在，但应从“一个安全功能”升级为“整个 AI Coding 治理的主导思想”：

- 高风险业务不能自动执行。
- 高风险目录不能被 AI 自由修改。
- 高风险变更必须拥有更高证据标准。

### 7.5 增加架构熵增巡检

建议每个里程碑至少做一次以下巡检：

- 是否新增重复路径。
- 是否存在新旧实现并存。
- 是否有目录职责漂移。
- 是否有绕过既有防腐层和统一入口的快捷实现。

## 8. 建议的治理实施顺序

本项目不宜一口气建设一套庞大流程，而应分阶段落地。

### 阶段 1：先立制度文档

产出：

- 本文档：治理总纲
- 模块边界与权限矩阵
- AI 改动提交模板

目标：

- 先把“问题是什么、边界是什么、如何判定是否合格”说清楚。

### 阶段 2：把规则转为 PR 与 CI 卡点

产出：

- 风险等级标签
- 最低验证矩阵
- 证据包模板
- 流水线检查项

目标：

- 让约束从“建议”变成“必须满足”。

### 阶段 3：补运行时隔离

产出：

- skill 执行边界
- 受限上下文注入
- 高风险变更白名单

目标：

- 控制故障半径和越权风险。

### 阶段 4：定期架构收口

产出：

- 模块巡检清单
- 重复逻辑识别清单
- 新旧路径清理计划

目标：

- 防止 AI 在长期迭代中把系统拖入慢性失控。

## 9. 不采纳的治理方式

以下方式不作为本项目的主治理策略：

### 9.1 不采用“人工逐行审查一切”的控制论

原因：

- 成本过高。
- 认知带宽不可扩展。
- 容易演化为形式审查。

### 9.2 不采用“大而全的状态机式协作流程”

原因：

- 维护成本高。
- 对模型能力变化过于敏感。
- 容易迅速过时。

### 9.3 不把“是否看起来整洁”当作上线标准

原因：

- AI 很擅长生成整洁代码。
- 但整洁不等于具备故障防御、边界正确和运行可观测性。

## 10. 对团队协作方式的要求

### 10.1 对人类开发者

- 负责定义红线，不负责阅读所有低价值样板。
- 负责定义契约、边界、回滚与验证标准。
- 发现文档与实现不一致时，优先修治理对象，而不是靠口头记忆维持一致。

### 10.2 对 AI Agent

- 优先在绿区和黄区受限活动。
- 涉及红区时，必须先请求设计澄清。
- 必须说明改动范围、验证方式与失败路径。
- 不得绕过既有统一入口和基础设施边界。

### 10.3 对 Reviewer

- 审边界、审证据、审失败路径。
- 少做低价值样式争论。
- 对高风险改动坚持更高证据门槛。

---

## 11. 成功判据

当以下现象开始出现时，说明本项目的 AI Coding 治理开始有效：

- 新功能迭代速度没有明显下降，但高风险错误进入主干的概率下降。
- Reviewer 花在逐行读样板代码上的时间下降，花在看验证证据上的时间上升。
- skill 或局部模块出问题时，可以快速下线或回滚，而不是牵一发动全身。
- 测试、日志、审计、追踪逐步成为默认动作，而不是上线前临时补丁。
- 文档、目录职责、运行时行为三者之间的偏差持续缩小。

## 13. 一句话结论

本项目的 AI Coding 可控治理，不建立在“人类逐行控制 AI 输出”之上，而建立在“人类锁死关键边界、AI 在受限区域内工作、所有改动必须通过硬证据准入”之上。

这是本项目在医保严肃场景下同时追求开发效率与上线可控性的最小可行治理路线。

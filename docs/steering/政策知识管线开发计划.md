# 政策知识管线开发计划

**版本**: 1.0 | **日期**: 2026-07-23
**依据**: `docs/steering/政策知识管线设计文档.md`（本计划的唯一需求来源）
**定位**: 把设计文档拆解为可执行、可验证、可回滚的最小单元序列。

> 与设计文档冲突时以设计文档为准；本计划只管"怎么交付"。
> 标注：`[已完成]` 现状已具备；`[半成品]` 有骨架未接通；`[未开始]` 尚未实现。

---

## 0. 价值地图（决策者视角：图什么、站哪、往哪走）

> 本节回答「为什么要重构、每个阶段值多少、什么时候见效」。阶段的工程细节（依赖/风险/任务）见后续章节。每个具体 TDD 计划开头也会标注自身在价值地图的位置。

### 0.1 最终目标（一句话）

把政策知识从「手工维护的扁平表 + 不可溯源的提取」变成「自动提取的结构化事实 + 字段级可溯源 + 质量受控 + schema 可演化」。

重构后这四个痛点消失：
1. **加维度要改代码** → 改语义层配置即可（核心维度固定 schema + 详情 dynamic field）。
2. **不知道"85%"哪来的** → 每个值带 `{来源句子、schema 版本、置信度}`（字段级溯源对象）。
3. **政策更新要手工重灌** → 上传文档自动提取入库（schema-driven extraction）。
4. **空字段照样进库** → 质量门禁（填充率/合规率）挡住（draft→published）。

### 0.2 价值 × 时机矩阵

| 业务价值 | 阶段 | 见效里程碑 | 当前 |
|---------|------|-----------|------|
| 重构不搞砸生产（安全网） | P0 | 现在 | ✅ 完成 |
| 知识模型可配置（加维度不改代码的地基） | P1, P2 | M1 | ✅ M1 达成（P0+P1+P2） |
| 政策原文自动变结构化知识（自动化跃迁） | P3 | M2 | 未开始 |
| 知识可信（质量门禁挡住垃圾数据） | P4 | M3 | 未开始 |
| 知识可演进（改 schema 不丢人工校对） | P5 | M3 | 未开始 |
| 结构化知识能灵活查（政策库+业务库联查） | P6 | M4 | 未开始 |
| 现有 57 条数据进新模型 | P8 | M5 | 未开始 |
| 运营自助操作（前端 5 tab） | P9 | M6 | 未开始 |
| **生产真正用上新模型** | P10 | M7 | ← 价值兑现点 |

### 0.3 为什么前期"看不到价值"（以及它是对的）

策略是「平行建新通路 → 最后一把切换」（设计文档 §9 灰度）：P0–P9 全程在新 collection（`*_v2`）上建，**生产政策问答始终读旧的**。所以 P10 切换前用户侧感受不到变化——这是策略决定的，不是执行问题。

- **代价**：投入大、见效晚。
- **收益**：重构期政策问答零停摆、可随时回滚（P0 安全网的价值）。
- **里程碑 M1–M7 是可验证的中间交付**，不是非等 P10。**M2（P3）后可在新 collection 上跑 demo，提前看到"政策自动变结构化"**，不必等切换。

| 体系 | 代表文件 | 状态 | 谁在用 |

| **旧体系** | `policy_retrieval/milvus_schema.py`（policy_nodes + 旧 policy_facts）、`policy_rules_schema.py`（19 字段扁平）、`milvus_retriever.py`、`runtime/policy_qa/policy_rules_search.py`、`structured_policy_retriever.py` | 在产 | **政策问答 1.1–1.5（生产路径）** |

### 1.2 Collection 命名冲突（迁移期地雷）

- `policy_facts_schema.py`（新）与 `milvus_schema.py`（旧废弃）**都定义 collection 名为 `policy_facts`**，但 schema 完全不同（旧版含 `knowledge_group_id`/`embedding_text`，新版是 `fact_text`/`vector`）。
- `milvus_retriever.py` 仍 `from .milvus_schema import FACT_COLLECTION`。
- 若环境里 Milvus 存的是某一版 schema，另一版的检索器会直接报字段缺失。**Phase 0 必须先厘清并隔离。**

## 2. 阶段总览

原则：**先建新通路（不碰旧路径）→ 打通数据 → 建发布闭环 → 灰度切换 → 下线旧路径**。每个 Phase 是一个可独立验证、可回滚的最小单元。

| Phase | 名称 | 依赖 | 风险 | 验证级别 |
|-------|------|------|------|----------|
| **P0** | 兼容基线与风险隔离 | — | R3（保护政策问答） | 单元+Flow |
| **P1** | 语义层提取契约（§7.1/§3.1） | P0 | R2 | 单元+API |
| **P2** | policy_rules 新 schema + 向量复用（§3.3/§4.1） | P0 | R3 | 单元+API |
| **P3** | 事实拆分 + 结构化入库（§3.2/§2） | P1, P2 | R2 | 单元+API+Flow |
| **P4** | 质量门禁与黄金样本（§5/§7.2） | P3 | R2 | 单元+API |
| **P5** | 重新结构化引擎（§6/§7.3-4） | P4 | R3 | 单元+API+Flow |
| **P6** | 混合检索（§4.2/§4.3/§7.5） | P3 | R2 | 单元+API+Flow |
| **P7** | datasource 多源 + 发现 tab（§7.6/§8.1） | P6 | R2 | 单元+API |
| **P8** | 数据迁移（§9） | P2, P3 | R3 | Flow（全量校验） |
| **P9** | 前端 5 tab 重构（§8） | P3, P6 | R2 | Flow |
| **P10** | 灰度切换与下线 | P8, P9 | R4 | Flow（生产回归） |

> 关键依赖链：`P0 → (P1, P2) → P3 → (P4→P5) / P6 → P7`，`P8/P9` 可与 P4–P7 并行启动前端/迁移脚手架但收口依赖后端。
> 建议起点：**P0 → P1 → P2**（打通语义层→新 schema 的地基，全程不触碰旧 policy_rules，零生产风险）。

## 4. 关键风险与兼容策略

### 4.1 保护政策问答（生产路径）— R3/R4
- 政策问答 1.1–1.5 现读旧 `policy_rules`。**P0 先固化回归基线**；P2–P8 全程用新 collection 名（`*_v2`），不触碰旧 collection；P10 才切换并回归。
- 任一阶段上线前必须跑 P0 基线。

### 4.2 命名冲突 — R3
- 新旧 `policy_facts` 同名。P0.2 强制厘清：新通路只认 `policy_facts_schema.py`，旧 `milvus_schema.create_policy_facts_collection` 去引用并标 deprecated。

### 4.3 迁移期双写/不一致 — R3
- PG 不存政策业务数据（§3.4 决策），避免双写。迁移期新旧 collection 并存，读入口用配置切换。

### 4.4 Milvus 硬约束（§6.1）
- 不支持 partial update → 必须 read-modify-write + upsert 整条（P5.2）。
- dynamic field 不能建标量索引 → `indexed=true` 必须进固定 schema（P2.1/2.4）。

### 4.5 LLM 失控
- schema 演化、重提取均为**人工触发**，不自动批量（设计文档 §10 开放问题 #4）。P5/P8 遵守。

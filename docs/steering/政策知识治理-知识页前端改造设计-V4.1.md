# 医保政策知识治理·AI原生产品设计（V4.1 · 结合现状落地版）

> **产品定位**：面向医保政策问答、待遇解释和业务辅助场景，建设“AI驱动、规则校验、人工决策、受控发布、全程可追溯”的政策知识生产与治理系统。
>
> **核心转变**：不再让人逐条完成政策拆分、字段填写和值域映射，而是由AI完成政策差异识别、规则抽取、统一语义映射、证据核验、冲突发现和影响分析，形成可审查的“知识变更集”；人只处理异常、高风险规则和最终发布决策。
>
> **核心语义原则**：结构化数据库字段、政策结构化字段和用户自然语言表达统一到同一套业务概念、语义字段、指标、标准值域和单位体系，使数据库查询结果能够确定性匹配适用政策。
>
> **场景边界**：本设计面向严肃的医保政策知识治理。AI不直接决定政策效力，不静默修改已发布知识，不绕过审核自动发布。规则运行验证、问答测试和检索评测继续由现有独立“测试”页承担，本次不重复建设。
>
> **版本说明**：V4.1 = V4.0（§1–§25，AI 原生重构设计评审稿，保留原文）+ §26–§31（结合当前代码/数据/API 现状的落地对齐增量）。
> **与 V3.x 的关系**：V4.0 是 V3.2（工作台+详情页+抽屉）的**路线升级**——底层对象（政策规则单元、统一语义、value_role）沿用 V3.2 §17.3 契约，页面层从"人逐条加工"升级为"AI 批量生产 + 人处理异常/决策"。
> **落地依据**：`docs/steering/政策知识治理-需求迭代记录.md` 迭代 13/14；现状代码见 `src/knowledge_extension/rule_explanation/`、`src/runtime/api/`、`src/semantic_layer/`、`src/apps/portal/app/policy-knowledge/`。

## 1. 设计结论

### 1.1 产品不再是“知识录入页面”

传统知识页的工作方式是：

```text
AI抽取候选
→ 人逐条打开
→ 人逐字段检查
→ 人逐个完成映射
→ 人逐条点击通过
```

这种设计只是把人工加工流程搬到线上，AI虽然参与了抽取，但人的工作量仍与知识条数近似线性增长。

AI原生知识治理应调整为：

```text
政策文件进入
→ AI完成整条知识生产链
→ 系统执行确定性质量门禁
→ 形成知识变更集
→ 按风险自动分流
→ 人只处理异常和高风险决策
→ 人工确认发布
→ 生成不可变知识快照
```

### 1.2 用户工作对象发生变化

| 层级 | 核心对象 | 主要使用者 |
|---|---|---|
| 知识底层 | 政策规则单元 | 系统、Agent、开发人员 |
| AI生产层 | 知识变更集 | 知识治理人员 |
| 人工协作层 | 异常决策任务 | 业务专家、审核人员 |
| 运行发布层 | 已发布知识快照 | 医保Agent运行时 |

底层仍然以政策规则单元表达知识；前台不再要求用户逐条加工全部规则，而是围绕“本次政策发生了什么变化、AI哪里不确定、哪些内容需要人决策”组织产品。

### 1.3 最终产品结构

知识模块收敛为四个工作空间：

1. **AI治理驾驶舱**：查看AI处理进度、自动完成率、人工任务和知识质量。
2. **待决策队列**：只呈现AI无法确定或风险较高的问题。
3. **知识变更集**：审查本次新增、修改、替代、失效和映射变化。
4. **已发布知识**：查询稳定知识资产、证据、版本、使用范围和历史。

## 2. 目标与非目标

### 2.1 产品目标

- 将人工工作从“全量逐条加工”降为“异常处理和关键决策”；
- 缩短一份政策从进入系统到形成可用知识的时间；
- 提高关键条件、金额、比例、有效期和例外的结构化准确性；
- 确保每个发布结论都有可定位的原文证据；
- 统一政策字段与数据库字段的概念、指标和值域；
- 支持新旧政策差异、替代关系和影响范围分析；
- 确保只有审核通过、已发布、当前有效的知识进入Agent运行时；
- 让每次人工纠正沉淀为可回归验证的治理资产。

### 2.2 本次非目标

- 不允许AI自动认定政策法律效力；
- 不允许AI直接解决高风险政策冲突；
- 不允许AI静默覆盖已发布知识；
- 不以模型置信度直接决定发布；
- 不在知识页重复建设完整规则测试和问答测试能力；
- 不要求第一期实现无人化知识发布；
- 不为了“多Agent”而暴露复杂的Agent协作过程给用户。

## 3. AI与人的职责边界

### 3.1 AI负责完成的工作

| 能力 | AI输出 |
|---|---|
| 文档解析 | 标题、章节、段落、表格、附件和引用关系 |
| 版本识别 | 新旧文件关系、增删改段落、疑似替代范围 |
| 规则抽取 | 业务主题、适用条件、规则行为、结果、例外和有效期 |
| 规则组合 | 固定值、比例、阶梯、决策表和规则组 |
| 语义映射 | 业务概念、统一字段、指标、标准值域和单位候选 |
| 证据对齐 | 字段级原文锚点和证据角色 |
| 完整度检查 | 按规则类型发现缺失内容 |
| 冲突发现 | 重复、差异、覆盖、替代和潜在冲突候选 |
| 影响分析 | 受影响的旧规则、指标、Skill和问答场景 |
| 风险分级 | 自动通过候选、批量审核候选、单条精审任务 |
| 变更集生成 | 新增、修改、替代、失效、映射变化和风险摘要 |

### 3.2 程序负责的确定性校验

| 校验 | 示例 |
|---|---|
| 数据类型 | 金额必须为数值，日期必须合法 |
| 单位标准化 | 10万元与100000元一致 |
| 比例标准化 | 85%与0.85一致 |
| 区间合法性 | 上下界、开闭区间、重叠和断档 |
| 决策表完整性 | 分支是否重复、冲突或缺少兜底 |
| 证据存在性 | 字段锚点是否仍位于当前文档版本 |
| 编码有效性 | 概念、指标和值域编码是否存在 |
| 发布状态 | 是否审核通过、是否存在阻断问题 |
| 版本一致性 | 是否基于最新知识版本修改 |
| 运行隔离 | 草稿和候选知识不得进入线上检索 |

### 3.3 人负责的工作

- 确认政策效力、适用范围和新旧替代关系；
- 审核资格、拒付、排除、例外和复杂计算规则；
- 处理新概念、新指标和新标准值；
- 决定冲突规则如何处理；
- 审核AI批量修改的变更范围；
- 对高风险规则进行单条精审；
- 承担最终发布责任；
- 确认人工纠正是否沉淀为可复用治理策略。

### 3.4 核心边界

> AI负责生产和推荐，程序负责确定性约束，人负责高风险决策和最终发布。

## 4. 核心领域模型

### 4.1 政策文档版本

政策文件必须首先成为有版本的权威来源对象：

```text
PolicyDocument
└─ PolicyDocumentVersion
   ├─ PolicyNode
   ├─ PolicyUnit
   ├─ Attachment
   └─ SourceAnchor
```

建议保存：

- 文件名称、文号、发布机关；
- 发布日期、生效日期、失效日期；
- 行政区划、统筹区；
- 文件版本和来源地址；
- 正文、附件和表格；
- 与上一版本的关系；
- 原始文件哈希；
- 解析版本和处理时间。

### 4.2 政策规则单元

政策规则单元是最终可被Agent使用的知识底层对象：

```text
政策规则单元
= 业务主题
+ 适用条件
+ 规则行为
+ 规则结果
+ 例外与补充
+ 生效范围
+ 原文证据
+ 统一语义映射
```

建议结构：

```json
{
  "rule_id": "KR-2026-0042",
  "rule_group_id": "KG-2026-0011",
  "topic_concept": "DEDUCTIBLE",
  "rule_type": "DECISION_TABLE",
  "conditions": [],
  "variants": [],
  "exceptions": [],
  "validity": {},
  "evidences": [],
  "semantic_bindings": []
}
```

### 4.3 规则分支与规则组

政策中的分级、分档和区间不应被机械拆成大量孤立知识。

例如：

> 一级医院400元，二级医院800元，三级医院1600元。

应表示为一个决策表规则：

| 条件 | 标准值 | 结果指标 | 结果值 |
|---|---|---|---|
| 医院等级 | `LEVEL_1` | 起付线 | 400元 |
| 医院等级 | `LEVEL_2` | 起付线 | 800元 |
| 医院等级 | `LEVEL_3` | 起付线 | 1600元 |

如果同一条款同时规定起付线和支付比例，可以形成两个规则单元，但共享 `rule_group_id`，保留同源关系。

规则关系包括：

```text
PARALLEL / SUPPLEMENT / EXCEPTION / REPLACE / REFERENCE
```

### 4.4 知识变更集

知识变更集是AI一次处理任务提交给人的完整成果，类似代码变更中的Pull Request：

```text
KnowledgeChangeSet
├─ source_document_version
├─ additions
├─ modifications
├─ replacements
├─ expirations
├─ semantic_mapping_changes
├─ conflicts
├─ impact_scope
├─ quality_report
├─ risk_summary
└─ review_decision
```

每个变更项必须包含：

- 变化前；
- 变化后；
- AI推荐；
- 推荐理由；
- 原文证据；
- 质量校验结果；
- 风险等级；
- 影响范围；
- 是否需要人工决策。

### 4.5 人工决策任务

AI不确定的问题不继续留在普通知识列表中，而是生成明确的决策任务：

```text
DecisionTask
├─ task_type
├─ question
├─ recommended_option
├─ alternatives
├─ evidence
├─ risk_level
├─ affected_items
├─ blocking_scope
└─ human_decision
```

任务类型包括：

- 新概念确认；
- 新指标确认；
- 新标准值确认；
- 低置信映射；
- 证据不足；
- 规则拆分或合并；
- 复杂公式确认；
- 例外规则确认；
- 新旧政策替代；
- 规则冲突；
- 发布影响确认。

### 4.6 已发布知识快照

Agent运行时不读取草稿表、候选表或审核过程表，而只读取经过发布生成的不可变快照：

```text
PublishedKnowledgeSnapshot
├─ snapshot_id
├─ policy_scope
├─ semantic_contract_version
├─ rules
├─ indexes
├─ published_at
├─ published_by
└─ source_change_set
```

新发布产生新快照，不原地覆盖旧快照；支持快速切换、回滚和审计。

## 5. 统一语义和值域设计

### 5.1 统一目标

结构化数据、政策知识和用户表达必须汇聚到同一标准语义：

```text
数据库 PER_TYPE=2 ─────────────┐
政策字段“退休人员” ─────────────┼→ person_type=RETIRED
用户表达“退休职工” ─────────────┘
```

统一内容包括：

- 业务概念；
- 语义字段；
- 指标定义；
- 标准值域和值编码；
- 数据类型；
- 单位和精度；
- 条件操作符；
- 来源映射。

### 5.2 来源映射

| 来源 | 映射示例 |
|---|---|
| 数据库字段 | `yb_zyjyxx.PER_TYPE → person_type` |
| 数据库值 | `2 → RETIRED` |
| 政策字段 | `psn_type → person_type` |
| 政策表达 | `退休人员 → RETIRED` |
| 用户表达 | `退休职工 → RETIRED` |

### 5.3 值角色

政策标准值和数据库实际值可以使用同一个指标编码、值域和单位体系，但必须保留其业务角色：

| 值角色 | 说明 | 示例 |
|---|---|---|
| `OBSERVED` | 数据库业务实际值 | 本次起付线650元 |
| `POLICY_STANDARD` | 政策规定标准 | 首次起付线1300元 |
| `POLICY_RATE` | 政策比例或系数 | 二次住院50% |
| `THRESHOLD` | 判断阈值 | 年度费用10万元 |
| `ACCUMULATED` | 累计值 | 年度累计8万元 |
| `CALCULATED` | 规则计算结果 | 1300×50%=650元 |

### 5.4 条件表达

政策条件统一表达为：

```text
语义字段 + 操作符 + 标准值
```

操作符包括：

```text
EQ / NE
IN / NOT_IN
GT / GE / LT / LE
BETWEEN
CONTAINS
EXISTS
ANY
```

必须区分：

| 状态 | 含义 |
|---|---|
| `ANY` | 政策明确对所有取值适用 |
| `UNKNOWN` | 当前业务数据未取得有效值 |
| `NOT_APPLICABLE` | 字段在当前场景不适用 |
| `NULL` | 数据缺失，原因未判定 |
| 条件不存在 | 政策没有设置该限制 |

### 5.5 确定性匹配

数据库查询结果标准化为运行时上下文：

```json
{
  "target_concept": "DEDUCTIBLE",
  "context": {
    "person_type": "RETIRED",
    "insurance_type": "EMPLOYEE_MEDICAL",
    "medical_type": "INPATIENT",
    "hospital_level": "LEVEL_3",
    "admission_order": "SECOND"
  },
  "business_date": "2026-08-01",
  "region": "110000"
}
```

匹配顺序：

```text
目标业务概念召回
→ 地区和统筹区过滤
→ 有效期和政策版本过滤
→ 标准条件逐项匹配
→ 主规则和例外优先级处理
→ 返回规则结果、证据和匹配轨迹
```

向量检索用于补充解释材料和召回相关段落，不负责决定最终适用哪条待遇规则。

## 6. AI知识生产流水线

### 6.1 总体流程

```text
1. 文件接入与来源校验
2. 文档解析与版面结构识别
3. 新旧版本差异分析
4. 政策规则候选抽取
5. 规则分支、例外和引用关系构建
6. 统一语义、指标和值域映射
7. 字段级证据锚定
8. AI语义复核
9. 确定性程序校验
10. 重复、冲突、替代和影响分析
11. 风险分级和人工任务生成
12. 知识变更集生成
13. 人工决策和审核
14. 发布前质量门禁
15. 生成已发布知识快照
```

### 6.2 差异优先处理

新政策版本进入时，AI不重新要求人审核全部知识，而先识别：

- 新增条款；
- 删除条款；
- 文字变化但语义不变；
- 条件变化；
- 金额或比例变化；
- 有效期变化；
- 例外变化；
- 引用文件变化；
- 疑似替代旧规则。

无语义变化的内容自动归入“无变化”，不产生人工任务。

### 6.3 AI复核与程序校验分工

AI复核关注语义：

- 是否遗漏关键条件；
- 是否把并列规则错误拆开；
- 是否识别例外；
- 是否错误理解引用关系；
- 是否存在疑似冲突。

程序校验关注确定事实：

- 金额、比例和日期是否与证据一致；
- 单位转换是否正确；
- 区间是否重叠；
- 决策表是否存在冲突；
- 标准编码是否有效；
- 证据锚点是否有效；
- 发布条件是否满足。

不能仅使用“第二个模型复核第一个模型”代替确定性校验。

### 6.4 AI输出必须可审查

每个AI结论必须同时提供：

- 结论；
- 结构化结果；
- 直接原文证据；
- 推断部分；
- 不确定部分；
- 候选方案；
- 风险等级；
- 校验结果；
- 对现有知识的影响。

不展示模型内部思维过程，只展示用户可以验证的依据和决策理由。

## 7. 风险分级与自动化等级

### 7.1 风险分级

| 等级 | 典型情况 | 默认处理 |
|---|---|---|
| 低风险 | 原文直接、复用已有概念和值域、无数值变化、无冲突 | AI完成，进入批量审核 |
| 中风险 | 新增条件、简单比例、低置信映射、证据跨段 | 人工快速确认 |
| 高风险 | 复杂计算、例外、资格、排除、跨文件引用、替代关系 | 单条精审 |
| 重大风险 | 核心待遇冲突、政策效力不清、可能影响患者权益 | 高级审核人员决策 |

### 7.2 自动化等级

| 阶段 | AI权限 | 人工要求 |
|---|---|---|
| L1 辅助生产 | AI生成全部候选 | 全量人工审核后发布 |
| L2 批量审核 | 低风险规则可批量确认 | 中高风险逐条审核，人工发布 |
| L3 风险抽样 | 低风险规则抽样检查 | 发布仍由有权限人员确认 |

医保政策场景初期建议从L1开始，积累真实质量数据后进入L2。第一阶段不启用AI自动发布。

### 7.3 批量处理边界

低风险批量确认必须满足：

- 来源政策版本一致；
- 原文直接支撑结论；
- 不涉及新概念、新指标和新值域；
- 不涉及复杂计算、资格、排除和例外；
- 不存在冲突；
- 不存在阻断问题；
- 确定性校验全部通过。

批量确认不等于批量发布。发布前仍执行独立质量门禁。

## 8. 页面路由与信息架构

现有一级导航保持：

```text
概览 / 文档 / 单元 / 知识 / 测试
```

“知识”模块内部增加二级工作空间：

```text
/policy-knowledge/knowledge
  → AI治理驾驶舱

/policy-knowledge/knowledge/decisions
  → 待决策队列

/policy-knowledge/knowledge/change-sets
  → 知识变更集列表

/policy-knowledge/knowledge/change-sets/[changeSetId]
  → 变更集审核页

/policy-knowledge/knowledge/published
  → 已发布知识

/policy-knowledge/knowledge/rules/[ruleId]
  → 规则详情页
```

现有测试页继续负责规则运行测试、问答测试和检索效果评测，不在知识详情页新增完整测试工作区。

## 9. 页面一：AI治理驾驶舱

### 9.1 页面目标

驾驶舱不是传统统计大屏，而是用户每天进入知识模块后的工作入口，回答：

- AI正在处理什么；
- 已经自动完成多少；
- 人还需要处理什么；
- 哪些任务风险最高；
- 当前知识质量是否达到发布要求。

### 9.2 页面布局

```text
┌─ 当前处理 ───────────────────────────────────────────────┐
│ 正在处理3份 │ 已完成12份 │ 失败1份 │ 需要人工决策18项      │
├─ AI生产成果 ─────────────────────────────────────────────┤
│ 生成326条 │ 自动校验通过281条 │ 待确认32条 │ 冲突13条      │
├─ 今日需要我处理 ─────────────────────────────────────────┤
│ 重大风险2 │ 高风险5 │ 新值域8 │ 证据不足3 │ 待发布2批       │
├─ 最近知识变更集 ─────────────────────────────────────────┤
│ 文件 │ 新增/修改/替代 │ 自动完成率 │ 风险 │ 状态 │ 操作       │
├─ 知识质量趋势 ───────────────────────────────────────────┤
│ 原文忠实度 │ 结构完整度 │ 语义一致性 │ 人工干预率          │
└──────────────────────────────────────────────────────────┘
```

### 9.3 核心指标

| 指标 | 说明 |
|---|---|
| AI自动完成率 | 无需逐条人工修改的规则占比 |
| 人工干预率 | 需要人工决策的规则占比 |
| 单份政策处理时间 | 从接入到形成变更集的时间 |
| 人工有效处理时间 | 人真正用于判断和修改的时间 |
| 一次审核通过率 | AI结果首次审核即通过的比例 |
| 关键字段纠错率 | 金额、比例、条件、有效期、例外被人工修正的比例 |
| 发布阻断率 | 因质量问题未能发布的变更占比 |
| 回归问题数 | 新策略导致历史正确规则发生退化的数量 |

知识总量只作为规模指标，不作为AI治理价值的核心指标。

### 9.4 任务入口

驾驶舱优先展示“需要我处理”，并按以下顺序排序：

```text
重大风险
→ 阻断发布的问题
→ 高风险规则
→ 新概念/新值域
→ 普通确认任务
```

## 10. 页面二：待决策队列

### 10.1 页面目标

待决策队列不展示所有知识，只展示AI无法确定、确定性校验未通过或业务上必须由人决定的问题。

### 10.2 队列分类

```text
全部
├─ 规则冲突
├─ 新旧政策替代
├─ 复杂计算
├─ 例外与排除
├─ 新概念/新指标/新值域
├─ 低置信映射
├─ 证据不足
└─ 发布影响
```

### 10.3 决策卡片

每个任务直接呈现一个明确问题：

```text
问题：政策中的“基层定点医疗机构”应映射到哪个标准值？

AI推荐：基层医疗机构（匹配度91%）

推荐依据：
· 原文定义与现有标准值定义一致
· 数据库已有17个字段使用该标准值
· 映射后不会产生规则冲突

其他候选：
A. 一级医疗机构（72%）
B. 新建标准值

影响范围：12条规则、2个指标、1个Skill

[接受推荐] [选择其他候选] [新建标准值] [查看上下文]
```

用户不需要先理解系统内部字段，再判断下一步操作。

### 10.4 决策后联动

人工决策后，系统自动：

- 更新本次变更集；
- 重新运行映射校验；
- 重新运行冲突检测；
- 更新影响范围；
- 判断其他同类任务能否被自动解决；
- 记录人工决策原因；
- 生成可沉淀的治理经验候选。

### 10.5 批量决策

仅当任务满足以下条件时提供批量接受：

- 相同问题类型；
- 相同来源政策版本；
- 相同推荐目标；
- 风险等级为低；
- 不涉及新概念或复杂计算；
- 批量影响范围可完整预览。

## 11. 页面三：知识变更集

### 11.1 变更集列表

列表字段：

| 字段 | 说明 |
|---|---|
| 来源政策 | 文件、文号、版本 |
| AI处理摘要 | 新增、修改、替代、失效数量 |
| 自动完成率 | 无需人工修改的比例 |
| 待决策 | 未解决任务数量 |
| 风险 | 最高风险等级和分布 |
| 影响范围 | 规则、指标、Skill和旧版本 |
| 状态 | 处理中、待决策、待审核、待发布、已发布、失败 |
| 负责人 | 当前审核或发布责任人 |

### 11.2 变更集审核页布局

```text
┌─ AI处理结论 ─────────────────────────────────────────────┐
│ 建议：有条件通过 │ 风险：中 │ 待解决问题：3                │
│ 新增86 │ 修改12 │ 替代9 │ 失效0 │ 无变化237              │
├─ 变更分类 ───────────────────────────────────────────────┤
│ 全部 │ 新增 │ 修改 │ 替代 │ 失效 │ 映射变化 │ 冲突         │
├─ 变更列表 ───────────────────────────────────────────────┤
│ 规则摘要 │ Before/After │ 证据 │ 校验 │ 风险 │ 影响 │ 操作 │
├─ 质量报告 ───────────────────────────────────────────────┤
│ 原文忠实度 │ 结构完整度 │ 语义一致性 │ 规则一致性          │
├─ 底部操作 ───────────────────────────────────────────────┤
│ 保存审核 │ 处理待决策 │ 通过变更集 │ 退回AI重处理 │ 发布    │
└──────────────────────────────────────────────────────────┘
```

### 11.3 AI结论先行

页面第一屏先展示AI推荐和可验证理由：

```text
AI建议：有条件通过

已通过：
· 281条规则结构和证据完整
· 现有概念和值域全部匹配
· 未发现有效期重叠

需人工决定：
· 2条新旧政策替代范围不明确
· 1个新标准值待确认

发布影响：
· 替代9条2025版规则
· 影响4个Skill
· 不影响现有数据库字段映射
```

### 11.4 变更Diff

修改和替代规则采用语义Diff，而不是只展示JSON差异：

```diff
适用范围：
  人员类别 = 退休人员
  医疗类别 = 住院

结果：
- 三级医院首次住院起付线 = 1300元
+ 三级医院首次住院起付线 = 1200元

+ 生效日期 = 2026-01-01
+ 替代规则 = KR-2025-0042
```

支持切换：

- 业务语义Diff；
- 原文Diff；
- 结构化JSON；
- 映射Diff。

默认使用业务语义Diff。

### 11.5 变更项详情

点击变更项进入规则审查工作区：

```text
顶部：AI建议 / 风险 / 校验 / 影响
左侧：新旧原文和证据
右侧：结构化规则变化
底部：接受 / 要求AI修改 / 人工编辑 / 标记问题
```

这不是常驻三栏加工流水线，而是针对某一变更的临时审查界面。

## 12. 页面四：已发布知识

### 12.1 页面目标

已发布知识是稳定知识资产视图，不再承担大量加工操作。

主要能力：

- 搜索已发布规则；
- 查看业务主题、适用条件、结果和例外；
- 查看原文证据；
- 查看统一语义和值域；
- 查看当前使用范围；
- 查看版本和替代关系；
- 查看来源变更集；
- 发起修订或撤回流程。

### 12.2 列表字段

| 字段 | 内容 |
|---|---|
| 规则标题 | 业务主题和结论摘要 |
| 适用范围 | 人群、险种、医疗类别、地区等 |
| 来源 | 政策文件、版本和条款 |
| 有效状态 | 未生效、生效中、已失效 |
| 语义状态 | 概念、指标和值域版本 |
| 使用范围 | 关联Skill、问答场景和指标 |
| 发布版本 | 快照版本和发布时间 |

### 12.3 规则详情

规则详情采用“知识阅读模式”：

```text
规则结论
适用条件
规则结果/决策表
例外与补充
有效范围
原文证据
统一语义映射
使用范围
版本历史
来源变更集
```

修改操作不直接编辑已发布内容，而是“发起修订”，生成新的知识变更集。

## 13. AI协作交互

### 13.1 AI不是独立聊天框

AI能力应嵌入用户当前任务：

- 在变更集页解释为什么发生变化；
- 在决策任务中提供候选和影响；
- 在规则详情中解释证据和映射；
- 在批量处理前展示将发生的变更；
- 在用户修改后自动重新校验。

聊天入口可以存在，但不能取代结构化结果、Diff、证据和明确操作。

### 13.2 自然语言修改

用户可以输入：

> 这条规则不是所有退休人员，只适用于城镇职工退休人员；补充险种条件，其他内容不变。

AI生成变更候选：

```diff
+ 险种类型 = 城镇职工基本医疗保险
```

并自动重新执行：

- 原文证据检查；
- 语义和值域映射；
- 完整度校验；
- 冲突检测；
- 影响分析。

用户确认Diff后才保存。

### 13.3 批量自然语言操作

支持：

> 将本文件中的“退休职工”统一映射为人员类别“退休”、险种“职工医保”，不要创建新概念。

执行前必须展示：

- 将修改多少条规则；
- 当前映射和目标映射；
- 是否存在例外；
- 影响哪些指标、Skill和已发布知识；
- 哪些规则因风险较高不会被批量修改。

批量自然语言操作只能生成变更集，不能直接修改已发布知识。

### 13.4 “为什么”交互

用户可以询问：

- 为什么这条不能自动通过；
- 为什么建议映射到这个标准值；
- 为什么判断为替代旧规则；
- 哪条原文支持这个比例；
- 如果采用另一个映射会影响什么。

AI回答必须引用当前变更、标准定义和原文证据，不输出无法验证的推断结论。

## 14. 证据与可追溯设计

### 14.1 字段级多证据

每个关键字段可以关联一个或多个证据：

| 证据角色 | 用途 |
|---|---|
| 主结论证据 | 支撑核心结论 |
| 适用条件证据 | 支撑人群、场景和地区 |
| 数值证据 | 支撑金额、比例和区间 |
| 例外证据 | 支撑排除和特殊处理 |
| 有效期证据 | 支撑生效和失效时间 |

证据锚点至少包含：

```text
document_version_id
unit_id
clause_path
page_no
exact_quote
start_offset
end_offset
anchor_hash
evidence_role
```

### 14.2 双向定位

- 点击规则字段定位到对应原文；
- 点击原文高亮定位到对应结构化字段；
- 修改字段后证据状态变为“需复核”；
- 文档版本变化时检查锚点是否失效；
- 跨文件证据明确展示来源文件和效力范围。

### 14.3 证据不足处理

AI不能用常识补齐政策没有表达的关键内容。证据不足时：

- 将字段标记为未知或待确认；
- 生成证据不足任务；
- 阻断高风险规则发布；
- 可以推荐相关条款，但不能将推荐条款静默作为正式证据。

## 15. 六维知识质量模型

不使用单一模型置信度代表知识质量。

| 维度 | 核心判断 |
|---|---|
| 原文忠实度 | 结论和字段是否有直接证据，是否存在无依据扩展 |
| 结构完整度 | 条件、结果、例外、有效期是否满足规则类型要求 |
| 语义一致性 | 是否使用统一概念、指标、值域、单位和操作符 |
| 规则一致性 | 是否重复、冲突、覆盖或错误替代其他规则 |
| 时效准确性 | 地区、版本、生效、失效和过渡关系是否清晰 |
| 运行准备度 | 是否满足问答、解释或计算使用条件 |

### 15.1 分类型完整度

| 规则类型 | 必填内容 |
|---|---|
| 固定标准 | 主题、适用条件、结果值、单位、有效期、证据 |
| 比例规则 | 计算对象、基数、比例、条件、证据 |
| 阶梯规则 | 分段条件、边界、各段结果、单位、证据 |
| 决策表 | 输入维度、分支条件、分支结果、兜底说明 |
| 资格条件 | 主体、资格条件、判断结果、例外、证据 |
| 排除规则 | 排除对象、适用范围、排除结果、证据 |
| 办理流程 | 办理主体、前置条件、材料、步骤、时限、证据 |
| 解释规则 | 业务概念、解释内容、适用范围、证据 |

### 15.2 阻断、警告和提示

| 等级 | 影响 |
|---|---|
| 阻断 | 不允许审核通过或发布 |
| 警告 | 允许继续，但必须人工确认 |
| 提示 | 不影响流程，用于优化质量 |

模型置信度仅用于任务排序和候选展示，不直接作为发布门禁。

## 16. 审核、发布与版本治理

### 16.1 状态分离

#### AI处理状态

```text
QUEUED / PROCESSING / NEEDS_INPUT / COMPLETED / FAILED
```

#### 变更集状态

```text
DRAFT / NEEDS_DECISION / PENDING_REVIEW / APPROVED / REJECTED
```

#### 发布状态

```text
UNPUBLISHED / PUBLISHED / SUPERSEDED / WITHDRAWN
```

#### 政策时效状态

```text
FUTURE / EFFECTIVE / EXPIRED
```

审核通过不等于已发布，已发布不等于当前有效。

### 16.2 发布前门禁

发布必须满足：

- 变更集审核通过；
- 所有阻断决策任务已处理；
- 关键字段有直接证据；
- 规则类型完整度达标；
- 关键语义和值域映射已确认；
- 金额、比例、日期和单位校验通过；
- 有效期、地区和政策版本明确；
- 冲突和替代关系已处理；
- 影响范围已确认；
- 当前版本未在审核后发生修改；
- 发布人具备相应权限。

### 16.3 不可变发布

- 已发布规则不能原地修改；
- 修订生成新规则版本和新变更集；
- 新发布生成新知识快照；
- 保留新旧快照和替代关系；
- 支持撤回和快速回滚；
- 每次发布记录人、时间、原因和来源变更集。

### 16.4 运行隔离

运行时只能读取：

```text
已审核
+ 已发布
+ 当前有效
+ 无阻断问题
+ 语义契约版本有效
```

草稿、候选、待决策、映射冲突和已失效规则不得进入正常问答召回范围。

## 17. 人工反馈与AI持续改进

### 17.1 反馈类型

人工修改后，系统识别其是否属于：

- 单条内容修正；
- 当前文件批量规则；
- 同类政策映射规则；
- 新增同义词；
- 抽取正反例；
- 规则拆分或组合模式；
- 冲突处理经验；
- 回归测试用例。

### 17.2 反馈沉淀流程

```text
人工修改
→ AI归纳反馈候选
→ 人确认适用范围
→ 生成治理策略新版本
→ 在历史政策集回归验证
→ 质量报告
→ 人工批准生效
```

AI不能根据一次纠正静默改变全局抽取和映射行为。

### 17.3 治理策略版本

需要版本化管理：

- 抽取提示和模板；
- 规则类型定义；
- 概念和值域映射规则；
- 同义词；
- 冲突检测策略；
- 风险分级策略；
- 规则完整度模板；
- 回归数据集。

每次策略变化都应记录影响范围、验证结果和回滚版本。

## 18. 严肃场景的问答边界

### 18.1 问答风险分层

| 类型 | 示例 | 要求 |
|---|---|---|
| 一般解释 | 什么是起付线 | 已发布定义知识和证据 |
| 流程咨询 | 异地备案怎么办 | 地区、有效期和流程版本明确 |
| 个性化匹配 | 退休人员三级医院能报多少 | 用户上下文完整、确定性规则匹配 |
| 费用解释 | 为什么统筹自付这么多 | 真实结算数据、规则和计算轨迹 |
| 待遇计算 | 本次起付线是多少 | 结构化规则执行和结果核验 |
| 资格认定 | 是否一定符合慢特病待遇 | 不由AI单独作最终行政认定 |

### 18.2 运行时回答结构

高风险回答应明确区分：

```text
业务事实：数据库查询到什么
政策标准：已发布规则规定什么
计算过程：系统如何计算
核验结果：实际值与政策值是否一致
原文证据：来自哪份政策哪一条
不确定项：还缺少什么信息
```

大模型负责组织自然语言，不负责脱离规则和证据自由决定待遇结论。

### 18.3 无法确定时的行为

- 缺少关键业务条件：询问用户或提示补充；
- 政策存在冲突：不给出唯一确定结论；
- 规则已失效：不得作为当前政策回答；
- 仅有候选知识：不得作为正式依据；
- 涉及最终行政认定：明确提示以医保经办或正式审核结果为准。

## 22. 分阶段落地计划

### 阶段一：最小可信闭环

建设：

- 政策文档版本；
- 政策规则单元；
- 统一语义和值域映射；
- 字段级证据；
- AI规则抽取；
- 确定性基础校验；
- 知识变更集；
- 全量人工审核；
- 已发布知识快照。

目标：先证明AI生产结果可审查、可追溯、可安全发布。

### 阶段二：异常驱动审核

建设：

- 待决策队列；
- 风险分级；
- 新旧政策Diff；
- 冲突和替代分析；
- AI建议和语义Diff；
- 低风险批量审核。

目标：将人工工作从全量审核转向异常和高风险处理。

### 阶段三：AI协作提效

建设：

- 自然语言单条修改；
- 批量自然语言变更；
- 影响范围分析；
- 同类任务自动联动解决；
- 六维质量驾驶舱。

目标：进一步降低人工编辑和重复判断成本。

### 阶段四：持续改进

建设：

- 人工反馈归类；
- 治理策略版本；
- 回归数据集；
- 风险抽样审核；
- 策略灰度和回滚。

目标：在不牺牲严肃性的前提下逐步提高自动完成率。

---

## 23. 第一阶段建议收敛范围

为了避免AI原生设计演变为复杂平台，第一阶段只做以下主链路：

```text
政策文件进入
→ AI识别版本变化
→ AI生成政策规则和统一语义映射
→ 程序完成基础校验
→ 形成知识变更集
→ 人工处理异常并审核
→ 人工发布
→ 生成已发布知识快照
```

第一阶段暂不建设：

- AI自动发布；
- 复杂多Agent可视化编排；
- 全自动全局策略自学习；
- 大量低价值统计大屏；
- 知识页内重复测试功能；
- 过度复杂的组织审批流。

## 24. 验收标准

### 24.1 AI生产

- 新文件能够自动生成完整知识变更集；
- 新旧政策能够识别新增、修改、替代和无变化内容；
- 固定值、比例、决策表、资格、排除规则均能正确表达；
- AI输出具有结构化结果、证据、不确定项和风险；
- 无语义变化内容不产生不必要的人工任务。

### 24.2 统一语义

- 政策字段和数据库字段能够映射到同一语义字段；
- 政策表达和数据库字典值能够映射到同一标准值；
- 金额、比例和单位能够标准化；
- 同一指标能够区分政策标准值、业务实际值和计算结果；
- 关键映射冲突能够阻断发布。

### 24.3 人机协作

- 人工默认只看到异常和高风险决策；
- 每个决策任务都有明确问题、推荐、候选、证据和影响；
- 人工修改能够以语义Diff方式确认；
- 批量操作能够预览完整影响范围；
- 人工纠正能够形成治理经验候选，但不会静默改变全局策略。

### 24.4 严肃性与安全

- 每个关键结论都有字段级原文证据；
- 模型置信度不能绕过发布门禁；
- 金额、比例、日期、单位和区间经过确定性校验；
- 审核、发布和政策时效状态相互独立；
- 草稿和候选知识不能进入Agent运行时；
- 已发布知识不可原地修改；
- 能够追溯回答所使用的知识快照和政策版本。

### 24.5 效率指标

- 能够统计AI自动完成率和人工干预率；
- 能够统计单份政策处理时间和人工有效处理时间；
- 能够统计关键字段纠错率；
- 能够识别重复人工决策并形成改进候选；
- 随着治理策略成熟，低风险人工干预率应持续下降。

## 25. 最终设计取舍

本版最终确定：

1. 底层知识对象继续使用支持规则分支的政策规则单元；
2. 人的主要工作对象升级为知识变更集和异常决策任务；
3. AI完成差异识别、规则抽取、语义映射、证据核验、冲突发现和影响分析；
4. 程序负责金额、比例、日期、单位、区间、编码和发布条件等确定性校验；
5. 结构化数据库字段与政策字段共用概念、指标、值域和单位体系；
6. 使用值角色区分政策标准、业务实际、累计值和计算结果；
7. 低风险内容支持批量审核，高风险内容进入单条决策；
8. 人工审核与最终发布保留，第一阶段不启用AI自动发布；
9. 发布生成不可变知识快照，Agent运行时只读取正式快照；
10. 自然语言修改只能生成可审查Diff，不能直接覆盖正式知识；
11. 人工反馈经过版本化、回归验证和人工批准后才能成为全局治理策略；
12. 专门测试能力继续保留在现有测试页，本次不在知识页重复扩展。

该方案不是让AI替代医保业务人员作最终政策判断，而是让AI承担高强度、重复性、可验证的知识生产工作，把人的时间集中到政策效力、复杂规则、异常冲突和发布责任上。在这一边界下，既能显著提高政策结构化速度和知识质量，也适合医保政策问答这一严肃场景长期落地。

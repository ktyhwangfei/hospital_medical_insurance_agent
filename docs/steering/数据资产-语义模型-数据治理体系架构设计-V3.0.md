# 数据资产 · 语义模型 · 数据治理体系架构设计 V3.0

> 日期：2026-09-15 · 状态：**方案稿，待评审**
> 取代：`数据治理流程一体化与治理Flow迁移设计-V2.0.md`（流程视角，已废弃）
> 架构立场：**语义标准是纽带，数据治理是数据资产生命周期，数据模型是独立一层。**
> 参考思路：dbt（数据加工分层）+ OpenMetadata（围绕 Data Asset 的治理）+ Cube（语义模型→编译→消费），**只借鉴分工，不引入任何外部运行时**。

## 1. 概念体系与边界（先定字典，再定代码）

| 对象 | 一句话定义 | 本项目医保例子 |
|---|---|---|
| 数据源 | 原始数据从哪里来 | 医院 SQL Server（o_Trade/o_FeeItem） |
| ODS | 原始数据的落地副本 | PG 发布投影 `mz_trade` / `mz_fee_item` |
| **数据模型** | 可信数据以什么结构组织（粒度/字段/多源标准化） | `dwd_mz_settlement` 结算明细模型 |
| 数据加工 | 原始数据 → 数据模型的转换执行 | Flow 编译物化 view |
| 数据质量 | 数据是否可信的门禁 | 勾稽恒等 / 非空率 / 值域检查 |
| 数据资产 | 已发布、可溯源、可被消费的数据 | data_catalog 登记的 model/metric/view |
| **业务语义** | 业务上如何理解这些数据 | 统筹支付 / 统筹自付 / 个人负担 |
| **语义模型** | 业务对象 + 属性 + 指标 + 维度 + 值域 + 关系 + 计算规则的结构化表达 | `semantic_*` 注册中心 |
| **语义层** | 编译、治理并向消费者提供语义模型的系统 | `SemanticQueryPlanner` → SQL |
| 指标 | 对业务对象的度量定义（业务口径标准） | 「统筹自付金额」SUM |
| Flow | 数据加工/转换/物化的确定性编排 | `governed_flow` |
| Tool | Agent 使用数据/知识/计算能力的受控入口 | `tool_query_semantic_metrics` |
| Workflow | 完成一个业务任务的确定性过程 | `wf_outpatient_settlement_explain` |
| Agent | 理解用户问题并选择能力 | Agent Hub 三智能体 |

三条铁律：

1. **指标 ≠ 数据模型。** 指标是业务度量定义（要什么）；数据模型是结构定义（数据怎么组织）。
2. **语义模型定义业务标准，数据治理按标准加工数据，数据模型是标准落到物理层的实现。** 双向收敛：加工中发现与标准不一致（多医院字段歧义），反过来修正语义。
3. **语义层不承担数据加工职责；数据治理不承担业务解释职责。**

## 2. 总体架构

```
                      【业务语义标准层】
              semantic_layer（对象/指标/维度/值域/关系/映射）
                              │
                 定义「要什么」· 验收「做得对不对」
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                                           ▼
  【数据治理体系】                            【语义服务体系】
  接入 → 探查 → 数据模型 → 加工(Flow)          语义编译(query_planner)
       → 质量 → 发布 → 血缘 → 资产                    │
  （runtime/data_governance + data_model      LogicalPlan → SQL
   + flow + discovery + data_catalog）               │
        │                                           ▼
        └────────► 【可信数据资产】 ◄───── Tool（受控入口）
                        │
                    Workflow（业务任务链）
                        │
                     Agent Hub
```

## 3. 现状盘点：已有 vs 缺口

### 3.1 已有（直接复用，不重造）

| 能力 | 位置 | 证据 |
|---|---|---|
| ODS 落地 | 同步 → PG 投影 `mz_trade/mz_fee_item` | P1 impl_done，批次/质量门/对账已上线 |
| 语义注册中心 | `semantic_*` 14 表：5 域/11 对象/166 指标/18 值域 | 版本锁定、提议评审流已上线 |
| 语义编译→SQL | `query_planner.py`：SemanticQuery → LogicalPlan → SQLAlchemy → SQL | 只读白名单断言 + 生效期裁剪 |
| **派生指标** | `semantic_metrics.expression` + `dependencies`，AST 渲染 | `query_planner._derived_expression` |
| 数据探查 | `runtime/discovery`：表/字段/类型/非空率/值分布/建议对象 | `/semantic-layer/discovery` 页 |
| Flow 生命周期 | draft→validating→pending_review→published→deprecated | 校验/编译/部署/回滚/T8 防篡改（#65） |
| 勾稽质量门 | `QualityGateNode` identity_assertion 运行时评估 | `flow_query_service._assert_identity` |
| 资产目录/血缘 | `data_catalog_assets`/`columns`/`lineage_edges` | #38 已上线 |
| Tool/Workflow | 三分类注册 + 声明式编排 + 降级 unavailable | #69 已上线 |

### 3.2 真正缺口（本方案要建的，只有三个）

1. **数据模型层（DataModel）** —— 当前完全没有。语义层的 dataset 直接绑物理投影表，跳过了「统一结构 + 多源标准化」这层。后果：多医院字段不一致（POOLING_PAY / FUND_PAY / TCZF）无处收敛；ODS 与消费之间没有可治理的结构标准。
2. **语义映射确认流** —— discovery 只产出 `mapped: bool` 标记，没有「候选 → 置信度 → 人工确认 → 绑定」工作流。语义发现（技术字段→业务语义）与数据探查（字段画像）混在一个扫描里。
3. **Flow 的物化职责** —— Flow 当前编译「消费视图」，需要扩展为「数据模型物化执行器」：以数据模型为输出契约，物化出 DWD view 并注册为语义 dataset。

## 4. 核心设计：数据模型层

### 4.1 定位

```
ODS（mz_trade 等投影）
   │  data_model_mappings（多源标准化规则）
   ▼
数据模型（dwd_mz_settlement）── 结构契约：粒度 + 字段 + 角色
   │  Flow 物化
   ▼
dwd view（物化产物）── 注册为 semantic dataset
   │
   ▼
语义指标绑定 → query_planner 消费
```

**关键落地决策**：`query_planner` **不改**。数据模型物化后的 view 以普通 dataset 身份注册进语义对象版本——query_planner、settlement_bridge、可信问题库、Flow 消费链路全部零改动。数据模型层只是**数据供给侧新增的标准化机制**，不是查询侧改造。[建议：这是本方案最小侵入点，评审重点]

### 4.2 表设计（落地为 2 张：模型文档 JSONB + 映射行级表）

> 落地调整（已实施）：字段清单随模型文档 JSONB 整体存储（与 `governed_flows.definition`
> 同模式，版本/乐观锁/content_hash 免费获得）；映射独立成行——确认流按
> (model, field, source) 粒度单独确认，且多医院多源需要行级查询。
> 以下为初始三表设计稿，`data_model_fields` 已并入 `data_models.definition`。

```sql
-- 数据模型：结构契约
CREATE TABLE data_models (
  model_code      TEXT PRIMARY KEY,          -- dwd_mz_settlement
  name            TEXT NOT NULL,             -- 医保结算明细模型
  layer           TEXT NOT NULL,             -- ods/dwd/dws/ads
  grain           TEXT NOT NULL,             -- 粒度声明：trade_no
  entity_code     TEXT NOT NULL,             -- 绑定业务实体（对齐语义对象）
  status          TEXT NOT NULL,             -- draft/published/deprecated
  version         INTEGER NOT NULL,
  owner           TEXT,
  description     TEXT,
  created_at / updated_at / revision ...
);

-- 数据模型字段：结构 + 业务角色
CREATE TABLE data_model_fields (
  model_code      TEXT NOT NULL REFERENCES data_models,
  field_code      TEXT NOT NULL,             -- pooling_payment
  name            TEXT NOT NULL,
  data_type       TEXT NOT NULL,
  field_role      TEXT NOT NULL,             -- identifier/dimension/fact/datetime
  value_domain    TEXT,                      -- 复用语义值域
  expression      TEXT,                      -- DWS 派生：personal_burden = a+b
  dependencies    JSONB,
  PRIMARY KEY (model_code, field_code)
);

-- 多源映射：一个模型字段 ← N 个物理来源（解决多医院字段不一致）
CREATE TABLE data_model_mappings (
  model_code      TEXT NOT NULL,
  field_code      TEXT NOT NULL,
  source_id       TEXT NOT NULL,             -- 数据源（医院）
  physical_table  TEXT NOT NULL,             -- mz_trade
  physical_column TEXT NOT NULL,             -- POOLING_PAY / FUND_PAY / TCZF
  transform_rule  TEXT,                      -- 值域码表映射/单位换算；空=直通
  status          TEXT NOT NULL,             -- draft/confirmed
  PRIMARY KEY (model_code, field_code, source_id)
);
```

关联关系（用户点名的六类对象怎么挂）：

```
semantic_object 1─N semantic_metric ──绑定──► 数据模型字段（model_code.field_code，嵌于 data_models.definition）
data_models 1─N data_model_mappings ──► 物理表（ODS/投影）
governed_flows ──物化──► data_models（flow 输出契约 = model_code）
data_catalog_lineage_edges：source_table → data_model → metric → consumer（新增 model 节点类型）
tool_versions ──target_ref──► query_planner 入口（不变）
```

指标绑定改造：`semantic_metrics` 增加 `model_field_ref`（`model_code.field_code`），与既有 `source_field` 并存过渡：新指标走模型字段，存量指标保留直绑；`source_field` 直绑标记为 deprecated 路径。

## 5. 语义映射确认流（Discovery 拆两半）

### 5.1 拆分

| | 数据探查（Data Profiling） | 语义发现（Semantic Mapping） |
|---|---|---|
| 回答 | 我手里的数据是什么 | 这个技术字段业务上是什么 |
| 归属 | **数据治理**（runtime/discovery，保留） | **语义层**（semantic_layer/mapping，新增） |
| 产出 | 表/字段/类型/非空率/值分布/TOP频率 | 候选语义字段 + 置信度 + 证据 |
| 现有基础 | `scan_sqlserver` 全部保留 | `suggested_object`/`mapped` 升级为确认流 |

### 5.2 新增表

```sql
CREATE TABLE semantic_field_candidates (
  candidate_id    TEXT PRIMARY KEY,
  source_id       TEXT NOT NULL,
  physical_table  TEXT NOT NULL,
  physical_column TEXT NOT NULL,
  candidate_field TEXT NOT NULL,         -- 候选语义字段（或 model 字段）
  confidence      NUMERIC,               -- 0~1
  evidence        JSONB,                 -- 字段名/注释/值域/样本/同表共现
  status          TEXT NOT NULL,         -- proposed/confirmed/rejected
  reviewed_by     TEXT,
  created_at / updated_at ...
);
```

确认后写入 `data_model_mappings`（status=confirmed），即完成「技术字段 → 业务结构」的落地。`rejected` 留档防重复推荐。

## 6. Flow 重新定位：数据模型物化执行器

| 维度 | 现状（#65 消费视图） | 目标（数据加工） |
|---|---|---|
| 输出契约 | consumer 节点 + 消费白名单 | **data_model（model_code）+ 字段清单** |
| 编译产物 | 消费 view | **物化 DWD view：`dwd_<model>_v<n>`** |
| 输入 | source_contracts（物理 dataset） | 不变 |
| 标准化 | 无 | **执行 data_model_mappings 的 transform_rule**（值域码表收敛/列重命名） |
| 质量门 | identity_assertion | 不变 + 语义验收（模型字段 ⊆ 语义标准声明） |
| 生命周期 | draft→published→deprecated，T8 防篡改 | **全部复用，不改** |
| 归属 | `runtime/flow` | 迁入 `runtime/data_governance/flow`（V2.0 结论保留） |

编译器扩展点：`compile_flow_view` 新增物化模式——按 mappings 生成 `SELECT physical_column AS field_code, <transform>` 标准化投影。最小改法：给 FlowDefinition 增加可选 `materialize_model` 字段，不破坏现有消费 Flow。

## 7. 指标模型（原子/派生，已有能力不重造）

- **原子指标**：`fact` 绑定模型字段（`model_field_ref`），如统筹支付 → `dwd_mz_settlement.pooling_payment`。
- **派生指标**：`expression` + `dependencies`，如「个人负担 = 统筹自付 + 大额自付 + 其他自付」。
- 既有 `_derived_expression`（AST 安全渲染）+ 循环依赖检测已覆盖，**本方案不动 query_planner**。
- 指标元数据补齐 business definition（口径句）/默认粒度/允许维度——#35 治理字段已建，直接录。

## 8. 标准样板闭环：Settlement / 统筹自付（唯一首期范围）

> 架构原则：先用一个闭环把所有层的边界逼出来，不泛化。

```
① 数据源     医院 SQL Server（o_Trade/o_FeeItem）
② 探查       discovery 扫描 → 字段画像（已有）
③ 语义发现   POOLING_PAY → 候选「统筹支付」→ 人工确认（§5）
④ 数据模型   dwd_mz_settlement：grain=trade_no，
             原子字段 pooling_payment/pooling_self_payment/large_payment/large_self_payment
⑤ 映射       mappings：本院 T_FundPay→pooling_payment（直通）（§4.2）
⑥ 加工       Flow 物化 dwd_mz_settlement_v1 view（§6）
⑦ 质量       identity 勾稽：total_fee = fund_pay + self_pay（容差 0.01）
⑧ 注册       物化 view 注册为 semantic dataset，对象版本更新（§4.1）
⑨ 指标       原子 4 个 + 派生 personal_burden（expression）
⑩ 发布       语义版本发布 → data_catalog 血缘成链
⑪ Tool       tool_query_semantic_metrics 查询（已有）
⑫ Workflow   wf_outpatient_settlement_explain（已有）
⑬ Agent      Agent Hub 结算解释（已有）
```

⑪~⑬ 已经在线——闭环验收时逐字段对照新旧链路数值必须一致（复用 #65 验收口径：与 `/semantic/query/processed-snapshot` 同读同值）。

## 12. 风险

| 风险 | 应对 |
|---|---|
| `model_field_ref` 与 `source_field` 双路径口径漂移 | Slice 3 强制一致性测试：同指标双路径数值必须相等 |
| Flow 物化模式破坏现有消费 Flow | `materialize_model` 可选字段，缺省走原路径；存量 Flow 回归测试全绿为准入 |
| 数据模型层被用成「又一张宽表直查」绕过语义层 | 物化 view 只允许经 dataset 注册进对象版本消费；data_model 表本身不提供查询端点 |
| 语义候选自动确认污染标准 | confirm 必须人工操作，无自动确认路径 |

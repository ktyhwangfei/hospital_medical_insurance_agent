# 政策知识管线设计文档

**版本**: 1.0 | **日期**: 2026-07-23

> 本文档是政策知识管线（`/policy-knowledge`）重构与语义层联动的**唯一实现依据**。
> 所有数据模型、接口、流程以本文档为准；与现有 `接口设计文档.md`、`语义层设计文档.md` 冲突时，政策知识管线部分以本文档为准。
> 标注说明：`[决策]` = 讨论确认的设计决策；`[来源]` = 引用现有代码/文档；`[推断]` = 基于约束的合理推断。

## 1. 核心设计原则：语义拉齐

> `[决策]` 本管线的全部价值在于把**政策世界**与**数据库世界**拉齐到同一套语义上。

**结构化字段不是"为了存规则"，而是"政策与数据库之间的语义桥梁"。** 语义层统一维护一套指标定义 + 值域字典，让两个世界说同一种话：

| 世界 | 同一个指标的体现 | 值 |
|------|------------------|-----|
| 政策世界 | 规则的结构化条件/结论（`insu_type=城镇职工 → payment_ratio=85%`） | 经字典标准化的标准值 |
| 数据世界 | SQLServer 表字段（结算表.险种列） | 码值或文本，经字典标准化为同一标准值 |

由此实现**双向精准查找**：

- **正向（政策→数据）**：拿政策规则的指标条件，去 SQLServer 查符合的结算数据
- **反向（数据→政策）**：拿患者/结算数据的指标值，去 `policy_rules` 查适用规则（报销比例/起付线）

> 这要求**值域字典是唯一真相**（落在语义层 `value_domain`），政策提取与数据取数都按它标准化。字典合一不是可选项，是语义拉齐的地基 `[决策]`。

### 1.1 三条架构铁律

1. **语义层 = 元数据真相源（single source of truth）**。政策要识别哪些字段/实体/关系，**只**由语义层 `zcgz | 政策规则` 对象下的指标定义决定 `[决策]`。
2. **政策管线 = 消费者**。单向**只读**依赖语义层（拉取"提取契约"），不反向耦合。语义层不知道政策管线存在 `[决策]`。
3. **PG 只存产品/任务类元数据**；政策业务数据（事实、规则）**全进 Milvus** `[决策]`。

## 2. 架构与数据流

```
┌─────────────────────────────── 语义层（元数据真相源）──────────────────────────────┐
│  zcgz「政策规则」对象                                                            │
│   ├ 指标（metric_kind ∈ {field, entity, relation}，indexed，extraction_hint）     │
│   └ 值域字典 value_domain（险种/医疗类别/医院等级…，唯一真相源）                  │
│         │                                                                         │
│         │ 提取契约（只读 API）                                                    │
│         ▼                                                                         │
└─────────┬─────────────────────────────────────────────────────────────────────────┘
          │
┌─────────▼──────────── 政策知识管线（消费者，自洽 5 tab）──────────────────────────┐
│  概览 │ 政策(PG) │ 事实(Milvus) │ 结构化(Milvus) │ 发现(扫描→候选指标回写语义层)  │
│                                                                                    │
│  结构化 = 按提取契约动态生成 LLM prompt → 产出 → 入库                              │
│  发现   = 扫描 policy_rules 高频实体/关系/值域 → 提议候选指标 → 人工确认 → 回写    │
└─────────┬─────────────────────────────────────────────────────────────────────────┘
          │ 数据落库
          ▼
┌─── Milvus ──────────────────────────────┐   ┌─── PG（产品/任务元数据）──────────┐
│  policy_facts  事实全文 + 事实向量        │   │  policy_documents  政策原文       │
│  policy_rules  结构化字段 + 复用事实向量   │   │  schema_update_task 更新任务      │
│  (核心维度=固定schema+索引, 详情=dynamic) │   │  golden_sample     黄金样本集     │
└──────────────────────────────────────────┘   │  datasource        数据源注册表   │
                                                 │  policy_rule_lineage 溯源        │
┌─── 数据源注册表（多源）──────────────────────┐ └──────────────────────────────────┘
│  SQL Server ×N（结构化数据，精确取值）        │
│  Milvus ×1（政策规则，混合检索）              │
│  source_field 三段式寻址 ds.table.column     │
└───────────────────────────────────────────────┘
```

### 2.1 端到端检索流（体现语义拉齐）

用户在「结构化」tab 拼条件（选险种=城镇职工、医院等级=三级、就医方式=住院）：

- **查政策规则**：条件 → `policy_rules` 标量过滤 → 命中规则（payment_ratio=85%）
- **查业务数据**：同一条件 → 经指标 `source_field` 映射 → SQLServer `WHERE 险种=? AND 医院等级=?` → 命中结算记录

> 同一套条件，两种执行目标，由指标映射决定打哪个库 `[决策]`。

## 3. 数据模型

### 3.1 语义层指标扩展（`[决策]` 在现有 Metric 上加字段）

```python
# 语义层 metric（zcgz 对象下）扩展属性
metric_kind: Literal["field", "entity", "relation"]   # 实体/关系也是指标的不同 kind
indexed: bool = False                                  # True=核心检索维度(进Milvus固定schema+标量索引)
                                                       # False=详情字段(走dynamic field)
extraction_hint: str                                   # 给 LLM 的提取说明（动态拼 prompt 用）
status: Literal["draft", "published"]                  # 质量门禁状态
schema_version: int                                    # schema 演化版本
# 现有保留: metric_code, name, object_code, source_field, semantic_type, value_domain
```

> `[决策]` 实体和关系**不**新增资源类型，统一用指标 + `metric_kind` 区分。语义层现有模型不破坏。

### 3.2 policy_facts @ Milvus（事实 = 语义单元 + 向量入口）

```
固定 schema:
  fact_id        (PK)
  doc_id         (标量索引，关联 policy_documents)
  fact_text      (事实全文)
  vector         (事实全文向量，语义搜索主入口)
  created_at
```

> `[决策]` 事实是向量化单元。事实向量是整条管线的语义检索主入口。

### 3.3 policy_rules @ Milvus（规则 = 结构化展开 + 复用事实向量）

```
固定 schema（核心检索维度，建标量索引，用于精准过滤）:
  rule_id        (PK)
  fact_id        (标量索引，关联 policy_facts)
  doc_id         (标量索引)
  rule_type, insu_type, med_type, hosp_lv, psn_type, setl_type   (核心过滤维度)
  schema_version
  vector         (复用对应 fact 的事实向量，混合搜索时辅助排序)

dynamic field（详情字段，字段级溯源，按 schema_version 解释）:
  payment_ratio:     { value, extracted_at, schema_version, confidence }
  deductible_amount: { value, extracted_at, schema_version, confidence }
  cap_amount:        { value, extracted_at, schema_version, confidence }
  amount_band:       { value, extracted_at, schema_version, confidence }
  time_period:       { value, extracted_at, schema_version, confidence }
  admission_order:   { value, extracted_at, schema_version, confidence }
  priority:          { value, extracted_at, schema_version, confidence }
  rule_value:        { value, extracted_at, schema_version, confidence }
  source_text:       { value, extracted_at, schema_version, confidence }
  entities:          [{ name, type, highlight, extracted_at, schema_version }]
  relations:         [{ subject, predicate, object, extracted_at, schema_version }]
  ... 语义层新加的详情指标自动落到这里（dynamic field 天然支持）
```

**设计要点**：

- **字段分层** `[决策]`：核心检索维度进固定 schema + 标量索引（高频过滤性能）；详情走 dynamic field（加指标零成本）。指标 `indexed=true` 才进固定 schema，变更需走 schema 变更流程（见 §6）。
- **字段级溯源** `[决策]`：每个字段值带 `{value, extracted_at, schema_version, confidence}`，而非裸值。代价是查询稍复杂，但可解释性值得——某字段提取错能追到版本/时间/置信度。
- **向量复用** `[决策]`：规则记录的 `vector` = 其所属事实的事实向量。一条事实多条规则 → 多条规则记录共享同一向量。
- **dynamic field 限制**：dynamic field **不能建标量索引**，过滤走扫表。所以 `indexed=true` 的指标必须进固定 schema `[来源: Milvus dynamic field 特性]`。

### 3.4 PG 元数据表（产品/任务类，不存政策业务数据）

```sql
-- 政策原文（现有，保留）
policy_documents (doc_id, title, content_text, status, coverage_ratio, ...)

-- schema 更新任务（重新结构化的异步载体）
schema_update_task (
  task_id, metric_code, change_type,      -- change_type: add|modify|remove
  strategy,                                -- strategy: incremental|full|soft_delete
  status, progress, total, processed,      -- 任务进度
  golden_score,                            -- 质量门禁得分
  created_at, updated_at, finished_at, error
)

-- 黄金样本集（质量门禁基准，已审核规则抽样 + 人工锁定）
golden_sample (
  sample_id, fact_id, metric_code, expected_value,
  locked_by, locked_at
)

-- 数据源注册表（多源）
datasource (
  id, name, type,                          -- type: sqlserver|milvus
  connection_config, enabled
)

-- 溯源（现有 policy_rule_lineage，保留并扩展到字段级）
policy_rule_lineage (rule_id, fact_id, doc_id, schema_version, field, source)
```

> `[决策]` PG 不存政策业务明细（事实/规则），只存元数据与任务。避免 PG/Milvus 双写不一致。

## 4. 向量与检索方案

### 4.1 向量方案（方案 A，确认采纳）`[决策]`

- **embedding 模型 = 现有 `sentence_transformer`**（复用 `get_embedding_provider("sentence_transformer")`，不引入新模型）。
- **向量源 = 事实全文**。事实是语义单元（人按条款读政策），规则是事实的结构化展开。
- **policy_facts**：存事实向量，是语义搜索主入口。
- **policy_rules**：`vector` 字段复用对应事实的事实向量，用于混合搜索时辅助排序。
- **检索结果按 `fact_id` 分组展示**：一条事实的多条规则作为一个整体呈现（起付线/各段比例/封顶线是一条规定的展开），不平铺成孤立规则。

> 定位：**结构化字段=精准搜索（主），向量=语义搜索（辅）**。同事实多规则共享向量导致的"扎堆召回"在此定位下合理——它们本就该一起看 `[决策]`。

### 4.2 三种检索模式

| 模式 | 数据源 | 机制 |
|------|--------|------|
| 精准搜索（高级搜索） | policy_rules | 纯标量过滤（核心维度），不用向量 |
| 语义搜索 | policy_facts | 事实向量召回 top_k，按 fact_id 取其规则 |
| 混合搜索 | policy_rules | 标量过滤（缩小范围）+ 向量排序（复用事实向量）|

### 4.3 跨世界精准查找（语义拉齐落地）

```
用户拼条件: { insu_type: "城镇职工", hosp_lv: "三级", med_type: "住院" }
   │
   ├─ 查政策规则 → policy_rules WHERE insu_type=? AND hosp_lv=? AND med_type=?
   │                → 命中 payment_ratio=85% 等规则
   │
   └─ 查业务数据 → 经指标 source_field 映射
                   → SQLServer: SELECT * FROM 结算表 WHERE 险种=? AND 医院等级=?
                   → 命中结算记录
```

> 同一套指标 + 同一套值域，条件可同时打政策库和数据库名 `[决策]`。

## 5. 质量门禁与指标发布

> `[决策]` 空指标不能发布。指标 draft→published 必须过质量门禁。

### 5.1 指标灰度发布管线

```
① 加指标(draft): zcgz 新增指标，填 metric_kind/indexed/extraction_hint/value_domain
② 试提取:       在「黄金样本集」上跑提取（只提取该新字段）
③ 算质量分:     填充率 / 值域合规率(字典命中) / 与标注一致性
④ 达标?
    否 → 调指标定义(改名/改字典/改 hint)，重试
    是 → 发布(published) → 触发 schema_update_task 批量增量更新
```

### 5.2 黄金样本集 `[决策]`

- **来源**：从已 `reviewed` 的规则里分层抽样（50–100 条 fact），人工锁定字段期望值。
- **用途**：质量门禁基准 + 提取逻辑回归测试集。
- **保护**：黄金集**不被**批量更新覆盖（`golden_sample.locked_at` 标记）。

### 5.3 质量分阈值（建议，待标定）`[推断]`

| 指标 | 建议阈值 | 说明 |
|------|----------|------|
| 填充率 | ≥ 60% | 该字段在样本上能提取到值的比例 |
| 值域合规率 | ≥ 90% | 提取值命中字典标准值的比例（枚举型指标适用）|
| 与标注一致性 | ≥ 0.8 | 与人工锁定值的吻合度 |

> 阈值需根据真实数据标定，首版可放宽，逐步收紧。

## 6. 重新结构化（schema 演化）

> 加/改/删指标后，需把变更应用到 `policy_rules` 历史数据。

### 6.1 Milvus 硬约束（决定方案形状）`[来源: Milvus 特性]`

1. **不支持 partial update**：只能按主键 `upsert` 整条。所以"只更新新字段"物理上仍需 **read-modify-write**（读原记录→内存 merge→upsert 整条）。
2. **dynamic field 老记录新字段返回 null**：加指标后历史规则没有该字段，必须主动更新才填上。

### 6.2 三种变更策略 `[决策]`

| 变更类型 | 策略 | LLM 范围 | 旧字段处理 |
|----------|------|----------|------------|
| 加字段 | incremental | 只提取新字段 | **冻结保护**（已审核字段不被重提取覆盖）|
| 改字段语义 | full | 整条重提取 | 旧值失效（语义变了）|
| 删字段 | soft_delete | 不提取 | 数据保留，按 schema_version 忽略（历史溯源不丢）|

> incremental 的价值不是省 Milvus 写入（都要 upsert 整条），是**保护人工已校对数据不被重新提取覆盖** `[决策]`。

### 6.3 批量更新任务工程要点 `[推断]`

- **异步任务化**：`schema_update_task` 记录状态/进度/失败重试。
- **幂等**：按 `rule_id` 去重，中断重跑不重复计费 LLM。
- **分批限速**：LLM 有 QPS 限制，按批（如每批 20 条）+ 并发控制。
- **并发保护**：read-modify-write 期间加乐观锁（记录 version），或"重提取期间锁定编辑"。
- **字段级溯源**：更新时写全 `{value, extracted_at, schema_version, confidence}`。

## 7. 接口契约

> 解耦关键：政策管线只依赖"提取契约"接口，不直接读语义层内部模型。

### 7.1 提取契约（语义层 → 政策管线，只读）

```
GET /api/v1/medical-insurance-ai-agent/semantic/objects/zcgz/extraction-schema
→ {
    schema_version: int,
    fields:    [{ code, name, kind:"field",    indexed, extraction_hint, value_domain, semantic_type }],
    entities:  [{ code, name, kind:"entity",   extraction_hint, value_domain }],
    relations: [{ code, name, kind:"relation", subject_hint, predicate_hint, object_hint }],
    dictionaries: { <value_domain>: [<标准值列表>] }
  }
```

> 只返回 `status=published` 的指标。政策管线据此动态生成提取 prompt `[决策]`。

### 7.2 质量门禁（政策管线）

```
POST /api/v1/medical-insurance-ai-agent/policy-pipeline/schema-update/validate
  body: { metric_code }
→ { filling_rate, compliance_rate, consistency, passed: bool, samples: [...] }
```

### 7.3 发布 + 触发批量更新

```
POST /api/v1/medical-insurance-ai-agent/policy-pipeline/schema-update/publish
  body: { metric_code, strategy: incremental|full }
→ { task_id }   # 异步任务
```

### 7.4 任务状态

```
GET /api/v1/medical-insurance-ai-agent/policy-pipeline/schema-update/tasks/{task_id}
→ { status, progress, total, processed, golden_score, error }
```

### 7.5 混合搜索（结构化 tab）

```
POST /api/v1/medical-insurance-ai-agent/policy-pipeline/rules/search
  body: {
    mode: precise|semantic|hybrid,
    filters: { insu_type, hosp_lv, med_type, ... },   # 核心维度标量过滤
    query: "住院报销比例",                             # semantic/hybrid 时的语义 query
    target: policy|database|both,                     # 查政策规则 / 查业务数据 / 都查
    top_k
  }
→ { groups: [{ fact_id, fact_text, rules:[...] }] }   # 按 fact_id 分组返回
```

### 7.6 数据源（语义层 discovery 改造）

```
GET  /api/v1/medical-insurance-ai-agent/semantic/datasources           # 列出数据源
POST /api/v1/medical-insurance-ai-agent/semantic/datasources           # 注册数据源(sqlserver|milvus)
POST /api/v1/medical-insurance-ai-agent/semantic/discovery/scan        # 扫描指定数据源(支持多源)
```

> `[决策]` discovery 数据源从"单 SQLServer"扩展为多源注册表。source_field 寻址从两段式 `table.column` 扩为三段式 `ds.table.column`（或加 `datasource_id` 列）。

## 8. 政策知识 5 tab 职责 `[决策]`

| tab | 职责 | 数据落点 |
|-----|------|----------|
| 概览 | 管线统计、质量概览、更新任务状态 | 聚合（PG task + Milvus count）|
| 政策 | 政策原文 CRUD、触发提取 | PG `policy_documents` |
| 事实 | 原文→最小事实拆分 + 向量化管理 | Milvus `policy_facts` |
| 结构化 | 按提取契约提取规则 + 混合搜索（精准/语义/混合，可查政策库或数据库）| Milvus `policy_rules` |
| 发现 | 扫描 `policy_rules` 高频实体/关系/值域 → 提议候选指标 → 确认回写语义层 | 扫描 Milvus，回写语义层 |

> 当前 `extractions` 页同时承载"事实"与"结构化"，重构后拆为两个 tab。原"两步骤详情"演进为「事实」tab 的拆分视图 + 「结构化」tab 的规则视图。

### 8.1 「发现」tab 产物

扫描已结构化规则，统计：

- 高频实体类型 / 高频实体值（政策反复出现但语义层未定义的）
- 高频关系模式（subject-predicate-object 重复组合）
- 值域候选（某字段的值集合，提议为新字典标准值）

→ 产出**候选指标** → 人工确认 → 回写语义层 `zcgz`（draft 状态）→ 走 §5 质量门禁。

> 与语义层 `discovery`（扫 SQLServer 表发现字段）产物相似（都产出候选指标），但数据源不同。复用"候选→确认→入库指标"流程，扫描器分置 `[推断]`。

## 9. 迁移方案（现有数据 → 新模型）

### 9.1 现状 `[来源: 现有代码]`

- `policy_extractions@PG`：93 条，旧扁平格式（`extracted_fields` 是单条规则字段，无 `fact_text`/`rules`/`entities`/`relations`），平均填充 3.0/15 字段。
- `policy_rules@Milvus`：19 固定字段 collection（由 `publish_extraction` 写入）。
- 语义层 `zcgz` 对象存在但 0 指标。

### 9.2 迁移步骤 `[推断]`

1. **重建 Milvus collection**：
   - `policy_rules`：启用 `enable_dynamic_field=True`，固定 schema 只留核心检索维度（§3.3），旧 19 字段中的详情字段转 dynamic。
   - 新建 `policy_facts`（§3.2）。
2. **种子语义层**：把 `数据模型1.xlsx` 政策规则表的字段导入为 `zcgz` 指标（draft），值域字典导入 `value_domain`。**此后 xlsx 退为一次性种子，唯一真相源转语义层** `[决策]`。
3. **数据迁移**：现有 `policy_extractions` → 拆为 `policy_facts`（fact_text 向量化）+ `policy_rules`（结构化字段，补字段级溯源对象）。旧扁平记录按"一条 extraction = 一条 fact + 一条 rule"迁移。
4. **重提取**（建议）：现有数据质量差（3/15 填充），迁移后对文档重新执行提取（按新契约），拉高填充率。

> 迁移期间新旧并存风险：建议灰度——先建新 collection，迁数据 + 校验，再切换读取入口，最后下线旧 collection。

### 9.3 不迁移/保留

- `policy_documents@PG`：保留（政策原文是产品数据，非业务规则）。
- `policy_rule_lineage@PG`：保留并扩展到字段级溯源。
- 现有 `extractions` API：迁移期保留兼容，迁移完成后下线。

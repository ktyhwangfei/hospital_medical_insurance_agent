# 数据库设计文档 — 业务流视角评估

**版本**: 3.0 | **日期**: 2026-05-13 | **状态**: 业务流校验（基于 v3.0 架构修正）

> 本文档基于《数据库设计文档 v3.0》和《总体技术架构-逻辑图》，从业务流程视角评估每张表在架构中的位置、字段完整性和合理性。

## 1. 业务流程与表关系

### 1.1 结算异常导办流程

```
POST /chat
  │
  ├─ [内存] detect_intent_smart()               → 意图识别（关键词/LangGraph图式）
  ├─ [内存] detect_blocked_actions()             → 检查 HIGH_RISK_ACTIONS（⚠ 未查询 risk_control_rules 表）
  │
  ├─ RuntimeOrchestrator.execute_request()
  │   ├─ [DB] skill_storage.get_skill()          → skills 表
  │   │
  │   ├─ SkillExecutionEngine._call_insurance_adapter()
  │   │   └─ [适配器] InMemoryInsuranceInterfaceAdapter
  │   │       ├─ [DB] _data_store.get_patient()                → patients 表
  │   │       └─ [DB] _data_store.get_insurance_transaction()   → insurance_transactions 表
  │   │
  │   ├─ SkillExecutionEngine._call_knowledge_service()
  │   │   └─ [DB] knowledge_store.get_error_code()             → error_code_knowledge 表
  │   │
  │   └─ SkillExecutionEngine._build_response()   → AgentResponse
  │
  ├─ [DB] runtime_state_store.save_workflow()     → workflows 表
  └─ [DB] record_audit_event()                   → audit_logs 表
```

**架构图数据流**: 统一交互API → 会话上下文 → 意图识别 → 任务规划 → 编排执行 → 能力调度（Skill/MCP） → 结果生成

**表访问顺序**: patients → insurance_transactions → error_code_knowledge → skills → workflows → audit_logs

### 1.2 高风险动作 + 人工确认流程

```
detect_blocked_actions(message)
  │
  ⚠ 仅检查内存中的 HIGH_RISK_ACTIONS set
  │  (「正式结算」「退费」「冲正」等 7 个关键词)
  │  未查询 risk_control_rules 表（L2 层未接入）
  │
  ├─ build_human_confirmation_response()
  │   └─ [DB] create_task()                       → tasks 表
  │       (task_type='human_confirmation', 仅填充 task_id/task_type/status/
  │        description/responsible_role/workflow_id)
  │
  POST /tasks/confirm  (用户确认后)
  │
  ├─ [DB] get_task(task_id)                       → tasks 表
  ├─ [DB] update_task_confirmation()              → tasks 表 (status→confirmed/rejected)
  ├─ [DB] runtime_state_store.get_workflow()      → workflows 表
  └─ [DB] record_audit_event()                   → audit_logs 表
```

**架构图数据流**: 编排执行引擎 → 能力调度 → [风险控制拦截] → 人工确认 → 恢复执行

**v3.0 变更影响**: tasks 表已扩展为"工作流执行单元"，但当前代码**仅写入 human_confirmation 类型**，新增的 input_data/output_data/executor_type/duration_ms 字段尚为空值。

### 1.3 LangGraph 图式执行流程

```
POST /chat (意图→LangGraph场景)
  │
  ├─ detect_intent_smart() → 路由到 LangGraph 图
  │
  ├─ scenario_executor._execute_langgraph()
  │   ├─ 编译图（settlement_exception / pre_discharge_qc）
  │   ├─ [内存] MemorySaver 检查点（⚠ 未使用 PostgreSQL checkpoints 表）
  │   ├─ 图节点执行：candidate_retrieval → discrimination → validation → decision
  │   │   ├─ [适配器] 调用多个业务适配器
  │   │   └─ model_service.gateway.generate() → 模型网关 → vLLM → LLM
  │   │
  │   ├─ interrupt() 触发人工确认
  │   │   ├─ [DB] create_task()                   → tasks 表
  │   │   └─ [内存] _checkpoint_registry 映射 task_id → (graph, thread_id)
  │   │
  │   └─ POST /tasks/confirm → Command(resume=...) 恢复图执行
  │
  ├─ [DB] save_workflow()                         → workflows 表
  └─ [DB] record_audit_event()                   → audit_logs 表
```

**架构图数据流**: 任务规划 → (复杂规划) → 模型网关 → vLLM → LLM → 编排执行 → 检查点恢复

**关键问题**: PostgreSQL `checkpoints` 表已定义但未接入，当前仍用内存 `MemorySaver` + `_checkpoint_registry` dict。

### 1.4 MCP 工具调用流程

```
POST /chat (意图→MCP工具调用场景)
  │
  ├─ scenario_executor._execute_mcp_invocation()
  │   ├─ [DB] mcp_registry.get_server()           → mcp_servers 表
  │   ├─ [DB] mcp_registry.get_capability()        → mcp_capabilities 表
  │   ├─ 安全边界校验（risk_level + required_roles）
  │   ├─ MCP SDK 调用（stdio 传输）
  │   └─ 返回工具执行结果
  │
  ├─ [DB] save_workflow()                         → workflows 表
  └─ [DB] record_audit_event()                   → audit_logs 表
```

**架构图数据流**: 编排执行 → 能力调度 → MCP → 业务系统适配器 → 医院业务系统/医保专业系统

**v3.0 变更影响**: 原 `tools` 表已移除，所有工具（含内置）统一通过 MCP 协议。当前内置工具尚未全部封装为 MCP Server。

### 1.5 模型服务测试流程

```
POST /model-test | POST /model-test/stream
  │
  ├─ model_service.gateway.generate()
  │   ├─ Router 路由到 Provider
  │   ├─ HTTP 调用 LLM API
  │   └─ 返回生成结果（非流式/SSE流式）
  │
  ⚠ 不写入任何表，无审计记录
```

**架构图数据流**: 统一交互API → 模型网关 → vLLM → LLM

### 1.6 Skill/MCP 管理 CRUD 流程

```
GET/POST /skills | GET/PUT/DELETE /skills/{skill_id}
  ├─ [DB] skill_storage.*                         → skills 表

POST /mcp/servers
  ├─ [DB] mcp_storage.save_server()              → mcp_servers 表

GET /mcp/storage/health
  ├─ [DB] mcp_storage.health_check()             → mcp_servers 表（连接验证）
```

## 3. 逐表评估

### 3.1 patients — 患者信息

| 评估项 | 结论 |
|--------|------|
| **架构位置** | DaaS 核心业务数据，被适配器查询 |
| **业务流** | `/patient-context` 端点 → 适配器内部查询 → 返回患者上下文 |
| **字段完整性** | ✅ 合理。仅存基础标识（patient_id + name），详细信息由 HIS/EMR 适配器实时获取 |
| **字段合理性** | ✅ 精简设计符合"平台不替代业务系统"原则 |
| **当前使用** | ✅ `_data_store.get_patient()` 已被实际调用 |
| **建议** | 保持现状 |

### 3.2 insurance_transactions — 医保交易记录

| 评估项 | 结论 |
|--------|------|
| **架构位置** | DaaS 核心业务数据，承载结算/上传状态 |
| **业务流** | 适配器查询 → 场景执行器分析异常 → 错误码匹配 → 导办建议 |
| **字段完整性** | ⚠ 缺少业务关键字段：`settlement_amount`、`uploaded_at` |
| **字段合理性** | ✅ error_code 关联到 error_code_knowledge 的设计合理 |
| **当前使用** | ✅ 适配器和场景执行器都在使用 |
| **建议** | 新增 `settlement_amount DECIMAL(12,2)`、`uploaded_at TIMESTAMPTZ` |

### 3.3 workflows — 工作流实例

| 评估项 | 结论 |
|--------|------|
| **架构位置** | PaaS 编排层状态机，对应架构图"编排执行引擎"的核心输出 |
| **业务流** | 每次请求处理完成后 save_workflow()，记录场景/步骤/状态 |
| **字段完整性** | ✅ 已有 session_id 和 patient_id 关联字段（v3.0 设计文档已标注） |
| **字段合理性** | ⚠ `steps` 用 JSON 而非 JSONB，无法建 GIN 索引 |
| **当前使用** | ✅ runtime_state_store 和 audit service 都在使用 |
| **建议** | steps/audit_refs/knowledge_events/knowledge_degradation_reasons 从 JSON 改为 JSONB |

### 3.4 tasks — 工作流执行单元（v3.0 重新定义）

| 评估项 | 结论 |
|--------|------|
| **架构位置** | PaaS 编排层，对应架构图"编排执行引擎 → 任务表" |
| **业务流** | 编排引擎每执行一个原子步骤（MCP调用/LLM调用/人工确认/Skill执行）写入一条 task |
| **字段完整性** | ✅ v3.0 新增字段覆盖全面：input_data/output_data/executor_type/duration_ms |
| **字段合理性** | ⚠ `confirmed_at` 仍为 VARCHAR(32) 应改为 TIMESTAMPTZ |
| **当前使用** | ⚠ 仅 human_confirmation 类型有实际写入，新增字段均未被代码填充 |
| **建议** | 1. confirmed_at 改为 TIMESTAMPTZ；2. 编排引擎各执行点逐步接入 task 写入 |

| 评估项 | 结论 |

## 5. 需要沟通的问题

### 5.1 v3.0 前向设计 vs 当前代码的落差

v3.0 对 tasks 和 audit_logs 做了大量前瞻性字段扩展，但当前代码完全未填充这些字段。

**建议**: 彻底清理。移除 `storage/tool/`、`domain/tool/`、`skill_routes` 中 tools 部分。前端原型中 tools 管理页面改为 MCP capabilities 管理。

### 5.3 knowledge_assets 与模板表合并

与 v2.0 评估结论一致：**不应合并**。查询模式不同、专属字段结构不同、生命周期不同。

### 5.4 risk_control L1/L2 分层防御

- L1（硬编码 HIGH_RISK_ACTIONS）存在误触发风险
- **短期**: 优化 L1，加入正则匹配（区分"执行退费"和"咨询退费流程"）
- **中期**: 接入 risk_control_rules 表，支持 JSONLogic 规则引擎

# 医保 AI 平台业务语义层（Business Semantic Layer）设计规范

**版本：V1.0**
**状态：正式设计规范**
**日期：2026-07-14**

---

# 第一章 文档概述

## 1.1 文档目的

本文档定义医保 AI 平台业务语义层（Business Semantic Layer）的总体架构、核心模型、建设方式及运行机制。

通过建设统一业务语义模型，将医院、医保等异构业务数据转换为标准化业务事实（Business Facts），为：

- 医保智能咨询 Agent
- 医院端智能助手
- 基金监管 Agent
- 智能审核系统
- 数据分析应用

提供统一的数据语义能力。

## 1.2 建设背景

随着医保 AI 应用不断深入，平台需要支撑大量 Skill（费用解释、待遇查询、政策解释、退费影响评估、慢特病咨询、转诊备案指导、基金异常分析等）。不同 Skill 均需要访问医院业务数据。

传统方式存在三大问题：

1. **数据强耦合**：Skill 直接依赖数据库结构，不同医院无法复用，数据结构变化影响所有应用，AI 无法理解业务含义
2. **业务语义缺失**：数据库字段名（如 `FUND_PAY`）无法被 AI 理解其真实业务含义
3. **数据来源不可追溯**：无法快速定位回答依据哪张表、哪个字段、哪个转换规则

因此，需要建设面向医保业务的统一语义层。

# 第二章 平台定位

## 2.1 定位声明

这不是传统意义上的"语义层"，而是 **Business Semantic Platform（业务语义平台）**。它包含两个独立子系统：

- **Design Time（语义资产建设平台）**：负责语义资产的建模、发现、治理和发布
- **Run Time（语义运行平台）**：负责根据语义资产将异构数据转换为标准化 Business Facts

## 2.2 设计边界

**本语义平台不负责：**

- SQL 优化
- 数据仓库建模
- 数据同步
- 政策规则计算
- 知识图谱推理
- Workflow 编排
- Agent 调度
- Prompt 管理

**只负责：构建标准化 Business Facts。**

# 第三章 总体架构

```
┌── Design Time（语义资产建设）──────────────────┐
│                                                 │
│  数据源扫描 → Excel 导入 → 语义发现              │
│       ↓                                         │
│  Business Domain（固定 11 域，纯目录）           │
│       ↓                                         │
│  Business Object（业务实体定义）                 │
│       ↓                                         │
│  Metric → Value Domain → Data Lineage           │
│       ↓                                         │
│  Semantic Registry（发布 → 版本管理）            │
│                                                 │
│  负责：数据架构团队                               │
└──────────────────────┬──────────────────────────┘
                       │  Skill 声明所需 Object + Metric
                       ▼
┌── Run Time（语义运行）──────────────────────────┐
│                                                 │
│  Skill Router（决定用哪个 Skill）                 │
│       ↓                                         │
│  Registry 查询（获取 Metric 映射）               │
│       ↓                                         │
│  Business Facts Builder（调适配器取数 → 值域统一）│
│       ↓                                         │
│  Business Facts（标准化 JSON）                   │
│       ↓                                         │

│       ↓                                         │
│  Policy Engine → LLM                            │
│                                                 │
│  负责：工程团队                                   │
└─────────────────────────────────────────────────┘
```

**两个平台之间只通过 Registry 耦合。Business Domain 不进 Builder。**

# 第四章 设计原则

## 4.1 原则一：一切服务 Skill

所有语义资产（Object、Metric、Value Domain、Lineage）的设计和建设，最终目的都是让 Skill 更容易构建、更易于跨医院复用。

每引入一个新概念之前，必须能回答：**"哪个 Skill 用得上？"**

## 4.2 原则二：设计时与运行时分离

Semantic Registry 负责资产管理。Business Facts Builder 负责运行时生成。

两者职责严格分开。Domain 不进入 Builder。Registry 不直接调用适配器。运行时只有一条链路：

```
Registry（查映射） → Builder（取数+标准化） → Facts → Skill
```

## 4.3 原则三：不要设计未来的能力

V1 不做以下概念（需要时再加）：

- Capability
- Ontology
- Knowledge Graph
- Business Event
- Business Service
- Rule Template
- Fact Template

      ↓

Object Relation 不作为一级模型，而是 Business Object 的属性。

# 第六章 Business Domain（业务域）

## 6.1 定义

Business Domain 是业务资产目录的一级分类，用于数据资产管理、语义检索、权限管理和业务导航。**不参与运行时计算。**

## 6.2 一级业务域（固定 11 域）

| # | 业务域 | 说明 | 覆盖的 Business Object |
|---|--------|------|----------------------|
| 1 | 医保结算 | 结算、费用、退费 | Settlement, Refund |
| 2 | 医保待遇 | 待遇资格、比例、限额 | Benefit |
| 3 | 医保政策 | 政策规则、政策条款 | Policy |
| 4 | 医保目录 | 药品、耗材、服务目录 | Directory |
| 5 | 慢特病 | 慢特病认定和资格 | ChronicDisease |
| 6 | 转诊备案 | 转诊、异地备案 | Referral |
| 7 | 参保信息 | 人员类别、险种 | Insurance |
| 8 | 就医服务 | 门诊、住院、诊断 | Visit, Diagnosis |
| 9 | 医疗资源 | 机构、医师、药品、耗材 | Drug, Institution |
| 10 | 申诉管理 | 拒付申诉 | Appeal |
| 11 | DRG/DIP | 分组与支付 | DrgDip |

## 6.3 元数据

| 字段 | 说明 |
|------|------|
| domain_code | 域编码（唯一标识） |
| name | 中文名称 |
| description | 业务说明 |
| sort_order | 排序 |
| created_at / updated_at | 时间戳 |

# 第七章 Business Object（业务对象）

## 7.1 定义

Business Object 是医保领域中可独立理解、独立管理、独立消费的业务语义单元。

**不是数据库表，不是字段集合，而是业务世界中的对象。**

## 7.2 元数据

| 字段 | 说明 |
|------|------|
| object_code | 对象编码（唯一标识），如 `Settlement` |
| name | 中文名称，如 `医保结算` |
| definition | 标准业务定义 |
| domain_code | 所属业务域 |
| identifier | 业务主键，如 `settlement_id` |
| source_object | 对应的领域模型类名（指向 `src/domain/`），如 `InsuranceTransaction` |
| source_adapter_port | 对应的适配器接口名，如 `InsuranceInterfacePort` |
| relations | Object Relation（JSONB），如 `[{"target":"Patient","type":"belongs_to","cardinality":"N:1"}]` |
| version | 版本号 |
| status | draft / published |
| created_at / updated_at | 时间戳 |

## 7.3 Object Relation（对象关系）

描述 Business Object 之间的业务导航关系。不作为一级模型，而是 Object 的 `relations` 属性。

示例：

```json
[
  {"target": "Patient",      "type": "belongs_to",     "cardinality": "N:1"},
  {"target": "Visit",        "type": "generated_from",  "cardinality": "1:1"},
  {"target": "Institution",  "type": "occurs_at",       "cardinality": "N:1"}
]
```

**约束**：
- 仅用于业务导航，不承载业务规则
- 默认支持一跳导航
- 不负责数据库 Join（数据库关联由 Builder 内部的 Mapping 实现）

## 7.4 与现有领域模型的关系

Business Object 是 Registry 中的元数据条目，描述业务概念的属性及其数据来源。它与 `src/domain/` 下的领域模型（frozen dataclass）通过 `source_object` 字段桥接：

```
Registry: Business Object "Settlement"
    source_object: "InsuranceTransaction"     ← 指向领域模型类名
    source_adapter_port: "InsuranceInterfacePort"  ← 指向适配器

Run Time: Builder 根据 source_object 找到领域模型，
         根据 source_adapter_port 找到对应的适配器 Port，
         通过适配器获取领域对象，再根据 Metric 的 source_field 提取属性值。
```

**约束**：Builder 不绕过适配器层直连数据库。数据获取始终通过 `adapters/ports/` 的 Protocol 接口。

# 第八章 Metric（业务指标）

## 8.1 定义

Metric 表示 Business Object 的可消费业务属性。包括金额、状态、日期、比例、数量等。

## 8.2 唯一标识

采用复合标识：`Object.Metric`。示例：

- `Settlement.deductible` — 结算.起付线
- `Settlement.fund_pay` — 结算.基金支付
- `Benefit.ratio` — 待遇.报销比例

**好处**：不同 Object 下的同名 Metric 不会冲突。

## 8.3 类型分类

| 类型 | 说明 | transformation 字段 |
|------|------|---------------------|
| Atomic | 直接来源于数据源，不经过计算 | null |
| Derived | 由多个指标计算得到 | 非空（JSONB，含计算公式） |

示例：

- Atomic：`fund_pay`、`deductible`、`total_fee`
- Derived：`reimbursement_ratio = fund_pay / total_fee`

## 8.4 重要程度分级

| 级别 | 含义 | Builder 行为 |
|------|------|-------------|
| core | 核心指标，缺一不可 | 缺失时 Builder 报错 |
| optional | 辅助指标，尽量获取 | 缺失时降级，不阻塞流程 |

## 8.5 元数据

| 字段 | 说明 | 示例 |
|------|------|------|
| metric_code | 复合编码（PK） | `Settlement.deductible` |
| object_code | 所属 Object（FK） | `Settlement` |
| name | 中文名称 | `起付线` |
| definition | 标准业务定义 | `医保开始报销前需先由个人承担的固定金额` |
| metric_type | Atomic / Derived | `Atomic` |
| semantic_type | Amount / Ratio / Enum / Date / Count | `Amount` |
| unit | 单位 | `元` |
| required | 是否必填 | `true` |
| default_value | 默认值（JSONB） | `null` |
| source_object | 领域模型类名 | `InsuranceTransaction` |
| source_field | 领域模型的属性名（非数据库列名） | `deductible` |
| source_adapter_port | 适配器接口名 | `InsuranceInterfacePort` |
| transformation | 转换逻辑（JSONB），Derived 时非空 | `null` |
| value_domain | 值域编码（FK），枚举型指标时才填 | `HOSPITAL_LEVEL` |
| importance | core / optional | `core` |
| usage_count | Skill 引用次数（数据价值探查） | `3` |
| quality_score | 数据质量评分 | `95.0` |
| version | 版本号 | `1.0` |
| status | draft / published | `published` |
| created_at / updated_at | 时间戳 | — |

## 8.6 建模约束

1. Metric 必须且仅属于一个 Business Object
2. 每个 Metric 必须具有标准业务定义
3. Metric 的 `source_field` 是领域模型的 Python 属性名，不是数据库列名
4. 数值型 Metric 不建立 Value Domain

# 第九章 Value Domain（值域）

## 9.1 定义

统一不同医院、不同系统的数据编码。将来源值映射为平台标准值。

## 9.2 适用条件

**仅适用于枚举型 Metric**。数值型指标（金额、比例、数量）不建立值域。

## 9.3 示例

医院等级：

| 来源值 | 标准值 |
|--------|--------|
| 三级 | LEVEL_3 |
| 03 | LEVEL_3 |
| 3 | LEVEL_3 |

医保类型：

| 来源值 | 标准值 |
|--------|--------|
| 职工 | EMPLOYEE |
| 01 | EMPLOYEE |

## 9.4 元数据

**value_domain 表：**

| 字段 | 说明 |
|------|------|
| domain_code | 值域编码（PK），如 `HOSPITAL_LEVEL` |
| name | 中文名称 |
| description | 说明 |

**value_domain_mapping 表：**

| 字段 | 说明 |
|------|------|
| domain_code | 值域编码（FK） |
| source_value | 来源系统的原始值 |
| standard_value | 平台标准值 |
| description | 说明（可选） |

## 9.5 运行时行为

Builder 在构建 Business Facts 时，对引用 Value Domain 的枚举型 Metric 自动进行标准化转换。Skill 永远只看到标准值（如 `LEVEL_3`），不感知来源系统的原始编码。

# 第十章 Data Lineage（数据血缘）

## 10.1 定义

描述业务指标的数据来源。用于保证数据可追溯。

## 10.2 V1 实现方式

**不独立建表。** 通过 `metric` 表的三个字段承载：

- `source_object`：领域模型类名
- `source_field`：领域模型的属性名
- `source_adapter_port`：适配器接口名

V1 追溯到适配器调用即可。多跳血缘、转换链、可视化追溯留到 V2。

## 10.3 约束

- 只描述数据来源，不承载计算逻辑
- 不承载政策规则
- V1 不穿透到数据库列名（数据库细节留在适配器内部）

# 第十一章 Business Facts（业务事实）

## 11.1 定义

Business Facts 是 Semantic Layer 的最终输出、Skill 的统一数据输入。

定义：当前业务场景下，由多个 Business Object 实例组成的标准化业务事实集合。

## 11.2 输出结构

```json
{
  "Settlement": {
    "fund_pay": 28560,
    "deductible": 1300,
    "self_pay": 4520
  },
  "Benefit": {
    "ratio": 85
  },
  "Institution": {
    "level": "LEVEL_3"
  },
  "_meta": {
    "version": "1.0",
    "generated_at": "2026-07-14T10:30:00Z",
    "warnings": []
  }
}
```

**特征**：
- 按 Object 分组
- 所有 Value Domain 已标准化
- 包含元数据（版本、生成时间、警告）
- Skill 不感知数据来源、字段映射、编码转换

# 第十二章 Business Facts Builder（运行时核心）

## 12.1 职责

根据 Skill 声明的 Object + Metric 需求，通过 Registry 获取映射信息，调用适配器获取数据，应用值域标准化，生成 Business Facts。

## 12.2 接口契约

**输入**：

```python
class BusinessFactsRequest:
    objects: list[ObjectMetricRequest]
    # [{"object_code": "Settlement", "metric_codes": ["fund_pay", "deductible"]},
    #  {"object_code": "Institution", "metric_codes": ["level"]}]
    context: dict  # patient_id, encounter_id, settlement_id …
```

**输出**：

```python
class BusinessFactsResponse:
    facts: dict
    # {"Settlement": {"fund_pay": 28560, …}, "Institution": {"level": "LEVEL_3"}}
    meta: FactsMeta
    # version, generated_at, warnings
```

## 12.3 执行流程

```
1. 接收 BusinessFactsRequest
2. 查 Registry → 获取每个 Metric 的 source_object + source_field + value_domain
3. 按 source_object 分组 → 找到对应的适配器 Port
4. 调适配器获取领域模型实例
5. 从领域模型中提取 source_field 的值
6. 若有 value_domain → 应用标准化转换
7. 拼装 BusinessFactsResponse
```

## 12.4 与适配器层的关系

Builder 不直连数据库。数据获取路径：

```
Builder
  → 查 Registry: Metric.deductible → source_object="InsuranceTransaction"
  → 映射表: InsuranceTransaction → InsuranceInterfacePort
  → 调适配器: InsuranceInterfacePort.get_transaction(ctx)
  → 获取: InsuranceTransaction.deductible
```

**约束**：Builder 只通过 `adapters/ports/` 的 Protocol 接口获取数据，不绕过防腐层。

# 第十三章 运行时全链路

```
用户问题
    │
    ▼
Intent 识别 → Business Action + Business Object
    │
    ▼
Skill Router（keyword + LLM hybrid）
    │
    ▼
Skill 声明 needed_objects + needed_metrics
    │
    ▼
Registry 查询 → 返回 Metric 映射表
    │
    ▼
Business Facts Builder
    │
    ▼
Business Facts（标准化 JSON）
    │
    ▼
Skill Execution（消费 Facts + 编排）
    │
    ▼
Policy Engine → LLM
    │
    ▼
AgentResponse（含 citations）
```

**三层职责分离（What / Why / How）**：

| 层 | 回答 | 示例 |
|---|---|---|
| Semantic Layer | What（是什么） | `deductible = 1300` |
| Policy Engine | Why（为什么） | `三级医院住院起付标准为 1300 元` |
| LLM | How（如何表达） | `您本次住院属于三级医院，因此按照现行医保政策，需要先承担 1300 元起付线…` |

# 第十四章 Skill 声明规范

## 14.1 新版声明格式

Skill 通过 `skill_manifest.yaml` 声明所需的 Object 和 Metric，不再手动声明数据类 MCP：

```yaml
# skill_manifest.yaml — 新版
skill_id: settlement_explain_skill
business_action: explain
business_object: settlement

needed_objects:
  - object_code: "Settlement"
    metrics:
      - deductible
      - basic_pooling_payment
      - basic_pooling_self_pay
      - large_amount_payment
      - large_amount_self_pay
      - personal_total_pay
      - person_type
      - insurance_type
      - service_type
      - hospital_level
    importance: "core"

  - object_code: "Institution"
    metrics:
      - level
    importance: "optional"

required_mcp:
  - structured-policy-rule   # 非数据类 MCP 仍声明
```

## 14.2 新旧对比

| 旧 | 新 |
|----|-----|
| `required_settlement_fields` 平铺字段名 | `needed_objects[].metrics[]` 按 Object 分组 |
| 手动声明 MCP `settlement-data` | 不需要——Builder 根据 Registry 自动找适配器 |
| 无 importance 分级 | `core` / `optional` |
| 枚举字段需 Skill 自己处理值域 | Builder 自动标准化 |

## 14.3 向后兼容

`SkillLoader` 检测 manifest 格式：
- 有 `needed_objects` → 走新路径（Registry + Builder + Facts）
- 只有 `required_settlement_fields` → 走老路径（MCP + 原始数据）

兼容过渡期约 2-3 周，期间两条路径并行。

# 第十六章 Registry 建设流程

## 16.1 建设原则

采用"自动发现 + 人工治理 + 持续运营"模式。

## 16.2 建设阶段

**阶段 1 — 自动发现**：
- 数据库 Schema 扫描（表 → 字段 → 类型 → 主键）
- Excel 数据字典导入（补充中文名称 + 业务定义）
- 适配器接口扫描（从 `src/adapters/ports/` 提取 Protocol 方法签名）

**阶段 2 — 语义发现（人工辅助）**：
- 字段聚类 → 候选 Business Object
- 字段语义分析 → 候选 Metric
- 枚举值检测 → 候选 Value Domain
- 表关联分析 → 候选 Object Relation

**阶段 3 — 人工确认**：
- 确认 Domain 归类
- 确认 Object 边界
- 补充 Metric 定义 + importance
- 确认 Value Domain 映射
- 标记数据质量

**阶段 4 — 发布**：
- 版本号分配
- 状态变更（draft → published）
- 通知下游 Skill 团队

## 16.3 治理审批流程

```
需求提出 → 业务评审 → 语义建模 → 架构评审 → 版本发布 → Skill 使用
```

支持：版本管理、审批流程、变更记录、影响分析、回滚。

# 第十八章 版本管理

所有语义资产（Domain、Object、Metric、Value Domain）支持版本管理。

示例：`Settlement` V1 和 V2 可以共存。Skill 通过 `skill_manifest.yaml` 声明依赖的版本，避免 Registry 变更影响线上 Skill。

Registry 变更触发影响分析：哪些 Skill 依赖了变更的 Object/Metric → 通知对应 Skill 团队 → 确认兼容性。

# 政策知识治理 · 知识审核「修改提示词 + 换大模型 + 重新提取」设计 V1.0

> **定位**：知识审核详情页（`/policy-knowledge/knowledge/review/[changeSetId]`）支持「就地修改提示词 / 换大模型 / 单条与批量重新提取」，并保证语义层指标修改后对重提取实时生效。前端 + 后端完整设计。
>
> **需求来源**：`docs/steering/政策知识治理-需求迭代记录.md` 迭代 18。
> **现状基线**：迭代 14–17（变更集审核、构建任务、发布管理、质量门禁）。
> **设计依据**：`docs/steering/政策知识管线设计.md` §3.1/§7.1；`src/semantic_layer/extraction_contract.py`；`src/knowledge_extension/rule_explanation/pipeline_orchestrator.py`。

---

## 1. 背景与现状

### 1.1 用户痛点

审核人员在「知识审核详情页」发现某条/某批候选知识提取错误（字段漏抽、规则类型判错、原文片段不准）时：

- 现状只能「拒绝 / 退回」走整批重建（`POST /change-sets/{id}/reprocess`，按文档全量重建），粒度太粗、无法针对单条。
- 无法在审核上下文内换一个提示词或换一个大模型重试，只能改代码或改语义层后整体重跑。
- 没有批量重提取能力，逐条退回→重建→重新审核链路过长。

### 1.2 现状关键事实（已核实代码）

| 关注点 | 现状实现 | 文件 |
|--------|---------|------|
| 真正的 LLM 提取 | `PipelineOrchestrator._extract_policy_facts` | `pipeline_orchestrator.py` |
| 提示词构建（schema-driven） | `_build_fact_extraction_prompt` → `build_prompt_from_schema`，**每次实时读语义层 `zcgz` published 指标**；不可用时回退 legacy 19 字段 | `pipeline_orchestrator.py` / `extraction_contract.py` |
| 模型调用 | `ModelGateway().generate(messages, model_type="llm", scene="policy_qa", max_tokens=8192)`；`ModelRouter.resolve(scene, model_type)` 从 `ROUTING_TABLE` 解析；**`gateway.generate` 不支持指定 `model_name`** | `gateway.py` / `router.py` / `config/model_routing.py` |
| 单元级重提取（体系 A） | `PipelineOrchestrator.reextract_unit(extraction_id)` → 端点 `POST /policy-pipeline/extractions/{id}/reextract`，状态回退 draft | `pipeline_orchestrator.py` / `policy_pipeline_routes.py` |
| 变更集审核（体系 B） | `ChangeSetService` 聚合 `KnowledgeItem` 生成 `KnowledgeChangeSet`；前端 `/knowledge/review/[changeSetId]` | `change_set_service.py` / `policy_workbench_routes.py` |
| 两套体系关联 | 体系 B 的 `KnowledgeItem` 由体系 A 的 extraction **实时派生**：`knowledge_id = hash(extraction_id, rule)`，`get_document → list_extractions → _build_knowledge_item` | `knowledge_workbench_service.py` |

### 1.3 缺口清单

1. **提示词无法手动覆盖**：schema-driven 自动拼，缺一个「自定义提示词」通道。
2. **无法换大模型**：`gateway.generate` 不接受 `model_name`；`scene` 固定 `policy_qa`。
3. **体系 B 审核页未接入重提取**：变更集只有 `reprocess`（按文档整批重建），无「针对单条/选中多条重新提取」。
4. **无批量重提取**：`reextract_unit` 一次一条，无并发与进度聚合。
5. **指标实时生效未在前端显性化**：schema 模式本就实时生效，但用户感知不到「当前注入了哪些指标」「改了指标会不会生效」。

### 1.4 已有可复用能力

- **指标动态注入**：`build_prompt_from_schema` 每次调用 `create_registry()` 读最新 published 指标 —— **本设计不重写，直接复用并保证 override 不破坏它**。
- **单元重提取**：`reextract_unit` 已有「清旧→重提→状态回 draft」的成熟语义，本设计在其上叠加 `override` 参数。
- **变更集重建**：`ChangeSetService.build_for_units` / `build_for_document` 已能从最新 extraction 聚合候选快照，重提取后复用即可刷新。
- **审核留痕**：`reviewKnowledge`（`POST /knowledge/{id}/review`）已有 approved/rejected 留痕机制，重提取的「退回重提」可复用其 note 前缀约定（`[退回重提取]`）。

## 2. 需求拆解与验收标准

| # | 需求 | 验收标准 |
|---|------|---------|
| R1 | 修改提示词 | 审核页可切换「schema（默认）/ 自定义」；自定义模式下可编辑提示词文本并实时预览最终 prompt；重提取使用所选提示词。 |
| R2 | 换大模型 | 审核页可从「可选模型列表」选择目标模型；重提取实际走所选模型（响应中带回 `model_name`）；未选时走默认路由。 |
| R3 | 单条重新提取 | 审核详情表每行新增「重新提取」操作；执行后该行对应 extraction 重提、候选快照刷新、行状态回到待审。 |
| R4 | 批量重新提取 | 工具栏复用勾选，对选中多条统一重提；返回逐条结果（成功/失败+原因），部分失败可定位重试；有进度反馈。 |
| R5 | 指标实时生效 | 重提取时实时读最新 published 指标（schema 模式）；对话框展示「当前生效指标列表 + 契约版本 + 提示词预览」；在语义层发布新指标后，下一次重提取的提示词预览立即包含新指标。 |

**安全边界（硬性）**：重提取**不得**触碰已发布快照（`published_knowledge_snapshots` 不可变）；仅作用于 draft/审核中候选；重提取后状态回退为 draft，必须重新审核才能发布。

## 4. 后端设计

### 4.1 数据模型：ExtractionOverride

新增于 `src/knowledge_extension/rule_explanation/knowledge_build_models.py`（与构建任务模型同文件，属同一提取域）。

```python
PromptMode = Literal["schema", "legacy", "custom"]

class ExtractionOverride(BaseModel):
    """单次重新提取的提示词 / 模型覆盖配置。

    - 未提供（None）时全部走默认（schema 提示词 + 默认模型路由）。
    - prompt_mode="custom" 时 custom_prompt 必填，且指标不会被自动注入
      （由调用方在 custom_prompt 中自行包含需要的指标口径）。
    """
    model_config = ConfigDict(frozen=True)

    prompt_mode: PromptMode | None = None
    custom_prompt: str | None = None        # prompt_mode="custom" 时必填
    model_name: str | None = None           # 非空时绕过 router 直接用该模型
    max_tokens: int | None = None           # 非空时覆盖默认 8192
    operator: str | None = None             # 触发人（审计留痕）

    @model_validator(mode="after")
    def _require_custom_prompt(self) -> "ExtractionOverride":
        if self.prompt_mode == "custom" and not (self.custom_prompt and self.custom_prompt.strip()):
            raise ValueError("prompt_mode=custom 时 custom_prompt 不能为空")
        return self
```

**设计取舍**：`frozen=True` 与现有 `CreateKnowledgeBuildTaskRequest` 一致；`operator` 仅做审计字段透传，不引入鉴权（沿用迭代 14 §31.9「第一阶段沿用 reviewed_by，权限角色后置」）。

### 4.2 模型选择扩展：ModelGateway.generate(model_override)

`src/model_service/gateway.py`，`generate` 与 `generate_stream` 均新增可选参数：

```python
def generate(
    self,
    messages: list[Message],
    model_type: str,
    scene: str,
    max_tokens: int | None = None,
    model_override: str | None = None,   # ← 新增
) -> ModelResponse:
    if model_override:
        model_name = model_override
        fallbacks = []                    # 显式指定时不走 fallback 链
    else:
        model_name, fallbacks = self._router.resolve(scene, model_type)
    chain = [model_name] + fallbacks
    ...  # 其余重试 / 异常分类逻辑不变
```

**为什么不新增 scene 而是加 override 参数**：
- 新增 scene 需要 `ROUTING_TABLE` 预配每个模型，运维负担重且无法动态选。
- `model_override` 是「一次性覆盖」，不影响全局路由表，符合「审核时换模型」的临时性语义。
- `override` 非空时关闭 fallback（用户显式选了某模型，失败应明确报错而非偷偷换模型，避免「以为换了模型其实没换」的误导）。

### 4.3 提取编排器扩展：PipelineOrchestrator

`src/knowledge_extension/rule_explanation/pipeline_orchestrator.py`。

**(1) `_build_fact_extraction_prompt` 接受 override**：

```python
def _build_fact_extraction_prompt(
    self, text: str, title: str, override: ExtractionOverride | None = None
) -> str:
    mode = override.prompt_mode if override else "schema"
    if mode == "custom" and override and override.custom_prompt:
        # 自定义提示词：不自动注入指标，由用户自行包含 {title}/{text} 占位符替换
        return override.custom_prompt.replace("{title}", title).replace("{text}", text)
    if mode == "schema":
        try:
            from src.semantic_layer.registry import create_registry
            from src.semantic_layer.extraction_contract import (
                build_extraction_schema, build_prompt_from_schema,
            )
            schema = build_extraction_schema(create_registry(), "zcgz")
            if schema.fields or schema.entities or schema.relations:
                return build_prompt_from_schema(text, title, schema)  # ★实时读 published
        except Exception:
            pass
    return self._legacy_fact_extraction_prompt(text, title)
```

**(2) `_extract_policy_facts` 透传 override**：内部调用改为 `self._build_fact_extraction_prompt(document_text, document_title, override)`，`gateway.generate(..., model_override=override.model_name if override else None, max_tokens=...)`。

**(3) `reextract_unit` 接受 override**：

```python
def reextract_unit(
    self, extraction_id: str, override: ExtractionOverride | None = None
) -> dict[str, Any]:
    ext = self._store.get_extraction(extraction_id)
    ...
    facts = self._extract_policy_facts(source, title, override=override)
    ...
    # 更新 extraction 记录时，额外写入本次提取的 override 与生效契约（审计）
    updated = self._store.update_extraction(extraction_id, {
        "extracted_fields": merged_fields,
        "confidence": avg_conf,
        "status": "draft",
        "last_override": override.model_dump() if override else None,   # 审计字段
    })
    return {"success": True, "extraction_id": extraction_id, "extraction": updated,
            "override_applied": override.model_dump() if override else None}
```

**指标实时生效保证（R5 核心）**：schema 模式下 `create_registry()` 每次新建实例读取最新 published 指标，**无缓存**，故语义层发布新指标后立即对下一次重提取生效。本设计不引入任何缓存层破坏这一特性。

### 4.4 变更集服务扩展：ChangeSetService.reextract

`src/knowledge_extension/rule_explanation/change_set_service.py`，新增方法。注意 `ChangeSetService` 当前依赖 `workbench_service` 与 `change_set_store`，需追加注入 `PipelineOrchestrator`（或其端口）。

```python
class ChangeSetService:
    def __init__(
        self,
        workbench_service: KnowledgeWorkbenchService,
        store: ChangeSetStore,
        orchestrator: "PipelineOrchestrator | None" = None,   # ← 新增可选注入
    ) -> None: ...

    def reextract(
        self,
        change_set_id: str,
        item_ids: list[str] | None,
        override: ExtractionOverride | None = None,
    ) -> "ReextractReport":
        """对变更集中指定条目（或全部）重新 LLM 提取并刷新候选快照。

        1. 仅 PENDING_REVIEW / NEEDS_DECISION 状态可重提；其他状态报错。
        2. item_ids 为空 → 对该 change-set 全部 item 重提；非空 → 仅这些。
        3. 通过 item.after 快照（KnowledgeItem dump）取 extraction_id 定位体系 A 记录。
        4. 逐条调 orchestrator.reextract_unit(extraction_id, override)。
        5. 全部完成后，用参与重提的 unit 重新 build_for_units 重建候选快照
           （knowledge_id 因 extraction 内容变化而变，旧 item_id 失效）。
        6. 返回逐条结果 + 聚合状态。
        """
```

**`item_ids → extraction_id` 映射**：`ChangeSetItem.after` 是 `KnowledgeItem.model_dump()`，含 `extraction_id` 字段（见 `knowledge_workbench_models.py:51`）。无需反查体系 B 工作台，直接从快照取。

**重建策略**：重提后该 unit 的 extraction 内容已变，需重新聚合。复用 `build_for_units`，传入参与重提的 `SelectedKnowledgeUnit`（由 extraction 反查 unit 文档原文）。新 change-set 与旧 change-set 通过 `supersedes_candidate_id` 建立血缘（沿用迭代 15 的不可原地覆盖约定）。

> ⚠️ **设计抉择：原地刷新 vs 新建候选**。
> 选项 A（原地刷新）：更新现有 change-set 的 items，item_id 重新生成。优点是审核上下文不跳转；缺点是破坏 change-set 不可变语义、丢失审核留痕。
> 选项 B（新建候选，supersedes 旧）：生成新 change-set，旧的置 RETURNED。符合迭代 15「每次构建生成独立、不可原地覆盖的候选结果；新结果通过 supersedes 指向旧」。
> **本设计采用选项 B**，但前端通过 `supersedes_candidate_id` 自动跳转到新候选，保证体验连续。详见 §6.4。

**端点实现要点**：

```python
class ReextractRequest(BaseModel):
    item_ids: list[str] | None = None      # None/空 → 整个 change-set
    override: ExtractionOverride | None = None

@router.post("/change-sets/{change_set_id}/reextract", response_model=ReextractReport)
def reextract_change_set(change_set_id: str, request: ReextractRequest) -> ReextractReport:
    service = _get_change_set_service()
    return service.reextract(change_set_id, request.item_ids, request.override)
```

**`/extraction-config` 出参**：

```python
class ExtractionConfigResponse(BaseModel):
    default_prompt_mode: PromptMode = "schema"
    default_model: str                    # ROUTING_TABLE ("default","llm")
    default_max_tokens: int = 8192
    schema_version: int                   # 当前 published 指标契约版本
    metrics: list[MetricContractSummary]  # 当前注入提示词的指标（code/name/kind/hint/value_domain）
    note: str  # "schema 模式实时读语义层 published 指标；在语义层发布新指标后下次重提取立即生效"
```

`MetricContractSummary` 复用 `extraction_contract.FieldContract` 的精简版（code/name/kind/extraction_hint/value_domain）。该端点直接调 `build_extraction_schema(create_registry(), "zcgz")` 取数——与提取时用的是**同一份契约**，保证前端展示与实际提取一致。

### 4.7 数据库与存储

- **`pipeline_store` extraction 表**：新增 `last_override` JSONB 列（记录本次重提用的 override，审计留痕）。PostgreSQL 迁移 + 内存实现双写。
- **`policy_knowledge_change_sets` 表**：已有 `supersedes_candidate_id` 列（迭代 14 S2 引入），重提取新建候选时写入旧 ID，无需新增列。
- **不新增独立表**：override 是「调用时参数」，不持久化为独立实体；只通过 extraction 的 `last_override` 与 change-set 的 `supersedes_candidate_id` 留痕。

### 4.8 安全与边界

| 风险 | 处理 |
|------|------|
| 重提触碰已发布快照 | `reextract` 仅允许 `PENDING_REVIEW/NEEDS_DECISION`；`APPROVED/PUBLISHED` 报错（与 `approve` 的 `allowed_statuses` 对称） |
| 自定义提示词注入 | `custom_prompt` 直接拼入 LLM，不做转义（审核人员是可信内部角色）；前端 textarea 不做 HTML 渲染（防 XSS 由 React 默认转义保证） |
| 模型不可用 | `model_override` 指定的模型失败时关闭 fallback，直接抛 `ModelServerError`/`ModelAuthError`，`ReextractItemResult.error` 回显，不偷偷换模型 |
| 批量部分失败 | 逐条独立，失败项 `success=False`，不中断其余；前端可对失败项单独重试 |
| 并发重提同一 extraction | 沿用 `KnowledgeBuildStore` 的 claim 机制思路：重提期间对该 extraction 加短期占用锁（内存实现用 set，PG 用行锁），避免并发 LLM 调用浪费配额 |
| MODEL_API_KEY 未配置 | 沿用 `reextract_unit` 现有语义：返回 `success=False, error="LLM 未返回结果（请检查 MODEL_API_KEY 与模型配置）"` |

```typescript
// —— 重新提取（迭代 18）——

export type PromptMode = 'schema' | 'legacy' | 'custom'

export interface ExtractionOverride {
  prompt_mode?: PromptMode
  custom_prompt?: string | null
  model_name?: string | null
  max_tokens?: number | null
  operator?: string | null
}

export interface ExtractionConfig {
  default_prompt_mode: PromptMode
  default_model: string
  default_max_tokens: number
  schema_version: number
  metrics: Array<{ code: string; name: string; kind: string; extraction_hint?: string | null; value_domain?: string | null }>
  note: string
}

export interface ModelOption {
  model_name: string
  display_name: string
  available: boolean
}

export interface ReextractItemResult {
  item_id: string
  extraction_id: string
  success: boolean
  error?: string | null
  model_used?: string | null
  prompt_mode_used?: PromptMode | null
  new_knowledge_count: number
}

export interface ReextractReport {
  change_set_id: string
  new_change_set_id: string | null
  total: number
  succeeded: number
  failed: number
  items: ReextractItemResult[]
  override_applied: ExtractionOverride | null
}

export const getExtractionConfig = () =>
  request<ExtractionConfig>(`${WORKBENCH_API}/extraction-config`)

export const listExtractionModels = () =>
  request<ModelOption[]>(`${WORKBENCH_API}/extraction-config/models`)

export const getPromptPreview = (params: { prompt_mode: PromptMode; custom_prompt?: string }) =>
  request<{ prompt: string; schema_version: number; field_count: number }>(
    `${WORKBENCH_API}/extraction-config/prompt-preview?${new URLSearchParams({
      prompt_mode: params.prompt_mode,
      ...(params.custom_prompt ? { custom_prompt: params.custom_prompt } : {}),
    })}`,
  )

export const reextractChangeSet = (
  changeSetId: string,
  body: { item_ids?: string[]; override?: ExtractionOverride },
) =>
  request<ReextractReport>(
    `${WORKBENCH_API}/change-sets/${encodeURIComponent(changeSetId)}/reextract`,
    json('POST', body),
  )
```

### 5.4 重提取执行与结果处理

`ReextractConfigDialog` 点「开始重新提取」：

1. 构造 `ExtractionOverride`（schema 模式时 `prompt_mode='schema'` 且不带 custom_prompt；custom 模式时带 custom_prompt）。
2. 调 `reextractChangeSet(changeSetId, { item_ids, override })`。
3. 根据 `ReextractReport`：
   - **全部成功**：toast「已重新提取 N 条，新候选已生成」→ 若 `new_change_set_id` 非空，`router.push` 跳转到新候选审核页（`/policy-knowledge/knowledge/review/${new_change_set_id}`）。
   - **部分失败**：展示逐条结果列表（成功/失败+原因），提供「仅对失败项重试」按钮（scope 缩小到失败 item_ids）。
4. 关闭对话框，父组件 `load()` 刷新。

**进度反馈**：批量重提取可能耗时（每条一次 LLM 调用）。对话框内显示 `Loader2` + 文案「正在重新提取 i / N…」。若后端实现为同步循环（阶段一），前端按钮置 disabled 直到返回；后续可演进为 SSE 流式进度（见 §7 后置）。

### 5.5 指标实时生效的前端显性化（R5）

- 对话框「生效指标」区直接渲染 `ExtractionConfig.metrics`，让用户看到**本次重提取将注入哪些指标**。
- 顶部文案明确：「语义层新增/修改指标并发布后，本次重提取立即生效」。
- schema 模式的「提示词预览」调 `/prompt-preview` 实时拼，用户在语义层改完指标（新 tab）后，回到本对话框刷新即可看到新指标进入预览——**所见即所提**。

### 5.6 UI 复用与一致性

- 对话框复用 `@/components/ui/dialog`（与现有 `ItemReasonDialog`/`ReasonDialog` 一致）。
- 模型下拉复用审核页既有 `<select>` 样式（`h-8 rounded-lg border-slate-200`）。
- 「重新提取」按钮配色用 `RefreshCw` + 次级色（slate），与主操作「通过」（emerald）区分，避免误点。
- 移动端：对话框内容滚动，按钮区 sticky 底部（与 `ReasonDialog` 一致）。

## 6. 跨层一致性核对

### 6.1 字段对齐（前端 DTO ↔ 后端 Pydantic）

| 字段 | 前端 TS | 后端 Pydantic | 备注 |
|------|---------|--------------|------|
| 提示词模式 | `PromptMode` | `PromptMode = Literal["schema","legacy","custom"]` | 一致；前端只暴露 schema/custom 两选项，legacy 仅后端可选项 |
| 自定义提示词 | `custom_prompt?: string\|null` | `custom_prompt: str\|None` | 一致 |
| 模型名 | `model_name?: string\|null` | `model_name: str\|None` | 一致 |
| 最大 tokens | `max_tokens?: number\|null` | `max_tokens: int\|None` | number/int |
| override | `ExtractionOverride` | `ExtractionOverride`（frozen） | 字段集合一致 |
| 重提报告 | `ReextractReport` | `ReextractReport` | 逐字段一致 |

### 6.2 命名规范

- 后端 `snake_case`（`prompt_mode` / `custom_prompt` / `model_name`），前端 TS 保持 `snake_case`（与现有 `policy-knowledge-api.ts` 全量 snake_case 一致，如 `KnowledgeReviewPayload.doc_id`）。**本模块不引入 camelCase 转换层**，匹配现有约定。

### 6.3 路由一致性

- 后端 `POST /api/v1/medical-insurance-ai-agent/policy-workbench/change-sets/{id}/reextract`
- 前端 `reextractChangeSet` 拼出的 URL 必须与上完全一致（含 `policy-workbench` 前缀）。

### 6.4 change-set 状态机扩展点

现有状态机：`DRAFT → PENDING_REVIEW → APPROVED → PUBLISHED`；旁路 `RETURNED/REJECTED/FAILED`。

重提取（选项 B：新建候选）引入的流转：
- 重提触发时，旧 change-set → `RETURNED`（decision: `{action: "reextracted", by, override, new_change_set_id}`）。
- 新 change-set 以 `PENDING_REVIEW` 创建，`supersedes_candidate_id = 旧ID`。

**不新增状态枚举**：复用 `RETURNED`，仅在 decision 中区分 `returned`（退回重建）与 `reextracted`（重新提取）两种原因。前端 `STATUS_LABELS` 与 `approveBlocked` 逻辑无需改动（`RETURNED` 已是非可审状态）。

## 9. 后置演进（非本期范围）

1. **流式进度**：批量重提取改为 SSE 流式推送逐条结果（`/change-sets/{id}/reextract/stream`），避免大批量时前端长等待。
2. **模型对比**：同一条用两个模型各提一次，对比结果辅助选型（复用 `/prompt-preview` + 双 override）。
3. **提示词模板库**：把常用自定义提示词存为模板（语义层或独立配置），审核页快速套用。
4. **重提取质量回溯**：把 `last_override` + `ReextractReport` 接入质量门禁，量化「不同提示词/模型对提取质量的影响」，反哺提示词优化。
5. **权限角色**：重提取能力按角色限制（迭代 14 §31.10 后置），当前仅 `operator` 留痕。

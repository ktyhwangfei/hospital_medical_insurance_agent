# 结算单解释平台功能补全详细设计 V1.0

> **版本**：V1.0  
> **日期**：2026-09-11  
> **状态**：待评审，尚未进入开发  
> **关联**：[#69 结算单解释平台架构设计方案](结算单解释平台架构设计方案-V1.0.md)、`PROGRESS.md`、`docs/steering/接口设计文档.md`、`docs/governance/SKILL-ISOLATION-DESIGN.md`  
> **适用范围**：在现有 `policy-qa` 单一业务入口内，补全 #69 所需的共性能力与三个真实业务场景；本文不触发代码、接口或数据迁移。

## 1. 评审结论

### 1.1 结论摘要

#69 的核心边界应予以采纳：**Skill 不是必选层，Graph 不是独立业务层，平台只沉淀已经被真实场景证明可复用的共性能力。**

当前项目已经完成“结算解释”最小闭环的大部分基础：`/policy-qa/stream` 单一入口、真实结算单读取、结构化政策检索、费用解释 Skill、公开结果白名单、一次有界恢复、会话轨迹、Skill 草稿/评测/Test Shadow/审批治理均已具备。后续重点不是新建一套 `platform/`、Tool 市场或 Graph 运行时，而是将现有主链中散落的事实读取、政策证据、适配器结果、校验与公开结果收敛成**受控的最小能力调用契约**，再逐项验证比较、预退费和慢特病待遇解释。

### 1.2 需要补全的功能层次

| 分层 | 结论 | 目标 |
|---|---|---|
| P0 共性闭环 | 必须优先设计并实现 | 受控场景输入、结算/费用/政策事实快照、能力调用契约、来源与公开结果映射、权限与高风险前置拦截 |
| P1 已有数据可验证场景 | 共性闭环后优先落地 | 先完成结算级跨结算比较；“同药”归因仅在费用明细和药品身份数据齐备后启用 |
| P2 外部系统依赖场景 | 保持候选或阻塞 | 门诊部分项目预退费影响分析，必须依赖医院收费系统的权威只读预结算 |
| P3 权威待遇数据依赖场景 | 先设计、后接入 | 慢特病已发生结算待遇解释；资格状态与行政导办依赖权威资格数据和权限体系 |
| 运营与隔离加固 | 按候选 Skill 物化需要实施 | Skill 静态边界、最小上下文注入、执行审计；不提前建设通用沙箱平台 |

### 1.3 明确不做的事项

下列事项不属于本轮功能补全，避免“平台化”演变成抽象先行：

1. 不新建 `src/platform/`、`src/tools/`、`src/domain/tool/` 或 `src/data_platform/storage/tool/`；后两者当前为空目录，禁止作为落点。
2. 不恢复已退役的通用场景执行器、LangGraph 业务图、旧 `/chat*`、`/settlement`、`/workflows*` 等入口。
3. 不建设独立 Graph DSL、Graph 运行时、通用 Tool CRUD/市场/专用存储或公开 Tool 调用事件流。
4. 不把全部业务流程强制 Skill 化；固定且稳定的业务步骤保持在 `runtime/policy_qa/` 受控流程中。
5. 不执行退费、冲正、正式结算、资格认定、资格修改或病案修改。系统只做只读分析、解释、导办与人工确认任务创建。
6. 不在权威事实、政策适用条件、身份授权或外部系统响应缺失时，以模型推测或本地模拟金额补全结论。

## 2. 现有建设基线与缺口评估

### 2.1 已可直接复用的建设成果

| 能力 | 现状与复用点 | 对 #69 的价值 |
|---|---|---|
| 唯一业务入口 | `POST /policy-qa/stream`、`PolicyQAPublicResult`、SSE `result/done`、公开步骤和一次有界恢复 | 新场景必须复用同一入口和安全公开契约，不新增平行业务 API |
| 结算解释主链 | `policy_qa_routes.py` → `settlement_data_provider.py` → `settlement_explain_skill` → `structured_policy_retriever.py` → `_build_public_result` | 可作为“事实读取—政策证据—确定性核验—公开解释”的首个成熟样板 |
| 语义与政策治理 | 结构化政策检索、适用性/有效期过滤、政策版本治理、指标政策承载、语义查询与受控数据流 | 可承接政策事实、适用性判断和来源引用，不另建平行政策模型 |
| 会话与任务闭环 | `policy_qa_trajectories`、会话生命周期、task/workflow、`waiting_human_confirmation` | 支持公开轨迹重放、人工升级与高风险动作的非自动闭环 |
| Skill 治理 | 草稿、版本制品、候选隔离评测、Benchmark、Test Shadow、人工审批、物化与热重载 | 可用于确有独立运营价值的预退费/地区导办等候选 Skill |
| 外部系统防腐层 | `adapters/ports/`、`AdapterCallResult`、`DataQualityStatus`、`BillingPort`、数据供给适配器 | 外部协议与运行时业务流程可保持隔离 |
| 安全围栏 | `authorization/`、`desensitization/`、`risk_control/`、审计存储 | 新场景必须复用权限、脱敏和高风险拦截，不能在 Skill 内自行实现 |
| MCP/扩展注册 | MCP 服务器/能力登记、风险等级与角色校验、扩展选择语义 | 仅作为可选能力来源；不把其误当作完整的业务 Tool 运行平台 |

### 2.2 缺口与优先级

| 编号 | 功能缺口 | 当前状态 | 优先级 | 主要依赖 |
|---|---|---|---|---|
| G1 | 结算、费用、待遇等事实的统一运行时快照与来源语义 | 结算上下文和政策证据存在，但跨场景事实契约未统一 | P0 | 现有数据提供器、语义层、外部适配器 |
| G2 | 运行时内部的最小业务能力调用契约 | MCP 是目录/传输能力，Adapter 是协议封装；两者之间缺少统一业务结果、恢复与来源语义 | P0 | `runtime/policy_qa`、`adapters`、`security` |
| G3 | 公开结果与内部校验状态的稳定映射 | 已有 `complete/partial/unavailable`，但缺少跨场景统一的内部原因码与事实/政策/计算三类核验摘要 | P0 | `public_contract.py`、验证链路 |
| G4 | 跨结算比较 | 已有比较资产/算法线索，但未纳入当前唯一主链和受控授权边界 | P1 | G1–G3、结算授权、费用明细 |
| G5 | “同药不同个人负担”归因 | 缺药品标准身份、规格/剂型、费用明细与待遇累计的完整权威事实 | P1 后置 | 药品主数据、费用明细、待遇事实 |
| G6 | 门诊部分项目预退费影响分析 | 候选草稿存在，正式加载和公开路由已撤回 | 外部阻塞 | 医院收费系统预结算 API、SSO、审计、候选评测与审批 |
| G7 | 慢特病待遇解释 | `BusinessObject.CHRONIC_DISEASE` 已有，未形成事实、资格、政策适用性和流程闭环 | 外部阻塞 | 权威资格/有效期/病种/定点数据、SSO、审计 |
| G8 | Skill 执行边界 | 当前属于约定式隔离；静态导入校验、最小上下文注入与执行审计尚未落地 | P0（仅对新候选） | `skill_infra`、脱敏与审计 |
| G9 | 可信 SSO/RBAC、敏感场景审计 | 现阶段为开发身份/局部权限能力，生产 SSO 仍待外部对接 | 外部阻塞 | 医院 SSO 文档、账号、测试环境 |

### 2.3 关键架构校准

1. **#69 第一阶段的“结算解释闭环”已经有实现基础，但尚未形成可复用的事实—能力—证据契约。** 因此优先补 G1–G3，而不是重建解释主链。
2. **Skill 管理控制面已经比 #69 第一阶段规划更丰富。** 后续不应再以“先建灰度、Graph 编辑器、版本平台”为前置条件；应把现有治理能力用于真实候选场景。
3. **当前公开结果三态是已上线契约。** #69 的六态应先成为内部核验原因，而不能直接破坏性替换 `complete/partial/unavailable`。
4. **比较、预退费、慢特病三个场景的成熟度不同。** 它们不能因为都出现在 #69 的愿景中而以同一节奏上线。

## 3. 总体设计

### 3.1 目标运行形态

```text
Portal /policy-qa
  → POST /policy-qa/stream
  → 请求与可信身份边界校验
  → 场景选择（固定受控流程；按需调用已治理 Skill）
  → 运行时能力调用契约
       ├─ 结算/费用/待遇事实
       ├─ 结构化政策证据与适用性判断
       ├─ 确定性差异或预结算结果
       └─ 外部资格/收费系统 Adapter
  → 事实、政策、计算/差异的确定性核验
  → 公开结果构建、脱敏、引用与不确定性
  → SSE result / done + 公开轨迹 + 脱敏审计摘要
```

职责保持如下：

| 层次 | 责任 | 不承担 |
|---|---|---|
| Agent/Runtime | 识别问题是否满足场景前提、选择固定流程、管理恢复预算、组装公开结果 | 自由生成医保计算、绕过授权、直接访问外部系统 |
| 固定流程 / Skill | 固定流程承接稳定步骤；Skill 承接医院/区域差异和需独立治理的业务方案 | 直接 SQL/HTTP、权限/审计重建、高风险执行 |
| 最小能力调用契约 | 将事实读取、政策检索、预结算、资格读取映射为统一业务结果 | 通用 Tool 市场、任意用户编排 |
| Adapter / MCP / Extension | Adapter 处理外部协议；MCP/Extension 管能力描述、传输或选择 | 业务流程时机与公开结果组装 |
| Security | 授权、脱敏、高风险拦截、审计 | 把业务规则放入安全层 |

### 3.2 入口与请求扩展原则

当前 `PolicyQARequest` 的主路径以 `question + settlement_id` 为边界。该约束在本设计中保持有效。若未来需要支持比较、预退费或慢特病待遇解释，扩展应采用**受限的判别联合**，而非自由 JSON 或多组彼此独立的可选参数。

目标请求形态如下，属于后续 R4 契约设计，不在本文发布：

```text
PolicyQARequest
├─ question: str
├─ settlement_id: str                   # 主结算单，始终必填
├─ session_id: str | null
└─ case_request: null | discriminated union
   ├─ compare_settlements
   │  └─ reference_settlement_ids: list[str]  # 1..4，总数最多 5
   ├─ preview_partial_refund
   │  └─ items: list[{fee_detail_id, refund_quantity}]
   └─ explain_chronic_disease_benefit
      └─ scope: settlement_participation | entitlement_status | guide
```

约束：

- `case_request` 缺省时，严格复用现有结算解释路径。
- `settlement_id` 不因新增能力变为可选；不恢复无结算锚点的平行诊疗/结算业务入口。
- 不接受客户端提供 `patient_id`、原始交易号、机构范围、角色、外部系统参数或权限证明。
- 业务动作只能由服务端受控分类和判别输入共同确定；文本中出现“退费”等高风险动词时，先走风险控制，不以 `case_request` 规避拦截。
- `case_request` 的扩展、公开字段变化和 Portal 消费调整必须通过 R4 审查，并与后端 Pydantic、前端 DTO、SSE 回放同步发布。

### 3.3 运行时最小能力调用契约

该契约是 `runtime/policy_qa/` 内部 seam，不是新的平台层或对外 Tool API。建议新增以下内部 DTO/Protocol，名称最终以领域字典评审为准：

```text
CapabilityCallContext
- qa_turn_id / session_id / workflow_id
- operation
- trusted_subject_scope（服务端构造的主体、机构、租户、用途摘要）
- recovery_budget

BusinessCapabilityRequest[T]
- capability_name
- validated_input: T
- call_context

BusinessCapabilityResult[T]
- outcome: completed | partial | unavailable | forbidden | waiting_human_confirmation
- reason_code
- data_quality: complete | degraded | missing
- value: T | null
- source_references: list[CapabilitySourceReference]
- public_summary
- retry_classification: none | transient_once

CapabilitySourceReference
- source_system
- source_record_ref（仅内部安全引用）
- observed_at
- version_or_policy_ref
- visibility: public | internal
```

首批能力仅限当前三个场景需要的最小集合：

| 能力名称 | 业务结果 | 实现来源 | 是否可重试 |
|---|---|---|---|
| `get_settlement_facts` | `SettlementFactSnapshot` | 现有结算数据提供器 / 数据供给适配器 | 仅连接/超时类一次 |
| `get_fee_detail_facts` | `FeeDetailFactSet` | 收费/HIS 只读适配器 | 仅连接/超时类一次 |
| `get_policy_evidence` | 结构化政策证据及适用性结果 | 现有政策检索与语义过滤 | 仅向量/数据库瞬时故障一次 |
| `compare_settlement_facts` | 确定性字段差异集 | Runtime 纯函数，复用已有差异算法 | 不重试 |
| `preview_partial_refund` | 权威预结算结果 | `BillingPort` 真实实现 | 仅明确瞬时不可用一次 |
| `get_chronic_disease_entitlement` | 权威资格与有效期事实 | 后续医保/院内资格 Adapter | 仅明确瞬时不可用一次 |

实现落点固定如下：

- 运行时调用协议、结果映射、恢复规则：`src/runtime/policy_qa/`。
- 外部端口与协议适配：`src/adapters/ports/`、`src/adapters/<system>/`。
- MCP 注册、传输和扩展选择：保持在 `src/knowledge_extension/`。
- 权限、高风险拦截、脱敏、审计接线：保持在 `src/security/`。
- 不在 `domain/tool/`、`data_platform/storage/tool/` 或新顶层目录创建抽象。

### 3.4 事实快照与来源原则

#69 所述 Business Fact 不应一开始抽象为一个大而泛的 `BusinessFact` 聚合。先以场景可验证的只读快照逐步沉淀：

| 快照 | 首批字段 | 权威来源与规则 |
|---|---|---|
| `SettlementFactSnapshot` | 结算标识、结算时点、人员/险种/就诊/机构维度、总费用、医保内金额、起付线、基金支付、统筹自付、大额支付/自付、个人支付、数据质量 | 当前结算读取链路；每次读取必须带来源与采集时点 |
| `FeeDetailFact` | 费用明细标识、项目编码/名称、数量、金额、目录/报销属性、药品身份引用 | 仅在院内费用明细契约稳定后纳入；禁止只靠名称近似认定同药 |
| `BenefitSnapshot` | 待遇状态、累计、适用时间、机构/异地限制、数据质量 | 必须来自权威待遇或资格系统；缺失即不做确定性待遇判断 |
| `PartialRefundPreview` | 预览标识、拟退明细、前后金额快照、结果状态、来源、采集时点 | 仅以收费系统权威预结算为准；本地不能反算替代 |
| `ChronicDiseaseEntitlementFact` | 资格状态、病种/目录受控引用、生效失效期、定点/异地限制、来源、数据质量 | 待真实资格数据源接入后创建；不可由政策文本或模型推断 |

快照不是第二数据库：

1. 权威真相始终在外部系统、受控数据源和已发布政策资产中。
2. Runtime 只持有本轮所需的引用、经裁剪的字段和数据质量，用于核验与公开结果构建。
3. 会话记忆可以保存引用与最小快照，但不得把全量患者、外部原始响应或隐藏推理写入轨迹。
4. 除既有 task/workflow/trajectory 与正式审计设施外，本阶段不新建“事实快照表”。

### 3.5 公开结果、核验原因与证据

`PolicyQAPublicResult` 继续是唯一公开白名单。内部核验原因与公开回答状态分层处理：

| 内部核验原因 | 公开 `answer_status` | 公开行为 |
|---|---|---|
| `verified` | `complete` | 事实、政策、计算/差异核验均满足，输出引用和核验摘要 |
| `noncritical_data_missing` / `policy_evidence_incomplete` | `partial` | 仅输出被证据支撑的部分结论，并列出未确认项 |
| `required_fact_missing` | `unavailable` | 明示缺失事实类别，不透露隐私对象存在性 |
| `required_policy_missing` | `unavailable` | 明示缺少可适用政策依据，不生成确定性结论 |
| `fact_policy_conflict` / `calculation_inconsistent` | `unavailable` | 明示发现冲突或勾稽不成立，建议人工核验 |
| `external_source_unavailable` | `unavailable` | 使用稳定、非技术性的停止原因；仅按恢复预算处理 |
| `access_denied` | 不进入业务结果 | API/权限层按不泄露资源存在性的方式处理 |
| `high_risk_action` | `unavailable` 或人工任务摘要 | 生成 `waiting_human_confirmation`，绝不自动执行 |

每个可确定结论至少应建立三类可追溯要素：

```text
结论
 ├─ 数据事实来源：结算/费用/资格快照及采集时点
 ├─ 政策事实来源：发布政策版本、原文位置、适用条件
 └─ 确定性过程：计算、差异比对或收费系统预结算的核验摘要
```

公开输出规则：

- 可展示的政策依据继续使用 `citations`、`policy_evidence`。
- 数据来源、预结算来源和计算/比对过程只以业务化摘要进入 `verification_summary`、`calculation_steps` 或 `warnings`。
- 禁止暴露 SQL、表名、字段名、内部 capability 名称、请求参数、外部原始 payload、异常栈、完整病种/诊断信息和模型隐藏推理。
- 没有可展示依据时必须填充 `uncertainties`，不允许以“系统分析”替代来源。

### 3.6 安全、权限与审计原则

新增场景首先经过以下顺序，任何一层失败均不得继续调用下游外部系统：

```text
可信身份与机构范围
  → 场景权限与患者/结算可见范围
  → 输入判别与数量边界
  → 高风险动作检测
  → 最小事实读取
  → 脱敏与公开结果构建
  → 脱敏审计摘要与公开轨迹
```

约束：

1. 请求体内的 `role`、患者标识或交易号不能作为生产授权事实。生产开放需要医院 SSO/JWT 提供的可信主体、机构、岗位和授权范围。
2. 跨结算比较、收费预结算和慢特病资格读取均属于敏感读取；缺可信身份或患者/结算关系时，必须在外部调用前失败关闭，并避免通过错误差异暴露资源是否存在。
3. “退费”“冲正”“正式结算”“资格认定/修改”等意图必须调用 `security/risk_control/`，转为 `waiting_human_confirmation`；人工确认不构成系统自动执行授权。
4. 审计仅记录脱敏主体、场景、来源系统、结果状态、稳定原因码、`qa_turn_id` 和人工任务关联，不记录原始患者数据、收费系统 payload 或内部推理。
5. Skill 不得自行鉴权、审计、脱敏或直接访问 Adapter/数据库/HTTP；这些都是基础设施和 Runtime 的职责。

## 4. 功能一：跨结算比较与“同药不同个人负担”归因

### 4.1 用户故事与范围

> 作为医保经办或收费人员，我需要比较多个经授权结算单的个人负担为何不同，并在数据和政策确实能证明时，看到人员类别、待遇、政策版本、起付线、累计支付或费用项目造成差异的可追溯说明。

本功能拆为两级，禁止跳级承诺：

| 阶段 | 可交付能力 | 明确不承诺 |
|---|---|---|
| C1 结算级比较 | 比较 2–5 张结算单的关键金额、人员、险种、医疗类别、机构、日期和待遇相关维度；给出可验证的差异归因 | 不宣称比较对象为同一药品 |
| C2 药品级归因 | 在药品标准身份、规格/剂型、费用明细、数量单位与待遇事实均齐备时，解释同药项目的个人负担差异 | 不以药品名称相似度、模型语义或模糊匹配作正式“同药”认定 |

### 4.2 输入与前置条件

```text
主结算单：settlement_id
参考结算单：reference_settlement_ids（1..4）
比较数量上限：总数最多 5
```

服务端必须先验证：

1. 所有结算单均位于调用者的机构、岗位和患者/业务授权范围内。
2. 结算单读取成功且关键金额字段满足数据质量要求。
3. C1 的结算日期、人员类别、险种、就诊类型、机构/医院等级等可用维度足以描述差异。
4. C2 额外要求费用明细、标准化药品身份、规格/剂型、数量单位、目录版本、待遇状态与累计事实齐备。

任一结算单不可见时，不能通过响应区分“无权限”和“不存在”。任一必要事实缺失时，可降级为 C1 或返回 `unavailable`，不得补造同药结论。

### 4.3 C1 执行流程

```text
校验比较输入与授权
  → 批量读取 SettlementFactSnapshot
  → 固定字段差异计算（金额使用 Decimal，字段顺序稳定）
  → 根据实际差异维度检索有效政策证据
  → 检查政策适用条件与结算时点
  → 输出已证明差异 / 未证明的差异 / 数据缺口
  → 公开结果、轨迹和脱敏审计摘要
```

固定差异字段至少包括：

- 结算时间、险种、人员类别、就诊类型、医疗机构/等级；
- 总费用、医保内金额、起付线、统筹支付、统筹自付、大额支付、大额自付、个人支付；
- 结算中的可用待遇或累计标识；
- 适用政策版本、政策有效期和适用维度。

差异算法只能比较事实，不得由 LLM 计算金额。LLM 如参与自然语言组织，只能消费已经验证的差异事实和政策证据。

### 4.4 C2 执行流程

```text
C1 前置核验通过
  → 获取 FeeDetailFactSet
  → 基于标准药品编码、规格、剂型、单位和目录版本进行精确可比性判断
  → 读取待遇/累计/目录限制事实
  → 对每个可比较项目计算确定性差异
  → 检索并校验对应政策适用性
  → 输出项目级归因或“无法确认同药匹配”
```

`DrugIdentity` 的最小比对键须经院方确认，至少包含受控药品编码、规格、剂型、计价单位和目录版本。只有所有必需键相等或通过院方批准的确定性映射时，才允许使用“同药”措辞。

### 4.5 结果与验收

| 结果 | 必要条件 |
|---|---|
| `complete` | 所有目标结算事实可读，关键差异可计算，政策适用性可核验，C2 还需药品可比性成立 |
| `partial` | 结算级差异可确认，但部分政策/待遇/费用维度无法确认；必须指出不能得出的结论 |
| `unavailable` | 授权、关键结算、必要费用明细、政策适用性或药品身份缺失；不生成确定性归因 |

验收重点：

- 比较对象数量、顺序、重复标识、越权访问和缺失事实均有确定性测试。
- 结算级差异输出顺序稳定，且所有金额以 `Decimal` 口径处理。
- C1 绝不输出“同药”措辞；C2 在任一药品可比性条件缺失时明确降级。
- 每条政策归因均经过发布状态、生效期、险种/人员/医疗类别等适用性过滤。
- 不执行重新结算、不修改费用或待遇。

### 4.6 Skill 决策

比较功能初期采用固定受控流程。若后续出现医院差异化比较模板、多个独立版本、单独评测指标或业务人员独立运营需求，再通过既有草稿—候选—评测—审批—物化链路将其 Skill 化。已有比较资产只能作为算法和测试参考，不能绕过当前加载、评测和发布治理进入主链。

## 5. 功能二：门诊部分项目预退费影响分析

### 5.1 用户故事与安全边界

> 作为收费人员，我需要在实际退费前，基于医院收费系统的权威预结算结果了解指定项目、指定数量退费后可能发生的金额变化；系统不得执行退费、冲正、重算或正式结算。

该功能是**只读预览**，不是交易能力。任何包含实际执行语义的请求都必须在调用 `BillingPort` 前拦截，转为 `waiting_human_confirmation`。

### 5.2 当前状态与发布门槛

当前 `outpatient_pre_refund_analysis_skill` 处于 `editing` 草稿，正式加载和公开路由已撤回。它必须保持候选状态，直至下列条件全部满足：

1. 获得医院收费系统正式只读预结算 API 契约、鉴权方式和联调环境。
2. 真实 Adapter 实现 `BillingPort.preview_partial_refund()`，并返回可校验的来源、金额、项目和错误码。
3. 完成 Adapter 契约测试、候选评测、Test Shadow、人工审批与发布门禁。
4. 收费岗位权限、可信身份、最小数据范围和脱敏审计接入完成。
5. 医院确认“预结算结果”与“最终人工执行结果”的责任边界和差异说明。

未满足任一条件时，只能返回“院端预结算能力未配置或不可用”，不得使用内存适配器、通用规则或模型生成金额。

### 5.3 输入与权威适配器契约

受控输入：

```text
settlement_id
items:
  - fee_detail_id
    refund_quantity
```

输入规则：

- `items` 不得为空；`fee_detail_id` 不得重复；`refund_quantity` 必须为正且不超过可退数量。
- 原始交易号、患者信息和收费系统内部标识必须由服务端从已授权的结算事实派生，不接受客户端传入。
- 金额使用 `Decimal`，不得用浮点数比较或呈现。

真实 `BillingPort` 返回至少应包含：

| 类别 | 最小字段 |
|---|---|
| 来源 | source system、来源记录安全引用、采集时间、预结算标识 |
| 项目核验 | 项目存在性、原数量、允许预览数量、项目级结果 |
| 金额快照 | 预览前后结算金额、各支付分项变化、币种和精度 |
| 状态 | 已接受/业务拒绝/未配置/瞬时不可用/响应不完整 |
| 稳定错误语义 | 可公开原因码与是否允许一次恢复 |

### 5.4 执行流程

```text
文本与判别输入检查
  → security/risk_control 检测高风险执行意图
  ├─ 命中：创建/返回 waiting_human_confirmation，不调用 BillingPort
  └─ 未命中：校验项目、数量、授权与结算事实
        → 服务端取得交易关联
        → 调用 BillingPort.preview_partial_refund()
        → 校验来源、金额精度、项目一致性和数据质量
        → 生成“只读预览”公开结果
```

恢复规则：只有 Adapter 明确分类为瞬时 `pre_settlement_unavailable` 时，才消耗全局一次恢复预算。未配置、参数非法、业务拒绝、项目不匹配、金额不一致、来源缺失和响应结构非法均不重试。

### 5.5 公开结果要求

公开结果必须：

- 明确使用“预览”“拟退影响”而非“已退款”“已冲正”；
- 展示经授权可见的前后金额摘要、项目摘要、来源引用和限制条件；
- 说明实际退费仍需在院内收费系统由人工按既有流程执行；
- 不展示原始交易号、内部收费 payload、风险规则命中细节和完整费用敏感信息；
- 在没有权威预结算来源时使用 `unavailable + uncertainties`，绝不展示模拟金额。

### 5.6 验收重点

- 高风险动词命中时，`BillingPort` 不得被调用。
- 无 Adapter、无权限、空项目、重复明细、非法数量和响应缺字段均失败关闭。
- 仅瞬时不可用可重试一次；总尝试数不超过既有全局预算。
- 每一笔可展示金额均可追溯至预结算来源和本次预览标识。
- 通过候选评测、Test Shadow 和人工审批前，候选不得参与正式 Skill Loader 或 `/policy-qa/stream` 路由。

### 5.7 Skill 决策

预退费保留为候选 Skill 的优先级高于直接写死到产品逻辑，因为医院间预结算规则、展示模板和运营审批差异明显。其共性部分——授权、风险拦截、Adapter 调用、错误分类、公开结果隔离——必须沉淀在 Runtime/Security/Adapters 中，不能复制到每个 Skill。

## 6. 功能三：慢特病待遇解释

### 6.1 场景分层

慢特病能力必须区分解释、资格状态和行政办理，避免将政策解释误称为资格认定：

| 子场景 | 可做内容 | 不可做内容 |
|---|---|---|
| T1 已发生结算待遇解释 | 说明本次结算中可见的慢特病待遇参与事实、相关政策条件和数据缺口 | 不推断当前资格是否应当生效 |
| T2 资格状态解释 | 读取权威资格状态、有效期、病种范围、定点/异地限制，并与结算和政策交叉核验 | 不作行政认定或修改 |
| T3 办理导办 | 基于已发布政策说明材料、渠道、时效和适用条件 | 不承诺一定获批，不替代备案/审批 |
| T4 行政操作 | 不建设 | 不发起、修改、撤销资格或病种 |

### 6.2 所需事实与数据契约

T1 可复用当前门诊结算事实、政策检索和 `mzsettlement_verify_skill` 中的已发生结算核验能力。T2 必须在真实资格数据源就绪后，新增由 Adapter 返回的 `ChronicDiseaseEntitlementFact`，至少包含：

```text
资格状态
病种或目录的受控引用
生效日期 / 失效日期
定点、异地、机构、医疗类别限制
来源系统 / 采集时间 / 数据质量
```

政策证据必须同时满足结算日期、地区、险种、人员类别、医疗类别、机构和资格条件。资格数据、病种信息与诊断信息均属于敏感健康数据，公开时必须采用角色可见字段和脱敏策略。

### 6.3 执行流程

```text
识别请求为 T1 / T2 / T3 / T4
  → T4：风险控制或人工导办，不进入写操作
  → T1：读取结算事实 → 政策检索 → 核验待遇参与事实
  → T2：读取结算事实 + 权威资格事实 → 政策适用性核验
  → T3：仅使用已发布办事政策 → 输出带边界声明的导办
  → 统一公开结果、引用、不确定性与审计摘要
```

结论边界：

- 资格事实不存在、失效期缺失、机构/异地条件未知时，不得输出“应享受”“不应享受”“系统漏报”等确定性资格结论。
- T1 可以输出“本次结算未显示待遇参与”或“现有结算事实不足以判断”，但二者不得混同。
- T3 必须明确“导办内容不是行政认定结果”。

### 6.4 设计落点与验收

| 责任 | 落点 |
|---|---|
| 场景判别、结算事实与政策适用性流程 | `src/runtime/policy_qa/` |
| 权威资格读取端口 | `src/adapters/ports/` |
| 医保/院内资格系统协议 | `src/adapters/` 对应防腐层 |
| 高风险行政意图拦截 | `src/security/risk_control/` |
| 政策检索与证据 | 复用 `structured_policy_retriever.py` 与政策知识治理通路 |

验收重点：

- 能稳定区分“已发生结算待遇事实”“资格状态”“办理导办”“行政操作”四类请求。
- 权威资格缺失时，结果必须是数据/政策不确定性，而非模型推断。
- 资格、病种、有效期、机构/异地条件和政策生效期任一关键条件不满足时，不能输出确定性待遇结论。
- 导办输出具备可展示政策依据，并清楚声明不构成认定。

### 6.5 Skill 决策

T1/T2 首先采用固定流程，因为核心是权威事实读取、授权和适用性核验。只有不同地区的导办规则、病种目录策略或结果模板被证明需要独立版本与运营时，才把 T3 导办部分作为候选 Skill；不得把资格读取和授权判断交给 Skill 自由编排。

## 7. Skill 候选的最小隔离与治理补全

### 7.1 目标与边界

现有 Skill 治理已覆盖草稿、版本、评测、Test Shadow、审批和物化，但执行仍是约定式隔离。对内置且稳定的既有结算解释 Skill 不进行无目标重构；对预退费、慢特病导办等新增候选 Skill，物化前应具备以下最小加固。

| 级别 | 需要补全 | 是否本阶段必须 |
|---|---|---|
| L1 | AST 静态扫描违禁 import；阻止直接数据库、HTTP、主应用基础设施、子进程和越界文件访问 | 新候选 Skill 物化前必须 |
| L2 | `SkillExecutionContext` 按 manifest 声明构造；最小化、脱敏、只读的上下文注入；执行开始/结束/错误审计 | 涉及患者/收费/资格数据的候选 Skill 物化前必须 |
| L3 | 子进程隔离、CPU/内存/网络/文件系统约束 | 第三方/用户上传 Skill 或高风险敏感 Skill 时再立项 |

### 7.2 SkillExecutionContext 约束

候选 Skill 的 manifest 需要声明自身所需上下文和 schema，例如：

```text
required:
- settlement_fact_snapshot
- applicable_policy_evidence
optional:
- fee_detail_fact_set
- chronic_disease_entitlement_fact
```

运行时仅注入已声明且已通过脱敏/字段可见性裁剪的字段。Skill 只能通过自身 `tool_interfaces.py` 的 Protocol 访问被注入的能力，不得直接 import `src.runtime`、`src.adapters`、`src.security`、`src.data_platform` 或 `src.model_service`。

### 7.3 不提前建设的治理能力

- 不新建第二套灰度状态机；现有 Test Shadow 和发布证据继续是候选验证主链。
- 不承诺生产流量 10/25/50/100% 切分，除非真实运行时多版本选择和观测需求出现。
- 不为内置 Skill 立即上容器/沙箱；此类成本仅在第三方 Skill 或明确资源隔离需求出现后评估。
- 不在 Skill 内实现权限、审计、脱敏或高风险动作判断。

## 8. 存储、接口、事件与可观测性设计

### 8.1 本阶段存储决策

| 数据 | 处理方式 | 原因 |
|---|---|---|
| 结算/费用/资格事实快照 | 运行时短生命周期对象；会话记忆仅存最小引用和裁剪字段 | 外部系统和已发布数据源才是权威真相，避免双写 |
| 公开对话重放 | 继续使用 `policy_qa_trajectories` | 已有公开快照边界，禁止写内部调用细节 |
| 任务/工作流摘要 | 继续使用现有 task/workflow 记录 | 记录场景、结果状态、来源系统摘要和停止原因即可 |
| 预退费候选评测/版本 | 复用既有 Skill 草稿、评测、发布存储 | 不建立平行候选治理体系 |
| 不可篡改审计 | 对接正式 `security/audit` 能力及未来 SSO | 不在 Runtime 临时造审计表 |
| Tool 调用原始日志 | 不新增专用表 | 当前缺少已验证查询与审计需求，且原始 payload 有敏感泄露风险 |

所有未来 PostgreSQL 表若确需新增，必须遵循项目既有 `CREATE TABLE` 与 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 双写要求，并通过真实 PG 冒烟验证；本文不预先创建表结构。

### 8.2 SSE 与错误契约

保持已有公开事件集：`step`、`result`、`error`、`done`。

- 不新增 `tool_call`、`adapter_payload`、内部计算图或模型推理事件。
- `done` 继续携带 `attempt_count` 和 `halt_reason`；新场景还应在内部任务摘要中关联 `case_type` 与 `qa_turn_id`。
- `result` 只携带 `PolicyQAPublicResult` 白名单，不为每个新场景复制一套响应模型。
- 任何新可展示字段都必须通过公开字段评审、脱敏规则、Portal DTO 和轨迹回放兼容性检查。

### 8.3 建议的无敏感指标

在正式可观测性接线时，按场景聚合如下指标，不附带患者或结算标识：

- `policy_qa_case_requests_total{case_type,outcome}`；
- `policy_qa_capability_calls_total{capability_name,outcome,reason_code}`；
- `policy_qa_capability_latency_ms{capability_name}`；
- `policy_qa_verification_total{case_type,answer_status,verification_reason}`；
- `policy_qa_human_confirmation_total{action_type}`；
- `policy_qa_source_unavailable_total{source_system,reason_code}`。

指标只用于运行质量、容量和失败分类分析；不得成为记录原始业务事实的旁路。

## 9. 实施顺序与上线门槛

### 9.1 建议顺序

| 阶段 | 目标 | 前置条件 | 产出与退出条件 |
|---|---|---|---|
| S0 评审冻结 | 确认本文范围、公开契约策略和安全边界 | #69 评审结论 | 决策表签核，不进入编码 |
| S1 共性契约 | 完成 G1–G3：受控判别输入、事实快照、能力调用结果、内部核验原因与公开映射 | S0；R4 安全/接口评审 | 现有结算解释零回归；新契约只在 Runtime 内生效 |
| S2 比较 C1 | 接入结算级跨结算比较 | S1；可信授权设计或受控测试身份 | 可解释确定性字段差异；不宣称同药 |
| S3 比较 C2 | 增加药品级归因 | 药品身份、费用明细、单位、目录与待遇事实确认 | 可比性不满足时可靠拒答；满足时才输出同药归因 |
| S4 预退费 | 真实预结算适配、候选评测与物化决策 | 收费系统契约、SSO/RBAC、审计、Skill L1/L2 | 仅只读预览；高风险执行请求始终拦截 |
| S5 慢特病 T1 | 已发生结算待遇解释 | 政策规则和结算可见事实充分 | 明确待遇参与/未显示/数据不足三态 |
| S6 慢特病 T2/T3 | 资格状态解释与导办 | 资格系统、权限、审计、敏感字段规则 | 不作行政认定；导办与资格解释边界清晰 |
| S7 平台化复核 | 检验是否存在已被多个场景验证的稳定共性 | 至少两个正式场景复用同一能力且有统一治理需求 | 决定是否另立 Tool 平台化议题；此前不建设 |

### 9.2 每个场景的发布门槛

所有连接到 `/policy-qa/stream` 的新场景均按 R4 风险处理，至少完成：

1. **Unit**：事实转换、能力结果映射、原因码、金额精度、输入边界、权限与高风险负例。
2. **API**：判别联合、SSE 事件顺序、白名单、错误不泄露、恢复预算、会话/轨迹。
3. **Flow**：真实或受控 Adapter 全链路、政策适用性、任务与人工确认闭环。
4. **安全**：越权读取、资源枚举、脱敏、原始 payload/SQL/推理泄露、高风险动作前置拦截。
5. **Portal 与浏览器**：场景输入、流式终止、不可用状态、引用展示、窄屏和键盘可达性。
6. **外部系统**：对接方提供的契约测试和安全联调；模拟器不可作为生产放行证据。

## 10. 需在评审中确认的决策

| 决策 | 推荐结论 | 影响 |
|---|---|---|
| 新场景请求扩展方式 | `settlement_id` 保持必填；使用受限 `case_request` 判别联合，不使用自由参数包 | R4 API 与前端 DTO |
| 公开状态策略 | 公开继续 `complete/partial/unavailable`；#69 六态先作为内部原因码 | 保护已存在公开契约 |
| 最小能力契约位置 | 放在 `runtime/policy_qa/`，不创建独立平台层 | 控制抽象边界 |
| MCP 与 Adapter 的关系 | MCP/Extension 负责能力目录、传输或选择；Adapter 负责外部协议；Runtime 决定调用时机和结果映射 | 避免职责重叠 |
| 比较 MVP | 先做结算级差异解释，药品级归因后置 | 防止数据不足时误称“同药” |
| 预退费交付策略 | 保持候选 Skill，真实预结算、评测和审批通过后才物化 | 保障金额与高风险边界 |
| 慢特病交付策略 | 先 T1，再 T2/T3；核心资格读取不交给 Skill | 避免行政认定越界 |
| 身份缺失时的策略 | 敏感新场景不得生产开放；请求自报角色不能替代 SSO | 合规与越权保护 |
| 新持久化表 | P0 不建；先复用公开轨迹、任务/工作流和正式审计 | 避免存储抽象先行 |
| Graph 与生产灰度 | 不纳入本轮；现有 Test Shadow 用于候选验证 | 避免重复控制面 |

## 12. 最终判断

#69 的长期目标无需通过一次“大平台重建”来实现。当前最有价值的增量是把已验证的结算解释链路整理为可被多个场景安全复用的事实、能力、核验和公开结果边界；随后用结算级比较、真实预结算、慢特病待遇解释逐项检验这些边界是否真的稳定。

只有当多个已上线场景重复要求同一能力，并且出现统一权限、审计、版本或运行治理的真实压力时，才把该能力提升为真正的平台 Tool。这样既遵循“共性下沉、个性上浮”，也能保证系统在数据、政策、权限或外部接口不足时诚实停止，而不是产生看似合理但不可追溯的医保结论。

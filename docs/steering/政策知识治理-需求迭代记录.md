## 流水线总览（当前架构）

```
文档上传 → 结构化拆分(Python structure_parser) → 单元(叶子)

```

### 锁定机制细节（需求 7.3）

| 操作 | 状态变更 | 效果 |
|------|---------|------|
| 保留 | `dupResolved.add(key)` | 当前单元清除重复标记，不再显示“处理”按钮 |
| 合并到此 | `dupMerged.set(key, targetKey)` | 当前单元从列表隐藏（合并到目标），双方锁定 |
| 编辑文本 | `textOverrides.set(key, newText)` + `dupResolved.add(key)` | 正文覆盖显示，同时清除重复标记 |

所有锁定状态在切换文档时重置（仅页面内状态，不持久化）。

### 设计决策

- **原文模式不带双向定位**：原文是 `content_text` 连续文本，叶子已混在其中，无法定位 `node_id`。树模式才保持点击叶子→右栏定位的能力。切换时明确提示。
- **合并仅在客户端**：`dupMerged` 隐藏当前单元，不调后端删除（可逆）。真实去重需后续持久化。
- **编辑覆盖不写回后端**：`textOverrides` 仅影响该单元卡片显示，不改 `leaf.text`（结构层原文不动）。适合人工临时修正提取/显示。

## 迭代 9：双向解析 + 相似度算法重做（本轮）

**状态**：✅ 已完成

### 背景

迭代 8 的重复处理有两个不足：
1. 单向解析——处理 #19→保留 #111 后，#111 仍显示「疑似重复」（即使 #19 是它唯一的重复），需手动再处理一次
2. 相似度算法过粗——全路径等权 Jaccard 把「支付 85%职工 15%」和「支付 90%职工 10%」等数字不同但结构相似的单元也标为重复

### 需求与实现

| # | 需求 | 实现 | 文件 |
|---|------|------|------|
| 9.1 | 双向解析 | `resolveDupKeep`/`resolveDupMerge` 增加级联逻辑：处理当前单元后，检查其重复伙伴（或目标单元的伙伴），若其他伙伴均已处理则同步清除目标标记 | `units/page.tsx` |
| 9.2 | 叶子 80% + 路径 20% | `dupSimilarity()` 加权公式：`0.8 * leafSim + 0.2 * pathSim`；新增 `leafAndPath()` 将全路径拆为叶子正文与祖先路径 | `units/page.tsx` |
| 9.3 | 数字权重提升 | 叶子含数字时：`leafSim = 0.6*文本二元组 + 0.4*数字 Jaccard`（数字占叶子相似度 40%）；新增 `extractNumbers()` | `units/page.tsx` |
| 9.4 | 数字完全不同→不相似 | `dupSimilarity()` 硬规则：两单元数字集合无交集（且均有数字）直接返回 0 | `units/page.tsx` |

### 双向解析逻辑

**保留此候选**（`resolveDupMerge(key, targetKey)`）：
- key 标记为重复（显示「重复·#target」）
- 检查 target 的其他重复伙伴，若均已处理 → target 同步清除标记（确认为主单元）

**保留本单元**（`resolveDupKeep(key)`）：
- key 判为独立
- 遍历 key 的未处理伙伴 P，检查 P 的其他伙伴（排除 key）是否均已处理 → 若是，P 同步清除标记

### 相似度公式

```
有两方均有数字时：
  numberSim = |A∩B| / |A∪B|（数字集合 Jaccard）
  numberSim === 0（无交集）→ 直接返回 0
  leafSim = 0.6 * 文本二元组Jaccard + 0.4 * numberSim
  similarity = 0.8 * leafSim + 0.2 * pathSim

无数字时：
  similarity = 0.8 * 文本Jaccard + 0.2 * pathSim
```

### 设计决策

- **数字硬规则优先**：数字完全不同直接判 0，在加权公式之前生效。这保证「支付 85%」与「支付 90%」不会误标为重复。
- **级联用 `findDupCandidates`**：不预存伙伴图，直接在处理器中调 `findDupCandidates` 检查。仅在用户点击时执行（非渲染路径），可接受 O(n) 开销。
- **保留本单元也可能级联多个**：若本单元的多个伙伴都仅与它重复，保留后全部同步清除。

### 验证

- 疑似重复数：迭代 8 的 100 → 迭代 9 的 84（数字敏感过滤了结构相似但数字不同的误报）
- 「统筹基金支付 85%」与「统筹基金支付 90%」单元互不标记为重复 ✓
- #19→保留#111 后，#111 同步清除标记（仅 1 个伙伴时）✓

| 10.2 | 工具栏统计标签 | 已选 N 后增加可点击的「疑似重复 N」「通过 N」「已驳回 N」徽章，点击即筛选，`stats` useMemo 实时计算 | `units/page.tsx` |

### 持久化数据结构

```json
// policy_documents.dup_state JSONB
{
  "resolved": ["node_id_1", "node_id_2"],  // 已处理（锁定）
  "merged": { "node_id_3": "target_node_id" }  // 标记为重复的目标映射
}
```

- 加载：`GET /documents/{id}/dup-state` → `setDupResolved(new Set(resolved))` + `setDupMerged(new Map(Object.entries(merged)))`
- 保存：每次 `resolveDupKeep`/`resolveDupMerge` 后调 `persistDupState(newResolved, newMerged)` → `PUT /documents/{id}/dup-state`
- 重启安全：数据在 PostgreSQL，uvicorn 重启不影响

### 设计决策

## 迭代 11：单元级审核 + 成对相对的重复关系（本轮）

**状态**：✅ 已完成

### 背景

用户测试时发现三类问题：
1. **审核只对“有提取记录”的单元生效**：无提取记录的单元只能「触发提取」，不能「通过/不通过」。但「通过/不通过」本应作用于**所有单元**（单元 = 文档叶子，是否有效单元与是否已 LLM 提取无关）。
2. **疑似重复标签不是“成对相对”**：候选的「✓重复」标签取决于「候选是否被标记为某人重复」（全局），而非「当前单元与此候选的关系」。导致：A-D 已确认重复后，B 的候选 D 也错误地显示「✓重复」（实际 B-D 未判定过）。
3. **三种关系结果的语义需明确**：每对关系的结果只有 3 种——①重复（留当前，候选是副本） ②不重复 ③留下相似单元（当前是副本，**也属于重复关系**，只是保留方向相反）。用户强调：点「留下相似单元」等于把这对标记为重复，必须理解此逻辑。

### 需求与实现

| # | 需求 | 实现 | 文件 |
|---|------|------|------|
| 11.1 | 单元级审核（无提取单元也可通过/驳回） | `dup_state.unit_audit` 持久化 `{node_id:{action,reason}}`；UnitCard 始终显示通过/不通过；`batchAudit` 分流：有提取→审提取记录，无提取→写 `unit_audit`；`effectiveStatus`：无提取时读 `unit_audit` | `units/page.tsx` |
| 11.2 | 待审核统计含无提取单元 | `stats` 的待审核 = `status in ('draft','pending')`；筛选 `draft` 同含 pending；工具栏阶段 1 追加「通过/已驳回」徽章便于看进度 | `units/page.tsx` |
| 11.3 | 重复标签成对相对 | 新增 `pairRel(a,b)` 返回 `'dup'\|'not_dup'\|'undecided'`（仅当 `merged[a]===b` 或 `merged[b]===a` 才算 dup）；Modal 候选标签、`nodeResolved`、`isUnique`、`currentResolved` 全部改用 `pairRel` | `units/page.tsx` |
| 11.4 | 三种关系结果语义 | Modal 每个候选三按钮：是重复(`merged[c]=cur`)/不是重复(not_dup 对)/保留此候选(`merged[cur]=c`，**也是重复**，仅方向相反)；候选已被别处标记为重复时禁用「是重复」（防覆盖） | `units/page.tsx` |
| 11.5 | 保留本单元只判定未决伙伴 | `resolveDupKeep` 仅对 `pairRel==='undecided'` 的伙伴写 not_dup，不动已判定对，避免状态冲突 | `units/page.tsx` |

### 数据结构（`policy_documents.dup_state` JSONB 扩展）

```json
{
  "not_dup": { "A": ["B","C"] },            // 双向 not-dup 对（迭代10）
  "merged": { "X": "Y" },                    // X 是 Y 的重复副本（方向性，迭代10）
  "unit_audit": {                              // 新增：无提取单元的审核决定
    "node_id": { "action": "approve|reject", "reason": "" }
  }
}
```

### 成对关系判定（需求 11.3 核心）

```
pairRel(a, b):
  if merged[a]===b || merged[b]===a  → 'dup'        // 任一方向标记过重复
  elif not_dup 含 (a,b) 对          → 'not_dup'      // 双向
  else                              → 'undecided'    // 未判定
```

- **A-D 已重复、B 候选 D**：`pairRel(B,D)` → `merged[D]===B`? 否(A) · `merged[B]===D`? 否 → `undecided` → D **不**显示「✓重复」，显示操作按钮 ✓
- **A 标记 B 为重复后，切到 B 为当前**：`pairRel(B,A)` → `merged[B]===A`? 是 → `'dup'` → A 显示「✓重复」 ✓

### 设计决策

- **单元级审核与提取级审核分流**：有提取记录的单元仍审提取记录（保证 knowledge 页 status=reviewed 流转）；无提取记录的单元用 `unit_audit`。`effectiveStatus` 优先用提取状态（有则用），无则回退 `unit_audit`，再无则 `pending`。
- **`unit_audit` 复用 dup_state 端点**：`GET/PUT /documents/{id}/dup-state` 本就是透传 JSONB，加 `unit_audit` 键无需改后端。
- **防覆盖**：候选已被别处标记为重复（`merged[candidate]` 指向非当前单元）时，「是重复」按钮禁用——避免把 `merged[D]=A` 改成 `merged[D]=B` 丢失原关系。「不是重复」「保留此候选」不受影响（前者写 not_dup 不动 merged；后者写 `merged[cur]=c`，不动候选既有 merged）。
- **无提取单元的通过≠待发布**：无提取记录的单元通过后状态显示「已通过」（非「待发布」，因无知识可发布），与有提取单元的 reviewed 区分。

用户提出新方向（AI 原生重构）：不再让人逐条加工政策知识，而是 AI 完成差异识别、规则抽取、统一语义映射、证据核验、冲突发现和影响分析，形成可审查的**知识变更集**（类 PR）；人只处理异常、高风险规则和最终发布决策；发布生成**不可变知识快照**，Agent 运行时只读快照。

### 关键决策

- 产品结构：知识模块收敛为**四个工作空间**（AI 治理驾驶舱 / 待决策队列 / 知识变更集 / 已发布知识）。

- 职责边界：AI 生产与推荐、程序确定性校验、人高风险决策与发布；第一阶段不启用 AI 自动发布（L1 全量人工审核起步）。
- **现状发现**：现有 `releases + QualityRun + Milvus collections + promote/rollback`（测试页）已是“候选版本→构建索引→质量门禁→人工发布→回滚”骨架，即 V4.0 快照/门禁的直接前身；AI 生产流水线是现有 `pipeline_store` 的编排升级。

## 迭代 15：知识页收敛为「构建 → 审核 → 发布管理」核心流程

**状态**：🟢 产品方向已确认，独立设计规格待书面复核

### 用户反馈（2026-08-05）

1. 已有一级页面“概览 / 文档 / 单元”承接前置资产，知识页不应重复设置驾驶舱、概览或通用工作台。
2. 唯一知识生产通路必须是：**文档 → 单元拆分与审核 → 从已审核单元构建知识 → 知识审核 → 发布管理**；禁止文档直接构建知识。
3. Schema 已由语义层统一维护；知识页只读复用语义契约，修改必须回到语义层完成。
4. “知识变更集”“待决策”等技术概念不再作为并列导航；前端使用“构建结果”“待处理问题”等业务语言，并统一纳入知识审核。
5. 知识页二级导航收敛为：**知识构建 / 知识审核 / 发布管理**。
6. 构建页只保留一个主操作“新建构建任务”；单元选择进入创建流程，不在主页同时保留“使用所选单元构建”按钮。
7. 构建来源约束与语义契约版本属于运行上下文，压缩为轻量信息栏，不占用首屏大卡片。

### 构建覆盖与版本决策

- 同一个单元版本同一时间只能存在一个未结束的知识候选生命周期，禁止并发构建和相互覆盖。
- 不同任务可以在前一生命周期结束后重新使用同一单元版本，但必须以“重新构建”显式发起并记录原因。
- 每次构建生成独立、不可原地覆盖的候选结果；新结果通过 `supersedes` 血缘指向旧结果。
- 不同单元构建出重复或冲突知识时，在知识审核阶段识别为重复、补充证据、规则分支、替代或冲突，不按任务先后自动覆盖。
- 只有发布管理可以把审核通过的候选结果提升为新的正式版本；已发布快照保持不可变并可追溯、可回滚。

### 设计产出

- 独立规格：`docs/superpowers/specs/2026-08-05-policy-knowledge-build-review-publish-design.md`
- 视觉方向：构建主页采用全宽任务列表；“新建构建任务”进入选择已审核单元、确认构建配置、冲突预检三步流程。

### 性能诊断结论（已量化）

- `GET /knowledge-build/tasks` ~10ms（单查询，无优化必要）。

### 迭代 16 实现方案

**① 构建页性能**

后端（`knowledge_build_service.py` / `knowledge_build_store.py` / `knowledge_workbench_service.py`）：

前端（`knowledge-build-page.tsx`）：
- 拆分为**独立并行加载**：任务表（~10ms）先渲染，eligible 到达后再更新摘要与按钮（不再被 2s 慢接口阻塞首屏）；
- 表格与摘要改为**骨架屏**加载态（替代纯文字“正在加载…”）。

**② 新建构建任务筛选**

`knowledge-build-wizard.tsx` 步骤一：
- 新增「全选当前筛选单元」复选框（只选未禁用项）；
- 新增「按来源文档」下拉筛选（doc_title 分组）；

**③ 审核详情表格化 + ④ 操作按钮设计**

```text

├─ 表格（每行 = 一条候选知识）─────────────────────────────────────────┤
```

| 操作 | 用途 | 交互细节 | 落库 |
|---|---|---|---|
| **通过** | 认可该条候选知识（单条审核意见） | 点击 → 行内二次确认（无需理由）→ 状态“已通过” | `reviewKnowledge(approved)` |

| **查看详情** | 完整结构化字段 / 语义映射 / 证据 / Diff | 链接跳转现有规则详情页 | — |

> 说明：后端单条审核仅支持 `approved/rejected`（`ReviewStatus`），行级“退回”以 `rejected` + 标记化 note 落库、前端区分展示；**整批状态流转**（通过审核 / 退回重新构建 / 拒绝）仍由底部聚合操作与现有 `approveChangeSet/returnKnowledgeReview/rejectChangeSet` 负责，行级操作是审核意见留痕、不改变变更集状态机。

保留：顶部 AI 摘要、待处理问题区、底部聚合操作栏（含“通过审核”阻断逻辑）、当前审核身份。

## 迭代 18（2026-08）：知识审核页支持「修改提示词 + 换大模型 + 单条/批量重新提取」

**状态**：🟡 设计阶段（设计文档已出，待评审后实施）

### 背景

用户在「政策知识 → 知识 → 知识审核」（`/policy-knowledge/knowledge/review/[changeSetId]`，体系 B 变更集审核详情页）发现候选知识提取有误时，当前只能「拒绝/退回」走整批重建（`reprocess` 按文档重建），无法在审核上下文内**就地用不同提示词或不同大模型重新提取**，也缺乏批量能力。

### 现状关键事实（已核实代码）

- **真正的 LLM 提取**在 `PipelineOrchestrator._extract_policy_facts`（`src/knowledge_extension/rule_explanation/pipeline_orchestrator.py`），提示词已 **schema-driven**：`_build_fact_extraction_prompt` → `build_prompt_from_schema` **每次实时读语义层 `zcgz` 的 published 指标契约**拼提示词，registry 不可用时回退硬编码 19 字段 legacy prompt。
- **指标动态注入实时生效已实现**：`build_extraction_schema(create_registry(), "zcgz")` 每次调用读最新 published 指标，故语义层新增/重命名指标并发布后，下一次提取即实时生效。
- **模型调用**：`ModelGateway().generate(messages, model_type="llm", scene="policy_qa", max_tokens=8192)`，`ModelRouter.resolve(scene, model_type)` 从 `ROUTING_TABLE` 解析 `model_name`。**`gateway.generate` 当前不支持指定 `model_name`**（只能换 scene 间接选，而 scene 固定为 `policy_qa`）。
- **两套体系**：体系 A（`pipeline_store` + `extractions`，有 `reextract_unit(extraction_id)` 单元重提取 + 端点 `POST /policy-pipeline/extractions/{id}/reextract`）；体系 B（`policy-workbench` + `KnowledgeChangeSet`，前端审核页走此）。**体系 B 的 `KnowledgeItem` 由体系 A 的 extraction 实时派生**（`knowledge_id = hash(extraction_id, rule)`）。
- **缺口**：① 提示词无法手动覆盖；② 无法换大模型；③ 体系 B 审核页未接入重提取；④ 无批量重提取。

### 需求拆解

| # | 需求 | 说明 |
|---|------|------|
| 18.1 | 修改提示词 | 审核页可切换提示词来源：schema（默认实时读指标）/ 自定义（手动覆盖文本）；自定义模式下提示「指标不会自动注入，需手动包含」 |
| 18.2 | 换大模型 | 审核页可选择目标模型；列出当前可用模型；扩展 `gateway.generate` 支持指定 `model_name` |

### 设计产出

- **独立设计文档**：`docs/steering/政策知识治理-知识审核重提取设计-V1.0.md`（前端 + 后端完整设计）。

### 设计决策要点

- **复用而非新建提取器**：所有重提取统一走 `PipelineOrchestrator._extract_policy_facts`，新增 `ExtractionOverride`（prompt_mode / custom_prompt / model_name / max_tokens）参数注入；不在体系 B 重写提取逻辑。
- **变更集刷新**：重提取更新体系 A 的 extraction 记录后，调用 `ChangeSetService` 重建该 change-set 的候选快照（`knowledge_id` 因 extraction 内容变化而变化，旧 `item_id` 失效，新候选进入待审）。重提取视为「同源单元的新一次构建」，沿用 `supersedes` 血缘思路。
- **模型选择**：扩展 `ModelGateway.generate(model_override: str | None = None)`，传入时绕过 router 直接走指定模型（仍经 provider 异常分类与 fallback）；新增 `GET /policy-workbench/extraction-config/models` 列出可选模型。
- **安全约束**：重提取不触碰已发布快照（`published_knowledge_snapshots` 不可变），仅作用于 draft/审核中的候选；重提取后状态回退为 draft（沿用现有 `reextract_unit` 语义），需重新审核。
- **实时生效保证**：schema 模式每次 `create_registry()` 读最新 published 指标，无需缓存失效；前端对话框展示当前提取契约版本 + 指标列表，引导用户「去语义层发布指标后重提即可生效」。

### 现状调查结论（2026-09-02，issue 前提校正）

1. **P0-1 前提部分过时**：主问答路径已有 release 感知——`structured_policy_retriever.resolve_rules_collection()`（`src/runtime/policy_qa/structured_policy_retriever.py:167`）读 active release 集合并带回退；但**两套解析机制不一致**（structured retriever 走 ORM + 行数完整性检查 `_is_complete_release_collection`，代码注释自认临时方案；`rules_search_service._resolve_active_release()`（`rules_search_service.py:31`）走裸 SQL + 命名拼接、无完整性检查），且 `broad_policy_retriever.py:127`、`answer_verification/milvus_port.py:31`、`policy_knowledge_routes.py:35` 三处仍硬编码 `policy_rules_v2`。
2. **写入侧断裂（更关键）**：回填脚本与 `publish_to_new_collections`（`pipeline_orchestrator.py:1096`）直写 `policy_rules_v2`，而 promote 产物是独立集合 `policy_rules_{release_id}`——**存在 active release 时，直写主集合的数据 Runtime 读不到**。测试环境实测（2026-09-02）：active release = `REL_20260827_MZ8_V3`（`policy_rules_REL_20260827_MZ8_V3`，418 行），`policy_rules_v2` 417 行，断裂现实存在。

4. **P0-4 结构性卡点**：两个 retriever 均无分数阈值/拒答出口（broad 路径永远返回 top_k），诚实拒答率（负例召回 0 条才算）在现状下必然≈0；`issue25_retrieval_baseline.py` 为纯合成语料（约 32 条）+ 内存 FakeMilvus，无真实语料模式，黄金用例 58 条全绑合成 ID。

### 设计方案（2026-09-02 与用户确认）

1. **P0-1 = 统一 resolver + 单一写入链**：抽一个权威 collection 解析模块（含完整性检查，替代现有两套），四条读路径（structured retriever / rules_search_service / broad retriever / answer_verification milvus_port / policy_knowledge_routes）全部接入；写入侧收敛——回填与直写不再绕过 release 读源。
2. **P0-2/P0-3 回填 = 感知 active 动态写入**：回填服务写入 Runtime 当前实际读的集合（有 active release 写其 rules 集合，否则写 `policy_rules_v2`），回填后立即可检索（对应验收标准 1）。
3. **P0-2 金额段 (0,0) = 跳过过滤（保留召回）**：`(0,0)` 视为"无法解析"，不参与范围过滤，规则仍可召回（不漏规则优先，接受其对 FAR 的潜在影响，复测时用数据验证）。

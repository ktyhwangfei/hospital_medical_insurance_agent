## 1. 设计理念：从"管理"到"治理"

### 1.1 为什么是治理，不是管理

> AI 时代，政策知识真正值钱的不是"存"，而是"**治**"。

| | 管理（Management）| 治理（Governance）|
|---|---|---|
| 关注 | 上传、维护、存储 | **质量、版本、审核、发布、追踪、影响分析** |
| 产物 | 一堆文档/规则 | **可信、可追溯、可演进、可审计**的知识 |
| AI 价值 | 检索素材 | RAG / Agent 敢用、能解释、可问责 |

本平台定位 **政策知识治理（Policy Knowledge Governance）**，治理机制是一等公民，不是存储的附属功能。

### 1.2 核心定位（产品叙事）

> **政策文档是知识来源（Source），Policy Unit 是知识锚点（Anchor），Policy Knowledge 是 AI 派生且受治理的结果（Governed Derived Knowledge）。**
>
> 三者构成治理平台的内核。连接业务运行时的**桥梁（Bridge）= 语义层**，是独立协作系统，不属于治理平台。

### 1.3 四条治理原则

| 原则 | 内容 |
|------|------|
| **一·锚点唯一** | Policy Unit 是唯一内容锚点。系统不管理 Chunk，知识都从 Unit 派生。 |
| **二·契约抽取** | Knowledge 由 AI 抽取，**但受语义层提取契约约束**，可校验、可治理（非开放式抽取）。 |
| **三·边界清晰** | 治理平台只到 **Knowledge**。业务映射（Object↔Metric）归**语义层**；只绑 Object+Metric，**不绑 Skill/SQL/Agent**，Agent Runtime 独立消费。 |
| **四·全程可追溯** | 每条 Knowledge 带证据（Evidence）、置信度（Confidence）、提取器（Extractor）、生命周期与关系。**无来源不发布**。 |

### 1.4 承重墙（不变项，红线）

以下能力由现有系统近 10 轮讨论（D1–D11）沉淀，本次治理重定位**不得削弱**：

- **语义拉齐**：政策世界与数据库世界共用同一套指标 + 值域字典（由语义层持有）。
- **结构化字段**：Knowledge 保留核心维度（固定 schema + 标量索引）+ 详情（dynamic + 字段级溯源）。
- **schema 驱动提取**：语义层发布提取契约，LLM 按契约抽取。
- **质量门禁**：黄金样本集 + 质量分。
- **向量复用**：Unit 全文向量化；Knowledge 复用所属 Unit 向量；按 `unit_id` 分组检索。

> 治理是把"质量/版本/审核/发布/追踪/影响分析"做厚，不是推翻这些地基重新盖。

## 2. 核心对象与边界

### 2.0 边界声明（最重要的一张图）

```
┌─── 政策知识治理平台（本设计，3 对象）──────────────────────┐
│                                                            │
│   Policy Document  ──来源──►  policy_documents @ PG         │
│          │ 章节解析                                          │
│          ▼                                                  │
│   Policy Unit      ──锚点──►  policy_facts @ Milvus         │
│          │ AI 按契约抽取 + 治理（证据/置信/生命周期/关系）    │
│          ▼                                                  │
│   Policy Knowledge ──治理►  policy_rules_v2 @ Milvus        │
│          │                                                  │
└──────────┼─────────────────────────────────────────────────┘
           │ 提取契约（单向只读，D6）
           ▼
┌─── 语义层（独立协作系统，不属本平台）─────────────────────┐
│   Business Object ──► Metric ──► source_field + 值域字典     │
│   （只绑 Object + Metric；不绑 Skill/SQL/Agent）            │
└──────────┬─────────────────────────────────────────────────┘
           │ 独立消费（解耦）
           ▼
       Agent / Skill Runtime
```

`[决策]` **治理平台边界止于 Knowledge**。映射（Knowledge 的业务概念 ↔ Object/Metric）由语义层通过提取契约建立并持有。Skill/SQL/Agent **不**进入映射定义——Agent Runtime 独立消费语义层。这是优先级一（必须）的解耦。

### 2.1 Policy Document（政策文档）— Source

**职责**：管理政策原文。不参与 AI。仅作治理对象的来源。

**落点**：`policy_documents` @ PG `[来源: 现有表]`。关键字段：`doc_id, title, issuer(发文机关), doc_no(文号), publish_date, effective_date, expire_date, version, status, content_text, 附件`。

> Document 自身也有生命周期（生效/失效/被替代），但作为来源，其治理粒度低于 Knowledge。V2.1 先做"上传新版本→触发重新解析→影响分析"，完整自动 Diff 列后续（§7）。

### 2.2 Policy Unit（政策单元）— Anchor ⭐

> 原系统的 `policy_facts`（"事实"）抽象偏学术，业务听不懂。重命名为 Policy Unit，并**显式绑定法律结构（章/条/款）**。

**为什么需要 Unit**：政策天然有法律结构（第一章/第三十五条/第二款），这就是天然知识单元，而非 512 token 的 chunk。

**落点**：`policy_facts` @ Milvus（物理名保留，对外称 Policy Unit，见 §6.2）。

**职责**：唯一内容锚点 / 唯一引用来源（citations 指向 Unit）/ **向量化单元**（语义检索主入口）。

**现成基础**：`structure_parser.py` 的 `ClauseNode`（level/marker/path/order_no，解析 章/条/款/项/目）`[来源: policy_struct/structure_parser.py]`——Unit 法律结构字段直接取自它。

**字段**：见 §4.2。新增 `chapter/article/clause/unit_no/context/status`。

### 2.3 Policy Knowledge（政策知识）— Governed Derived ⭐

**职责**：来源于 Unit，由 AI 按提取契约抽取，**全程受治理**（证据/置信/提取器/生命周期/关系）。

**落点**：`policy_rules_v2` @ Milvus（物理名保留，对外称 Policy Knowledge）。

**四项治理增强（V2.1 核心）**：

| 增强 | 字段 | 治理价值 |
|------|------|----------|
| **Evidence 证据** | `evidence{quote, unit_id, location}` | 可解释（为什么是 85%）+ 审计（对照原文核验）+ citations |
| **Confidence 置信度** | `confidence`(Knowledge 级聚合) | 审核优先级排序 + 低置信自动标记 |
| **Extractor 提取器** | `extractor{name, model, version, extracted_at}` | 可复现 + 可问责（哪次模型抽的）|
| **Lifecycle 生命周期** | `status` + `superseded_by` + `references` | 版本治理 + 替代/引用关系 |

**保留的承重能力**：
- **结构化字段**（核心维度固定 schema + 标量索引；详情 dynamic + FieldTrace 字段级溯源）`[决策]` 不丢，丢了精准过滤和跨世界联查就废。
- **knowledge_type**（8 类：Definition/Rule/Formula/Condition/Constraint/Exception/Procedure/Reference）叠加在结构化字段之上。
- 一个 Unit 可挂多条不同 type 的 Knowledge。

> **"取消 Fact"的真实含义**：原 Fact 的"语义单元+向量化单元"角色由 **Unit** 承担，原 Rule 的"结构化展开"角色由 **Knowledge** 承担。Fact 这个中间概念吸收进 Unit，不再单独命名 `[决策]`。

### 2.4 映射归语义层（解耦边界）— 优先级一（必须）

**Mapping 不在治理平台**。它由语义层持有，且**收敛到只绑 Object + Metric**：

```
语义层（独立系统）:
  Business Object ──► Metric ──► source_field + 值域字典
        ▲
        │ Knowledge 的结构化字段 ↔ Metric 的对应关系
        │ （由"提取契约"在抽取时建立，单向只读依赖，D6）
  Policy Knowledge（治理平台产出）
```

**明确不绑**：Skill、SQL（source_field 是取数地址，不是绑定）、Agent。

**Agent Runtime 独立消费**：Skill/Agent 在运行时按需读语义层，治理平台不感知、不耦合。这带来两个后果：
1. 治理平台改 Knowledge/Mapping，不需要通知 Skill/Agent（它们各自最新读）。
2. **影响分析止于 Metric**：政策变动的影响能定位到"哪些 Metric 受影响"，但"哪些 Skill/Agent 受影响"是 Agent Runtime 自己评估的职责，治理平台不越界 `[决策]`。

> 这正是优先级一要的解耦：治理平台与运行时通过语义层松耦合，互不绑死。

## 3. 知识治理机制（治理平台的核心价值）

> 这一节是"治理"区别于"管理"的所在。五项机制：生命周期、关系、证据可追溯、质量门禁、影响分析。

### 3.1 Knowledge 生命周期状态机 `[决策]`

```
            submit                 approve
   ┌────► Draft ────────► Review ────────► Published
   │       │                │ reject          │
   │       │ (重抽取)        ▼                 │ supersede
   │       └──────────── (回到 Draft)         │ (新版本替代)
   │                                          ▼
   │reactivate                         Superseded
   │                                          │
   │   policy废止                            │
   │  Published ─────────────────► Deprecated │
   └──────────────────────────────────────────┘
                 (可重新激活→Draft)
```

| 状态 | 含义 | 是否供 RAG/Agent 使用 |
|------|------|----------------------|
| **Draft** | AI 刚抽取，待提交审核 | 否 |
| **Review** | 人工审核中 | 否 |
| **Published** | 已审核发布 | **是（唯一生效态）** |
| **Superseded** | 被新版本替代（保留可追溯）| 否（已被替代）|
| **Deprecated** | 政策废止 / 失效 | 否 |

**转换**：
- Draft → Review（提交审核）→ Published（通过）/ → Draft（驳回重抽取）
- Published → Superseded（被替代）/ → Deprecated（废止）
- Superseded/Deprecated → Draft（可选：重新激活，如政策恢复）

> `[决策]` 只有 **Published** 进入 RAG/Agent 检索池。其他状态对运行时不可见，但治理平台保留全量历史。

### 3.2 知识关系：替代与引用 `[决策]`

| 关系 | 含义 | 存储 |
|------|------|------|
| **替代（Supersede）** | K_new 替代 K_old。政策更新重抽取后，新版本替代旧版本 | `K_old.superseded_by = K_new.id`；K_old → Superseded |
| **引用（Reference）** | K 引用另一条 K 或外部政策（如"依据《XX 办法》第 N 条"）| `K.references = [{type: internal\|external, target, label}]` |

- **替代链**：可沿 `superseded_by` 追溯一个知识点的完整演进史（v1→v2→v3）。
- **引用图**：政策间的引用关系形成轻量知识网络，支撑"这条政策被哪些政策引用"的反查。

> V2.1 先做替代 + 引用两种关系。更复杂的关系（依赖/冲突/补充）列为后续（§7）。

### 3.3 证据与可追溯：Evidence / Confidence / Extractor `[决策]`

**Evidence（证据）**——每条 Knowledge 必须带支持它的原文证据：
```
evidence: {
  quote: str,        # 政策原文中支持本知识的确切片段
  unit_id: str,      # 证据来自哪个 Unit（= source_unit）
  location: str,     # 章/条/款 定位（取自 Unit）
}
```
价值：**可解释**（"AI 说支付比例 85%，因为第三十五条第二款原文：…"）+ **审计**（审核人对照 quote 核验）+ **citations**（QA 直接引用）。
> 现有 `source_text` 详情字段演进为结构化 Evidence。

**Confidence（置信度）**——Knowledge 级聚合置信度（0–1）：
- 与字段级 `FieldTrace.confidence` 并存：字段级用于字段溯源，Knowledge 级用于审核排序与低置信预警。

**Extractor（提取器）**——记录"谁、用什么模型、哪个版本、何时抽的"：
```
extractor: {
  name: str,         # 提取器/管线名（如 policy_pipeline_v2）
  model: str,        # LLM 模型（如 deepseek-chat）
  model_version: str,# 模型版本
  extracted_at: str, # ISO 时间
}
```
价值：**可复现**（同模型版本可重跑）+ **可问责**（某条错误知识可追溯到具体模型版本）。

> 三者合起来，治理平台才真正具备 Explainability + Audit 能力——这正是"治理"区别于"存储"的关键（优先级二）。

### 3.4 质量门禁 `[来源: 政策知识管线设计 §5]`

- **黄金样本集**：已审核 Knowledge 分层抽样（50–100 条），人工锁定期望值。
- **质量分**：填充率（≥60%）/ 值域合规率（≥90%）/ 与标注一致性（≥0.8）。阈值待标定。
- **门禁**：指标 draft→published 必须过质量分；Knowledge 不过 Evidence 校验（quote 为空或与 unit_text 不符）不得进 Published。

### 3.5 影响分析（Impact Analysis）⭐ 治理独有能力

> 政策一变，影响多大？这是"管理"做不到、"治理"必须做的能力。

**影响链**（止于 Metric，见 §2.4 解耦边界）：
```
Document 更新/废止
   ↓ Diff（定位新增/修改/删除条款）
受影响 Unit 列表
   ↓
该 Unit 下的 Knowledge（按 status 过滤）
   ↓ 经提取契约反查
关联 Metric（语义层，止于此）
   ↓ （不再下钻——Skill/Agent 是 Runtime 自己评估）
影响报告：N 条 Knowledge 待重审 / M 个 Metric 受影响
```

**触发点**：
- 文档上传新版本 → 自动 Diff → 生成影响报告（概览页展示）。
- Knowledge 置为 Deprecated → 通报关联 Metric（语义层侧标记）。

> `[决策]` 影响分析**不**自动改 Skill/Agent 配置（解耦）。它只产出"影响报告"，由人或 Runtime 各自决策。

> `[决策]` `status` 与 `knowledge_type` 是主导航/过滤维度，建议固定字段 + 标量索引（需重建 collection 一次，重灌 337 条，§6.3）。fallback：先 dynamic + 应用层过滤。

### 4.4 关系存储

- 替代：`Knowledge.superseded_by`（单值，指向最新版本）。沿此可追溯版本链。
- 引用：`Knowledge.references`（列表）。支持内部（指向另一 knowledge_id）与外部（自由文本引用）。
- 文档级：`Document.superseded_by_doc`。

> V2.1 不引入独立关系表，关系内联在 Knowledge 记录。若关系图查询需求增长，后续抽独立表（§7）。

### 4.5 语义层 @ PG（不变，协作系统）

## 5. 前端交互设计

> 治理平台 **4 个模块**：概览 / 文档 / 单元 / 知识。**无映射模块**（映射在语义层 `/semantic-layer`）。
> 视觉规范遵循 `原型设计文档.md` v3.0。

### 5.1 模块总览

| 模块 | 对象 | 主数据源 | 治理交互 |
|------|------|----------|----------|
| **概览** | — | 聚合 | 治理看板：质量/待审/生命周期分布/**影响分析** |
| **文档** | Document | PG | 上传/版本/失效/触发解析 + 文档级影响 |

| **知识** | Knowledge | Milvus policy_rules_v2 | 审核视图(生命周期/证据/置信) + 检索视图 + 关系视图 |

```
┌─ 治理指标卡 ─────────────────────────────────────────────┐

│  Draft ████  Review ██  Published ████████  Superseded █ │
│  Deprecated █                                            │

│  平均置信度 / 低置信预警数 / 黄金样本质量分               │
├─ 影响分析（治理独有）──────────────────────────────────┤
│  最近文档变更 → 影响 N 条 Knowledge / M 个 Metric          │
│  [查看影响报告]                                          │
└──────────────────────────────────────────────────────────┘
```

**API**：聚合 `policy-pipeline/summary` + `policy-knowledge/stats` + `semantic/summary`（现有，重组展示）+ **新增** `policy-pipeline/impact/recent`（最近影响报告）。

### 5.3 文档（Documents）

上传 PDF/Word → 填元数据 → 触发"章节解析 + Unit 生成"。列表显示状态/覆盖率。**上传新版本**触发影响分析（§3.5）。`[来源: 现有 documents tab]`

### 5.4 单元（Units）⭐ 核心页面

```
┌─ 左：文档大纲树 ──┬─ 中：Unit 正文 ──────┬─ 右：AI 分析 ──────────┐
│  📄 XX 医保办法    │ 第三章 待遇享受          │ ─ 该 Unit 的 Knowledge ─ │
│  ├ 第三章 待遇享受 │ 第三十五条 支付比例       │  💡[Rule] 支付比例85%     │
│  │ ├ 第三十五条●  │ 第二款：城镇职工在三…     │     📎证据: "...比例为85%" │
│  │ └ 第三十六条   │ (unit_no 可复制引用)     │     ⚠置信0.92 [v2]       │
│  └ 第四章 …       │                          │  ⛓[Constraint] 封顶30万  │
│                   │ [重新抽取][发布]         │ ─ 关联指标(语义层) ─      │
│                   │                          │   • Settlement.payment_ratio →│
└───────────────────┴──────────────────────────┴──────────────────────────┘
```

- **左栏**：从 Unit 的 `chapter/article/clause` 渲染层级树。
- **中栏**：`unit_text` + `unit_no`（可引用键）+ 重新抽取/发布。
- **右栏**：该 Unit 挂载的 Knowledge 卡片（type 图标/标题/结构化值/**证据 quote**/**置信度**/**版本**）；"关联指标"是**只读跨链**，点击跳语义层（不在治理平台内编辑）。

### 5.5 知识（Knowledge）— 拆三视图

**审核视图**（治理核心）：
```
┌─ 筛选 ──────────────────────────────────────────────┐
│  生命周期[Review▼]  类型[Rule▼]  文档[___▼]  低置信☑  │
├─ Knowledge 列表 ────────────────────────────────────┤
│ [Rule] 支付比例85% 来源:第三十五条第二款 ◐Review v2  │
│   📎证据:"...比例为85%" 🤖deepseek-v3 置信0.92       │
│   [✓通过→Published] [✗驳回→Draft] [↻重抽取]          │
│   关系: 替代v1 │ 引用: XX办法§12                     │
└──────────────────────────────────────────────────────┘
```

**检索视图**：保留现有三模式（精准/语义/混合）+ 跨世界（命中政策↔命中业务数据）。结果按 `unit_id` 分组（D10），**仅 Published 入池**。

**关系视图**（治理独有）：选一条 Knowledge → 展开其**替代链**（v1→v2→v3 时间线）+ **引用/被引用**关系图。

**API**：审核用 `policy-pipeline/extractions`(status 过滤) + `publish`；检索用 `policy-pipeline/rules/search`(mode/target，加 `knowledge_type`/`status` 过滤)；关系用 **新增** `policy-pipeline/knowledge/{id}/relations`。

### 5.6 映射在语义层（不在本平台）

映射管理在 `/semantic-layer/{object,metric,mapping,value-domain}`（现有）。治理平台仅在单元页/知识页提供**只读跨链**跳转。双向反查（Metric→Knowledge）由语义层侧实现（读取提取契约的 Knowledge↔Metric 对应）。

## 6. 数据流设计

### 6.1 治理生命周期（端到端）

```
导入 Document → 章节解析 → 生成 Unit(带法律结构+向量化)
   → AI 按契约抽取 Knowledge(类型+结构化字段+Evidence+Confidence+Extractor) [Draft]
   → 质量门禁(证据校验+质量分)
   → 人工审核 [Review] → 通过 [Published]
   → RAG/Agent 使用(仅 Published，citations 指向 Unit)
   → 政策更新 → 影响分析 → 重抽取 → 新版本 [替代旧版本→Superseded] → 差异审核 → 重发布
   → 政策废止 → [Deprecated]
```

> 全程：**人工维护 Unit，AI 维护 Knowledge，治理覆盖全生命周期。**

### 6.2 提取流（含治理增强）

```
① 语义层发布提取契约(只读): extraction-schema(fields/entities/relations/dictionaries)
② Document → 章节 → Unit 拆分(structure_parser → ClauseNode → Unit 带 unit_no + 向量化)
③ Knowledge 抽取(契约+类型): 每条产出
     { knowledge_type, 核心维度(经字典标准化), 详情(FieldTrace),
       evidence{quote,unit_id,location}, confidence, extractor{name,model,version,at} }
④ 字段级溯源(FieldTrace) + Knowledge 级溯源(extractor)
⑤ 质量门禁(填充率/合规率/一致性 + 证据校验) → 达标才入库 [Draft]
```
`[来源: 政策知识管线设计 §5]`。V2.1 新增：②Unit 带 unit_no；③产出 evidence/confidence/extractor。

### 6.3 检索流（三模式 + 跨世界，仅 Published）

精准/语义/混合三模式 `[来源: 政策知识管线设计 §4]`。**检索池只含 `status=published`**（治理约束）。跨世界联查：同一指标条件打政策库 + SQLServer，共享值域字典对齐。

### 6.4 演化流（版本治理）

加/改/删指标 → `schema_update_task`（incremental/full/soft_delete）`[来源: 政策知识管线设计 §6]`。政策版本更新 → 影响分析 → 重抽取 → **新 Knowledge 替代旧**（旧→Superseded，`superseded_by` 指向新）→ 差异审核 → 重发布。

### 6.5 影响分析流

Document 变更 → Diff(受影响 Unit) → 该 Unit 下 Knowledge(status 过滤) → 经提取契约反查关联 Metric → **生成影响报告（止于 Metric）**。`[决策]` 不下钻 Skill/Agent。

## 7. 与现有系统的关系（迁移边界）

### 7.1 重命名 + 边界映射 `[决策]`

| 现有 | 新对外概念 | 归属 | 改动 |
|------|-----------|------|------|
| policy_documents @ PG | Policy Document | 治理平台 | 补元数据 + 文档级替代 |
| policy_facts @ Milvus | Policy Unit | 治理平台 | 加 dynamic 字段(章/条/款/unit_no/status) |
| policy_rules_v2 @ Milvus | Policy Knowledge | 治理平台 | 加 status/confidence/version/evidence/extractor/superseded_by/references |
| semantic layer @ PG | Business Mapping | **语义层（独立）** | 不改模型；收敛只绑 Object+Metric |
| Fact 概念 | 取消（并入 Unit）| — | 仅文案 |

### 7.2 collection 物理名 `[推断]`

**建议不改**（`policy_facts`/`policy_rules_v2` 保留），仅对外文案用 Unit/Knowledge。改物理名 = 全量迁移+改读取入口，风险高收益低。若评审坚持统一，作独立迁移阶段。

### 7.3 Milvus 加固定字段成本

- Unit 的 `chapter/article/clause`：先 dynamic（零成本），需过滤时再 promote。
- Knowledge 的 `status`/`knowledge_type`：建议固定字段 + 标量索引（主导航+检索池过滤）。代价 = 重建 `policy_rules_v2` 一次，重灌 337 条（可重提取，可控）。fallback：先 dynamic + 应用层过滤。

### 7.4 前端路由

`/policy-knowledge/{概览,documents,facts,structured,discovery}` → **4 模块**：

| 模块 | 路由 | 复用 |
|------|------|------|
| 概览 | `/policy-knowledge` | page.tsx（改治理看板+影响分析）|
| 文档 | `/policy-knowledge/documents` | documents/page.tsx |
| 单元 | `/policy-knowledge/units` | facts/page.tsx **重构三栏** |
| 知识 | `/policy-knowledge/knowledge` | structured/page.tsx **拆审核/检索/关系三视图** |

> 映射留在 `/semantic-layer/*`。discovery 收敛到语义层或概览。

### 7.5 后端 API 改动 `[推断]`

- **新增**：`GET policy-pipeline/impact/recent`（影响报告）；`GET policy-pipeline/knowledge/{id}/relations`（替代/引用关系）。
- **增强**：`extractions` 响应加 `unit_no/chapter/article/clause`；`rules/search` 加 `knowledge_type/status` 过滤。
- **保留**：extraction-schema / publish / schema-update / discovery 不变。
- **生命周期**：`publish` 接口扩展为状态机转换（draft→review→published；published→superseded/deprecated）。

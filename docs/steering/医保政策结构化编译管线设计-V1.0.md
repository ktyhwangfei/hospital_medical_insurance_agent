# 医保政策结构化编译管线设计规范

## Policy Rule Compiler Design Specification

**版本**: V1.0 | **日期**: 2026-08-10
**适用范围**: 医保政策知识结构化、政策规则提取、政策问答、费用解释、政策证据检索
**核心目标**: 将 LLM 的概率性政策理解结果，稳定编译为可检索、可推导、可校验、可追溯、可版本管理的标准政策规则。

---

# 1. 背景

当前医保政策结构化流程主要采用：

```text
政策原文
   ↓
政策单元切分
   ↓
LLM Extraction
   ↓
直接写入结构化规则
```

该方式在简单政策条款中能够工作，但随着政策复杂度增加，逐渐暴露出明显问题。

以住院待遇第三十六条结构化为例，为了修复 LLM 对人群、基金比例、个人比例、分段规则、退休人员相对比例等内容的提取差异，系统连续增加了多个后处理脚本：

```text
fix_extraction_data
complete_extraction_fields
normalize_fund_rules
fix_normalize_damage
revert_overderivation
split_merged_rules
merge_fund_personal
expand_retiree_ratios
```

这些脚本存在明显特征：

* 硬编码 document_id；
* 硬编码 unit_id；
* 硬编码退休人员 60%；
* 不同脚本互相依赖；
* 存在固定执行顺序；
* 一个脚本修改产生的问题需要下一个脚本修复；
* 修改 Extraction JSON 后影响 knowledge_id、审核状态及其他派生数据；
* 无法推广到其他政策条款。

本质上，当前问题并非某一个 Prompt 不够完善，也不是某个后处理脚本质量不高，而是缺少一个位于：

```text
LLM Extraction
```

与：

```text
最终 Policy Rule
```

之间的稳定语义编译层。

因此，本方案正式引入：

# Policy Rule Compiler

将政策知识结构化过程从：

```text
LLM → 最终规则
```

调整为：

```text
LLM → Raw Fact → Compiler → Canonical Rule
```

---

# 2. 设计目标

Policy Rule Compiler 的核心目标不是替代 LLM，而是明确 LLM 与规则系统的职责边界。

## 2.1 LLM 负责

回答：

> 政策原文表达了什么？

包括：

* 条款涉及什么业务概念；
* 涉及哪些人群；
* 涉及哪些待遇项目；
* 存在哪些条件；
* 存在哪些数值；
* 存在哪些比较关系；
* 存在哪些引用关系；
* 是否存在分段；
* 是否存在例外；
* 是否存在公式或相对关系。

LLM 输出允许存在一定形式差异。

---

## 2.2 Policy Rule Compiler 负责

回答：

> 系统应该如何稳定表达这些政策事实？

负责：

* 字段标准化；
* 值域标准化；
* 人群标准化；
* 数值和单位标准化；
* 相同政策条件下规则组合；
* 引用关系解析；
* 相对比例推导；
* 互补关系推导；
* 分段规则规范化；
* 规则一致性检查；
* 规则冲突检查；
* 规则完整性检查；
* 最终 Canonical Rule 生成。

---

## 2.3 Validator 负责

回答：

> 当前结构化结果是否足够可信，可以进入正式知识库？

验证结果分为：

```text
PASS
WARN
REVIEW
FAIL
```

Validator 不负责偷偷修改规则。

---

# 3. 核心设计原则

## 3.1 Raw Extraction 永远不可修改

LLM 原始提取结果属于事实证据链的一部分。

一旦生成：

```text
Raw Extraction
```

禁止后续程序直接修改其内容。

后续任何：

* 规范化；
* 合并；
* 推导；
* 修正；
* 人工审核；

都必须生成新的数据对象。

原则：

```text
Raw Extraction = Immutable
```

---

## 3.2 原始事实与推导事实严格区分

例如政策原文：

```text
退休人员个人支付比例为在职职工个人支付比例的60%。
```

LLM 可以提取：

```json
{
  "population": "退休人员",
  "metric": "个人支付比例",
  "relation": "relative_ratio",
  "base_population": "在职职工",
  "factor": 0.6
}
```

这是：

```text
PolicyFact
```

假设同档在职职工个人支付比例：

```text
10%
```

Compiler 推导：

```text
退休人员个人支付比例 = 6%
```

这属于：

```text
Derived Fact
```

必须显式记录：

```json
{
  "derived": true,
  "derived_from": [
    "fact_xxx",
    "fact_yyy"
  ]
}
```

禁止将 6% 伪装成政策原文直接表达的事实。

---

## 3.3 Normalize 不允许承担业务推理

Normalize 只负责：

```text
"百分之十"
"10%"
0.1
```

统一为：

```text
0.10
```

或者：

```text
退休
退休人员
退休职工
```

统一映射至：

```text
retiree
```

Normalize 不允许：

```text
个人支付10%
→ 基金支付90%
```

因为后者属于业务推导。

---

## 3.4 Derive 必须是确定性推导

所有 Derived Rule 必须满足：

```text
输入确定
+
关系确定
+
公式确定
=
输出确定
```

如果任一条件不确定，则不得生成最终派生规则。

例如：

```text
退休人员待遇适当提高
```

不得推导：

```text
退休人员支付比例 = 在职 × 60%
```

此类情况必须进入：

```text
REVIEW
```

---

## 3.5 Compiler 不允许出现政策条款硬编码

禁止：

```python
if unit_id == "xxx":
    ...

if document_id == "doc_xxx":
    ...

if article_no == 36:
    ...
```

也禁止：

```python
if population == "retiree":
    ratio = employee_ratio * 0.6
```

正确方式是：

```text
PolicyFact
      ↓
PolicyRelation
      ↓
Generic Expression Engine
```

例如：

```json
{
  "relation_type": "MULTIPLY",
  "target": "personal_ratio",
  "reference": "employee.personal_ratio",
  "factor": 0.6
}
```

Compiler Engine 不需要知道这是：

```text
退休人员
```

还是：

```text
第二次住院
```

---

# 4. 总体架构

完整政策知识结构化链路：

```text
                    Policy Document
                          │
                          ▼
                  Policy Unit Splitter
                          │
                          ▼
                Semantic Extraction
                     LLM 提取
                          │
                          ▼
                     Raw Fact
                    【不可修改】
                          │
                          ▼
                Policy Rule Compiler
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
        ▼                 ▼                 ▼
 Canonicalization   Rule Composition   Relation Resolution
        │                 │                 │
        └─────────────────┼─────────────────┘
                          ▼
                      Derivation
                          │
                          ▼
                      Validation
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
            PASS        REVIEW        FAIL
             │
             ▼
                         Publish
                           │
                           ▼
                 Canonical Policy Rule
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
        Search           Agent           Explain
      Policy Search      Runtime       Evidence Chain
```

# 5. 核心领域对象

第一阶段建议正式建立四个核心对象：

```text
PolicyFact
PolicyRelation
CanonicalRule
PolicyRuleCompiler
```

辅助对象：

```text
PolicyCondition
PolicyExpression
PolicyEvidence
CompilationResult
ValidationIssue
```

---

# 6. PolicyFact 设计

PolicyFact 表示：

> 从政策文本中直接识别出来、但尚未经过业务推导的最小政策事实。

示例：

```json
{
  "fact_id": "fact_xxx",
  "document_id": "doc_xxx",
  "unit_id": "unit_xxx",

  "subject": "personal_payment_ratio",

  "population": "retiree",

  "conditions": {
    "hospital_level": "tertiary",
    "service_type": "inpatient",
    "segment": "0-30000"
  },

  "value_type": "relative_ratio",

  "value": null,

  "relation": {
    "operator": "multiply",
    "factor": 0.6
  },

  "evidence": {
    "text": "退休人员个人支付比例为在职职工个人支付比例的60%",
    "start_offset": 125,
    "end_offset": 153
  },

  "source": {
    "type": "llm_extraction",
    "extraction_id": "ext_xxx"
  },

  "confidence": 0.96
}
```

---

# 7. PolicyRelation 设计

PolicyRelation 用于表达政策事实之间的关系。

政策结构化不能只保存：

```text
A = 60%
```

还必须能够表达：

```text
A = B × 60%
```

建议第一阶段支持以下 RelationType。

---

## 7.1 ABSOLUTE

直接值。

例如：

```text
起付线1300元
```

表示：

```json
{
  "relation_type": "ABSOLUTE",
  "value": 1300,
  "unit": "CNY"
}
```

---

## 7.2 RELATIVE

相对于另一规则。

例如：

```text
第二次住院起付线为第一次的50%
```

表示：

```json
{
  "relation_type": "RELATIVE",
  "operator": "MULTIPLY",
  "factor": 0.5
}
```

---

## 7.3 COMPLEMENT

互补关系。

例如规则明确规定：

```text
基金支付比例 + 个人支付比例 = 100%
```

可表达：

```json
{
  "relation_type": "COMPLEMENT",
  "total": 1.0
}
```

注意：

不得默认所有医保比例都满足该约束。

---

## 7.4 SEGMENT

分段关系。

例如：

```text
0-3万元：90%
3-10万元：95%
10万元以上：97%
```

标准表达：

```json
{
  "relation_type": "SEGMENT",
  "segments": [
    {
      "lower": 0,
      "upper": 30000,
      "ratio": 0.90
    },
    {
      "lower": 30000,
      "upper": 100000,
      "ratio": 0.95
    },
    {
      "lower": 100000,
      "upper": null,
      "ratio": 0.97
    }
  ]
}
```

---

## 7.5 REFERENCE

引用其他条款。

例如：

```text
按照前款规定执行
```

表示：

```json
{
  "relation_type": "REFERENCE",
  "reference_type": "PREVIOUS_PARAGRAPH"
}
```

---

## 7.6 OVERRIDE

覆盖默认规则。

例如：

```text
退休人员按95%支付
```

如果前文已定义普通人员90%，则可表达：

```text
OVERRIDE
```

---

## 7.7 EXCEPTION

例外规则。

例如：

```text
但特殊病种除外
```

用于建立：

```text
Default Rule
        ↓
Exception Rule
```

---

# 8. CanonicalRule 设计

CanonicalRule 是最终进入政策知识运行时的标准规则。

示例：

```json
{
  "rule_id": "rule_xxx",

  "business_domain": "medical_insurance_benefit",

  "subject": "personal_payment_ratio",

  "population": "retiree",

  "conditions": {
    "service_type": "inpatient",
    "hospital_level": "tertiary",
    "segment": {
      "lower": 0,
      "upper": 30000
    }
  },

  "result": {
    "value": 0.06,
    "unit": "RATIO"
  },

  "source_type": "DERIVED",

  "derivation": {
    "operator": "MULTIPLY",
    "formula": "employee.personal_ratio * 0.6",

    "dependencies": [
      "rule_employee_xxx",
      "fact_retiree_factor_xxx"
    ]
  },

  "effective_period": {
    "from": "2024-01-01",
    "to": null
  },

  "evidence_ids": [
    "evidence_xxx"
  ],

  "compiler_version": "1.0.0",

  "status": "PUBLISHED"
}
```

---

# 9. Compiler Pipeline

正式管线定义为：

```text
① Canonicalization
② Rule Composition
③ Relation Resolution
④ Derivation
⑤ Validation
⑥ Publish
```

---

# 10. 第一阶段：Canonicalization

职责：

> 将 LLM 输出转换成统一语义表示。

主要处理：

### 人群标准化

```text
退休职工
退休人员
退休参保人
```

统一：

```text
retiree
```

---

### 比例标准化

```text
10%
百分之十
0.1
```

统一：

```text
0.10
```

---

### 金额标准化

```text
3万元
30000元
30,000
```

统一：

```json
{
  "value": 30000,
  "unit": "CNY"
}
```

---

### 区间标准化

```text
3万元以下
不超过3万元
≤30000
```

统一：

```text
upper = 30000
upper_inclusive = true
```

---

### 字段标准化

例如：

```text
个人负担比例
个人支付比例
个人承担比例
```

统一映射：

```text
personal_payment_ratio
```

这些字段必须与当前语义层统一值域体系复用。

---

# 11. 第二阶段：Rule Composition

职责：

> 将属于同一个政策条件组合的多个事实组织成统一规则。

例如模型可能提取：

```text
基金支付90%
```

和：

```text
个人支付10%
```

如果满足：

```text
同 unit
同人群
同服务类型
同医院级别
同金额分段
同生效时间
```

则可以组合成：

```json
{
  "fund_ratio": 0.90,
  "personal_ratio": 0.10
}
```

---

## 11.1 RuleKey

规则组合必须使用统一 RuleKey。

建议：

```text
RuleKey =
business_subject
+ population
+ service_type
+ hospital_level
+ treatment_type
+ segment
+ admission_order
+ effective_period
+ additional_conditions
```

禁止：

```text
同一个 unit 就默认可以合并
```

Unit 只是证据来源，不应该成为业务规则身份。

---

# 12. 第三阶段：Relation Resolution

这是整个 Compiler 中最关键的模块之一。

职责：

> 找到某条关系规则所依赖的基准规则。

例如：

```text
退休人员个人支付比例为在职人员的60%
```

首先形成：

```text
Target:
retiree.personal_ratio

Reference:
employee.personal_ratio
```

Resolver 根据条件：

```text
service_type
hospital_level
segment
effective_period
其他维度
```

寻找：

```text
employee.personal_ratio
```

---

## 12.1 匹配原则

Reference Resolution 应采用：

```text
严格条件匹配优先
↓
允许继承的维度
↓
显式默认值
↓
无法确定
```

绝对禁止：

```text
随便选择最近一条规则
```

---

## 12.2 ResolutionResult

结果：

```text
RESOLVED
AMBIGUOUS
NOT_FOUND
CONFLICT
```

只有：

```text
RESOLVED
```

才允许进入 Derivation。

---

# 13. 第四阶段：Derivation

Derivation 负责确定性推导。

第一阶段建议只支持有限表达式。

---

## 13.1 MULTIPLY

```text
target = reference × factor
```

例如：

```text
退休个人比例
=
在职个人比例 × 0.6
```

---

## 13.2 COMPLEMENT

仅当 PolicyRuleType 明确声明：

```text
fund_ratio + personal_ratio = 1
```

时允许：

```text
fund_ratio = 1 - personal_ratio
```

不能将该逻辑设为医保全局默认。

---

## 13.3 DIRECT_COPY

例如：

```text
按照前款同标准执行
```

可以：

```text
target = reference
```

---

## 13.4 ADD / SUBTRACT

为后续政策表达预留：

```text
A = B + X
A = B - X
```

第一版可暂不启用。

---

# 14. Policy Expression

建议不要为：

```text
退休
第一次住院
三级医院
```

分别开发 Python 函数。

Compiler 内部统一执行：

```text
PolicyExpression
```

例如：

```json
{
  "operator": "MULTIPLY",

  "target": {
    "metric": "personal_payment_ratio",
    "population": "retiree"
  },

  "reference": {
    "metric": "personal_payment_ratio",
    "population": "employee"
  },

  "factor": 0.6
}
```

Expression Engine 只认识：

```text
operator
target
reference
factor
```

不认识：

```text
第三十六条
退休人员
北京市
```

这是避免 Compiler 二次过拟合的核心。

---

# 15. 第五阶段：Validation

Validator 是严肃医保场景中必须存在的质量门禁。

原则：

> Validator 可以阻止错误进入知识库，但不能偷偷帮 Compiler 修改数据。

---

# 16. Validation 分层

建议分成四层。

---

## 16.1 Schema Validation

检查：

* 必填字段；
* 类型；
* 单位；
* 合法值域；
* 比例范围；
* 金额范围；
* 时间格式。

例如：

```text
personal_ratio = 1.6
```

直接：

```text
FAIL
```

---

## 16.2 Semantic Validation

检查业务语义。

例如：

```text
retiree
```

必须属于：

```text
population
```

不能出现在：

```text
hospital_level
```

---

## 16.3 Relation Validation

例如：

```text
RELATIVE
```

必须存在：

```text
reference
factor/operator
```

否则：

```text
REVIEW
```

---

## 16.4 Rule Consistency Validation

例如同一条件下出现：

```text
个人比例 = 10%
```

同时又出现：

```text
个人比例 = 15%
```

且时间范围完全相同，则：

```text
CONFLICT
```

进入人工审核。

---

# 17. Validation Issue 标准模型

```json
{
  "issue_id": "issue_xxx",

  "severity": "ERROR",

  "code": "RELATIVE_BASE_NOT_FOUND",

  "stage": "RELATION_RESOLUTION",

  "fact_id": "fact_xxx",

  "message": "退休人员个人支付比例依赖在职职工比例，但当前条件下未找到唯一基础规则",

  "recommended_action": "MANUAL_REVIEW"
}
```

错误码必须稳定，不应只有自然语言 message。

---

# 18. Publish

只有满足：

```text
PASS
```

或者允许发布的：

```text
WARN
```

才能生成正式 Canonical Rule。

对于：

```text
REVIEW
FAIL
```

禁止进入正式 Agent Runtime。

可以进入：

```text
Draft Knowledge
```

等待人工审核。

---

# 19. 规则状态

建议统一：

```text
EXTRACTED
NORMALIZED
COMPILED
REVIEW_REQUIRED
APPROVED
PUBLISHED
REJECTED
SUPERSEDED
```

避免当前：

```text
提取状态
审核状态
knowledge状态
```

之间相互污染。

---

# 20. Evidence 设计

CanonicalRule 无论直接提取还是推导，都必须能够回到原文。

例如：

```text
CanonicalRule
     │
     ├── Direct Evidence
     │
     └── Derivation Dependencies
             │
             ├── Rule A Evidence
             └── Fact B Evidence
```

最终问答中应能够解释：

```text
为什么得到退休人员6%？
```

回答链路：

```text
原文：
退休人员个人支付比例为在职人员的60%

基础规则：
对应档位在职人员个人支付比例10%

计算：
10% × 60% = 6%
```

这与后续医保政策解释 Agent 的证据链可以直接复用。

---

# 21. 时间版本模型

政策规则必须天然支持时间维度。

CanonicalRule 至少包含：

```text
effective_from
effective_to
```

# 58. 核心结论

本次设计的核心不是增加一个新的"后处理模块"。

真正变化是重新定义政策结构化系统的职责边界：

```text
LLM
负责理解政策
```

```text
PolicyFact
负责保留政策原始语义
```

```text
PolicyRelation
负责描述事实之间的关系
```

```text
PolicyRuleCompiler
负责将政策事实确定性编译为标准规则
```

```text
Validator
负责阻止不确定或冲突规则进入正式知识库
```

```text
CanonicalRule
负责服务最终 Agent Runtime
```

最终实现：

> **概率性理解，确定性编译，显式推导，严格校验，全程可追溯。**

这应该作为后续医保政策知识结构化模块的基础架构原则。

# 59. V1 最小成功标准

Policy Rule Compiler V1 不要求"理解所有医保政策"。

只需要达到：

> 对规则性强、数值明确、条件明确的待遇政策，可以稳定自动编译；对于不确定政策，可以准确识别不确定并阻止错误规则进入运行时。

也就是说：

```text
高置信度规则
→ 自动化

低置信度规则
→ 人工审核

政策原文
→ 永远保留

推导关系
→ 永远可追溯
```

对于医保政策问答和费用解释系统，这比追求"100%自动结构化"更加可靠，也更适合长期落地。

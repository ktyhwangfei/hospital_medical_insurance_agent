# 政策问答 轨迹持久化与挂起/升级/恢复 设计 V1.0

> Issue #30：轨迹持久化存储，以及问答挂起、升级、恢复等相关设计。
> 本文是实施的唯一设计依据；实现偏差以本文为准修正代码或修正本文（需评审）。

## 一、现状与问题（2026-08-31 勘察）

| 能力 | 现状 | 问题 |
|------|------|------|
| 每轮轨迹 | SSE 公开事件（context_need / step / memory_update / result）只在内存推送；task 表仅存 question/answer 各截断 500 字摘要 | 公开轨迹不可重放；刷新页面已渲染对话全丢 |
| 多轮对话 | sessionId 由前端 `useState` 生成、跨轮复用；消息仅存前端 state | 刷新即换新会话，历史对话无法找回 |
| 会话记忆 | BusinessMemory 已持久化（memory store） | 但对话本身不持久，记忆无载体可恢复 |
| 挂起 | 无 | 用户中途离开/补材料，会话无法显式暂停 |
| 升级 | 回答文本建议"咨询医保办" | 无升级工单、无人工回复回填通道 |
| 恢复 | 无 | 无会话列表、无恢复入口 |

既有可复用设施：`sessions`/`workflows`/`tasks` 三表（PG+内存双实现+工厂）、`qa_turn_id` 稳定主键（贯穿 result/done/task）、`task_closure` 服务、前端 `PolicyQAChatMessage` 完整快照模型。

## 二、设计目标

1. **轨迹持久化**：每轮 QA 的可重放公开快照落库，按会话完整回放（重建对话、记忆面板、锚点）。
2. **会话生命周期**：`active → suspended/escalated/closed` 状态机，支持挂起、恢复、关闭。
3. **升级闭环**：问题升级为医保办人工工单（复用 task_closure，`waiting_human_confirmation`），回复回填后会话恢复可用。
4. 不破坏 Issue #21 契约：单一 answer、结算单必填上下文、有界恢复预算、公开事件不泄露内部推理。

## 三、数据模型

### 3.1 新表 `policy_qa_trajectories`（每轮一行可重放快照）

| 列 | 类型 | 说明 |
|----|------|------|
| qa_turn_id | VARCHAR(80) PK | 复用现有 `qat_` ID，与 tasks 表同键 |
| session_id | VARCHAR(128) | 关联 sessions |
| user_id | VARCHAR(64) | 所有权校验用 |
| tenant_id | VARCHAR(64) | 与 task 口径一致 |
| settlement_id | VARCHAR(64) | 当轮结算上下文 |
| question | TEXT | 问题原文（仅本人回放可见，见 §七） |
| answer_status | VARCHAR(32) | verified/partial/unavailable |
| payload | JSONB | 重放快照：`{context_need, memory_updates[], result, attempt_count, halt_reason}` |
| created_at | TIMESTAMPTZ | 轮次时间 |

索引：`(session_id, created_at)`。

**设计取舍**：
- 每轮一行而非每事件一行——重放 = 读会话全部行按序应用，无需事件流还原；
- **不存 step 进度事件**——"识别问题意图…"是流式瞬时指示，重放只展示最终结果；快照 = 前端 `PolicyQAChatMessage` 重建所需全部字段（result + context_need + memory_updates）；
- **失败轮也写一行**（无 result、`answer_status=unavailable`、payload 含 halt_reason），保证对话序列完整；
- 内部推理/提示词/SQL 细节不入轨迹（与公开契约同口径，防泄漏白名单沿用 `_sanitize`）。

### 3.2 `sessions` 表扩展（CREATE + ALTER 双写，遵守已知陷阱）

| 新列 | 类型 | 说明 |
|------|------|------|
| status | VARCHAR(32) NOT NULL DEFAULT 'active' | active / suspended / escalated / closed |
| status_reason | TEXT NULL | 挂起/升级原因 |
| status_updated_at | TIMESTAMPTZ NULL | 最近状态变更 |

`Session` 领域模型同步加字段；`SessionStorage` 端口新增 `update_session_status(session_id, status, reason)`。

### 3.3 升级工单：复用 tasks 表

- `task_type = "policy_qa_escalation"`，`status = "waiting_human_confirmation"`（对齐安全约束术语）；
- `input_data`：session_id、question_excerpt、reason、qa_turn_id（可选关联轮次）；
- `output_data.escalation_reply`：医保办回复文本，resolve 时回填；
- `responsible_role = "insurance_office"`。

## 四、会话状态机

```
active ──suspend──▶ suspended ──resume──▶ active
   │                                    ▲
   ├──escalate──▶ escalated ──resolve───┘
   │                   │
   └────close────▶ closed ◀──close──────┘（suspended/escalated 亦可显式关闭）
```

- 非法转移返回 409（如 suspended 直接 escalate）；
- suspended / escalated 会话拒绝新问答（`/stream` 校验 session status，非 active 返回 409，错误码 `SESSION_NOT_ACTIVE`）；
- closed 不可再转任何状态（终态）。

## 五、API（挂现有 policy-qa 前缀）

| Method/Path | 作用 | 请求/响应要点 |
|------|------|------|
| GET `/policy-qa/sessions?user_id=` | 用户可恢复会话列表 | 返回 session_id、status、last_active、轮次数、首问摘要 |
| GET `/policy-qa/sessions/{session_id}` | 会话详情 | 状态 + 状态原因 + 升级回复（若有） |
| GET `/policy-qa/sessions/{session_id}/trajectory` | 轨迹重放 | 按时间序全部轮次快照；校验 session 归属 |
| POST `/policy-qa/sessions/{session_id}/suspend` | 挂起 | `{reason?}`；仅 active 可挂起 |
| POST `/policy-qa/sessions/{session_id}/resume` | 恢复 | suspended→active，响应携带完整轨迹（一次请求完成恢复） |
| POST `/policy-qa/sessions/{session_id}/escalate` | 升级 | `{question, reason?}`；仅 active 可升级；创建工单 |
| POST `/policy-qa/escalations/{task_id}/resolve` | 工单处理 | `{reply, resolved_by}`；回填回复，会话→active |

写入路径：`/stream` 成功/失败收尾时与 `record_qa_task` 同段写入轨迹（非阻塞，失败仅告警）。

## 六、前端（Portal `/policy-qa`）

1. **刷新恢复**：sessionId 持久化到 localStorage（key `policy-qa-session-id`）；页面加载时若存在 → GET trajectory 重建 messages/memories/anchor；404/失败 → 新会话。
2. **会话操作区**（顶栏）：
   - 「挂起」：suspended 态输入框禁用，展示原因与「恢复」按钮；
   - 「升级医保办」：escalated 态输入框禁用，展示工单状态；恢复入口显示回复内容；
   - 「历史会话」：GET /sessions 列表 → 点击 = resume/重放切换。
3. 恢复重放只渲染最终消息（含验证摘要/引用/计算步骤），不重放过程步骤。

## 七、安全与边界

- 轨迹含问题原文（患者/结算关联）：读取按 `session.user_id` 所有权校验，非本人 404；当前 dev 阶段 user_id 由前端声明（与现有 /stream、history 口径一致），SSO 接入后（§10.1）改认证上下文；
- 轨迹 payload 只存公开契约字段，沿用 `_sanitize` 防泄漏白名单；
- 升级工单内容为脱敏摘要（question_excerpt ≤500 字，与 task 口径一致）；
- 挂起/关闭不删除数据，仅状态变更，可审计。

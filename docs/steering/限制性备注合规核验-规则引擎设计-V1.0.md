# 限制性备注合规核验：规则引擎设计

**2026-11-06路线变更：本文件转为历史技术方案。** 用户反馈逐药规则难以维护，当前改用[处方思路复核与医保办解释方案](限制性备注-处方思路复核与医保办解释方案-V1.0.md)。不再以维护本文件的概念码、ICD映射及可执行条件树作为医保办使用前提；历史代码、证据和已完成迭代A保留。

V1.1，2026-11-05，Issue #85。状态：设计方向确认，具体规则、取数与核验器按质量要求实施验收（原型见主设计文档 §11）。本文是《限制性备注合规核验-医保办运营解释设计 V3.1》的核心子设计，回答五个问题：**规则怎么配置、怎么执行、怎么维护、怎么生效、依赖字段怎么读怎么加**。

设计总原则：**规则是数据不是代码**——引擎只认识封闭的条件类型集合，新增/修改规则、调整参数、换院区映射都不改代码；只有新增条件类型（新核验器）才改代码，且按先红后绿走完整验证。

**解释目标与质量前提**：在选中结算单范围内，用项目内涵及经核验的关联事实，让患者更全面地了解医保支付条件、本单已有的支持依据及尚不能确认的信息。规则条件核验为费用解释增加信息，不要求每项条件都能解释出比例差异。用于某个解释结论的规则、映射与字段须质量合格，核验结果须有对应证据；不把缺资料写成未满足，也不把条件支持自动写成本次结算采用该比例的原因。

**2026-11-05评审校准**：名称/诊断映射精度、支付标准及量纲处理、样例目录版本属于具体配置、取数与实现验收事项，不据此否定本设计。保持现有分层和执行方式；本次补清取数状态、匹配状态及解释条件，实施问题保留反例逐项验收。

## 1. 规则文档格式（配置态）

规则以 JSON 文档存储（PG `compliance_rules.rule_doc` JSONB + 索引列），承载原型领域模型中的规则信息。配置态与领域态字段结构不同，实施时明确转换并做往返校验。下面以院内艾普拉唑原记录示意配置结构；参数、规格单位及版本待核，保留为draft，不作为可直接发布的质量合格规则：

```json
{
  "rule_id": "rule-XA02BCA084B001010100453-20240320",
  "rule_revision": 1,
  "engine_version": "1.0",
  "status": "draft",
  "item": { "code": "XA02BCA084B001010100453", "name": "注射用艾普拉唑钠" },
  "catalog_version": {
    "effective_from": "2024-03-20", "effective_to": "2050-12-31",
    "source": "bjyb.yb_ypzdml"
  },
  "source_bz": "限：1.预防重症患者应激性溃疡出血；2.消化性溃疡出血。支付标准不得高于：63.00元(10mg/支)",
  "condition_groups": [
    {
      "logic": "any_of",
      "conditions": [
        { "type": "disease", "concept": "dg.stress_ulcer_prophylaxis_critical",
          "source_span": "预防重症患者应激性溃疡出血" },
        { "type": "disease", "concept": "dg.peptic_ulcer_bleeding",
          "source_span": "消化性溃疡出血" }
      ]
    },
    {
      "logic": "any_of",
      "conditions": [
        { "type": "price_cap", "concept": "unit.vial_10mg",
          "source_span": "支付标准不得高于：63.00元(10mg/支)",
          "price_cap": { "amount": "63.00", "unit": "支", "strength_text": "10mg" } }
      ]
    }
  ],
  "content_hash": "sha256:…",
  "created_by": "parser+人工", "reviewed_by": "待审核"
}
```

结构约束（入库即校验，不合法拒收）：
- `condition_groups` 组内 `any_of`、组间 `all_of`（原型已实现的组合语义，覆盖全部实测 bz 形态）；
- `type` 必须是引擎已注册的核验器类型（当前 disease / price_cap；后续 usage / institution / population / prescriber / filing 逐个按切片注册）；引用未注册类型的规则**只能存 draft，不能发布**；
- 每个条件必须有 `concept` + `source_span`，禁止自然语言裸条件；
- `price_cap` 参数（金额/单位/规格）在规则文档里（来自 bz），**换算知识在映射层**（来自院区），两者不混。

## 2. 执行流程（运行态）

```
输入：结算单（或批次范围）
 │
 ├─ 1. 规则定位
 │    先取得 item_code、费用日期、当日目录bz及版本，并记录取数状态
 │    定位依据有效 → 规则库索引
 │    （item_code, 目录版本区间覆盖费用日期, status=published）
 │    → 命中的 (rule_id, rule_revision)；未命中按§2.1区分，不能直接判无限制
 │
 ├─ 2. 字段需求推导
 │    遍历命中规则的全部条件 → 每个核验器声明 required_fields
 │    → 合并去重 = 本次执行的字段需求集（§3）
 │
 ├─ 3. 上下文装配（一次取数，非逐行 N+1）
 │    字段需求集 → 字段目录解析来源表列 → 按表合并查询
 │    → 行级字段值 + 取数/质量状态 + 来源关联（原型输入模型实施时补齐）
 │
 ├─ 4. 映射解析
 │    规则引用的概念码 → 值域映射（hospital > regional > default）
 │    → 任一概念码无映射：该条件 fail-closed 判 unverifiable，报告指明缺哪条
 │
 ├─ 5. 逐条件核验 + 聚合（原型 engine.evaluate_rule 已实现）
 │    可用于核验的字段 → checker；缺失/取数失败/低质量 → 明确不可判断原因
 │    checker(condition, 映射, 字段值) → ConditionVerdict（带证据链）
 │    组内 any_of → 组间 all_of → 行级风险层 contra/suspect/review/clear
 │
 └─ 6. 报告组装
      金额引用费用分解结果（引擎不重算）；裁定 + 证据链 + 规则 revision
      + 映射 revision + engine_version 全部留痕，可回放
```

执行的两条铁律（原型已落实）：裁定只产证据不产金额；金额口径三分（fee/fee_in/fee_out）不混用。

### 2.1 取数状态与匹配结果分开

“未命中”必须说明对象：是没有适用的已发布规则，还是字段没有匹配到条件。字段目录的`availability`只说明接入能力，不能代替本次实际取数结果。每个字段保留值、来源/关联键、适用时点及本次状态：`present`（值及来源关联有效）、`empty`、`placeholder`、`invalid`、`not_available`、`fetch_failed`、`ambiguous`；空值与数值0、布尔false分开。

| 本次情况 | 处理及解释 |
|---|---|
| 定位字段未取得、失效或关联歧义 | 规则定位未完成，说明缺哪个字段或哪段关联；不写“没有规则” |
| 定位依据有效，bz有内容，但无适用的已发布规则 | 说明规则待配置/待发布或缺少适用版本；不判无限制、不跳过覆盖记录 |
| 当日唯一目录已取得，本类限制原文确为空 | 只说明“本次取得的目录未记载本类限制”，不推断其他支付条件均不存在 |
| 规则存在，但某条证据路径必需字段缺失、占位、无来源、取数失败或存在歧义 | 该路径不执行匹配，状态为`not_evaluated`；其他已审核路径能完整证明条件时可使用，否则保留不可核验/资料不足及原因 |
| 字段有效，执行条件后未匹配 | 记录`not_matched`及实际比对依据；仅当事实足以直接否定该条件时才判冲突，诊断未见记载等仍是资料不足 |
| 字段有效，执行条件后匹配 | 仅在事实足以证明本条件时判支持；按原条件关系聚合，不能从一个关键词推广到整个复合条件 |

规则匹配、字段取数和条件匹配分别留状态与原因。保留四链路原范围中的无法定位/无法核验记录，医保办可查看覆盖缺口；缺口不自动生成风险工单。

### 2.2 经质量校验后用于患者解释

解释生成前检查：①本次采用的规则版本、适用范围、条件及映射已审核；②实际支持结论的字段来源、关联、时点、质量合格；③条件核验和聚合结果与证据一致。OR已有完整且有效的支持路径时，其他可选路径缺字段不阻断该路径结论；仍需如实保留其未核验范围，不能用部分解析规则冒充完整规则。

满足上述前提，可以告诉患者“目录限定了什么、本单哪些记录支持、哪些还不能确认”，使现有费用解释更全面。未知结果也可解释为“目前缺少某项记录，尚不能确认”，不能改写成符合或不符合。金额类别和实际结算原因引用已验证的费用分解结果；若要进一步说明“正因某条件所以采用某比例/全自费”，还须有本次结算原因或已验证的确定性费用分支依据。不能从单纯条件通过推导金额类别，不能承诺尚未实际启动的人工复核。

## 3. 字段目录：依赖字段怎么读、怎么加（重点）

### 3.1 三层模型

```
核验器声明（规则视角）        字段目录（治理配置层）              取数器（技术层）
required_fields        →     FieldDefinition                 →  Fetcher
"diagnosis.code"             逻辑字段 → 来源绑定                 按表执行 SQL
"diagnosis.name"             { table: o_Diagnose,               经 RecordQueryMapping
"price.unit_price"             column: DiagnoseCode,            解析院区物理列名
                               join: T_TradeNo+RecipeNo,
                               cardinality: many,
                               availability: placeholder_prone }
```

`FieldDefinition` 字段：`field_key`（如 `diagnosis.code`）、`label`、来源绑定（表/列/关联键/基数）、`availability`（`available` / `placeholder_prone` / `unavailable`）、`added_at`/`added_by` 留痕。这是治理配置（PG 表 + 审核），不是代码注解。

### 3.2 字段需求从规则推导，不是写死

每个核验器注册时声明所需字段：

```python
DISEASE_CHECKER.required_fields = {"diagnosis.code", "diagnosis.name", "diagnosis.medical_record"}
PRICE_CAP_CHECKER.required_fields = {"price.unit_price", "item.specification"}
POPULATION_CHECKER.required_fields = {"patient.birthday", "patient.sex"}   # 后续切片
```

扫描一张单时，引擎先按命中规则合并需求集——只查需要的字段。新增规则若引用的字段已在目录里，**零代码生效**；这就是"规则是数据"的另一半：数据需求也是推导的。

### 3.3 字段怎么增加（三种情形，成本递增）

| 情形 | 操作 | 改代码？ |
|---|---|---|
| 字段在已接入表（如要用 `o_FeeItem.HowToUse` 用法） | 字段目录加一行绑定 + 审核 | 否 |
| 字段需新关联表（如用法要查医嘱表） | 注册新 Fetcher（明确 seam）+ 目录绑定 | 是，小步 |
| 字段全院区都无数据源（如检验值、重症状态） | 目录登记 `unavailable` | 否——核验器 fail-closed 判 unverifiable，报告如实声明缺口 |

`placeholder_prone` 字段（诊断编码/医师名等）由引擎统一走占位纪律：命中占位形态 → `insufficient_evidence` 并如实标注，各核验器不各自实现。

### 3.4 与既有映射层的关系

字段目录管"逻辑字段 → 逻辑表列"，院区物理差异仍走 `RecordQueryMapping`（表名/列名映射）；值域差异走 `ValueDomainMapping`（概念码 → 真实代码）。三层各司其职：**字段目录解决"读什么"，RecordQueryMapping 解决"列叫什么"，ValueDomainMapping 解决"值是什么意思"**。换院区时三者分别登记，规则与引擎零改动。

## 4. 规则维护与生效（生命周期）

### 4.1 状态机

```
draft（解析器生成或手工录入）
  → pending_review  【闸门：AST 合法性 + 概念码映射齐备校验 + 样例单回放冒烟】
  → published       【原子生效，同项目同目录版本区间唯一】
  → retired         【停用留痕，不物理删除】
```

闸门细节（对齐可信问题库 approve 闸门与数据模型发布纪律）：
- **映射齐备**：规则引用的每个概念码在 default 或本院作用域至少有一条有效映射，否则 422 拒绝转审（故意保留无映射的特殊情形需审核人显式豁免并写明理由，如重症预防条件）；
- **质量合格**：存在映射不等于内容正确。针对具体规则验收必要条件是否完整、字段关联及质量是否可靠、否定/时点是否处理正确、支付标准适用口径/量纲/版本是否正确；具体实现方式由该规则和核验器确定。豁免只允许发布时保留未核验范围，不改变运行时未知语义；
- **回放冒烟**：发布前必须用指定样例单跑一遍 draft 规则，审核人看到的是"这条规则在真实单上的裁定+证据链"，不是抽象文本；
- **结构冻结**：published 后 `condition_groups` 不可改，变更 = 新 revision（revision 乐观锁防并发覆盖）。

### 4.2 生效语义

- 规则按 `(item_code, catalog_version)` 索引；published 即对**费用日期落在目录版本区间内**的结算单生效；
- 目录换版（yb_ypzdml 新版 sxrq/jzrq）→ 生成新规则 revision 绑定新版本，旧版保留用于历史单回放；
- 报告与落库结果记录 `rule_revision` + 映射 revision + `engine_version`——任何历史裁定都能用当时的规则与映射重放复核；
- 进程内规则缓存按 revision 键，发布事件触发失效（对齐 workflow 配置缓存模式），无需重启。

### 4.3 维护入口

治理 API（Slice 2）：`POST /compliance/rules`（draft）、`POST …/{id}/submit-review`、`POST …/{id}/publish`、`POST …/{id}/retire`、`POST …/{id}/replay`（回放冒烟）。权限走医保办角色；全部写操作记审计事件（actor/revision/内容哈希）。批量生成（解析器扫目录全量 bz）产出的永远是一批 draft，逐条人工审核后才能发布——**AI 只产草稿**的纪律与 Skill 治理一致。

## 5. 与当前原型的差距清单（实施时逐项收敛）

| 原型现状 | 设计目标 | 收敛动作 |
|---|---|---|
| 规则写在 `rules_seed.py` 代码常量 | 规则文档入 PG，生命周期管理 | Slice 2 存储 + 治理 API |
| 映射写在代码常量 | `value_domain_mappings` 表 + 作用域解析 | Slice 2 |
| 字段装配写死在探针脚本 | 字段目录 + 需求推导 + 按表合并查询 | Slice 1 重构：探针改为经字段目录装配 |
| 条件类型 2 个（disease/price_cap） | 核验器注册表，逐类型按切片注册 | usage/population 等按 Slice 3/4 |
| 报告出 stdout/JSON 文件 | 扫描批次 + 报告 API | Slice 2 |

保留的部分：封闭 AST、组内 any_of/组间 all_of、缺失不判不符的裁定纪律、证据链和双方向解释。原型证明了样例链路可运行；具体规则配置、字段获取、核验器和解释模板仍须通过质量验收，再用于正式解释。

## 6. 边界

- 引擎永不执行规则文档之外的逻辑；规则文档不能引用未注册核验器类型、不能携带可执行代码；
- 字段目录只读绑定，不开放任意 SQL；
- 回放冒烟与正式扫描都是只读，不触碰结算动作；
- 占位/缺失/无映射的裁定语义（insufficient_evidence / unverifiable）在任何配置下不可被规则覆盖——这是引擎级纪律，不是规则级选项。

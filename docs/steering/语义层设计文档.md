### 0.2 核心发现：不需要重新发明指标

数据模型1 的 19 个政策规则字段**就是语义层的第一批指标**。当前的问题不是"缺少指标定义"，而是"指标定义在 Excel 里，代码不知道怎么读"。

语义层要做的事情：
- **把 Excel 里的元数据代码化**，而不是另外写一套
- **把三个来源的字典统一**到一个可维护的 YAML 目录
- **建立指标 ↔ 政策字段 ↔ 标准化规则的正式关联**
- **提供 CRUD 管理界面**，让业务人员可视化管理语义映射

## 一、问题定义

### 1.1 当前痛点

| # | 痛点 | 现状 | 根因 |
|---|------|------|------|
| 1 | **指标元数据在 Excel 里，代码不可读** | 19 个政策字段的中文名、加工类型、字典引用全在 `数据模型1.xlsx` 的政策规则表 Sheet | Excel 是给人看的，无法被 `semantic_layer/registry.py` 解析 |
| 2 | **标准化字典三处维护** | `字典` Sheet → `DictionaryNormalizer`（Excel读取）；`data_model1_loader.py` → 硬编码 PSN_TYPE_MAPPING 等 dict；`semantic_mapping.py` → 硬编码 DEFAULT_MAPPING | 同一个"退休人员→retiree"映射存在三处，改一处漏两处 |
| 3 | **指标依赖关系隐藏在代码中** | 技能通过 `getattr(ctx, "deductible")` 访问指标，calculator.py 的 `decompose()` 隐式依赖 SQL 结果 | 新增技能需要阅读代码才能知道需要哪些数据 |
| 4 | **指标 → 政策检索脱节** | `McpResultNormalizer` 独立于 `SemanticMapper`，各自有字段映射逻辑 | 同一字段在两个模块的映射可能不一致 |
| 5 | **大模型读不懂数据 schema** | 没有任何结构化描述告诉 LLM "当前可用指标有哪些、每个指标什么意思" | LLM prompt 中只能用自然语言拼接，不可靠 |
| 6 | **语义映射不可见、不可管理** | DEFAULT_MAPPING 硬编码在 Python 代码中，业务人员无法查看/修改，每次变更需改代码部署 | 缺少 CRUD 管理界面和持久化存储 |
| 7 | **缺少业务对象层级** | 19 个指标平铺，无法区分哪些属于 Settlement、哪些属于 Patient、哪些属于 Hospital | 没有 L1 业务对象层的组织维度 |

## 二、三层语义模型（v3.0 新增）

### 2.1 设计动机

当前指标定义缺少层级结构。19 个指标平铺在 `policy_fields.yaml` 中，不区分归属。这导致：
- AI 无法回答"Settlement 对象有哪些可用字段"这类问题
- 新增指标时没有"放入哪个业务对象"的指引
- 数据源映射（L3）隐藏在 SQL 字符串中，无法程序化查询

参考 dbt Semantic Layer、MetricFlow、Cube.js 的思想，引入三层模型：

```
L1 业务对象层 ──→  "统筹支付"属于 Settlement（结算记录）
L2 指标层 ──────→  AI 只认识"统筹支付"，不认识 TCZF_PAY
L3 数据层 ──────→  "统筹支付" = yb_settlement.TCZF_PAY（来自 SQL Server）
```

### 2.2 第一层：业务对象层（L1）

定义业务对象。每个业务对象是一组相关指标的容器。

| 业务对象 | 英文 | 说明 | 典型字段 |
|---------|------|------|---------|
| 患者 | `Patient` | 参保人基本信息，包括人群分类、险种归属 | person_type, insurance_type |
| 结算记录 | `Settlement` | 一次医保结算的完整记录，包括费用、支付、自付 | TCZF_PAY, TCZF_SELF, QFX, total_fee, self_fee, first_pay_fee, CASH_PAY |
| 医疗机构 | `Hospital` | 提供医疗服务的医院信息 | hosp_lv, hosp_name |
| 医保政策 | `Policy` | 政策规则的定义维度 | insu_type, med_type, payment_ratio, deductible_amount, cap_amount |

**数据模型（新增）**：

```python
# src/domain/indicator/models.py 追加

class BusinessObject(BaseModel):
    """业务对象定义 — L1 层"""
    object_id: str                    # "Settlement" | "Patient" | "Hospital" | "Policy"
    name: str                         # 中文名："结算记录"
    description: str = ""             # 业务说明
    fields: list[str] = []            # 该对象包含的 indicator_id 列表
```

### 2.3 第二层：指标层（L2，核心）

这是语义层最重要的一层。**AI 永远只认识业务术语，不认识物理字段名。**

```
统筹支付 → 属于 Settlement → AI 看到的名称
TCZF_PAY → 属于 Settlement → 物理字段，AI 不应该知道
```

每个指标通过 `business_object` 字段归属到 L1 业务对象，通过 `source` 字段映射到 L3 数据源。

```yaml

  unit: 元
  source:
    type: sql
```

### 2.5 Metric Layer：计算指标

医保解释场景里很多指标不是简单字段取值，而是**需要计算**。

例如：

```
统筹范围内费用 = total_fee - self_fee - first_pay_fee
```

参考 dbt Semantic Layer / MetricFlow / Cube 的思想，引入结构化公式定义：

```python
# src/domain/indicator/models.py 追加

class MetricFormula(BaseModel):
    """结构化计算公式 — Metric Layer"""
    expression: str                     # "total_fee - self_fee - first_pay_fee"
    dependencies: list[str]             # ["total_fee", "self_fee", "first_pay_fee"]
    type: str = "arithmetic"            # "arithmetic" | "conditional" | "ratio" | "aggregation"

class FormulaEvaluator:
    """公式求值器 — 轻量级算术表达式引擎"""
    
    def evaluate(self, formula: MetricFormula, 
                 values: dict[str, float]) -> float:
        """根据依赖指标的实际取值，计算派生指标的值"""
        # 验证所有依赖项已取值
        for dep in formula.dependencies:
            if dep not in values:
                raise ValueError(f"缺少依赖指标: {dep}")
        
        # 简单算术求值（支持 + - * / 和括号）
        expr = formula.expression
        for dep in formula.dependencies:
            expr = expr.replace(dep, str(values[dep]))
        return self._safe_eval(expr)
```

**计算指标示例**：

```yaml
- indicator_id: in_scope_total
  name: 统筹范围内费用
  business_object: Settlement
  category: numeric
  value_type: float
  unit: 元
  source:
    type: derived                  # 🆕 派生计算类型
  computation: "total_fee - self_fee - first_pay_fee"
  depends_on:
    - total_fee
    - self_fee
    - first_pay_fee
  formula:
    expression: "total_fee - self_fee - first_pay_fee"
    dependencies: [total_fee, self_fee, first_pay_fee]

- indicator_id: out_of_scope_total

    - first_pay_fee

    expression: "self_fee + first_pay_fee"
```

## 四、核心概念模型

### 4.1 从 Excel 元数据到代码模型

数据模型1 的"政策规则表" Sheet 的每一行，直接映射为一个 `IndicatorDefinition`：

```
Excel 行:
  字段名称: deductible_amount
  字段中文名称: 起付金额
  加工类型: 分词
  说明: 起付标准金额
  字典: NaN

↓ 自动生成 ↓

IndicatorDefinition:
  indicator_id: "deductible_amount"
  name: "起付金额"
  business_object: "Policy"         # 🆕
  description: "起付标准金额"
  processing_type: "分词"
  value_type: "float"
  unit: "元"
  dictionary_ref: null
  policy_field: "deductible_amount"
  is_nested: false
```

### 4.2 指标分类（基于数据模型1 实际字段）

这 19 个字段按语义角色分为四类：

**A. 维度指标（用于过滤和路由）**— 6 个字段，每个关联一个字典

| indicator_id | 中文名 | 业务对象 | 字典 | 物理字段 |
|-------------|--------|---------|------|---------|
| `insu_type` | 险种类别 | Policy | 险种类别(5条) | insu_type |
| `med_type` | 医疗类别 | Policy | 医疗类别(12条) | med_type |
| `hosp_lv` | 医疗机构等级 | Hospital | 医疗机构等级(4条) | hosp_lv |
| `psn_type` | 人群标签 | Patient | 人群标签(12条) | psn_type |
| `setl_type` | 结算方式 | Settlement | 结算方式(12条) | setl_type |
| `admission_order` | 住院次数 | Settlement | — | admission_order |

**B. 数值指标（用于对标和计算）**— 3 个字段

| indicator_id | 中文名 | 业务对象 | 单位 |
|-------------|--------|---------|------|
| `deductible_amount` | 起付金额 | Policy | 元 |
| `payment_ratio` | 支付比例 | Policy | % |
| `cap_amount` | 封顶金额 | Policy | 元 |

```python
    sql_params: list[str] = field(default_factory=list)


@dataclass(frozen=True)
class NormalizationRule:
    """标准化规则"""
    field_name_mapping: dict[str, str] = field(default_factory=dict)

    dictionary_path: str | None = None

class MetricFormula(BaseModel):

    expression: str                     # "total_fee - self_fee - first_pay_fee"
    dependencies: list[str] = Field(default_factory=list)
    type: str = "arithmetic"            # "arithmetic" | "conditional" | "ratio" | "aggregation"

    # 依赖与计算

    use_in_filter: bool = False
    use_in_embedding: bool = False

    @field_validator("name")
```

## 六、语义映射管理模块设计（v3.0 新增）

### 6.1 设计目标

- **可视化**：Admin 后台提供语义映射的查看、搜索、新增、编辑、删除界面
- **持久化**：映射数据存储在 PostgreSQL（生产）或内存（开发），不再硬编码
- **可导入**：支持从 YAML/JSON 批量导入映射规则
- **人工确认**：新增映射需标记来源，区分自动学习和人工确认
- **版本追踪**：每次修改记录时间戳

### 6.2 存储层

**PostgreSQL 表结构**：

## 八、关键设计决策

### 8.1 domain/indicator/ 放模型，semantic_layer/ 放引擎

严格遵循 DDD 分层。对标现有的 `domain/skill/` vs `runtime/skill_registry/` 分离模式。

### 8.2 指标定义从 Excel 自动生成，不手工写 YAML

`indicators/_from_datamodel1/policy_fields.yaml` 由 `datamodel1_importer.py` 自动生成。手工维护的仅限于 `indicators/fee/` 下的费用类指标。

### 8.3 字典三源归一 + 可管理

所有标准化字典统一存放在 `indicators/dictionaries/`，同时通过 `SemanticMappingService` 的 CRUD API 持久化到 PostgreSQL。Admin 页面提供可视化管理。

| 来源 | 当前存储位置 | 归一后位置 |
|------|-------------|-----------|
| 数据模型1 → 字典 Sheet | Excel 文件 | `indicators/dictionaries/` + PostgreSQL `semantic_mappings` 表 |
| `data_model1_loader.py` 硬编码映射 | Python dict | PostgreSQL（导入） |
| `semantic_mapping.py` 硬编码映射 | Python dict（DEFAULT_MAPPING） | PostgreSQL（导入） |

### 8.4 外观模式逐步迁移

三个现有标准化器保留，但通过 `semantic_layer/normalizer.py` 统一入口调用。

**迁移路径**:
1. Phase 1: `normalizer.py` 作为外观，内部 delegate 到三个现有实现
2. Phase 2: 字典迁移到 YAML + PostgreSQL，三个实现改为读持久化数据
3. Phase 3: 三个实现逐步 thin-ify，核心逻辑收归 `normalizer.py`

### 8.5 三层模型向后兼容

`business_object`、`MetricFormula`、`IndicatorSource` 的新增字段（`data_source`/`table_name`/`field_name`）均为可选，现有 19 个指标无需立即迁移。

### 8.6 公式求值器轻量级

初期只支持四则运算 `+ - * /` 和括号。不引入重量级表达式引擎。后续按需扩展条件表达式和聚合函数。

## 十、数据来源路径（L3 数据源的四种类型）

语义层指标可以从四种不同的数据源获取值：

### 来源1: SQL 数据库（type="sql"）
传统方式，通过 SQL 查询关系型数据库。
```
语义层指标 zyfdxx.bdtczf → source_field="yb_zyfdxx.bdtczfje" → SQL Server 查询
```

### 来源2: 业务适配器（type="adapter"）
通过防腐层适配器调用外部系统接口。
```
语义层指标 djxx.fund_type → source_adapter_port="InsuranceInterfacePort" → HIS/医保系统
```

### 来源3: Milvus 向量库（type="milvus"）
从 Milvus 向量数据库中检索已入库的政策规则。
```
语义层指标 → Milvus policy_rules 集合 → 向量检索 + 标量过滤
```

### 🆕 来源4: 非结构化政策原文的结构化字段（type="policy_extraction"）

**这是 v3.1 新增的数据来源路径**，打通了"非结构化文本 → 结构化规则 → 语义层指标"的完整链路。

```
非结构化政策原文（policy_documents.content_text）
    ↓ LLM 全文提取
政策片段（policy_extractions.source_text，含 fact_text + rules 数组）
    ↓ 规则展开 + 审核
结构化规则（19 个字段，对齐 数据模型1-政策规则表）
    ↓ 存储于 policy_extractions.extracted_fields JSONB
语义层指标 zcgz.{field_name}
    ↓ type="policy_extraction", data_source="policy_pipeline", table_name="policy_extractions"
消费者（PolicyQA、费用解释、结算导办等场景）
```

**业务对象**：`zcgz`（政策规则），归属 `ybzc`（医保政策）域。
**19 个指标**：rule_id, fact_id, policy_id, clause_id, source_text, insu_type, med_type, hosp_lv, psn_type, setl_type, payment_ratio, deductible_amount, cap_amount, time_period, admission_order, amount_band, priority, rule_type, rule_value。
**数据存储**：PostgreSQL `policy_extractions` 表，`extracted_fields` JSONB 列。
**种子数据**：`src/semantic_layer/seed.py::_seed_metrics` 中 `zcgz.*` 指标。

**与其他来源的区别**：
| 特性 | SQL | Adapter | Milvus | Policy Extraction |
|------|-----|---------|--------|-------------------|
| 数据性质 | 结构化 | 结构化 | 半结构化 | 非结构化→结构化 |
| 更新频率 | 实时查询 | 实时调用 | 入库后静态 | 提取后静态（需审核） |
| 置信度 | 1.0 | 1.0 | 1.0 | LLM 提取置信度 0.7-0.95 |
| 人工审核 | 不需要 | 不需要 | 不需要 | **需要**（草稿→审核→发布） |
| 值域映射 | SQL CASE / value_domain | adapter 转换 | 无 | 字典标准化 |

**设计理由**：医保政策以非结构化文本（通知、办法、实施细则）形式存在，无法被传统数据通道直接消费。通过 `policy_pipeline` 的 LLM 提取管线将其结构化为 19 个标准字段后，即可纳入语义层统一管理，实现政策规则与业务数据的关联查询。

[来源: 语义层设计 v3.1 | 实现: src/semantic_layer/seed.py + src/knowledge_extension/rule_explanation/pipeline_orchestrator.py]

## 十一、风险与注意事项

1. **不破坏现有功能**: 外观模式逐步迁移，每个 Phase 保持向后兼容
2. **Excel → YAML 同步**: `datamodel1_importer.py` 是幂等的，每次运行覆盖生成文件
3. **字典 YAML 是配置源，PostgreSQL 是运行源**: 字典 YAML 定义标准化映射的权威版本；PostgreSQL 中的 `semantic_mappings` 表是运行时查询和 Admin UI 管理的持久化存储
4. **三层模型向后兼容**: 所有新增字段（`business_object`、`data_source`、`table_name`、`field_name`）均带默认值，现有指标无需立即迁移
5. **公式安全**: `FormulaEvaluator` 只能执行算术表达式，禁止执行任意 Python 代码
6. **旧 SemanticMapper 迁移**: 唯一消费者是 `contextual_policy_qa.py`，影响面可控
7. **SQL 注入防护**: 继承现有 `PostgresDialect` 的参数化查询模式
8. **测试覆盖**: 严格按照 AGENTS.md 的验证流程（单元 → API → Flow）
9. **不要过早抽象**: 先支持费用场景（当前唯一完整的场景），再逐步扩展

## 字段绑定与运行方式

每个字段声明：稳定 `key`、标准 `label`、分区/行列/跨列、金额范围 `scope`、来源表、来源列、读取方式、算法账面属性 `observed_attribute`、对应计算字段 `field_code`、匹配证据与状态。普通门诊列经 `RecordQueryMapping` 解析，院区覆盖仍然生效；门特来源列使用现有 mz 套表物理列定义。

例如，“医疗保险范围内金额”绑定：

```json
{
  "key": "fee_in",
  "label": "医疗保险范围内金额",
  "source_table": "outpatient_trade_table",
  "column_keys": ["op_fee_in"],
  "record_mapping": true,
  "operation": "column",
  "observed_attribute": "fee_in",
  "field_code": "T_FeeIn",
  "scope": "patient_actual",
  "row": 2,
  "column": 1
}
```

当前默认解析到 `dbo.o_Trade.T_FeeIn`。该示例为配置字段摘录，完整配置包含布局、证据等校验必需项。

运行链：**配置 → 查询列清单 → 同一行绑定器 → 原单事实与算法账面观测值 → 公开模板及标准字段名 → 两处共用组件**。问题使用完整标准字段名时，也直接通过模板定位计算字段；原单字段没有计算绑定时只提供该原单事实，不定位到另一个清算口径。

公开契约 1.8 的 `settlement_facts.display_template` 仅含业务键、标准名、布局、金额、来源类型、缺失状态与对应计算字段。物理表列和匹配证据留在后端配置。`SettlementTemplateView` 同时供费用分解页和结算解释右栏使用：宽区域按模板双列排列，窄区域按行序单列排列。

金额区读原单值；明细合计不覆盖同名原单金额。解释只关联配置指定的计算字段，并核对当前展示金额是否与该字段账面值一致。旧 1.0—1.7 响应保留旧展示兼容；1.8 及以后缺模板时明确提示配置问题，不回退到名称猜测。

## 重要范围约束

- `operation=column`：单列原样值；`sum`：全部分项取得后求和；`sum_present`：保留既有门特快照的已返回分项汇总口径，原始分项仍分别列示；`unmapped`：未找到原单列；`context`：已有基本信息或患者脱敏摘要。
- 门特源表没有独立“个人支付总金额”列，模板明确 unmapped，不用算法值冒充原单值。算法的个人应付仍保留在计算结果中。
- 居民门特总医保内/外合计与特殊病分项分别维护；算法的 `TSBYBN/TSBYBW` 对应特殊病行，不绑定到包含普通门诊部分的合计行。
- 定额普通汇总 `tczhf/bczhf/jczhf` 等作为 patient_book 事实列示；医院清算明确使用 `tczhf1/bczhf1/jczhf1/gfylbchbxde` 等列，并放入 hospital_quota 分区。核定定额、原始个人自付一、医院垫付合计也从配置指定列取得。
- 首次识别模板不采集新的患者身份原文；姓名、性别、医保号和脱敏身份证仅在已有患者摘要可用时展示。

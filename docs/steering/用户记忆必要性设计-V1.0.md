# 用户记忆必要性设计 V1.0

> Issue：[#29 用户记忆必要性设计](https://github.com/ktyhwangfei/hospital_medical_insurance_agent/issues/29)
> 状态：设计完成，暂不进入实现
> 日期：2026-08-31
> 适用范围：当前唯一业务入口 Portal `/policy-qa`

## 1. 决策摘要

**当前 MVP 不需要新增“用户记忆”实现；跨会话用户偏好有条件地必要。**

现有 `BusinessMemory` 已覆盖一次会话内的结算、政策和对话连续性，当前问答又必须由用户提供结算单号，因此用户记忆不是政策问答正确性或可追溯性的前提。[来源: `src/runtime/memory/models.py:36-58`; `PROGRESS.md` §1.1 单元 1.6]

跨会话记住少量展示偏好，可能减少院端经办人员重复展开计算过程或政策依据的操作，但仓库尚无该价值的使用数据，而且 `/policy-qa/stream` 仍信任客户端传入的 `user_id='demo'`、`role='cashier'`。在医院 SSO、租户身份和持久审计就绪前落库，会产生错绑用户和跨租户读取风险。[来源: `src/runtime/api/policy_qa_routes.py:590-625`; `src/apps/portal/src/lib/use-policy-qa-stream.ts:287-293`; `PROGRESS.md` §1.1 单元 10.1-10.2]

因此采用两步最小方案：

1. 现在只保留会话级 `BusinessMemory`，不新增表、API、向量库或自动画像。
2. 先用会话内的展开/折叠操作验证重复偏好价值；只有在可信 SSO/RBAC、持久审计和试点价值同时成立后，才实现一张显式、白名单化的 `user_preferences` 表。

## 2. 业务价值与必要性

### 2.1 可能成立的价值

| 使用者 | 重复成本 | 最小记忆带来的价值 | 是否影响业务结论 |
|---|---|---|---|
| 医保办经办 | 每次重新展开计算过程、政策依据 | 跨会话恢复展示习惯 | 否 |
| 收费员 | 在摘要与详细查证之间重复切换 | 减少界面操作，缩短查证路径 | 否 |
| 医保运营人员 | 经常查看完整证据 | 默认展开引用，但仍保留全部引用 | 否 |

[推断] 这些价值来自当前 Chat-first 单答案、计算步骤和引用的真实交互结构，不代表已经验证的用户需求。首个试点只应度量“用户是否反复做同一个展示切换”，不能用模型猜测偏好。

### 2.2 当前不构成必要性的能力

- 问答正确性：由真实结算数据、Skill 确定性计算、政策证据和公开结果验证保证。
- 当前会话连续性：由 `session_id`、`RuntimeContext` 和 `BusinessMemory` 保证。
- 历史追溯：已有 session/workflow/task 和问答历史，不应复制到用户记忆。
- 权限与角色：应从每次请求的 SSO/RBAC 实时获得，不能记忆。
- 患者或结算快捷访问：共享院端终端上风险高，且当前产品要求显式输入结算单号。

## 3. 与现有会话上下文的边界

| 维度 | 现有 `BusinessMemory` | 候选 `UserPreference` | 问答历史/审计 |
|---|---|---|---|
| 目的 | 支撑当前会话推理与上下文裁剪 | 恢复用户显式设置的展示偏好 | 追溯业务执行和访问行为 |
| 身份键 | `session_id` | `tenant_id + user_id` | workflow/task/audit 标识 |
| 内容 | 领域对象引用、必要快照、对话摘要 | 两个低风险枚举偏好 | 问题、结果摘要、执行与审计事件 |
| 写入方式 | Runtime 自动写入 | 用户显式设置 | 系统自动记录 |
| 生命周期 | session/topic/time；`sticky` 仅跨话题 | 跨会话、有限期限、可随时删除 | 按业务与审计留存制度 |
| 是否进入推理 | 是，受上下文裁剪 | 首版否，只控制 Portal 展示 | 否 |
| 权威性 | 缓存/索引，外部系统仍是事实来源 | 非业务事实 | 追溯证据，不是业务事实 |

现有存储端口只有 `list_by_session` 和 `delete_by_session`，没有租户或用户维度；把用户偏好塞入 `BusinessMemory` 会破坏作用域、过期和授权语义。[来源: `src/data_platform/storage/memory/ports.py:11-28`]

早期上下文设计也明确把复杂长期记忆和跨会话画像排除在 MVP 之外；本设计延续该边界，只为有证据的显式展示偏好预留后续实现。[来源: `docs/specs/04-runtime_context上下文管理设计.md` §11]

## 4. 存什么

### 4.1 首个实现切片的白名单

只有以下两个可空枚举字段进入候选实现：

| 字段 | 允许值 | 用途 | 默认值 |
|---|---|---|---|
| `calculation_display_mode` | `summary` / `expanded` | 计算过程默认折叠或展开 | `summary` |
| `citation_display_mode` | `summary` / `expanded` | 政策依据默认折叠或展开 | `summary` |

它们只改变 Portal 的渐进披露状态，不改变回答文本、金额、计算、检索、引用集合、风险判断或权限。[建议]

### 4.2 明确禁止写入

- 患者、就诊、结算标识及其快照：`patient_id`、`encounter_id`、`settlement_id`、姓名、证件号、手机号、金额、诊断、病历。
- 原始问题、完整对话、模型摘要、政策结论、规则命中、问答历史。
- 用户角色、权限、科室、租户、可访问患者范围；这些必须来自当前认证上下文。
- 密钥、Token、登录渠道凭据、设备指纹。
- 高风险动作、人工确认结果、待办状态、风控阈值。
- 模型从对话推断的习惯、人格标签、能力评价、疾病或风险画像。
- 向量 embedding 或“相似用户”标签。

医疗健康信息属于敏感个人信息，只能在特定目的、充分必要并采取严格保护措施时处理；当前展示偏好不需要任何医疗健康字段。[来源: 《中华人民共和国个人信息保护法》第 28-30 条]

## 5. 放哪里、怎么存

### 5.1 归属

```text
Portal /policy-qa
  → 认证后的“我的问答偏好”API
  → runtime/context 消费 UserPreference（仅生成展示状态）
  → data_platform/storage/user_preference 持久化
  → PostgreSQL user_preferences

gateway/auth + tenant
  └── 从签名 Token 提供 tenant_id/user_id，不接受请求体冒充

security/authorization
  └── 强制“只访问我的偏好”和租户隔离

security/audit
  └── 记录读写删事件，不记录偏好值
```

- PaaS `runtime/context` 是消费方，因为偏好只在构造用户展示上下文时生效。
- DaaS `data_platform/storage/` 是存储归属，沿用项目的 ports/adapter 与 PostgreSQL 持久化约定。
- `gateway/auth` 与 `gateway/tenant` 负责认证和租户解析，`security/` 负责授权、脱敏校验和审计；它们都不保存偏好副本。
- 不使用 Milvus：偏好是结构化枚举，不需要语义检索。
- 首版不使用 Redis：一行 PostgreSQL 点查足够；只有性能测量证明需要时再缓存。
- 不使用浏览器 `localStorage`：院端共享终端可能在换人登录后遗留上一用户偏好。

### 5.2 最小表结构

候选实现采用固定列，不采用 EAV、JSONB 或“记忆类型注册表”：

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `tenant_id` | `VARCHAR(64)` | 复合主键；来自已验证身份 |
| `user_id` | `VARCHAR(128)` | 复合主键；来自已验证身份 |
| `calculation_display_mode` | `VARCHAR(16)` | 可空；数据库 `CHECK` 白名单 |
| `citation_display_mode` | `VARCHAR(16)` | 可空；数据库 `CHECK` 白名单 |
| `revision` | `INTEGER` | 乐观锁，初始 1 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 最近一次用户显式修改时间 |
| `expires_at` | `TIMESTAMPTZ` | 到期时间 |

主键为 `(tenant_id, user_id)`。不设 `preference_id`、`deleted_at`、`source`、`metadata` 或任意 JSON，避免演变成通用画像平台。删除采用硬删除，操作证据由独立审计日志保留。

## 6. 生命周期机制

### 6.1 写入与更新

1. 用户在 Portal 明确提交偏好；禁止从聊天内容、点击轨迹或模型输出自动提取。
2. 服务端只接受两个白名单枚举；请求体不接受 `tenant_id`、`user_id`、角色或权限字段。
3. 首次写入创建一行；后续 `PUT` 必须带 `expected_revision`，冲突返回 409。
4. 每次用户显式修改递增 `revision`、更新 `updated_at`，并重新计算 `expires_at`。
5. 写入前执行敏感字段拒绝检查；未知键、对象、数组、自由文本全部拒绝。

### 6.2 读取与使用

1. 完成签名 Token 校验和租户解析后，按 `(tenant_id, user_id)` 点查。
2. 到期或不存在时返回产品默认值，不影响政策问答。
3. 首版只把两个字段传给 Portal 控制折叠/展开，不注入模型 Prompt，也不改变 Skill 输入。
4. 偏好服务不可用时失败开放到默认展示状态；不能阻断政策问答主链。
5. 每个 API 查询始终包含 `tenant_id` 和 `user_id`，禁止仅按 `user_id` 查询或提供跨用户列表。

### 6.3 过期

[建议] `expires_at = updated_at + 180 天`，读取不续期，防止后台访问令偏好永久保留。到期记录不再返回；由日常维护任务硬删除，任务缺失时可在下一次用户访问时惰性删除。正式期限由医院隐私/数据留存制度确认。

### 6.4 删除

- `DELETE /me/policy-qa-preferences` 立即硬删除当前租户下当前用户的一行并恢复默认值。
- 用户撤回、账号注销、保存期限届满或处理目的不再必要时应删除；审计只保留事件类型、主体、字段名、结果和时间，不保留被删值。[来源: 《中华人民共和国个人信息保护法》第 47 条]
- 技术或法定原因暂不能删除时，停止除存储和必要安全保护外的处理，并记录原因；不得继续加载到问答。

## 7. 身份绑定与授权

### 7.1 实现门禁

以下条件全部满足前，不得启用持久用户偏好：

1. `/policy-qa/stream` 从医院 SSO 的已签名 Token 获得 `tenant_id`、`user_id`、角色，忽略客户端同名字段。
2. `tenant_id` 有稳定的医院/机构映射，且数据访问查询强制带租户条件。
3. 用户偏好 API 只能读、改、删“我”的记录，不提供按 `user_id` 参数查询。
4. `security/audit` 的持久存储和查询已可用；偏好写入与删除不能静默降级到仅内存审计。
5. Portal 登出/换人登录时清空内存中的会话、锚点和已加载偏好。

当前业务流不满足第 1、4 项，故本 Issue 不实现表或 API。[来源: `src/runtime/api/policy_qa_routes.py:590-625`; `PROGRESS.md` §1.1 单元 10.1-10.2]

### 7.2 授权规则

- 普通用户：仅能读取、更新、删除自己的偏好。
- 管理员：不能浏览个人偏好值；如需响应删除请求，只执行按已核验主体的删除流程。
- 系统支持人员：只看审计事件和错误，不看偏好值。
- 当前角色或科室变化立即以 SSO/RBAC 为准，用户偏好不得扩大权限。

## 8. 脱敏、审计与高风险边界

### 8.1 脱敏和输入防护

- 采用固定枚举列后，正常记录本身不含需要展示脱敏的自由文本。
- API 请求若出现患者、结算、联系方式等未知字段，直接拒绝而非尝试保存后脱敏。
- 日志、指标和审计不得记录偏好值、Token 或完整请求体；`user_id` 按医院审计规范进行最小可识别处理。
- 返回错误使用项目统一 `{error_code, message, audit_event}` 契约。

### 8.2 最小审计事件

| 事件 | 记录内容 | 不记录内容 |
|---|---|---|
| `user_preference.read` | tenant、actor、命中/默认、时间、trace | 偏好值 |
| `user_preference.updated` | tenant、actor、变更字段名、revision、结果 | 新旧值 |
| `user_preference.deleted` | tenant、actor、删除结果、时间 | 被删值 |
| `user_preference.expired` | tenant、主体标识、删除结果、时间 | 被删值 |

### 8.3 不可被偏好改变的边界

用户偏好永远不能：

- 自动选择患者、就诊或结算单，或跳过结算单号必填校验；
- 修改医保计算、政策检索条件、证据集合、引用和不确定性；
- 覆盖脱敏、权限、租户隔离、风险规则或高风险动作拦截；
- 自动触发退费、冲正、正式结算、病案修改或人工确认；
- 把摘要显示等同于省略安全警告或确定性不足声明。

安全、权限、真实数据和政策证据与偏好冲突时，前者无条件优先。[来源: 根 `AGENTS.md` §安全约束]

## 9. 最小 API 与落地顺序

只有门禁和价值条件都满足时，实施一个可独立验证的用户故事：

> 已登录的院端经办人员显式保存政策问答展示偏好，在同租户下一次登录恢复；其他用户和租户无法读取，用户可立即删除并恢复默认值。

最小 API：

```text
GET    /api/v1/medical-insurance-ai-agent/me/policy-qa-preferences
PUT    /api/v1/medical-insurance-ai-agent/me/policy-qa-preferences
DELETE /api/v1/medical-insurance-ai-agent/me/policy-qa-preferences
```

落地顺序：

1. **价值验证**：会话内提供两个展示切换并统计匿名聚合次数，不保存用户级明细。
2. **安全前置**：完成 SSO/RBAC、租户解析、持久审计和 Portal 换人清理。
3. **后端最小切片**：固定 Pydantic 模型、存储端口、内存/PostgreSQL 实现、三个 `/me` API。
4. **Portal 接入**：只恢复折叠/展开状态；偏好服务失败使用默认值。
5. **验证**：严格按单元 → API → Flow；安全用例至少覆盖身份冒充、跨租户、跨用户、未知字段、过期、删除和审计不含值。

如进入实现，新增领域概念前同步更新 `src/domain/AGENTS.md` 通用语言字典；表落地后再同步 `docs/steering/数据库设计文档.md`，不得把候选设计写成已实现事实。

## 10. 方案比较

| 方案 | 收益 | 风险/成本 | 决策 |
|---|---|---|---|
| A. 继续仅用会话记忆 | 零新增数据、当前业务已可用 | 不能跨会话恢复偏好 | **当前采用** |
| B. 显式白名单用户偏好 | 跨会话/终端恢复两个展示习惯 | 依赖可信身份、租户隔离和持久审计 | **门禁满足后推荐** |
| C. 自动学习的用户画像/向量记忆 | 理论上可个性化回答 | 医疗敏感信息、不可解释推断、删除困难、可能改变业务结论 | **拒绝** |

个人信息处理应限定在明确目的所必要的最小范围，并公开处理目的、方式和范围；固定枚举、显式写入和可删除比自动画像更符合该原则。[来源: 《中华人民共和国个人信息保护法》第 6-7 条]

## 11. 验收门槛与待确认决策

### 11.1 进入实现的验收门槛

- 试点观察到同一类展示切换在不同会话中重复发生，并由产品负责人确认跨会话恢复有价值。
- SSO Token 的 `tenant_id`、`user_id` 和角色 claim 契约已确定并接入业务流。
- 偏好处理目的、告知方式、保存期限和删除流程通过医院信息/法务审核。
- 持久审计可查询，且安全测试证明无跨租户、跨用户和偏好值泄露。

### 11.2 仍需用户/院方确认

1. 是否确有“跨设备/跨终端恢复展示偏好”的需求；若只需当前会话，现有能力已经足够。
2. 首个白名单是否仅保留 `calculation_display_mode` 与 `citation_display_mode`。
3. 180 天保存期限是否符合医院制度，或应使用更短期限。
4. 医院 SSO 中稳定的租户与用户 claim 名称，以及账号注销事件如何通知本系统删除。

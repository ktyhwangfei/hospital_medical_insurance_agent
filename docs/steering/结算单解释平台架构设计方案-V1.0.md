# 1. 建设背景

医保智能服务助手与普通问答类人工智能应用存在明显差异。

用户提出的问题通常不是单纯询问政策，而是围绕某一次真实发生的医保业务事实提出解释、比较、分析和确认需求。例如：

* 我的统筹自付为什么这么多；
* 我的个人负担为什么这么高；
* 同样的项目为什么两次费用不一样；
* 这项费用为什么不能报；
* 这次特病待遇到底有没有生效；
* 退费后为什么金额没有按预期变化。

这类问题必须同时依赖真实业务数据、医保政策、待遇规则、业务语义和确定性计算，最终回答不仅要"说得通"，还需要能够说明：

> **基于什么数据、依据什么政策、经过什么业务判断和计算，最终为什么得到这个结果。**

与此同时，系统作为长期产品，还会持续面对政策变化、业务流程变化、医院差异、区域差异、数据源变化和新业务场景扩展等问题。

因此，本方案的核心不是单纯建设一个 Agent，而是建立一套能够长期演进的产品结构，使：

> **平台能力稳定沉淀，业务逻辑独立演进，数据与知识保持统一语义，智能理解与确定性业务执行明确分离。**

---

# 2. 设计目标

本方案重点解决五个问题。

### 2.1 保障医保业务结果可信

关键数据查询、政策适用、医保计算、一致性校验和证据生成必须具备明确的确定性边界。

### 2.2 降低长期运维成本

业务流程和业务差异不应不断侵入平台核心代码，避免最终形成难以维护的大型业务代码体系。

### 2.3 支持业务持续扩展

在已有平台能力可以满足需求时，新业务应尽可能通过增加或调整业务流程完成，而不是重复开发底层能力。

### 2.4 保持平台边界清晰

只有真正具有通用性、稳定性和平台价值的能力才下沉到平台，避免个性化业务逻辑不断污染平台。

### 2.5 支持逐步产品化运营

业务流程成熟后，可以进一步独立管理、版本化、测试、发布和回滚，使业务流程逐渐成为可运营的产品资产。

---

# 3. 核心设计结论

本方案首先明确一个原则：

> **长期运营并不等于必须使用 Skill。**

对于流程稳定、场景较少的业务，采用固定工作流完全可以满足需求。

只有当业务流程开始出现独立管理和持续变化的需求，例如：

* 流程经常调整；
* 同一业务存在多个版本；
* 不同医院或地区存在差异；
* 新业务大量复用已有平台能力；
* 业务流程需要独立于产品代码发布；
* 业务人员和领域专家需要参与维护；

此时，才需要将业务流程进一步产品化为 Skill。

因此：

> **Skill不是系统必须存在的技术层，而是一种将业务流程独立运营的产品机制。**

# 4. 总体架构

系统采用"Agent + 业务流程 + 平台能力"三层结构。

```text
┌─────────────────────────────────────────────┐
│                  用户交互层                  │
│      用户问题 / 会话上下文 / 业务上下文       │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│                   Agent层                   │
│    问题理解 / 问题实例化 / 业务对象识别       │
│              流程选择 / 对话管理             │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│                业务流程层                   │
│                                             │
│       固定工作流 / Skill                    │
│                                             │
│   Skill可包含业务逻辑、业务规则和执行流程     │
│   流程可通过图形化方式展示                   │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│                 平台能力层                  │
│                                             │
│  Tool：数据 / 知识 / 政策 / 计算 / 校验 / 证据 │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│             医保语义与知识层                 │
│                                             │
│ 业务对象 / 指标 / 维度 / 值域                │
│ Business Fact / Policy Fact                 │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              数据与基础设施层               │
│ 业务数据库 / 政策库 / 向量库 / 外部业务系统   │
└─────────────────────────────────────────────┘
```

其中：

> **Agent解决"用户想解决什么问题"。**

> **业务流程解决"这个问题应该怎么解决"。**

> **Tool解决"平台能提供什么通用能力"。**

> **语义层解决"业务概念如何与数据和政策保持一致"。**

# 5. 平台、Tool、Skill与流程的职责边界

## 5.1 平台

平台提供相对稳定、能够被多个业务复用的通用能力。

主要包括：

* 数据访问能力；
* 知识访问能力；
* 政策事实获取；
* 政策适用性判断；
* 通用医保计算；
* 业务一致性校验；
* 证据构建；
* 权限控制；
* 审计；
* 版本管理；
* 运行监控；
* Tool运行机制；
* 业务流程运行机制。

平台回答：

> **"系统能够做什么？"**

---

## 5.2 Tool

Tool是平台能力对外提供的标准化业务接口。

例如：

* 获取结算事实；
* 获取费用事实；
* 获取待遇事实；
* 获取政策事实；
* 判断政策适用性；
* 执行医保计算；
* 比较结算；
* 分析退费；
* 执行一致性校验；
* 构建业务证据。

Tool应该以业务能力为粒度，而不是数据库字段为粒度。

不建议：

```text
查询某张表
查询某个字段
查询另外一个字段
```

建议：

```text
获取结算事实
获取费用事实
获取待遇事实
```

Tool内部可以调用数据库、接口、算法等底层实现。

因此：

> **Tool是平台能力的业务化接口。**

---

# 6. Skill的定义

Skill不是简单的Tool组合器。

Skill应该被定义为：

> **面向具体业务场景的、可以独立演进的业务解决方案单元。**

一个Skill既可以：

* 调用平台Tool；
* 定义能力调用顺序；
* 定义业务判断；
* 定义场景特有规则；
* 定义场景特有的数据处理；
* 定义异常处理；
* 定义结果组织；
* 定义业务输出要求。

因此：

> **Skill既承载"怎么做"，也可以承载"这个业务特有的逻辑"。**

平台不应该为了追求所谓"统一"，把所有业务逻辑都下沉到平台。

---

# 7. Skill与平台能力的边界

判断某个逻辑应该进入平台还是Skill，需要遵循以下原则。

## 7.1 进入平台的逻辑

满足以下特征之一：

* 多个业务都会复用；
* 是稳定的底层业务能力；
* 具有明确的平台治理价值；
* 涉及统一的数据访问；
* 涉及统一权限；
* 涉及统一审计；
* 属于通用计算能力；
* 属于基础知识访问能力。

例如：

> 获取结算事实。

应属于平台。

---

## 7.2 留在Skill的逻辑

满足以下特征之一：

* 只针对一个业务场景；
* 只针对一个特定业务流程；
* 属于特定场景的判断策略；
* 属于客户或医院个性需求；
* 只用于特定业务结果组织；
* 暂未证明具有跨业务复用价值。

例如：

> 结算解释过程中，先判断统筹自付占比，再决定是否展开费用明细。

如果这一判断仅服务于结算解释，那么可以留在结算解释Skill。

---

# 8. 个性化业务逻辑的处理原则

在产品化过程中，医院、区域和具体业务场景必然会出现差异。

例如：

某医院希望结算解释优先展示：

> 药品费用 → 诊疗费用 → 材料费用。

另一个医院希望优先展示：

> 医保支付 → 个人支付 → 不予支付项目。

这种差异不应该立即进入平台。

合理方式是：

```text
平台
提供：
获取费用
获取结算
获取政策
执行计算
```

Skill负责：

```text
如何组织这些能力
如何判断展示哪些内容
如何解释
如何处理医院特定业务要求
```

由此形成：

> **平台提供通用能力，Skill隔离业务差异。**

---

# 9. Skill不能成为"代码换皮"

Skill虽然可以承载个性化逻辑，但也不能把所有东西都塞进去。

以下情况必须回到平台：

* Skill需要访问一个平台尚未提供的数据源；
* Skill需要新增通用数据能力；
* Skill需要一种新的基础计算能力；
* 多个Skill开始重复实现同一种能力；
* Skill逻辑已经成为多个业务共同依赖；
* Skill需要平台级权限或审计能力。

因此：

> **Skill负责隔离个性，平台负责沉淀共性。**

---

# 10. 业务流程的定义

业务流程可以采用两种实现方式：

```text
固定工作流
```

或

```text
Skill中的业务流程
```

固定工作流适合：

* 流程稳定；
* 场景较少；
* 不需要独立运营；
* 不存在明显差异。

Skill适合：

* 流程经常变化；
* 需要独立版本；
* 不同医院存在差异；
* 业务人员需要参与运营；
* 新业务不断增加。

因此，不要求第一阶段所有流程立即Skill化。

---

# 11. Graph的定位

Graph不再作为独立的核心业务架构层。

> **Graph只是业务流程的一种结构化、可视化和运行表达形式。**

也就是说：

```text
Skill
├── 业务定义
├── 业务逻辑
├── 数据要求
├── Tool依赖
├── 执行流程
├── 校验要求
└── 测试
```

其中：

```text
执行流程
    ↓
图形化展示
    ↓
Graph视图
```

Graph本身不承担独立的业务职责。

因此：

> **Graph不是必须独立存在的业务抽象。**

底层运行时可以采用流程图方式执行，也可以采用其他工作流机制。

例如使用LangGraph只是技术实现，不应成为业务架构的核心概念。

---

# 12. Skill中的业务流程可视化

尽管Graph不是独立架构层，但Skill需要具备清晰的流程展示能力。

例如：

```text
结算解释 Skill

业务目标：
解释本次医保结算个人负担形成原因

流程：

[获取结算事实]
       ↓
[实例化用户问题]
       ↓
[确定关注指标]
       ↓
[获取费用事实]
       ↓
[获取待遇事实]
       ↓
[获取政策事实]
       ↓
[判断政策适用]
       ↓
[执行计算]
       ↓
[一致性校验]
       ↓
[构建证据]
       ↓
[生成解释]
```

这是为了让：

* 产品人员；
* 研发人员；
* 医保专家；
* 运营人员；

都可以理解一个业务Skill是如何工作的。

---

# 13. Agent设计

Agent负责处理系统中天然存在的不确定性。

主要职责：

* 自然语言理解；
* 用户问题实例化；
* 业务对象识别；
* 分析目标识别；
* 需要哪些事实的判断；
* Skill选择；
* 多轮对话理解；
* 最终自然语言组织。

Agent不直接承担：

* 医保核心计算；
* 关键政策数值判断；
* 核心业务规则执行；
* 最终业务数据修正；
* 自动修改Skill；
* 自动修改政策。

原则：

> **Agent负责理解，不负责替代业务系统做确定性业务处理。**

---

# 14. 结算事实驱动的问题实例化

医保结算解释场景可以优先利用真实结算上下文缩小问题空间。

例如用户：

> "我的统筹自付为什么这么多？"

系统首先获取：

* 结算信息；
* 人员类别；
* 就诊类型；
* 医保内金额；
* 起付线；
* 统筹支付；
* 统筹自付；
* 大额支付；
* 大额自付；
* 个人支付。

然后形成结构化问题：

```text
业务对象：结算

分析目标：解释统筹自付

目标指标：统筹自付

需要的数据：
结算事实
费用事实
待遇事实

需要的政策：
待遇政策
起付线政策
相关费用政策

最终要求：
可计算
可解释
可追溯
可验证
```

通过这种方式，Agent面对的不是完全开放的问题空间，而是已经由真实业务事实限定的问题。

# 15. 医保语义层

语义层属于平台基础能力。

核心业务对象：

* 参保人员；
* 结算；
* 费用；
* 待遇；
* 政策；
* 医保目录；
* 医疗机构；
* 药品；
* 诊疗项目；
* 退费。

核心指标：

* 医保内金额；
* 起付线；
* 统筹支付；
* 统筹自付；
* 大额支付；
* 大额自付；
* 个人支付；
* 医保外费用。

核心维度：

* 人员类别；
* 参保类型；
* 就诊类型；
* 医疗机构；
* 时间；
* 药品；
* 诊疗项目；
* 待遇类型。

值域包括：

* 职工；
* 居民；
* 在职；
* 退休；
* 普通门诊；
* 普通住院；
* 特病等。

语义层解决的问题不是简单字段映射，而是：

> **同一个医保业务概念如何同时关联到自然语言、真实数据、政策知识和计算规则。**

# 16. Business Fact与Policy Fact

## 16.1 Business Fact

用于描述真实业务发生了什么。

例如结算事实：

```text
结算标识
参保类型
人员类别
就诊类型
总费用
医保内金额
起付线
统筹支付
统筹自付
大额支付
大额自付
个人支付
结算时间
```

费用事实：

```text
费用项目
项目编码
项目名称
数量
单价
金额
医保类别
个人负担
```

所有事实都应保留来源信息。

---

## 16.2 Policy Fact

用于描述政策规定了什么。

主要包括：

```text
政策标识
政策版本
业务对象
业务条件
政策数值
单位
适用人群
适用业务
生效时间
失效时间
来源文件
原文位置
```

Policy Fact必须能够支撑：

* 政策匹配；
* 适用性判断；
* 规则计算；
* 证据生成。

---

# 17. 数据与政策双向验证

系统建立：

> **数据帮助理解政策如何在真实系统中落地，政策反过来检查数据是否具备执行条件。**

例如政策规定：

> 某项待遇需要人员类别、待遇状态和时间条件。

系统检查真实数据是否存在：

```text
人员类别
待遇状态
结算时间
```

如果数据能够支撑：

> 建立数据与政策之间的业务对应关系。

如果不能：

> 明确标记数据不足或规则不可执行。

禁止通过大模型自行补全。

# 18. 平台Tool体系

第一阶段优先建设以下通用Tool。

## 数据类

* 获取结算事实；
* 获取费用事实；
* 获取待遇事实；
* 获取退费事实。

## 政策类

* 获取政策事实；
* 政策检索；
* 政策适用性判断。

## 计算类

* 医保结算计算；
* 个人负担分解；
* 待遇累计计算；
* 其他经验证的确定性计算。

## 分析类

* 跨结算比较；
* 费用差异分析；
* 退费分析。

## 校验类

* 数据一致性校验；
* 数据与政策一致性校验；
* 结果完整性校验。

## 证据类

* 证据构建；
* 来源追踪；
* 计算过程记录。

# 19. Tool注册与管理

平台建立统一Tool注册机制。

每个Tool至少描述：

```text
工具名称
业务说明
业务对象
输入参数
输出结构
权限要求
数据来源
执行方式
超时策略
错误处理
版本
状态
```

Skill只感知：

> "我需要获取结算事实。"

不感知：

* SQL；
* 数据库地址；
* 数据库表；
* 服务内部实现。

# 23. 结算解释Skill示例

一个"结算解释Skill"可以定义：

### 业务目标

解释当前结算中个人负担形成原因。

### 关键输入

* 用户问题；
* 结算标识；
* 相关业务上下文。

### 业务逻辑

首先读取结算事实，识别用户关注指标；根据关注指标决定需要进一步获取费用、待遇及政策信息；结合政策适用性判断和平台提供的确定性计算能力形成解释。

### 个性化逻辑

例如某医院要求：

> 优先展示费用分类和具体费用项。

该逻辑可以留在Skill中。

### 平台Tool

调用：

* 获取结算事实；
* 获取费用事实；
* 获取待遇事实；
* 获取政策事实；
* 判断政策适用性；
* 执行计算；
* 一致性校验；
* 构建证据。

这样能够实现：

> 通用能力在平台，业务差异在Skill。

# 24. 多医院、多区域产品化

长期产品化以后，最重要的场景之一是：

> **同一平台服务不同医院或区域。**

不同客户可能存在：

* 数据差异；
* 流程差异；
* 展示差异；
* 特殊业务处理；
* 个性化规则。

平台不应该为每个客户增加大量分支代码。

更合理的是：

```text
统一平台
   │
   ├── 医院A结算解释Skill
   ├── 医院B结算解释Skill
   ├── 区域A待遇确认Skill
   └── 区域B待遇确认Skill
```

但这些Skill共享：

* 数据能力；
* 政策能力；
* 计算能力；
* 权限；
* 审计；
* 运行基础设施。

这才体现Skill的长期产品价值。

# 25. 业务变化与平台变化的边界

| 变化       | 主要处理方式      |
| -------- | ----------- |
| 调整业务流程顺序 | Skill / 工作流 |
| 增加业务判断   | Skill       |
| 调整结果组织   | Skill       |
| 客户特殊业务要求 | Skill       |
| 增加业务场景   | 新Skill或新工作流 |
| 新增通用查询能力 | 平台Tool      |
| 新增底层计算能力 | 平台          |
| 新增数据源    | 平台          |
| 新增通用业务对象 | 平台          |
| 政策内容变化   | 政策知识/规则     |
| 政策版本变化   | 政策知识/规则     |
| 平台权限体系变化 | 平台          |

核心原则：

> **能被业务流程独立吸收的变化，不进入平台。**

# 26. 防止平台不断膨胀

平台建设必须坚持：

> **共性下沉，个性上浮。**

当某个Skill中出现一项新的能力时，不应立即下沉平台。

只有当：

* 多个Skill都需要；
* 逻辑已经稳定；
* 具备明确复用价值；
* 需要统一治理；

才考虑把它提升为平台能力。

这样可以避免：

```text
平台
├── 结算特殊规则
├── 医院A特殊规则
├── 医院B特殊规则
├── 某区域特殊规则
└── 某客户特殊规则
```

最终平台重新变成巨型业务系统。

# 36. 最终架构原则

### 原则一：不为Skill而Skill

只有业务流程真正需要独立运营时才Skill化。

### 原则二：共性进入平台，个性留在Skill

平台沉淀通用能力，Skill隔离业务差异。

### 原则三：Skill不是Tool调用器

Skill可以承载业务规则、业务判断、数据处理和流程。

### 原则四：Tool不是数据库接口

Tool应该提供稳定的业务能力。

### 原则五：Graph不是独立业务层

Graph是Skill业务流程的可视化和执行表达。

### 原则六：Agent不承担确定性医保业务

Agent负责理解和选择，业务规则和计算必须由确定性能力执行。

### 原则七：数据和政策必须语义统一

自然语言、数据事实、政策事实和计算规则必须建立统一业务语义。

### 原则八：不确定就停止，而不是猜测

数据不足、政策不足、语义冲突和规则冲突必须显式返回。

### 原则九：业务变化与能力变化分离

业务流程变化进入Skill；能力边界变化进入平台。

### 原则十：先验证，再抽象

任何平台化能力都应由真实业务复用需求证明，而不是预先设计大量抽象。

---

# 37. 最终产品定位

本系统最终建设的不是一个单纯的医保问答Agent，也不是一个强制Skill化的流程平台，而是：

> **一个以医保领域通用能力为基础，以业务流程为核心，以Agent负责自然语言问题理解，以数据和政策语义统一为基础，并能够随着业务复杂度增长逐步将业务流程产品化运营的医保智能服务平台。**

最终形成清晰的责任边界：

```text
                         用户
                           ↓
                         Agent
                 "用户想解决什么"
                           ↓
             固定流程 / Skill
                 "这个问题怎么解决"
                           ↓
                         Tool
                  "平台能提供什么能力"
                           ↓
              语义 / 数据 / 政策 / 计算
                           ↓
                        业务结果
```

其中：

> **平台负责共性。**

> **Skill负责个性和业务方案。**

> **Tool负责能力提供。**

> **Agent负责问题理解。**

> **Graph负责流程的可视化表达。**

最终目标不是让架构越来越复杂，而是：

> **随着业务不断增加，尽量把变化限制在正确的位置，使稳定的产品能力不被业务变化反复侵入。**

这一版把前面争论的几个核心问题真正统一起来：**Skill不是必选项、Graph不是独立层、Skill不是Tool编排器、个性化逻辑可以留在Skill、平台只沉淀真正的共性能力**。其中最关键的长期架构原则就是最后那句：**把变化限制在正确的位置。**

# 政策知识治理·知识页前端改造设计（V3.2 · 结合现状落地版）

> **定位**：将知识页从“三栏加工流水线”重构为“知识工作台 + 知识详情页 + 语义映射抽屉”，围绕政策规则单元完成发现问题、原文核验、结构化维护、统一语义映射和审核发布。
>
> **核心原则**：结构化业务数据与非结构化政策抽取结果使用同一套业务概念、语义字段、标准值域、指标标识和单位体系，使数据库查询结果标准化后能够确定性匹配适用政策。
>
> **范围**：本文定义知识页前端改造及其必要的数据契约，不扩展专门测试页。规则运行验证、问答验证和检索效果评测继续由现有“测试”页承担。
>
> **版本说明**：V3.2 = V3.1（§1–§16，设计评审稿，保留原文）+ §17–§20（结合当前代码/数据/API 现状的落地对齐增量）。
> **落地依据**：`docs/steering/政策知识治理-需求迭代记录.md` 迭代 13；现状代码见 `src/apps/portal/app/policy-knowledge/`、`src/knowledge_extension/rule_explanation/`、`src/runtime/api/`、`src/semantic_layer/`。

## 1. 设计结论

知识页只服务两个核心任务：

1. **批量治理**：回答“有哪些政策知识需要处理、哪些存在问题、当前处于什么状态”。
2. **单条精审**：回答“这条规则从哪里来、结构化是否准确、是否完成统一语义映射、能否被 Agent 稳定使用”。

页面结构收敛为：

| 页面或组件 | 核心任务 | 不承担的任务 |
|---|---|---|
| 知识工作台 | 搜索、筛选、风险发现、批量治理、进入详情 | 不展开全文，不维护全部字段映射 |
| 知识详情页 | 原文核验、规则编辑、证据关联、审核 | 不承担批量任务，不展示全局映射资产 |
| 语义映射抽屉 | 当前规则涉及字段的概念、值域、指标及来源映射 | 不取代语义层的全局配置页面 |
| 独立测试页 | 规则运行验证、问答测试、检索评测 | 本次不改造 |

原三栏“单元审核 → 知识评审 → 值域标化 → 指标映射”不再作为知识页的主视觉结构。加工步骤保留为后台状态和筛选条件，核心对象统一收敛为**政策规则单元**。

## 2. 设计边界与基本原则

### 2.1 以政策规则为中心，不以加工步骤为中心

用户维护的不是一组孤立字段，而是：

> 在特定地区、时间、人群和业务条件下，针对某个业务主题执行什么规则，得到什么结果，并由哪些政策原文提供证据。

因此，页面的稳定主线为：

```text
政策原文与版本
  → 政策规则单元
    → 适用条件 / 规则行为 / 规则结果 / 例外
      → 统一语义和值域映射
        → 审核与发布
          → Agent 运行时使用
```

### 2.2 统一语义、统一值域、区分值角色

结构化数据库字段、政策结构化字段和用户自然语言表达必须汇聚到同一个标准语义空间：

```text
数据库字段 PER_TYPE=2 ───────┐
政策原文“退休人员” ───────────┼→ person_type=RETIRED
用户问题“退休职工” ───────────┘
```

统一包括：

- 同一个业务概念编码；
- 同一个语义字段编码；
- 同一个标准值域和值编码；
- 同一个指标或业务量标识；
- 同一个数据类型、单位和精度标准；
- 同一套条件操作符。

统一不代表丢失来源差异。系统通过 `value_role` 区分值在运行时的角色：

| 值角色 | 含义 | 示例 |
|---|---|---|
| `OBSERVED` | 数据库查询得到的业务实际值 | 本次实际起付线 650 元 |
| `POLICY_STANDARD` | 政策规定的标准值 | 首次住院起付线 1300 元 |
| `POLICY_RATE` | 政策规定的比例或系数 | 二次住院按 50% |
| `THRESHOLD` | 政策判断阈值 | 年度费用超过 10 万元 |
| `ACCUMULATED` | 累计业务值 | 年度累计医保内费用 8 万元 |
| `CALCULATED` | 根据规则计算出的结果 | 1300 × 50% = 650 元 |

### 2.3 原文、规则、映射三层解耦

- **原文层**保存政策文件版本、章节、段落和证据锚点；
- **规则层**保存适用条件、规则行为、规则结果、例外和有效范围；
- **语义层**保存业务概念、指标、标准值域以及来源映射。

三层相互关联，但不将原文、规则和物理数据库字段固化在同一对象中。

### 2.4 审核通过不等于立即上线

知识编辑、知识审核、知识发布和政策时效是不同维度。只有满足以下条件的规则才能进入 Agent 运行时：

- 结构化字段满足对应规则类型要求；
- 原文证据完整；
- 关键字段完成统一语义和值域映射；
- 不存在阻断问题；
- 审核通过；
- 已发布；
- 当前业务日期处于政策有效期内。

## 3. 核心对象与知识粒度

### 3.1 核心对象：政策规则单元

一条政策规则单元由以下内容构成：

```text
政策规则单元
= 业务主题
+ 适用条件
+ 规则行为
+ 规则结果
+ 例外与补充
+ 生效范围
+ 原文证据
+ 统一语义映射
```

建议的最小结构：

```json
{
  "rule_id": "KR-2025-0042",
  "rule_group_id": "KG-2025-0011",
  "topic_concept": "DEDUCTIBLE",
  "rule_type": "DECISION_TABLE",
  "conditions": [],
  "variants": [],
  "exceptions": [],
  "validity": {},
  "evidences": [],
  "semantic_bindings": []
}
```

### 3.2 不强制将一个政策表述拆成多个孤立事实

以下原文：

> 一级医院起付线 400 元，二级医院 800 元，三级医院 1600 元。

应优先结构化为一个带规则分支的规则单元：

| 条件字段 | 条件值 | 结果字段 | 结果值 |
|---|---|---|---|
| `hospital_level` | `LEVEL_1` | `deductible_amount` | 400 元 |
| `hospital_level` | `LEVEL_2` | `deductible_amount` | 800 元 |
| `hospital_level` | `LEVEL_3` | `deductible_amount` | 1600 元 |

只有出现独立业务结论时才拆分。例如同一段同时规定“起付线”和“支付比例”，可拆为两个规则单元，但使用同一个 `rule_group_id` 保留其同源关系。

### 3.3 规则关系

规则之间至少支持以下关系：

| 关系 | 含义 |
|---|---|
| `PARALLEL` | 同一条款中的并列规则 |
| `SUPPLEMENT` | 对主规则的补充说明 |
| `EXCEPTION` | 对主规则的例外 |
| `REPLACE` | 新规则替代旧规则 |
| `REFERENCE` | 引用另一政策或规则 |

知识详情页需要显示规则所在规则组及其关联规则，避免审核人员只看到孤立卡片。

## 4. 状态模型

不再使用单一 `review_status` 承载所有状态，拆分为以下维度。

### 4.1 编辑审核状态

```text
DRAFT → PENDING_REVIEW → NEEDS_REVISION → APPROVED
```

| 状态 | 含义 |
|---|---|
| 草稿 | 尚未提交审核 |
| 待审核 | 已提交，等待人工核验 |
| 需修改 | 审核发现问题并退回 |
| 审核通过 | 内容审核完成 |

### 4.2 发布状态

```text
UNPUBLISHED → PUBLISHED → SUPERSEDED / WITHDRAWN
```

| 状态 | 含义 |
|---|---|
| 未发布 | 不进入线上 Agent 运行时 |
| 已发布 | 可被运行时检索和匹配 |
| 已被替代 | 被新版本规则替代，保留历史追溯 |
| 已撤回 | 因错误或其他原因停止使用 |

### 4.3 政策时效状态

由生效日期、失效日期和当前业务日期动态计算：

```text
FUTURE / EFFECTIVE / EXPIRED
```

### 4.4 数据处理状态

用于处理抽取噪声，不与政策适用性混淆：

| 状态 | 含义 |
|---|---|
| `NORMAL` | 正常知识候选 |
| `IGNORED` | 无需形成知识规则 |
| `EXTRACTION_INVALID` | AI 抽取错误 |

不使用 `not_applicable` 表示抽取无效，因为“不适用”在医保政策中具有明确的业务语义。

## 6. 页面一：知识工作台

### 6.1 页面定位

知识工作台只负责：

- 搜索和筛选；
- 查看治理状态；
- 发现阻断问题和风险；
- 执行受控批量操作；
- 进入单条规则详情。

工作台不铺开整段原文，不直接维护复杂规则分支，也不展示全部语义映射配置。

### 6.2 页面布局

```text
┌─ 页头 ─────────────────────────────────────────────────────┐
│ 政策知识治理 / 当前政策集 / 契约版本 / 统计摘要 / 导出        │
├─ 筛选区 ───────────────────────────────────────────────────┤
│ 搜索 │规则类型│来源│有效状态│审核状态│发布状态│映射状态│风险   │
├─ 视图切换 ─────────────────────────────────────────────────┤
│ 全部规则 / 待处理 / 存在阻断问题 / 待发布 / 已失效             │
├─ 规则列表 ─────────────────────────────────────────────────┤
│ 标题与结论 │ 来源 │ 适用范围 │ 完整度 │ 映射 │ 状态 │ 问题    │
├─ 批量操作栏 ───────────────────────────────────────────────┤
│ 提交审核 / 通过审核 / 退回修改 / 忽略候选 / 更多               │
└────────────────────────────────────────────────────────────┘
```

### 6.3 列表字段

| 字段 | 展示内容 | 说明 |
|---|---|---|
| 规则标题 | 业务主题 + 结论摘要 | 首屏回答“讲什么” |
| 规则类型 | 固定值、比例、阶梯、资格、排除、流程、解释等 | 决定编辑器和完整度模板 |
| 来源 | 政策文件、版本、条款 | 支持快速定位 |
| 适用范围 | 人群、险种、医疗类别、医院等级、地区等 | 只显示摘要 |
| 有效期 | 生效日期至失效日期 | 区分未生效、生效中、已失效 |
| 完整度 | 按规则类型计算 | 不使用统一字段数量评分 |
| 映射状态 | 已映射字段数、待确认字段数 | 展示统一语义准备情况 |
| 审核状态 | 草稿、待审核、需修改、已通过 | 内容治理状态 |
| 发布状态 | 未发布、已发布、已替代、已撤回 | 运行时使用状态 |
| 问题 | 阻断问题和警告数量 | 点击进入详情并定位 |

### 6.4 默认排序

默认优先级：

```text
阻断问题 > 待审核 > 低完整度 > 映射待确认 > 普通规则
```

不以 AI 置信度作为主排序依据。置信度仅作为辅助信息展示在详情或提示中。

### 6.5 批量操作安全边界

批量操作支持：

- 提交审核；
- 通过审核；
- 退回修改；
- 忽略候选；
- 重新抽取。

只有同时满足以下条件的规则才能批量通过：

- 不存在阻断问题；
- 来源政策版本一致；
- 规则类型和必填字段完整；
- 原文证据完整；
- 关键语义字段已映射；
- 不存在未保存修改。

批量确认弹窗显示规则数量、规则类型、政策版本、阻断问题和警告问题摘要。存在例外、复杂计算或跨文件证据的规则默认要求单条审核。

### 6.6 行操作

规则行的主操作保持克制：

```text
查看详情 / 提交审核 / 通过 / 退回
```

拆分规则、合并规则、重新抽取、忽略候选放入“更多”菜单，避免高风险操作常驻。

## 7. 页面二：知识详情页

### 7.1 页面定位

知识详情页用于完成一条政策规则的精细审核和长期维护，必须同时回答：

1. 规则来自哪里；
2. 原文具体支持哪些字段；
3. 规则适用于什么条件；
4. 产生什么结果；
5. 是否存在例外；
6. 是否完成统一语义和值域映射；
7. 当前是否满足审核和发布条件。

### 7.2 页面布局

桌面端采用稳定双栏：

```text
┌─ 顶部状态栏 ───────────────────────────────────────────────┐
│ 规则编号 / 政策版本 / 审核状态 / 发布状态 / 有效状态 / 操作   │
├──────────────────────────────┬──────────────────────────────┤
│ 左：政策原文与证据            │ 右：政策规则编辑器             │
│                              │                              │
│ 章节目录                      │ 规则标题与类型                 │
│ 当前引用段落                  │ 适用条件                       │
│ 前后文                        │ 规则行为                       │
│ 多证据高亮                    │ 规则结果或规则分支             │
│ 版本与条款信息                │ 例外与补充                     │
│                              │ 生效范围                       │
│                              │ 证据与映射状态                 │
├──────────────────────────────┴──────────────────────────────┤
│ 底部固定操作：保存草稿 / 提交审核 / 通过 / 退回 / 发布         │
└────────────────────────────────────────────────────────────┘
```

左侧优先保障原文阅读空间，建议使用 `minmax(520px, 1fr) + 440~520px`，而不是完全固定 60%/40%。右侧编辑器保持稳定宽度，超宽屏时不无限拉伸表单。

### 7.3 顶部状态栏

展示：

- 规则编号；
- 所属规则组；
- 来源政策和版本；
- 编辑审核状态；
- 发布状态；
- 政策时效状态；
- 完整度；
- 阻断问题数量。

“审核通过”和“发布”必须是两个独立动作。发布按钮仅在通过所有发布前校验后可用。

### 7.4 左侧：政策原文与证据

#### 7.4.1 章节导航

- 使用政策节点路径还原章节树；
- 点击章节定位对应原文单元；
- 当前规则引用节点高亮；
- 支持展开前后 1～2 个相邻单元；
- 支持从当前证据返回完整政策文档。

#### 7.4.2 多证据展示

一条规则可以关联多个证据，不再依赖 `citations[0]`。每条证据具有明确角色：

| 证据角色 | 用途 |
|---|---|
| 主结论证据 | 支撑规则核心结论 |
| 适用条件证据 | 支撑人群、地区、场景等条件 |
| 数值证据 | 支撑金额、比例、区间等值 |
| 例外证据 | 支撑排除或特殊处理 |
| 有效期证据 | 支撑生效、失效或过渡期 |

建议证据锚点至少包含：

```text
document_version_id
unit_id
clause_path
page_no
exact_quote
start_offset
end_offset
anchor_hash
evidence_role
```

#### 7.4.3 字段—原文双向联动

- 点击右侧条件、结果、例外或有效期，左侧定位并高亮对应证据；
- 点击左侧高亮片段，右侧定位到关联字段；
- 一个字段可以关联多个证据；
- 修改规则字段后，将对应证据标记为“需复核”；
- 原文版本发生变化后，使用锚点哈希识别证据失效风险。

### 7.5 右侧：政策规则编辑器

#### 7.5.1 基础信息

- 规则标题；
- 业务主题；
- 规则类型；
- 所属规则组；
- 规则关系；
- 业务解释摘要。

#### 7.5.2 适用条件

条件采用结构化表达，而不是只保存标签：

```text
语义字段 + 操作符 + 标准值
```

示例：

| 语义字段 | 操作符 | 标准值 |
|---|---|---|
| 人员类别 | 等于 | 退休人员 `RETIRED` |
| 医疗类别 | 等于 | 住院 `INPATIENT` |
| 医院等级 | 等于 | 三级 `LEVEL_3` |
| 住院次序 | 大于等于 | 第二次 `SECOND` |

标准操作符包括：

```text
EQ / NE
IN / NOT_IN
GT / GE / LT / LE
BETWEEN
CONTAINS
EXISTS
ANY
```

必须区分：

| 状态 | 含义 |
|---|---|
| `ANY` | 政策明确对所有取值适用 |
| `UNKNOWN` | 当前数据没有取得有效值 |
| `NOT_APPLICABLE` | 该字段在当前业务场景不适用 |
| `NULL` | 数据缺失且原因未判定 |
| 条件不存在 | 政策没有设置该限制 |

#### 7.5.3 规则行为

规则行为根据规则类型动态展示：

| 规则类型 | 行为示例 |
|---|---|
| 固定值 | 返回固定金额或比例 |
| 比例计算 | 基数 × 比例 |
| 阶梯计算 | 根据区间执行不同结果 |
| 决策表 | 根据多个条件选择结果分支 |
| 资格判断 | 满足条件则具备或不具备资格 |
| 排除规则 | 满足条件则排除支付或处理范围 |
| 办理流程 | 返回办理步骤、材料和时限 |
| 解释规则 | 返回业务定义或解释文本 |

#### 7.5.4 规则结果和规则分支

简单规则使用单一结果编辑器；存在分档、分级、区间或组合条件时使用决策表编辑器。

结果字段至少包含：

```text
target_metric_code
value
value_role
data_type
unit
precision
formula / reference_metric
```

数值标准化示例：

- `85%`、`0.85`统一存储为同一比例值；
- `10万元`、`100000元`统一到标准单位；
- 页面保留原文表达，同时展示标准化结果；
- 金额和比例的边界、开闭区间必须显式保存。

#### 7.5.5 例外与补充

例外不能只保存为一段描述文本。能够结构化的例外应包含：

- 触发条件；
- 例外行为；
- 例外结果；
- 优先级；
- 证据锚点；
- 与主规则的关系。

暂时无法结构化的内容可以保留为补充说明，但应产生“待结构化”警告。

#### 7.5.6 生效范围

包括：

- 行政区划；
- 统筹区；
- 政策版本；
- 生效日期；
- 失效日期；
- 过渡期；
- 替代或被替代规则。

生效范围参与政策匹配，不能仅作为展示字段。

#### 7.5.7 机器可用性

不提供可以绕过校验的人工开关，改为系统推导的“运行准备度”：

```text
问答就绪：已满足
计算就绪：缺少计算基数
资格判断：不适用于当前规则类型
```

准备度由规则类型、必填字段、证据、语义映射、审核状态、发布状态和阻断问题共同决定。人工可以限制使用范围，但不能将未满足条件的规则强行标记为可用。

### 7.6 问题面板

详情页右上角展示当前规则的问题清单：

- 阻断问题：必须处理后才能审核或发布；
- 警告问题：允许带警告审核，但需要确认；
- 提示信息：不影响流程。

点击问题直接定位到对应字段或原文证据。

### 7.7 主操作

```text
保存草稿 / 提交审核 / 通过审核 / 退回修改 / 发布
```

更多操作：

```text
拆分规则 / 合并规则 / 重新抽取 / 忽略候选 / 撤回发布
```

拆分、合并或修改已审核规则时：

- 生成新版本；
- 保留原规则身份和版本关系；
- 记录变更原因；
- 使原审核结论失效；
- 已发布规则不能原地覆盖。

## 8. 语义映射抽屉

### 8.1 定位

语义映射抽屉只展示当前规则涉及的语义字段和映射情况，帮助审核人员确认：

> 政策中的字段、数据库中的字段以及用户表达，是否已经映射到同一个业务概念和标准值域。

抽屉不是完整语义资产管理页面。复杂配置可跳转到语义层对应的概念、指标、值域或映射详情页。

### 8.2 Tab 一：统一语义字段

展示当前政策字段映射到哪个统一语义字段：

```text
政策字段：psn_type
统一语义字段：person_type
业务概念：参保人员类型
值域：insured_person_type
数据类型：CODE
状态：已确认
```

系统提供候选映射和置信度，人工执行“确认、改绑、新建语义字段”。

### 8.3 Tab 二：标准值域映射

同屏展示多来源值向标准值的汇聚关系：

| 来源 | 原始字段或表达 | 原始值 | 标准值 |
|---|---|---|---|
| 政策原文 | `psn_type` | 退休人员 | `RETIRED` |
| 数据库 | `PER_TYPE` | 2 | `RETIRED` |
| 用户表达 | 自然语言 | 退休职工 | `RETIRED` |

支持：

- 确认已有标准值；
- 修改错误映射；
- 提交新标准值候选；
- 查看同义词和历史映射；
- 查看哪些数据库字段和政策规则正在使用该值。

### 8.4 Tab 三：数据来源与指标映射

展示统一业务语义如何从结构化数据中取得业务实际值，以及该规则可以解释哪些指标：

```text
统一语义字段：person_type
数据库字段：yb_zyjyxx.PER_TYPE
原始值映射：2 → RETIRED
取值方式：直接字段

统一指标：deductible_amount
数据库来源：yb_zyfdxx.qfje
政策规则结果：DEDUCTIBLE
标准单位：元
值角色：OBSERVED / POLICY_STANDARD
```

政策标准值和数据库实际值可以使用同一个指标编码、值域和单位体系，但必须保留 `value_role`、来源、业务时间和证据差异。

### 8.5 映射状态

每个字段的映射状态统一为：

```text
UNMAPPED / SUGGESTED / CONFIRMED / CONFLICT / INVALID
```

- AI 自动生成的结果只能进入 `SUGGESTED`；
- 审核人员确认后进入 `CONFIRMED`；
- 值域冲突或一对多歧义进入 `CONFLICT`；
- 来源字段失效或目标资产删除进入 `INVALID`。

关键条件字段和结果字段存在 `UNMAPPED`、`CONFLICT` 或 `INVALID` 时，应阻断发布。

## 9. 完整度、问题检测与发布校验

### 9.1 完整度按规则类型计算

不使用一套统一字段数量评分。不同规则类型使用不同必填模板：

| 规则类型 | 核心必填内容 |
|---|---|
| 固定标准 | 业务主题、适用条件、结果值、单位、有效期、证据 |
| 比例规则 | 计算对象、计算基数、比例、条件、证据 |
| 阶梯规则 | 分段条件、区间边界、各段结果、单位、证据 |
| 决策表 | 输入维度、分支条件、分支结果、默认分支或兜底说明 |
| 资格条件 | 主体、资格条件、判断结果、例外、证据 |
| 排除规则 | 排除对象、适用范围、排除结果、证据 |
| 办理流程 | 办理主体、前置条件、材料、步骤、时限、证据 |
| 解释规则 | 业务概念、解释内容、适用范围、证据 |

暂未建设的字段显示“尚未检测”，不直接按缺失记零分。

### 9.2 问题检测职责划分

#### 前端即时检测

- 当前表单必填项为空；
- 数值缺少单位；
- 区间上下界错误；
- 存在未保存修改；
- 当前字段未关联证据；
- 当前编辑值与标准数据类型不一致。

#### 后端治理检测

- 规则类型完整度；
- 条件是否缺失；
- 是否需要拆分或合并；
- 同版本规则重复或冲突；
- 跨版本替代关系；
- 政策效力和有效期冲突；
- 语义映射冲突；
- 是否满足审核和发布条件。

后端返回结构化问题列表，前端只负责展示、定位和处理，不在前端长期固化医保业务判断逻辑。

### 9.3 冲突检测边界

不能仅以“相同人员类型和医疗类别下结果不同”判断冲突。冲突检测至少考虑：

- 地区和统筹区；
- 政策版本和有效期；
- 完整适用条件；
- 规则优先级；
- 主规则和例外关系；
- 上位政策和下位政策；
- 新旧政策替代关系。

### 9.4 发布前阻断校验

发布前必须校验：

- 审核状态为已通过；
- 当前版本未发生审核后的修改；
- 规则类型必填字段完整；
- 主结论和关键条件具有证据；
- 关键语义字段完成映射；
- 标准值域不存在冲突；
- 有效期和地区范围明确；
- 不存在阻断问题；
- 已发布版本之间不存在未解决冲突。

## 10. 数据匹配设计

### 10.1 数据库结果标准化

数据库查询结果先通过字段映射和值域映射，形成标准化运行时上下文：

```json
{
  "target_concept": "DEDUCTIBLE",
  "context": {
    "person_type": "RETIRED",
    "insurance_type": "EMPLOYEE_MEDICAL",
    "medical_type": "INPATIENT",
    "hospital_level": "LEVEL_3",
    "admission_order": "SECOND"
  },
  "business_date": "2026-08-01",
  "region": "110000"
}
```

### 10.2 政策规则标准化

政策规则使用相同的语义字段和值域：

```json
{
  "target_concept": "DEDUCTIBLE",
  "conditions": [
    {"field": "person_type", "operator": "EQ", "value": "RETIRED"},
    {"field": "medical_type", "operator": "EQ", "value": "INPATIENT"},
    {"field": "hospital_level", "operator": "EQ", "value": "LEVEL_3"},
    {"field": "admission_order", "operator": "GE", "value": "SECOND"}
  ],
  "result": {
    "target_metric_code": "deductible_amount",
    "operation": "MULTIPLY",
    "reference_metric": "first_admission_deductible",
    "value": 0.5,
    "value_role": "POLICY_RATE"
  }
}
```

### 10.3 确定性匹配顺序

```text
1. 按目标业务概念召回候选规则；
2. 按地区、统筹区、政策版本和业务日期过滤；
3. 对标准化适用条件逐项执行操作符匹配；
4. 处理主规则、例外规则和优先级；
5. 返回政策结果、证据和匹配轨迹；
6. 向量检索仅补充解释材料，不决定最终适用规则。
```

知识页负责确保规则结构和语义映射正确；匹配执行效果由现有独立测试页验证。

## 12. 视觉与交互规范

### 12.1 信息层级

- 页面只保留一个蓝色主操作；
- 审核通过使用绿色状态，不将所有确认按钮都设为绿色；
- 阻断问题使用红色，警告使用琥珀色，提示使用灰蓝色；
- AI 置信度不占据主视觉；
- 语义编码作为辅助信息，业务中文名称作为主信息；
- 标签只用于摘要，复杂条件使用结构化表单或决策表。

### 12.2 状态色

| 状态 | 色彩建议 |
|---|---|
| 草稿、未发布 | 灰色 |
| 待审核、处理中 | 蓝色 |
| 需修改、存在警告 | 琥珀色 |
| 审核通过、已发布 | 绿色 |
| 阻断、映射冲突、已撤回 | 红色 |
| 已失效、已被替代 | 中性灰 |

政策失效是正常生命周期，不应默认显示为错误红色。

### 12.3 响应式设计

- 工作台在窄屏降为卡片列表；
- 详情页在中等屏幕支持原文区和编辑区切换；
- 移动端原文和规则编辑器纵向排列；
- 语义映射抽屉在移动端使用全屏模式；
- 复杂决策表优先保障横向滚动，不压缩字段到不可读。

### 12.4 空状态与降级

- 无有效期数据：显示“尚未识别”，不显示“缺失0分”；
- 无映射候选：允许提交新概念或标准值候选；
- 原文页码不可用：保留条款路径和段落锚点；
- 后端治理检测暂不可用：显示“尚未检测”，不由前端伪造确定结论；
- 历史版本不可用：隐藏对比入口，不展示不可操作占位按钮。

## 15. 验收标准

### 15.1 工作台

- 能按规则类型、来源、状态、有效期、映射状态和风险筛选；
- 能区分审核状态、发布状态和政策时效状态；
- 能显示阻断问题和警告问题；
- 批量通过不能绕过阻断校验；
- 点击规则可稳定进入独立详情页。

### 15.2 详情页

- 原文和规则结构可以同屏核验；
- 条件、结果、例外和有效期均可定位到具体证据；
- 支持一个规则中的多个分支；
- 支持同一条款产生多个关联规则；
- 修改审核通过的规则会产生新版本并使原审核结论失效；
- 审核通过与发布明确分离。

### 15.3 统一语义映射

- 政策字段和数据库字段能绑定同一语义字段；
- 政策文本值和数据库字典值能绑定同一标准值；
- 数值、比例和单位能够标准化；
- 同一指标能够区分政策标准值、数据库实际值和计算结果；
- 映射冲突能够被识别并阻断发布；
- 可以从当前规则查看其对应的数据字段、指标和值域关系。

### 15.4 治理与运行边界

- 前端只负责即时表单校验，业务完整度和发布校验由后端提供；
- 只有已审核、已发布、当前有效且无阻断问题的规则进入 Agent 运行时；
- 知识页不重复建设独立测试页已有能力；
- 向量检索不替代统一值域下的确定性政策匹配。

---

## 16. 最终取舍

本次改造保留以下结论：

1. 使用“知识工作台 + 知识详情页 + 语义映射抽屉”替代原三栏流水线；
2. 核心对象从孤立知识卡片升级为支持规则分支的政策规则单元；
3. 结构化业务数据与政策结构化字段统一业务概念、语义字段、标准值域、指标标识和单位；
4. 使用值角色区分政策标准值、数据库实际值、累计值和计算结果，不建设割裂的两套语义体系；
5. 审核、发布、政策时效和抽取处理状态分别管理；
6. 完整度按规则类型计算，发布阻断逻辑由后端治理服务提供；
7. 一条规则支持多证据及字段级证据锚点；
8. 专门测试能力继续保留在现有测试页，本次不扩展知识页测试功能。

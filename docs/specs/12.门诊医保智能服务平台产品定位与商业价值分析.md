# 第一章 产品定位重新思考（Why）

## 1.1 当前市场对于AI医疗产品存在两个误区

近年来，大模型的发展推动了医院智能客服、智能导诊、智能咨询等产品快速发展，但实际落地过程中，大多数产品都面临相同的问题：

* 患者仍然优先咨询人工；
* AI回答缺乏业务依据，医院不敢作为正式答复；
* 不同渠道（窗口、APP、公众号、自助机）重复建设，解释口径不一致；
* 通用大模型容易被替代，缺乏持续竞争力。

因此，仅以"AI聊天机器人"作为产品定位，很难形成医院愿意持续投入的产品价值。

---

## 1.2 我们重新定义产品

我们建议将产品定位由：

> 门诊医保智能助手

升级为：

> **门诊医保智能解释平台（Medicare Explain Platform）**

产品定位如下：

> 面向医院构建统一的医保解释能力中心，通过医保规则、语义层、政策知识库和智能解释引擎，将医保结算结果转换为患者能够理解、医院能够认可、医保能够追溯的标准化解释，并统一服务于患者端、窗口端、医院APP、公众号、自助机等多个渠道。

这里有一个非常重要的变化：

AI不再是产品。

**解释能力才是产品。**

# 第二章 为什么医院愿意购买（Business Value）

医院不会因为"AI很先进"而采购产品。

医院采购的原因通常来自四类价值：

* 提升患者满意度；
* 降低运营成本；
* 降低投诉风险；
* 满足监管要求。

因此，需要围绕医院的核心指标建立产品价值。

---

## 2.1 提升门诊服务效率

当前门诊医保咨询主要集中于收费完成后的复杂问题。

例如：

* 为什么这次个人支付金额这么高？
* 为什么同样的药这次不能报销？
* 为什么报销比例和上次不同？

这些问题通常需要工作人员跨系统查询、人工分析，平均耗时5～15分钟。

产品上线后，患者可先通过智能解释平台获得费用组成、待遇依据及政策说明，仅在复杂场景再进入人工咨询。

**价值体现：**

* 缩短患者等待时间；
* 减少窗口排队；
* 提升门诊服务效率。

---

## 2.2 降低窗口重复劳动

医保窗口每天大量咨询属于重复性解释。

例如：

* 起付线是什么？
* 为什么目录外不能报？
* 为什么基金支付比例不同？

这些问题本质上都是基于已有结算结果的解释，而不是人工判断。

统一解释平台可以承担重复解释工作，使窗口人员聚焦特殊和异常问题。

**价值体现：**

* 降低重复咨询工作量；
* 提高医保办工作效率；
* 降低人工培训成本。

---

## 2.3 提升患者满意度

患者投诉并不一定源于支付金额，而更多源于：

> **不知道为什么。**

智能解释平台提供：

* 金额来源；
* 医保规则；
* 政策依据；
* 办理建议。

帮助患者理解医保结算过程，降低因信息不透明导致的不满。

---

## 2.4 提高解释一致性

目前不同渠道的解释方式存在差异：

* 收费窗口；
* 医保办；
* 电话咨询；
* APP；
* 自助终端。

不同人员经验不同，解释口径容易不一致。

平台统一输出解释内容，可确保：

* 一次建设；
* 多渠道共享；
* 同一问题得到一致解释。

---

## 2.5 降低投诉处理成本

投诉处理中最困难的问题并不是回答患者，而是：

> 如何证明医院解释正确。

平台自动保存：

* 数据来源；
* 规则依据；
* 政策版本；
* 解释过程。

形成完整解释链路，为投诉处理提供依据。

# 第三章 为什么竞争对手难以替代（Competitive Advantage）

## 3.1 我们卖的不是大模型

通用大模型已经具备优秀的自然语言能力。

因此：

医院不会因为聊天能力采购产品。

真正不可替代的是：

> **医保专业知识和业务能力。**

---

## 3.2 平台核心竞争力

平台真正的能力包括：

### 医保语义层（Semantic Layer）

统一医保指标、业务概念、数据口径。

例如：

* 起付线；
* 基金支付；
* 目录内费用；
* 慢特病待遇。

---

### 医保规则中心（Rule Engine）

统一维护医保规则。

例如：

* 起付线规则；
* 支付比例规则；
* 人员待遇规则。

---

### 医保政策中心（Policy Center）

建立政策知识库：

* 国家政策；
* 北京政策；
* 医院实施细则。

实现政策版本管理。

---

### 医保解释引擎（Explain Engine）

这是平台最核心的能力。

输入：

结构化医保结算结果。

输出：

患者能够理解的自然语言解释。

例如：

> 您本次个人支付较高，主要原因是部分费用属于医保目录外项目，同时本年度起付线尚未全部满足，因此基金支付比例较低。

解释内容来源于真实数据，而非AI推测。

---

### AI Agent

AI负责：

* 理解患者问题；
* 调用解释能力；
* 组织自然语言。

AI本身不是核心资产，而是能力入口。

# 第七章 产品边界

为了保证医院可上线、可审计、可追责，平台坚持以下原则：

| 原则      | 说明                |
| ------- | ----------------- |
| 只解释真实数据 | 不生成虚假业务数据         |
| 只解释已有结算 | 不预测未来待遇           |
| 规则优先    | 业务规则由规则引擎执行       |
| 模型辅助    | LLM负责理解和表达        |
| 全过程留痕   | 数据来源、规则版本、政策依据可追溯 |

# 第八章 产品战略定位

我们最终建议将产品定位确定为：

> **医保智能解释平台（Medicare Explain Platform）**

它不是一个聊天机器人，而是医院医保解释能力中心。

平台以语义层、规则中心、政策中心和解释引擎为核心，通过统一的能力服务患者端、窗口端、医院APP、自助终端及客服热线，实现医保解释能力标准化、平台化和可复用。

# 我认为还需要补一份决定成败的文档

到这里，我反而认为**PRD还不是第一优先级**。

下一份文档建议写：

> **《医院采购价值分析（Hospital Value Proposition）》**

这份文档不讲技术，而回答采购委员会最关心的几个问题：

1. **医院为什么现在需要建设这个平台，而不是继续用人工？**
2. **与DeepSeek、豆包、腾讯元宝相比，医院为什么要采购这套产品？**
3. **它每年能为医院减少多少咨询压力、降低多少投诉、提升多少满意度？**
4. **为什么这是一套可以复制到所有医院的标准产品，而不是一次性定制项目？**

如果这四个问题回答得足够扎实，产品的商业价值就建立起来了；后面的PRD和技术架构，就是在实现这个价值，而不是单纯堆砌AI功能。

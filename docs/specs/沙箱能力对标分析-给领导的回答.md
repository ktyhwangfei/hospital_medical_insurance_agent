# 医保新平台 AI 框架 — 沙箱能力现状与建设建议

> **背景**：领导问"医保新平台 AI 框架平台中考虑实现各种沙箱功能？"
> **参考来源**：`docs/research/医保基金监管Agent系统架构与沙箱技术应用说明_原文整理.docx`
> **分析对象**：当前院端医保智能体产品
> **分析日期**：2026-07-08

---

## 一、先澄清：参考文档的沙箱 vs 我们的产品定位

参考文档描述的是**医保基金监管 Agent**（政府/监管方视角，面向海量结算数据的违规识别），定义了 5 种沙箱。我们的产品是**院端医保智能体**（医院侧，面向患者/医生/收费员/医保办的导办与解释）。两者定位不同，但**沙箱的核心思想完全适用**——控制 Agent/模型/脚本/外部调用的执行边界。

---

## 二、5 种沙箱 vs 当前产品能力 —— 一句话总结

| 沙箱类型 | 参考文档定义 | 当前产品已有 | 差距 | 优先级 |
|---------|-------------|:--:|------|:--:|
| **1. Agent 执行沙箱** | 控制 Agent 生成的 SQL/脚本执行边界 | 🟡 部分 | 缺资源隔离、脚本执行沙箱 | 🔴 高 |
| **2. 数据查询沙箱** | 控制数据访问范围、字段、行数 | 🟡 部分 | 缺查询行限制、字段级精细管控 | 🔴 高 |
| **3. 模型调用沙箱** | 防止敏感数据进入 LLM | 🟡 部分 | 脱敏能力弱、缺提示词安全审查 | 🔴 高 |
| **4. 规则调试沙箱** | 新规则上线前历史数据回放验证 | ❌ 无 | 全新能力 | 🟡 中 |
| **5. 外部合作沙箱** | 外部算法在沙箱运行，结果审核后出域 | ❌ 无 | 全新能力 | 🟢 低 |

---

## 三、逐项展开 —— 已有 vs 差距 vs 建议

### 1. Agent 执行沙箱（当前最紧迫）

**参考文档要点**：
> Agent 可能自动生成 SQL、Python、规则脚本 → 不能让 Agent 直接连生产库 → 需要只读权限、禁止生产库访问、限制 CPU/内存/时长、记录全部日志。

**当前产品已有**：

| 能力 | 实现位置 | 状态 |
|------|---------|:--:|
| 高风险动作拦截（退费/冲正/病案修改等） | `security/risk_control/service.py` → L0(DB规则)+L1(硬编码) | ✅ |
| 角色权限校验（5 角色 × 场景） | `security/authorization/service.py` → `visible_fields_for(role)` | ✅ |
| 全链路审计日志 | `gateway/access_log/` + `runtime/api/middleware.py` GatewayAuditMiddleware | ✅ |
| 请求安全校验 | `gateway/request_guard/` | ⚪ 空壳 |
| 限流熔断 | `gateway/rate_limiter/` | ⚪ 空壳 |
| MCP 工具安全边界校验 | `knowledge_extension/mcp_registry/` + 风险等级 + 角色权限 | ✅ |
| 适配器隔离（外部系统通过 Protocol 封装） | `adapters/base/service.py` → ports/adapter 模式 | ✅ |

**关键差距**：
- 没有 **Agent 脚本执行沙箱**（当前 Agent 不会自动生成 SQL/Python，但 LangGraph 编排中 workflow 步骤的执行没有资源隔离）
- `request_guard` 和 `rate_limiter` 是空目录，没有实现
- 没有 CPU/内存/执行时长的硬限制机制

**建设建议**（对领导的回答）：
> "Agent 执行沙箱方面，我们已经实现了**三层防线**（鉴权 → 脱敏 → 高风险拦截），全链路审计也记录每次 AI 交互。当前差距主要是**缺少 Agent 自动生成脚本时的执行资源隔离**（CPU/内存/时长限制），以及网关层的请求校验和限流还未实现。这在我们当前阶段（Agent 不自动生成 SQL/脚本）风险可控，后续随编排复杂度提升再补。"

---

### 2. 数据查询沙箱

**参考文档要点**：
> 控制表访问范围、字段访问范围、查询条件、返回记录数、是否允许查看个人字段、是否允许下载结果。普通筛查只返回聚合指标，不返回个人标识。

**当前产品已有**：

| 能力 | 实现位置 | 状态 |
|------|---------|:--:|
| 角色字段可见性 | `authorization/service.py` → `visible_fields_for(role)` | ✅ |
| 敏感数据访问策略 | `security_policy/models.py` → DEFAULT_SENSITIVE_DATA_POLICY | ✅ |
| 外部系统防腐层（适配器封装） | `adapters/` 7 个内存适配器 + base 基类 | ✅ |
| 脱敏输出 | `desensitization/service.py` → `mask_name()` | 🟡 仅姓名 |

**关键差距**：
- 适配器当前全部为**内存实现**，未对接真实 HIS/EMR/收费系统 → 没有真实的查询边界控制
- 没有**查询返回行数限制**（对 Agent 发起的查询没有 `LIMIT` 强制干预）
- 没有**字段级精细脱敏**（当前只脱敏姓名，缺少身份证/手机号/住址）
- 没有**查询结果下载控制**

**建设建议**（对领导的回答）：
> "数据查询沙箱的核心思想——'Agent 不能直接访问生产库'——我们已经通过**适配器防腐层**（adapters/）实现了接口隔离，Agent 不直连 HIS/EMR。角色字段可见性也已落地。当前主要差距是**脱敏粒度不够**（只做了姓名脱敏）和**查询行级限制**未实现。建议在适配器对接真实系统时同步补齐。"

---

### 3. 模型调用沙箱

**参考文档要点**：
> 原始数据 → 脱敏/摘要/聚合 → 模型调用沙箱 → 大模型分析 → 结果审查。调用前做去标识化、字段脱敏、最小必要数据、提示词安全检查。

**当前产品已有**：

| 能力 | 实现位置 | 状态 |
|------|---------|:--:|
| 统一模型网关（防止裸调 HTTP） | `model_service/gateway/` → 路由策略 + OpenAI 兼容 Provider | ✅ |
| 模型异常分类 | `model_service/exceptions/` → 错误码体系 | ✅ |
| 模型路由降级 | `model_service/router/` → type+scene 路由 | ✅ |
| PII 脱敏 | `desensitization/service.py` → `mask_name()` | 🟡 仅姓名 |
| SSE 流式输出控制 | `runtime/api/` → done 事件标志 | ✅ |

**关键差距**：
- **脱敏能力严重不足**：只脱敏姓名（`name[0] + '**'`），没有身份证/手机号/住址/医保卡号/银行卡号的脱敏
- **没有提示词安全审查**：没有检查 prompt 中是否夹带了敏感信息
- **没有模型输出敏感信息扫描**：没有对 LLM 返回内容做敏感信息回溯检查
- **没有模型调用前的"最小必要数据"筛选**：当前是把上下文直接组装进 prompt，没有做数据最小化

**建设建议**（对领导的回答）：
> "模型调用沙箱是我们**当前最薄弱的环节**。模型网关已经统一了调用入口和路由，但**进入模型之前的数据脱敏只覆盖了姓名**，身份证/手机号/医保卡号等敏感字段的脱敏还没做。建议优先补齐 PII 脱敏能力（扩展 `desensitization/service.py`），再做提示词安全审查和模型输出敏感信息回溯检查。这在我们对接真实患者数据前必须完成。"

---

### 4. 规则调试沙箱

**参考文档要点**：
> 新规则 → 历史数据回放 → 沙箱验证 → 误报率/命中率评估 → 人工确认 → 正式上线。

**当前产品已有**：❌ 无

**建设建议**（对领导的回答）：
> "规则调试沙箱在我们当前阶段**非刚需**，因为我们的规则体系（政策知识库 + Skill 脚本）还在初始化阶段，规则变更频率不高。但架构上可以先预留接口，等政策规则量上来之后再建——比如新的医保政策生效前，在沙箱中用历史问答数据验证规则准确率。"

---

### 5. 外部合作沙箱

**参考文档要点**：
> 数据不出域、算法进沙箱、结果经审核后出域。适用于商业保险合作、第三方模型服务、科研分析。

**当前产品已有**：❌ 无

**建设建议**（对领导的回答）：
> "外部合作沙箱在我们当前院端部署场景下**暂不需要**。我们的定位是医院内部使用，不涉及外部算法提交或第三方模型合作。如果后续平台从院端扩展到卫健委/医保局的多机构协作场景，再考虑建设。"

---

## 四、总结：给领导的回答框架

### 一句话结论

> **"沙箱理念我们已经在践行——安全三层防线（鉴权+脱敏+高风险拦截）、模型调用网关、适配器防腐层都是沙箱思想的具体落地。按基金监管文档的 5 类沙箱对标：Agent 执行沙箱和数据查询沙箱已有基础框架，模型调用沙箱的脱敏能力需立即补齐，规则调试和外部合作沙箱暂非当前阶段刚需。"**

### 对标表格（汇报用）

| 沙箱类型 | 成熟度 | 核心已有 | 核心差距 | 建议阶段 |
|---------|:--:|------|------|:--:|
| Agent 执行沙箱 | 🟡 40% | 高风险拦截 + 角色权限 + 全链路审计 | 脚本执行隔离、资源限制 | Phase 1 补齐 |
| 数据查询沙箱 | 🟡 35% | 适配器防腐层 + 字段可见性 | 脱敏粒度、查询行限制 | Phase 1 补齐 |
| 模型调用沙箱 | 🟡 25% | 模型网关统一入口 | **PII 全面脱敏**（最紧迫） | 🔴 立即补齐 |
| 规则调试沙箱 | ⚪ 0% | — | 全新建 | Phase 2 |
| 外部合作沙箱 | ⚪ 0% | — | 全新建 | Phase 3 |

### 路线建议

```
立即（本周）:
  └─ 模型调用沙箱：扩展 desensitization/service.py
     → 增加身份证/手机号/医保卡号/银行卡号脱敏
     → 在 model_service/gateway 调用前加脱敏检查点

Phase 1（本月）:
  ├─ Agent 执行沙箱：实现 gateway/request_guard + rate_limiter
  └─ 数据查询沙箱：适配器层加查询行限制

Phase 2（下月）:
  └─ 规则调试沙箱：政策规则变更验证流程

Phase 3（远期）:
  └─ 外部合作沙箱：多机构协作场景
```

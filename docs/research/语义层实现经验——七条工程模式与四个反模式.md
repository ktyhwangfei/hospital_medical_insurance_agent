## 一、七条工程模式（跑通了，可复用）

### 模式 1：DSL → 执行器 的严格分离

> 对应原文："中间那层 DSL 就是语义层，它把指标的定义、维度、计算逻辑预先封装好了。Agent 查 Q3 毛利率不需要知道底层 SQL 怎么写。"

本项目的落地方式：

```
DSL 层（What）           执行器层（How）
─────────────────       ─────────────────
IndicatorDefinition  →   MetricDataQueryService（取数）
  （静态元数据）         FormulaEvaluator（计算）
SemanticRegistry     →   BusinessFactsBuilder（组装+标准化）
  （映射关系）           SemanticNormalizer（值域归一）
```

**关键代码证据**：
- `src/domain/indicator/models.py` 的 `IndicatorDefinition` 是纯数据模型，不含任何"怎么取数"的逻辑
- `src/semantic_layer/formula_evaluator.py` 只负责"给定公式+变量值，算出结果"，不关心公式从哪来
- `src/semantic_layer/builder.py` 的 `BusinessFactsBuilder` 只负责"按 Registry 映射取数+标准化"，不持有任何指标定义

**为什么有效**：DSL 层可以被业务人员 review（它只是 YAML/JSON），执行器层可以被工程师优化（它是纯函数），两者互不污染。这是用户说的"语义层把脑子里的东西写出来"的工程化体现。

**可复用结论**：任何语义层建设，第一刀切下去就是"把定义（What）和执行（How）拆成两个不互相 import 的模块"。本项目这条做得对。

### 模式 2：AST 白名单求值器（安全的公式计算）

> 对应原文："模型用了什么算法？输入输出的语义是什么？"

派生指标（Derived Metric）的计算公式必须能被安全求值。本项目的做法值得作为标准模式：

**反例（不要这样）**：
```python
result = eval(formula.expression, {}, values)  # ❌ 任意代码执行风险
```

**本项目做法**（`src/semantic_layer/formula_evaluator.py`）：
```python
def _eval_node(self, node, values):
    if isinstance(node, ast.Constant):       # 白名单 1：数字字面量
        return float(node.value)
    if isinstance(node, ast.Name):           # 白名单 2：变量引用
        return float(values[node.id])
    if isinstance(node, ast.BinOp):          # 白名单 3：算术运算
        return _BIN_OPS[type(node.op)](self._eval_node(node.left), ...)
    if isinstance(node, ast.UnaryOp):        # 白名单 4：一元正负
        ...
    raise ValueError(f"不支持的 AST 节点类型: {type(node).__name__}")
```

**三个工程细节值得抄**：
1. **白名单**：只允许 `Constant / Name / BinOp / UnaryOp / Expression` 五种 AST 节点，其他全部抛错。函数调用、属性访问、订阅统统禁掉。
2. **`lru_cache(maxsize=256)`** 编译表达式：同一公式只 parse 一次，热路径性能优化。
3. **依赖前置校验**（`_validate_dependencies`）：求值前先检查所有 `dependencies` 都在 `values` 里，给出清晰的错误信息（"公式需要 [a,b]，已提供 [a]"）。

**可复用结论**：语义层里的公式求值，永远用 AST 白名单，永远不用 `eval`。医保的"统筹范围内费用 = 总费用 - 自费 - 乙类先行自付"这种公式，这个模式足够了。条件表达式（`CASE WHEN`）再扩展，但白名单原则不变。

### 模式 3：值域映射从 SQL CASE 收敛到语义层

> 对应原文："词表规范，同义词、近义词、歧义词。"

这是本项目最扎实的一条实现经验，也是最值得抄的迁移路径。

**起点（问题）**：医保系统的码值转换散落在 SQL `CASE` 语句里：
```sql
-- business_sql.yaml 里原本是这样的
CASE a.FUND_TYPE
  WHEN '3' THEN '城镇职工'
  WHEN '4' THEN '工伤保险'
  WHEN '31' THEN '离休统筹' ...
END
```

**终点（方案）**：`src/semantic_layer/seed.py` 把这些 CASE 声明式地搬进语义层值域：
```python
_YB_DICTIONARY_MAPPINGS = {
    "FUND_TYPE": {"3": "城镇职工", "4": "工伤保险", "31": "离休统筹", ...},
    "YLLB": {"11": "普通门诊", "12": "急诊", "21": "普通住院", ...},
    "PERSON_TYPE": {"1": "在职人员", "2": "退休人员", ...},
}

def ensure_yb_dictionary_mappings(store):
    """幂等 ensure：把医保字典码→标签映射补入语义层值域。"""
    ...
```

`seed.py` 的注释写得非常诚实：
> "将散落在 SQL CASE 里的码→标签映射，声明式收敛进语义层值域。语义层成为码→标签转换的唯一真源，business_sql.yaml 退役后此处保留。"

**为什么这是好模式**：
1. **单一真源**：`FUND_TYPE='3'` → `'城镇职工'` 这个映射，整个系统只有一处定义
2. **可测试**：值域是数据，可以单独写表驱动测试
3. **可治理**：映射变更走 Registry 的版本管理，不再埋在 SQL 里
4. **幂等**：`ensure_*` 函数每次启动 upsert，安全重复执行

**可复用结论**：迁移到语义层时，第一步不是建模，是"把现存的码值转换逻辑（SQL CASE、Python dict、Excel 字典）全部收口到 ValueDomain + ValueDomainMapping"。这一步做完，语义层就已经"活"了。

### 模式 4：指标依赖的递归解析

> 对应原文："agent 要做归因分析……每一步都是 agent 在调用不同的工具。"

派生指标依赖基础指标，查询时必须把依赖展开。本项目的 `resolve_dependencies` 是教科书式的递归实现：

```python
def resolve_dependencies(self, indicator_ids):
    result, seen = [], set()
    def _add_with_deps(ind_id):
        if ind_id in seen: return      # 防环
        seen.add(ind_id)
        definition = registry.get(ind_id)
        if definition and definition.depends_on:
            for dep_id in definition.depends_on:
                _add_with_deps(dep_id) # 先加依赖
        result.append(ind_id)          # 后加自己（拓扑序）
    for ind_id in indicator_ids:
        _add_with_deps(ind_id)
    return result
```

**三个细节**：
1. **`seen` 集合防环**：避免循环依赖导致死递归
2. **拓扑序**：先递归加依赖，后加自己，保证 `values` 字典里依赖项先就绪
3. **去重 + 保序**：用 `seen` 去重，用 `result.append` 保插入顺序

**可复用结论**：派生指标的依赖必须显式声明（`depends_on` 字段），运行时递归展开。`FormulaEvaluator` 求值前调一次 `resolve_dependencies`，保证所有 `dependencies` 都已取值。

### 模式 5：LLM 可读化生成器（语义层 → 提示词）

> 对应原文："语义层让 AI 读懂数据。"

这条直接回答"语义层怎么让 LLM 用上"。`src/semantic_layer/llm_readable.py` 提供了三个生成器：

| 方法 | 用途 | 输出示例 |
|------|------|---------|
| `generate_available_indicators()` | 告诉 LLM 系统有哪些指标 | "当前可用指标 (共 19 个): 维度指标: insu_type 险种类别... 数值指标: deductible_amount 起付金额 (单位: 元)" |
| `generate_indicator_summary(ctx)` | 告诉 LLM 当前取值 | "患者 P001 的指标取值: 起付金额: 650元 (来源: SQL查询, 置信度: 1.0)" |
| `generate_policy_context(ctx)` | 政策检索前缀 | "【患者医保政策查询上下文】险种类别: 城镇职工 医院等级: 三级医院..." |

**工程细节**：
- 按 `category`（dimension / numeric / condition / meta）分组展示，符合 LLM 的认知组织方式
- 每个值带**来源**和**置信度**——这正是原文强调的"来源可追溯"
- `_format_value` 处理 float 显示（`650.0` → `650元`），避免提示词里出现 `650.0元` 这种 LLM 困惑的格式

**可复用结论**：语义层不能只是数据结构，必须有"翻译成 LLM 可读文本"的生成器。三个粒度（系统有哪些 / 当前是什么 / 检索前缀）覆盖了大多数提示词注入场景。

### 模式 6：Ports/Adapter 隔离数据源

> 对应原文："builder 不直连数据库……通过适配器层。"

`src/semantic_layer/builder.py` 的取数路径严格遵守防腐层纪律：

```
Builder
  → 查 Registry: Metric.deductible → source_object="InsuranceTransaction"
  → source_adapter_port="InsuranceInterfacePort"
  → 调适配器 Protocol: InsuranceInterfacePort.get_transaction(ctx)
  → 取领域模型属性: InsuranceTransaction.deductible
```

**关键代码**（`builder.py`）：
```python
adapter = self._adapter_builders.get(port)
if adapter is None:
    warnings.append(f"Adapter '{port}' not available")
    continue
adapter_data = self._call_adapter(adapter, port, request.context)
```

Builder 永远不 `import` 数据库驱动，永远不写 SQL，永远只通过 `adapters/ports/` 的 Protocol 拿数据。这意味着：换数据源（SQL Server → Milvus → 内存 mock）只改适配器实现，语义层一行代码不动。

**可复用结论**：语义层的"数据层（L3）"映射必须是逻辑映射（指向领域模型属性名 `source_field`），不是物理映射（指向数据库列名）。本项目把数据库细节留在适配器内部，这是正确的。

---

### 模式 7：幂等种子 + 首启动初始化

> 对应原文："智能中台是长出来的，不是一次设计出来的。"

`seed.py` 的 `ensure_yb_dictionary_mappings(store)` 是幂等的——每次进程启动调一次，已存在的映射 upsert，不重复插入。`PostgresRegistryStore._seed_if_empty` 在首次启动时用这份数据初始化空库。

**为什么重要**：语义资产是"长"出来的，意味着每次部署都可能带来新的映射。幂等 ensure 保证：
- 开发环境（内存存储）和测试环境每次启动都有一致的基础数据
- 生产环境首次部署自动初始化，不需要手动跑 SQL
- 后续 `ensure_*` 函数增量补数据时，不影响已有数据

**可复用结论**：语义层的所有种子数据用"幂等 ensure 函数"提供，不要用一次性 migration 脚本。前者支持增量演进，后者只支持一次性初始化。

## 二、四个反模式（踩过的坑，要规避）

### 反模式 1：两套语义注册表并存

**现象**：本项目当前同时存在两套语义层实现：

| 实现 A（domain/indicator 系） | 实现 B（semantic_layer/models 系） |
|------------------------------|-----------------------------------|
| `src/domain/indicator/models.py`：`IndicatorDefinition`、`IndicatorValue` | `src/semantic_layer/models.py`：`Metric`、`BusinessObject`、`ValueDomain` |
| `src/semantic_layer/registry.py`：`IndicatorRegistry`（扫 YAML） | `src/semantic_layer/registry.py`：`SemanticRegistry` + `RegistryStore`（PostgreSQL） |
| `indicators/*.yaml` 驱动 | `seed.py` 驱动 |
| 编码：`pooling_pay`、`deductible_amount` | 编码：`zydyxx.*`（物理码） |

`seed.py` 的注释已经承认了这个分裂：
> "编码与 skill_manifest.yaml 的 needed_objects 一致（zydyxx.* 物理编码），是 skill 依赖的唯一真源。**旧 Settlement.* 编码已废弃。**"

**后果**：
- 同一个"起付线"概念，在 A 系叫 `deductible_amount`，在 B 系叫 `Settlement.*`（已废弃）或某个 `zydyxx.*` 物理码
- 维护者要同时理解两套模型，认知负担翻倍

**根因**：v3 设计文档（A 系）和 v1.0 规范（B 系）是两批人/两个阶段设计的，落地时没有强制收敛到一套。

**🔧 已修正（2026-07-23）**：初版曾建议"把 A 系 `IndicatorRegistry` 降级为只读视图或彻底删除"。**这个建议是错的**——P0 验证发现 A 系 `IndicatorRegistry`（`registry.py` 的 `get_registry()`）和 B 系 `SemanticRegistry`（`get_semantic_registry()`）**都是活的**：
- B 系服务于 runtime（`scenario_executor`、`semantic_routes`、`policy_qa` 经 `settlement_bridge`）
- A 系服务于 `skills/settlement_explain_skill/`（`strategies/semantic_utils.py` 懒加载 `get_registry()` 做维度提取）

因此"双注册表"**不能靠删除收敛**。真正的修正方向是：先把 `skills/settlement_explain_skill/` 从 A 系引擎解耦（`semantic_utils.py` 改为从 B 系 `SemanticRegistry` 取维度），再退役 A 系。这是个独立的最小可验证单元，不是"删死代码"。

### 反模式 2：意图→指标映射硬编码

> 🔧 **已修正（2026-07-23）**：`resolver.py` 经全项目 grep 确认零引用，已作为死代码删除。本反模式作为"教训记录"保留——若未来重新引入意图→指标解析，切勿重蹈硬编码覆辙。

**现象**：~~`src/semantic_layer/resolver.py`~~（已删除）曾用两个类变量硬编码映射：

```python
class IndicatorResolver:
    INTENT_INDICATOR_MAP = {           # 意图 → 指标（硬编码）
        "policy_explanation": ["deductible_amount", "in_scope_total", ...],
        "settlement_anomaly": ["error_code", "settlement_status", ...],
    }
    ENTITY_INDICATOR_MAP = {           # 实体词 → 指标（硬编码）
        "统筹自付": "pooling_self_pay",
        "起付线": "deductible_amount",
        "门槛费": "deductible_amount",  # 同义词
        ...
    }
```

文件 docstring 自己都承认问题：
> "当前实现基于硬编码的意图→指标映射，**后续可从 skill 注册表动态发现**。"

**后果**：
- 新增一个业务场景（如"DRG 分组解释"），要改 `resolver.py` 的 Python 代码并重新部署
- `ENTITY_INDICATOR_MAP` 的同义词（"起付线/起付金额/门槛费"）和 `indicators/dictionaries/` 里的字典是两套数据，改一处漏一处
- 这正是原文批评的"规范散落在代码里"

**修正方向**：意图→指标的映射应该由 Skill 的 `skill_manifest.yaml` 声明（Skill 声明它需要哪些 Object + Metric），Resolver 从 SkillRegistry 动态聚合，而不是在 Resolver 里写死。同义词应该统一进 `ValueDomain`/`SemanticMapping`，让 Resolver 查询而非硬编码。

### 反模式 3：三个标准化器并存 + 一个空外观

**现象**：`src/semantic_layer/normalizer.py` 的 `SemanticNormalizer` 定位是"统一入口，外观模式"，docstring 写：
> "后续 Phase 将逐步整合：DictionaryNormalizer、McpResultNormalizer、SemanticMapper。"

但实际状态是：四个标准化器同时存在，`SemanticNormalizer` 只是又加了一个实现，并没有真正整合旧的三个。

**后果**：
- 同一个字段标准化逻辑可能在四处实现
- "外观模式"如果只是新增一层而不替代底层，就只是又增加了一层间接
- 原文批评的"同一个映射存在三处"在这个项目里真实发生了

**修正方向**：外观模式的正确做法是"先建外观，旧实现逐步 thin-ify 成纯委托，最后删除"。本项目停在了第一步。需要补一个收敛 milestone：让 `DictionaryNormalizer`、`McpResultNormalizer`、`SemanticMapper` 全部变成 `SemanticNormalizer` 的薄委托，逻辑收归一处。

---

### 反模式 4：Builder 的 "default" 端口兜底

**现象**：`src/semantic_layer/builder.py`：
```python
port = metric.source_adapter_port or "default"
if port not in adapter_builders:
    warnings.append(f"Adapter '{port}' not available for {object_code}")
    continue
```

当 `source_adapter_port` 为空时，默认用 `"default"` 端口。

**后果**：
- 一个没填 `source_adapter_port` 的指标，会悄悄走到 `"default"` 适配器，可能拿到错误来源的数据
- 这种兜底在生产环境是隐患——失败应该早暴露（fail fast），而不是悄悄降级
- 违反了原文"数据来源可追溯"原则：一个指标连"从哪取数"都没声明清楚，却还能出结果

**✅ 已修复（P0-3，2026-07-23）**：`builder.py` 已删除 `or "default"` 兜底，改为空 `source_adapter_port` 时精确告警（`Metric '...' has no source_adapter_port configured, skipped`）并跳过。回归测试见 `src/tests/unit/semantic_layer/test_builder.py::test_metric_without_source_adapter_port_warns_not_routes_to_default`。

## 四、给后来者的五条实操建议

把所有经验浓缩成五条可执行的建议：

### 建议 1：先收口码值，再建模

不要一上来就设计 L1/L2/L3 三层模型。第一步是**把现存的 SQL CASE、Python dict、Excel 字典全部搬进 ValueDomain**（模式 3）。这一步做完，语义层就活了，AI 查出来的数据已经带中文标签。三层模型是给"跨领域分析"准备的，初期用不上。

### 建议 2：AST 白名单求值，永远不用 eval

派生指标公式求值，必须用 `formula_evaluator.py` 那套 AST 白名单。这不是过度设计——医保公式里混入恶意表达式（即使是误操作）的代价远大于多写 50 行代码。

### 建议 3：意图→指标映射必须从 Skill 声明动态发现，禁止硬编码

`INTENT_INDICATOR_MAP` 这种硬编码是技术债的开端。Skill 声明 `needed_objects`，Resolver 动态聚合，这样加场景不用改 Resolver。

### 建议 4：外观模式必须配合旧实现的收敛

建 `SemanticNormalizer` 外观的同时，必须排期让 `DictionaryNormalizer`/`McpResultNormalizer`/`SemanticMapper` 变成薄委托。只建外观不收敛，就是又加一层壳。

### 建议 5：单注册表原则——但收敛前先解耦消费方

本项目最大的实现教训就是两套注册表并存。任何语义层建设，上线前必须强制 review：是否只有一个 `Registry`？指标编码是否只有一套？

🔧 **已修正（2026-07-23）**：初版建议"先收敛再说"过于轻松。P0 验证发现两套注册表**都有活消费方**（A 系→skills/，B 系→runtime），所以"收敛"的前置工作是**先解耦消费方**：把 `skills/settlement_explain_skill/` 从 A 系 `get_registry`/`llm_readable`/`normalizer` 迁移到 B 系 `SemanticRegistry`，确认零引用后才能退役 A 系。跳过解耦直接删 A 系，会让 settlement_explain_skill 崩。

## 五、一句话总结

> **语义层的实现经验不在"设计了什么模型"，而在"把散落在 SQL CASE、Python dict、人脑里的东西，收口成单一真源、安全求值、动态解析、LLM 可读的工程实践"。**
>
> 本项目跑通了收口（模式 3）、求值（模式 2）、解析（模式 4）、可读（模式 5），但卡在了注册表分裂（反模式 1）、硬编码（反模式 2）、外观未收敛（反模式 3）。
>
> 下一步的重心不是"加更多指标"，是"收敛成一套注册表 + 把查询能力暴露成 MCP 工具 + 跑通一个完整场景"。模型会贬值，这套工程实践和收口后的语义资产只会增值。

# 分阶段实施建议

> 日期: 2026-07-31 | 版本: 1.0

---

## 阶段总览

```
Phase 0（今天）    — 最小原型：Skill 单元测试落地，不依赖任何外部服务
Phase 1（本周）    — 评估框架：检索评估框架搭建 + 标注 query 集
Phase 2（本月）    — 完整落地：回归测试 + 基线管理 + 性能基准
Phase 3（远期）    — 深度质量：人工标注 + 输出质量 LLM-as-Judge
```

## Phase 0 — 今天就能做的（最小原型）

### 0.1 Skill 功能正确性测试（T1 单元）

**目标**：新建 `src/tests/unit/skills/`，写 4 个核心测试文件。

**可行原因**：
- 复用 `test_strategies.py` 已有的 `settlement_context` + `mock_evidence` fixtures
- 不依赖 FastAPI / Milvus / MCP / SQL Server
- 与 `src/tests/unit/shared/skills/` 互补（那个测 SkillLoader，这个测 Strategy）

**文件清单**：

| 文件 | 测什么 | 预计测试数 |
|------|--------|:--:|
| `src/tests/unit/skills/conftest.py` | shared fixtures | — |
| `src/tests/unit/skills/test_skill_functional.py` | 6 种 strategy execute() 冒烟 + 输出完整性 | ~15 |
| `src/tests/unit/skills/test_skill_robustness.py` | 零证据/空证据/缺失字段/极端值 | ~12 |
| `src/tests/unit/skills/test_skill_capability_alignment.py` | manifest 白名单 + 关键词覆盖 | ~5 |

**命令**：
```bash
python -m pytest src/tests/unit/skills/ -v
```

### 0.2 检索评估框架骨架

**目标**：创建 `src/tests/evaluation/` 目录，写入 `eval_metrics.py` + `eval_queries.yaml`。

**可行原因**：
- `eval_metrics.py` 是纯 Python 函数，不需外部依赖
- `eval_queries.yaml` 是静态数据文件
- 暂不运行（需要 Milvus），只搭架子

**文件清单**：

| 文件 | 内容 |
|------|------|
| `src/tests/evaluation/__init__.py` | 空文件 |
| `src/tests/evaluation/eval_metrics.py` | recall_at_k, mrr, hit_at_k, evaluate_all |

| `src/tests/evaluation/test_retrieval_quality.py` | 检索质量评估（标记 xfail 或 skip，等 Milvus 就绪） |

## Phase 1 — 本周（需要基础设施就绪）

### 1.1 检索质量评估运行

**前置条件**：Milvus 运行（`127.0.0.1:19530`）+ `policy_rules_v2` 数据已就绪（337 rules）。

**执行**：
```bash
# 首次：生成基线
python -m pytest src/tests/evaluation/test_retrieval_quality.py -v

# 保存基线
python -m pytest src/tests/evaluation/test_retrieval_quality.py -v --eval-save-baseline
```

**产出**：
- 首次 Recall@5 / MRR / Hit@1 基线值
- `baseline/baseline_v1.json` 用于后续回归

### 1.2 Skill 集成测试（T2b Flow）

**目标**：扩展 `src/tests/integration/flow/` 现有测试，增加 Skill 输出质量断言。

**改动**：在现有 `test_settlement_exception_flow.py` 或 `test_skill_intent_matching.py` 中添加：
- Skill 路由后，验证 `assembler.execute()` 返回的 `StrategyResult` 完整性
- 验证不包含 forbidden tokens

### 1.3 覆盖率工具集成

```bash
pip install coverage

# 运行全量测试 + 生成报告
coverage run -m pytest src/tests/unit/ src/tests/integration/api/ src/tests/integration/flow/ -v
coverage report --include="src/*" --skip-covered
coverage html -d coverage_report/
```

## Phase 2 — 本月（需要新数据/新基建）

### 2.1 人工标注 query 集

**需要**：医保业务专家

**做法**：
- 从现有 10 个 query 扩展到 30-50 个
- 对每个 query，人工判断 top-5 结果的相关性（relevant / partially / not）
- 标注粒度：逐 pair (query, result)

### 2.2 Skill 输出质量评估（LLM-as-Judge）

**需要**：模型 API 可用（MODEL_API_KEY）

**做法**：
```python
# 用 LLM 评估 patient_answer 质量
def evaluate_answer_quality(answer: str, expected_points: list[str]) -> dict:
    prompt = f"""
    请评估以下医保费用解释的质量：
    {answer}
    
    应包含以下要点：
    {expected_points}
    
    评分（1-5）：说明是否清晰、是否正确使用了政策依据、是否面向患者友好。
    """
    response = model_gateway.generate(prompt, scene="eval")
    # parse score and feedback
```

### 2.3 性能基准测试

**目标**：建立检索延迟基准，存入 Locust 压测场景。

**改动**：
- 新增 `src/tests/performance/scenarios/retrieval_perf.py`
- 配置 `--tags retrieval` 独立运行
- 输出 P50/P95/P99 延迟分布

### 2.4 回归测试集成

**目标**：每次发版前跑评估 → 与基线对比 → 检测退化。

**做法**：
- CI 中增加 `pytest src/tests/evaluation/test_retrieval_regression.py -v`（需要 Milvus）
- 如果 CI 无法连接 Milvus，改为手动触发（make target）

## Phase 3 — 远期

### 3.1 自动化标注

**目标**：用 LLM 自动标注检索结果相关性，降低人工成本。

### 3.2 A/B 测试框架

**目标**：支持新旧检索策略对比（如不同 reranker 权重、不同 embedding provider）。

### 3.3 持续质量监控

**目标**：把评估指标接入监控面板（Prometheus/Grafana），实时追踪召回质量。

---

## 总结：各研究对象的下一步建议

| 对象 | 立即能做 | 短期目标 | 中期目标 |
|------|---------|---------|---------|
| 测试模块 | 修复 33+2 轻量级测试债务 | 集成 coverage.py | CI pipeline |
| Skill 质量 | Phase 0: 新建 `unit/skills/` 4 文件 | Phase 1: Flow 集成测试 | Phase 2: LLM-as-Judge |
| 知识召回质量 | Phase 0: 搭建 eval 框架骨架 | Phase 1: 首次评估 + 基线 | Phase 2: 人工标注 + 回归 |

**建议优先动手的顺序**：
1. Phase 0.1 Skill 测试（零依赖，立刻产出）
2. Phase 0.2 检索评估框架（骨架，为 Phase 1 铺路）
3. Phase 0.3 轻量测试债务修复（清理已知失败）
4. Phase 1.1 首次检索评估（需要 Milvus 运行）

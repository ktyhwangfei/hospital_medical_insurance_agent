# 治理中心全流程可视化配置：开源调研与落地方案 V1.0

> 状态：方案评审，暂不开发  
> 日期：2026-09-04  
> 目标：把“数据加工 → 语义指标 → 受控消费 → 智能问数/运营页面”配置成可复用、可审计、可视化的治理资产。

## 1. 结论先行

不引入完整的 Airflow、Dagster、dbt、Superset、DataHub 或 OpenMetadata 作为本系统的运行底座。它们分别解决了编排、转换、BI 和目录问题，但整套引入会带来部署、权限、数据模型和医保口径治理的重复建设。

建议建设一个轻量的 **Governed Data Flow**：

```text
数据源/适配器
    → 加工定义（声明式、白名单算子）
    → 编译产物（首批 SQL View）
    → 语义指标/维度（版本锁定）
    → 消费契约（query_planner / Skill / 仪表盘 / 助手）
    → 结果、解释、血缘、质量证据
```

可视化编辑器只编辑声明式定义，不直接编辑 SQL 或调用外部数据库；后端负责校验、编译、预览、发布和回滚。这样既满足“全流程可视化”，又保留现有的安全边界和口径签核。

### 2.1 共识与取舍

- **编排侧共识**：资产图、声明式定义、编译后执行、运行证据，比手写脚本和自由 SQL 更可治理。
- **消费侧共识**：指标/维度/权限/口径一次定义，多种 API、图表和 AI Agent 复用。
- **治理侧共识**：资产 owner、版本、质量、血缘、使用方和变更影响必须同一条链可查。
- **本项目取舍**：只吸收这些模式，不复制平台。首批以 view 为产物、无调度；只有测得查询性能瓶颈后才增加物化表或调度。

## 4. 目标架构

### 4.1 控制面与数据面

```text
Portal Governance Flow Canvas
  ├─ Flow Definition API（草稿、校验、版本、审批、发布、回滚）
  ├─ Compiler（白名单算子 → 参数化 SQL/View + query contract）
  ├─ Lineage/Impact（批次 → view → metric → consumer）
  └─ Preview/Quality（脱敏样本、SQL explain、口径断言、权限检查）

Data plane
  adapters/ports → source data → published views → query_planner
                                      ├→ policy-qa / Skill
                                      ├→ #40 dashboard/report
                                      └→ assistant/stream（后续）
```

### 4.2 Flow 节点最小集合

1. **Source**：引用已登记的数据源/适配器和语义对象，不允许填写任意连接串。
2. **Filter**：字段、值域、时间范围；字段必须来自 source contract。
3. **Join**：仅允许已登记的兼容关系，默认禁止笛卡尔积。
4. **Aggregate**：`count_distinct`、`sum`、`avg`、`count`，每个算子带空值、负数、去重和冲正策略。
5. **Derived metric**：引用已发布指标和 AST 白名单公式，不执行 `eval` 或任意 SQL。
6. **Dimension**：引用值域/维度及权限级别，保留下钻边界。
7. **Quality gate**：口径签核、字段完整性、勾稽恒等、样例结果和权限检查。
8. **Consumer**：query_planner、Skill、仪表盘卡片、周报或助手工具；只读引用发布版本。

首批不做任意 Python 节点、脚本节点、循环节点、在线调度节点和自由 SQL 节点。

### 4.3 定义与版本

Flow 是版本化治理资产，建议结构如下（字段名可在实现时落 Pydantic）：

```text
flow_id / name / owner / status
nodes[] / edges[]
source_contracts[]
metric_outputs[]
policy_definition / policy_carrier
quality_gates[]
materialization: view
revision / content_hash
published_at / published_by
lineage_refs[] / consumer_refs[]
```

状态沿用现有治理风格：`draft → validating → pending_review → published → deprecated`。发布必须原子锁定 flow revision、semantic revision 和产物 hash；下游永远按已发布 revision 读取。

## 5. 关键流程

### 5.1 配置到发布

1. 用户从已登记资产拖入 Source，选择业务对象和字段。
2. 画布连接 Filter/Join/Aggregate/Metric/Consumer 节点。
3. 后端校验图无环、节点参数、值域、权限、来源契约和 policy_definition。
4. 生成可读的查询计划、参数化 SQL/View 草案和影响范围；提供脱敏样例预览。
5. 执行质量门禁：口径签核、数据类型、空值/负数/去重规则、结果恒等式、权限和存量一致性。
6. 提交审核；审核人看到 diff、口径句、SQL 计划、血缘和消费影响。
7. 发布 View 与语义注册变更；刷新 lineage/catalog；通知受影响消费方。
8. 失败只留草稿和证据，不改变当前 active revision。

### 5.2 智能问数

自然语言只负责识别候选指标/维度/时间和澄清问题；执行仍走已发布消费契约：

```text
用户问题 → 意图/候选解析 → SemanticRegistry
        → 已发布 Flow/metric contract
        → query_planner 生成受控计划
        → 权限过滤 → 查询 View
        → 结果 + 查询理解 + lineage/citations
```

没有已发布指标、口径不完整、权限不足或来源不健康时，返回 `unavailable/need_clarification`，不生成猜测性 SQL。

## 6. 技术选型建议

| 层 | 方案 | 理由 |
|---|---|---|
| 画布 | 复用现有 Next.js/React；采用成熟 React Flow 类组件时先做依赖评估 | 只需节点/边、缩放、键盘可达和小地图；不自建图编辑器 |
| 定义 API | FastAPI + Pydantic，接入现有 runtime API | 保持响应契约、鉴权和审计一致 |
| 存储 | PostgreSQL JSONB 定义 + 关系型 revision/lineage/consumer 索引；内存存储用于测试 | 与现有 data_platform、semantic/discovery 表和双写 DDL 约定一致 |
| 编译 | 自建小型 AST/SQL 编译器，算子白名单；复用现有 FormulaEvaluator/query_planner | 避免引入完整 dbt runtime，同时保证不可注入和可解释 |
| 执行 | 首批 `CREATE OR ALTER VIEW`；查询经 query_planner 和 adapters | 遵守 #62 的 view 先行和防腐层纪律 |
| 血缘 | 节点级静态 lineage + 发布批次/产物 hash；接入 #38 目录 | 先满足可追溯，再评估列级血缘 |
| 质量 | 复用现有治理门禁、测试夹具、ops findings | 不再造一套质量规则引擎 |
| AI 接口 | ModelGateway + 受控 query tool/MCP（后续） | 遵守统一模型入口与 MCP 安全边界 |

## 7. 分阶段落地

### Phase 0：契约冻结（约 3-5 天）

- 冻结 Flow DSL、节点白名单、状态机、revision/hash 和错误码。
- 明确 #62 四字段作为 golden flow；明确 T_CureType 与 med_type 不混用。
- 产出 API/数据库/前端 DTO 对照和威胁模型。

### Phase 1：后端最小闭环（约 1.5-2 周）

- 草稿 CRUD、图校验、预览查询计划、view 编译、发布/回滚。
- 接入 #62 四字段和 #36 query_planner。
- 记录 revision、产物 hash、审计、血缘和质量证据。
- Unit → API → Flow 验收；不做调度。

### Phase 2：治理画布与目录联动（约 1-1.5 周）

- Source/Filter/Join/Aggregate/Metric/Quality/Consumer 节点。
- 资产搜索、详情、影响分析、版本 diff；接入 #38。
- 桌面三栏 + 移动端只读详情，满足键盘可达和无横向溢出。

### Phase 3：消费产品化（约 1-1.5 周）

- 复用 #40 指标卡、图表、下钻和周报配置。
- 受控问数的澄清、查询理解、结果引用和失败态。
- 每条 AI 摘要绑定 metric revision、数据批次和政策 citations。

### Phase 4：运行运营（有测量后再做）

- 只有当 View 查询 P95/并发达到明确阈值，才增加物化表、调度、缓存或异步运行。
- 与 #45/#53 对接失败巡检、L1 重试和修复后验证。

## 8. 验收与非目标

### 必须验收

- 从画布创建首批四字段 Flow，预览、审核、发布后可被 query_planner 和问数消费。
- 未签核口径、任意字段/算子、循环图、越权维度、未发布 revision 均被拒绝。
- 发布前后数值一致；View、指标、消费方和数据批次可追溯。
- 回滚只切换 active revision，不删除历史证据。
- 数据源不可用、质量门禁失败、口径不确定时 fail closed，并显示可解释原因。
- 画布和详情页在 1440px、1024px、390px 下可用，关键操作可键盘完成。

### 明确不做

- 不嵌入完整 Airflow/Dagster/dbt/Superset/DataHub/OpenMetadata。
- 不做任意 SQL/Python 执行器，不允许画布绕过 adapters、security、ModelGateway。
- 不在首批建设通用数仓、实时 CDC、物化调度和复杂列级血缘。
- 不把自然语言直接编译为可执行 SQL；必须落到已发布语义/消费契约。

## 9. 决策记录

以下决策已于 2026-09-04 确认：

1. 接受 **配置与证据可视化，执行仍以 View + query_planner 为主**，首批不建设实时 DAG 运行画布。
2. #62 四字段作为唯一 Golden Flow，其他指标只读复用。
3. 接受使用成熟的流程画布组件；具体选择 React Flow 或兼容组件，放到 Phase 0 做包体积、许可证、Next.js 构建、移动端和键盘可达性验证后确定，当前不提前引入依赖。
4. 新建治理 Flow 父 issue：`治理 Flow 控制面：数据加工到智能问数的可视化配置与复用闭环`；#38/#40/#45 作为接入依赖，不重复实现目录、消费和健康运营能力。

## 10. 研究边界

本次调研只核验了 GitHub 公共仓库主页、README、许可证和本仓库 issue/API 信息；未对各项目进行部署压测或逐文件代码审计。技术选型需在 Phase 0 对组件许可证、包体积、浏览器可访问性和医院部署约束做一次小型验证。

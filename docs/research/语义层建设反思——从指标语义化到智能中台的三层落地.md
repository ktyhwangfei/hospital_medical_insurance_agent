> **日期**：2026-07-22 | **状态**：持续更新

## 零、核心论点

```text
"语义层的厚度决定 AI 的准确率，不是模型不行，是语义层太薄。
同一个模型接上规范的语义层和指标体系，准确率能从 50-60% 跳到 98% 以上。
模型会贬值，语义资产只会增值。"
```

这句话值得印在语义层建设的每一个 PRD 首页。但它隐含了一个前提：**语义层不是设计出来的，是长出来的**。本文围绕这个前提，结合本项目已有的 v3 三层语义模型、SemanticRegistry、BusinessFactsBuilder 等实践，做一次系统性的反思。

## 一、语义层：已有的成果与盲区

### 1.1 已经做对了什么

**三层模型（L1 业务对象 → L2 指标 → L3 数据源）与行业共识一致。**

本项目 v3 设计文档定义了：

| 层 | 本项目实现 | 对标行业 |
|----|-----------|---------|
| L1 业务对象 | `BusinessObject`（Settlement / Patient / Hospital / Policy） | dbt Semantic Layer / MetricFlow 的 `dimension grouping` |
| L2 指标层 | `IndicatorDefinition` + `MetricFormula` | Cube.js 的 `measures` |
| L3 数据源 | `IndicatorSource`（data_source + table_name + field_name） | Looker 的 `lookml` 数据映射 |
| Metric Layer | `FormulaEvaluator` + `MetricFormula`（expression + dependencies） | MetricFlow 的 `derived metrics` |
| 值域标准化 | `ValueDomain` + `BusinessFactsBuilder` 自动转换 | dbt 的 `type_code` 转换 |

**Design/Runtime 分离做对了。** `src/semantic_layer/models.py`（设计时模型）与 `src/semantic_layer/builder.py`（运行时 Builder）职责清晰，Registry 是唯一耦合点。这完全符合用户提到的语义层设计哲学。

**DSL 中间层的选择也做对了。** 用户指出 NL → DSL → SQL 是已被 BenchMark 验证的模式。本项目的设计正是这一模式：

```text
用户输入 → Intent 识别 → SemanticRegistry（DSL：指标定义+维度+计算逻辑）
  → BusinessFactsBuilder（执行器：调适配器取数+值域标准化）
  → BusinessFacts（标准化 JSON）→ Skill 消费
```

**值域体系已经落地。** `indicators/dictionaries/` 下已有 5 个字典类别（hospital_level / insurance_type / medical_type / person_type / settlement_type），`SemanticMapping` 模型支持 CRUD 管理，不再硬编码。

### 1.2 盲区与不足

#### 盲区一：DSL 层是设计出来了，但没有真正「运营」起来

用户的核心观点之一是：

> "以上所有规范的生命周期管理——谁定义、谁审批、怎么发布？不需要一次做完 7 个指标规范，指标是 B 选项，其他是加分项。先把核心指标的定义、口径、维度、计算逻辑标准化，AI 就能开始用。"

对照本项目的现状：

| 维度 | 当前状态 | 反思 |
|------|---------|------|
| 谁定义 | 语义层设计由开发团队推动 | ❌ 业务人员没有参与路径 |
| 谁审批 | 无审批流程 | ❌ 所有 `seed.py` 中的条目全是 `status=draft` |
| 怎么发布 | 有版本号字段 (`version`) | ⚠️ 但无发布审批机制 |
| 生命周期管理 | `SemanticRegistry` 仅做静态加载 | ❌ 无法告知下游变更影响 |
| 指标准入标准 | 无 | ❌ 任何人都可在 `indicators/fee/` 下新增 YAML |

结果就是：**DSL 层在代码层面存在，但在组织层面不存在。** 业务人员的指标知识仍然在 Excel 和人脑中，没有真正沉淀为可运营的资产。

**建议改进**：
- 在 `SemanticRegistry` 之上加一层 **治理运营引擎**（Governance Engine），管理指标的提交 → 评审 → 发布 → 废弃全生命周期
- 每个指标增加 `steward`（业务负责人）、`approval_status`、`change_history` 字段
- 建立"指标发布即契约"的机制：发布后的指标定义作为所有下游 Skill 的契约，变更需通知所有依赖方

#### 盲区二：语义层的「厚度」不够均匀

用户的核心洞察：

> "AI Agent 推理质量的关键不是没有本体，是语义层厚不厚、活不活。厚 = 不光要有实体关系图（客户、订单、供应商），还要有：数据来源是哪个表、刷新频率多高、词表规范、同义词/近义词/歧义词、客单价和平均订单金额是不是一回事、退货在售后和仓储语境里的含义是不是一样、模型用了什么算法、输入输出的语义是什么。"

对照本项目：

| 厚度维度 | 当前状态 | 差距 |
|---------|---------|------|
| 实体关系 | ✅ 有 L1 和 Object Relation | 🟢 基本够用 |
| 数据来源 | ✅ 有 L3 `IndicatorSource` | 🟢 已显式化 |
| 刷新频率 | ❌ 未记录 | 🔴 缺失 |
| 词表规范（同义/近义/歧义） | ⚠️ `semantic_tags` 部分覆盖 | 🟡 AI 仍然可能搞混 |
| 跨语境歧义 | ❌ 未记录 | 🔴 例如 "自付" 在结算 vs 政策语境含义可能不同 |
| 计算口径版本 | ⚠️ `version` 字段存在但未运营 | 🟡 审计时无法确认用的是哪个版本 |
| 质量评分 | `quality_score` 在 `Metric` 模型中有 | 🟡 但未被 Builder 使用 |
| 使用热度 | `usage_count` 在 `Metric` 模型中有 | 🟡 但未被自动追踪 |

**关键改进点**：**同义词/近义词/歧义词的管理** 和 **口径版本追溯**。

当前 `DictionaryEntry.synonyms` 只解决了"一个标准值有哪些同义说法"，但没有解决"同一个词在不同语境下含义不同"这个问题。例如：

- `"自付"` 在 Settlement 语境 = 统筹自付（TCZF_SELF）
- `"自付"` 在 Policy 语境 = 个人自付比例
- `"自付"` 在患者视角 = 个人现金支付 + 统筹自付

这不是语义层的 bug，是语义层厚度不够的问题。需要补充 **语境索引**：每个语义标签标注所属的 Business Object + 场景。

#### 盲区三：计算指标（Metric Layer）的依赖解析不够健壮

本项目已实现 `FormulaEvaluator`，支持 `expression + dependencies` 的结构化公式。但用户提到的场景揭示了更深层的挑战：

> "毛利率怎么算，人知道，但 AI 不知道这个版本的口径含不含营销分摊、数据是 T+1 还是实时。"

对照本项目的 `MetricFormula`：

```yaml
- indicator_id: in_scope_total
  computation: "total_fee - self_fee - first_pay_fee"
  formula:
    expression: "total_fee - self_fee - first_pay_fee"
    dependencies: [total_fee, self_fee, first_pay_fee]
    type: arithmetic
```

这里暴露一个问题：**公式本身不够解释**。它告诉 AI "统筹范围内费用 = 总费用 - 自费费用 - 乙类先行自付"，但没有告诉 AI：

- 这个口径是哪个版本的政策规定的？
- 自费费用包含哪些项目（全自费药品、诊疗项目？）？
- 乙类先行自付的比例是多少？

用户要的是一个能自我解释的语义层。**`MetricFormula` 需要增加 `rationale`（公式的业务依据）、`policy_ref`（政策文件引用）、`caveats`（注意事项）**。

## 二、工具层：项目中最大的隐形缺口

### 2.1 现状分析

> "语义层解决的是 AI 读得懂，工具层解决的是 AI 动得了手。你的指标定义好了、维度规范好了，但 Agent 怎么去查？"

本项目的现状：

| 工具能力 | 实现 | 可被 AI 调用？ |
|---------|------|---------------|
| 指标查询 | `BusinessFactsBuilder.build()` | ❌ 内部 Python 调用，无 API 暴露 |
| 政策检索 | `policy_bridge.py` → Milvus | ⚠️ 只有内部桥接，未被封装为工具 |
| 结算查询 | `settlement_bridge.py` | ❌ 内部桥接 |
| 技能执行 | ~~`skill_bridge.py`~~→ Skill assembler（🔧 该文件零引用，P0 已删除） | ⚠️ 技能执行另有 API 路由，但非 MCP 标准 |
| 知识检索 | `rule_explanation/policy_retrieval/` | ⚠️ 模型内部用 |
| MCP 工具 | `mcp_registry/` 有注册中心 | ✅ 但仅有 stdio 传输 |

现状是：**项目的能力是存在的，但这些能力没有以 AI Agent 可直接调用的工具形式暴露。**

用户提到的毛利润率归因分析需要至少三种工具：指标查询工具、事件查询工具、知识检索工具。本项目中，这三种能力都在，但：

- 它们是通过内部函数调用链串联的（代码耦合）
- 不是通过标准协议（MCP / API）暴露给 Agent 的
- 没有工具注册、参数校验、权限校验的工具层基础设施

### 2.2 差距具体化

对照用户提到的工具系统演进（参考 `Nano agent` 课程）：

| 进化阶段 | 本项目状态 | 差距 |
|---------|-----------|------|
| L1: 直接调用 | ✅ Python 函数级 | 🟢 |
| L3: 权限控制 + 参数校验 | ❌ 无统一工具注册 | 🔴 每个工具各自为政 |
| L5: 持久化（思考与计划持久化） | ⚠️ 有 task_closure 但非工具层内置 | 🟡 |
| L19: MCP 接入 | ⚠️ mcp_registry 存在但空 | 🔴 MCP 工具列表为空 |

### 2.3 改进路线

1. **短期**：把 `BusinessFactsBuilder` 的指标查询能力封装为 MCP 工具（`query_metric`），暴露标准接口参数（`metric_code`, `dimensions: [{name, value}]`, `time_period`）
2. **中期**：将政策检索、技能查询、事件日志统一注册到 `mcp_registry/`，形成工具目录
3. **长期**：工具注册带上参数校验（JSON Schema）+ 权限标识（角色可见范围）+ 调用审计

用户说得好：**"最先核心的那个接口，可能就是你的指标查询 API。跑通一个场景再逐步扩展。"**

## 三、记忆层：尚未开始的工程

### 3.1 现状与差距

> "没有记忆的 Agent 每次对话从零开始，他不知道你的业务上下文，不记得上次分析的结论，不了解你的偏好。"

本项目目前的记忆能力：

| 记忆类型 | 当前状态 | 差距 |
|---------|---------|------|
| 对话上下文 | ✅ `runtime/context/` 有会话上下文管理 | 🟢 当前会话内 |
| 业务规则 | ⚠️ Policy Engine 中硬编码 | 🟡 难以版本管理和审计 |
| 领域知识图谱 | ❌ 本体论在设计文档里，没有实例化 | 🔴 没有结构化的供应商关系、物料依赖 |
| 历史分析记忆 | ❌ 不存在 | 🔴 每次分析都从头开始 |
| 用户偏好 | ❌ 不存在 | 🔴 无法越用越懂 |
| 口径版本记忆 | ⚠️ 有 version 字段但未关联 Agent | 🔴 Agent 不知道当前用哪个版本 |

### 3.2 最该先做的

用户把记忆层分为三块：

1. **业务规则** — 毛利率的最新口径、库存安全线、促销审批规则
2. **领域知识图谱** — 供应商关系、物料依赖、客户分群、渠道结构
3. **历史分析记忆** — 上次怎么应对的、效果如何

对本项目而言，**优先级顺序应该是：业务规则记忆 → 历史分析记忆 → 领域知识图谱**。

因为：
- 业务规则变化频繁（医保政策每年调整），Agent 必须知道"当前生效版本"
- 历史分析记忆最能体现"越用越准"的价值——医保结算分析是重复性工作
- 领域知识图谱建设周期长，属于厚积薄发

### 3.3 快速起步方案

> "那个开源项目里记忆系统从第 9 课开始迭代，用 Markdown 文件 + YAML 元数据存储，支持按类型检索、时间排序、按相关性调取。"

参考这个思路，本项目记忆层的 MVP 可以：

1. **用 `task_closure/` 的输出作为历史记忆的原始素材** — 每次 Agent 分析完成后，输出结构化摘要（分析目标、发现、结论、未解决的问题）
2. **把 `SemanticRegistry` 中指标的 `version` 字段联动到运行时** — Agent 在查询指标时，显式携带版本号，Builder 按版本取数
3. **业务规则先用 YAML 管理**（参考 `indicators/dictionaries/` 的模式），挂在 `knowledge_extension/` 下，后续再演进到专用存储

## 四、四步落地路线图检验

用户给出了一个落地路线图。用这个路线图检验本项目的建设路径：

### 现有路线（本项目实际走的）

```
语义层设计（v3 三层模型 + Metric Layer）
  → Registry 实现（YAML 加载）
  → Builder 实现（映射 + 标准化）
  → Seed 数据
  → 下一步：Admin UI
```

### 用户推荐的路线

```
第一步：指标语义化（核心 20-30 个指标的结构化文档）
  → 第二步：核心查询接口化（一个 MCP 工具起步）
  → 第三步：一个场景（跑通毛利归因）
  → 第四步：逐步加厚
```

**两个路线的最大差异**：本项目走的是"设计驱动"（先建三层模型再填充数据），用户推荐的是"指标驱动"（先定义最核心的指标并跑通场景，再演进到完整语义层）。

**这不是对错问题，而是阶段问题。** 本项目的语义层基础设施已经建好，但下一步的重心应该从"补充更多指标"转向"拉通工具层，跑通一个完整场景"。否则会出现：

> 语义层设计得再漂亮，Agent 调用不到就是零。

### 修正后的下一步优先级

| 原计划 | 建议调整 | 理由 |
|-------|---------|------|
| Admin UI 语义映射管理页面 | **后置** | 内部工具，价值在指标运营起来之后 |
| 增加更多指标 YAML | **后置** | 核心 20-30 个已够用 |
| Builder 连接更多适配器 | **后置** | 一个场景验证后再扩展 |
| **指标查询 MCP 工具** | **最优先** | 让 Agent 能动起来 |
| **工具层权限控制** | **次优先** | 玩具 Demo 到生产的分水岭 |
| **单场景端到端跑通** | **次优先** | 证明三层建设有效 |

医保场景对记忆层的需求比通用 BI 分析更强——因为政策年年变，每次都需要基于"当前版本"给出建议。

## 六、治理：从代码到组织

### 6.1 谁定义、谁审批、怎么发布

用户提出这个问题时指的不仅是技术实现，更是**组织流程**。

本项目 `seed.py` 中所有条目都是 `status=draft`，这说明语义层还处在"开发团队搭建"阶段，没有进入"业务团队运营"阶段。

**需要建立的治理机制**：

```text
业务指标负责人（Steward）定义指标口径
  → 数据治理委员会审批
  → SemanticRegistry 发布（status → published）
  → 通知所有下游 Skill
  → 版本号递增
  → 旧版本进入 archived 状态
```

这个机制可以在代码中通过以下方式支撑：

- `SemanticRegistry.publish()` 方法：原子性地将一组指标从 draft 转 published
- `ImpactAnalyzer`：发布前分析哪些 Skill 依赖了被变更的指标
- `Metric.changelog`：每次变更记录"谁、什么时候、为什么改"

### 6.2 数据隐私与工具权限

> "Agent 查毛利率可以，但能看所有 BU 的毛利率吗？一线就是合规事故。"

本项目已有 `security/authorization/` 和 `security/desensitization/`，但**工具层没有嵌入权限控制**。

需要补充：

1. 每个工具注册时携带 `required_role` / `required_permissions`
2. `BusinessFactsBuilder` 在返回 `BusinessFactsResponse` 前，根据调用者角色过滤不可见的数据
3. 高风险查询（含财务明细、患者隐私）走 `waiting_human_confirmation`

用户说得好：**"从玩具 Demo 到生产系统的分水岭往往就在这。"**

---

## 七、Harness 工程化：本项目缺什么

用户提到的 Harness（Agent 驾驭框架）包含：

| Harness 组件 | 本项目 | 差距 |
|-------------|-------|------|
| Agent Loop | `scenario_executor.py` + LangGraph | 🟡 有编排但未独立为框架 |
| 权限系统 | `security/` | 🟢 但未嵌入工具层 |
| 上下文管理 | `runtime/context/` | 🟢 当前会话 |
| Hooks（工具调用前后插入审计、脱敏、日志） | ❌ 不存在 | 🔴 每个工具需要自己实现 |
| 记忆管理层 | ❌ | 🔴 |
| 可观测性 | `observability/` 骨架 | 🟡 未嵌入 Agent Loop |

**最应该优先补的是 Hooks 机制**。因为：

1. 工具层暴露后，每次工具调用都需要审计（谁、什么时间、调了什么工具）
2. 敏感数据需要脱敏（`security/desensitization/` 需要在返回前介入）
3. 风控拦截（`security/risk_control/`）需要在执行前检查

Hooks 机制让这些"横向关注点"可以像插件一样配置，不改核心代码。这正是用户说的：**"每次工具调用前后都可以挂自定义逻辑：审计、日志、安全扫描、数据脱敏，像插件一样配置。"**

## 八、总结：反思清单

### 8.1 已经做对的

- ✅ 三层语义模型（L1-L2-L3）设计正确，与行业共识一致
- ✅ Design/Runtime 分离，Registry 作为唯一耦合点
- ✅ Metric Layer 支持派生指标（FormulaEvaluator）
- ✅ Value Domain 标准化体系 + `BusinessFactsBuilder` 自动转换
- ✅ 值域映射从硬编码迁移到可管理存储（`SemanticMapping`）

### 8.2 需要立即补的

| # | 行动 | 优先级 | 工作量估算 |
|---|------|--------|-----------|
| 1 | 把指标查询封装为 MCP 工具（`query_metric`） | P0 | 2-3 天 |
| 2 | 工具层嵌入权限校验（角色 → 指标可见范围） | P0 | 3-5 天 |
| 3 | 建立 Hooks 机制（工具调用前/后挂审计、脱敏、风控） | P1 | 5-7 天 |
| 4 | 补充指标歧义标注（跨语境词义） | P1 | 2-3 天 |
| 5 | `MetricFormula` 增加 `rationale` + `policy_ref` + `caveats` | P1 | 1-2 天 |

### 8.3 需要後置或持续做的

| # | 行动 | 理由 |
|---|------|------|
| 6 | Admin UI 语义映射管理页面 | 先有指标运营，再要管理界面 |
| 7 | 领域知识图谱 | 长线工程，先以 YAML 形式管理业务规则 |
| 8 | 用户偏好记忆 | 在 Agent 对话场景跑通后再做 |
| 9 | 更多指标 YAML | 核心 20-30 个已够用，有需求再加 |

### 8.4 核心认知

> **"语义层是长出来的，不是设计出来的。每跑一轮分析就知道还缺什么，补上就是了。"**

这是对语义层建设者最好的建议。不要试图在产品上线前把所有语义都建模完。正确的节奏是：

1. 搭好基础设施（已做）
2. 暴露一个工具给 Agent（马上做）
3. 跑一个场景（马上做）
4. 根据 Agent 的实际需求补语义、补工具、补记忆（持续做）

**模型会贬值，语义资产只会增值。** 现在投入三层建设，是在为 AI 能力的持续提升打地基，而不是为某一款模型做适配。

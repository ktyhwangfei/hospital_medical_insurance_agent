Loop Engineering循环工程：一篇讲透 Agent 的 Halt、Verify 与 Recover模型 决定天花板， Loop 决定你能不能真的够得着天花板。

我见过太多这样的情况：同一个模型，接的是同一家云厂商的 API，甚至 System Prompt 都大同小异，换一个团队来接，效果能差出一个数量级。有的 Agent 能跑通一整套发布流程，中间不用人插手；有的看着功能列表差不多，实际用起来三步一卡，得靠人不停地扶着走。

这种时候大部分人的第一反应是查模型——是不是版本不对、参数没调好、Prompt 写得不够精细。但我拆过不少这样的系统之后，越来越确信一件事：真正拉开差距的，往往不在模型这一层，而在一个很多团队压根没花心思打磨的地方——那圈把模型包起来、让它一轮一轮反复干活的 Loop。

这篇文章想把这件事说清楚：现在做 Agent，Model 已经不是瓶颈了，Loop 才是。

01
LAYER

你在优化的到底是哪一层
先纠正一个我见过无数次的误区。很多团队把 Agent 简单等同于 Model，出了问题第一反应是换模型、调参数、加 few-shot。这个思路在半年前可能还有效，现在基本上是在错误的地方使劲。

把 Agent 拆成两层来看

Model 负责推理、规划、生成、判断——说白了，负责“想”。Harness 负责的是另一整套东西：工具怎么调、上下文怎么给、记忆怎么存、什么时候该停、出错了怎么办、哪些操作不能碰。这一层负责“干”。

Model 决定这个 Agent 脑子够不够用，Harness 决定它能不能把活儿稳稳地干完。而现在主流模型的推理能力，说实话已经过剩了——过剩到大部分任务里，模型本身早就不是那个卡脖子的环节。真正卡住生产落地的，是 Harness 里这套让模型反复运转的循环机制，我把它叫做 Loop。

「下次团队里有人说“要不要换个更强的模型试试”，先别急着立项。换个问题问自己——这圈 Loop，停得住、验得了、恢复得了吗？」

十次里有八次，问题出在这三件事上，跟模型没关系。


02
HEARTBEAT

Loop 的心跳：别把“看了一眼”当成“验证过了”
经典的 ReAct 框架讲的是 Think → Act → Observe，这套东西教科书式地对，但我用下来发现里面藏着一个坑，而且是个很容易被忽视的坑：Observe 不等于 Verify。

这个区别听起来像是在抠字眼，但它决定了一个 Agent 是玩具还是能上生产。我更习惯用四拍来描述一个 Loop 应该长什么样：


Gather

收拢这一轮需要的上下文——任务是什么、之前做了什么、外部给了什么反馈。


Act

真的去动手，调工具、改文件、跑命令。


Verify

这一步是关键，不是看一眼结果“好像可以”，而是要拿出证据——测试跑没跑通、Exit Code 是不是 0、返回结构对不对、外部系统里的状态是不是真的变了。


Repeat

成功就收工，失败就进恢复流程，没做完就带着新信息进入下一轮。

我拿一个后端工程师都懂的场景打个比方：写完代码，看了一眼没报红，就直接合入主干，不跑测试。这在任何一个正经团队里都会被打回去。但很多 Agent 系统里天天在干这件事——模型自己说“任务完成了”，系统就信了，因为看起来确实“没什么问题”。

「一个没有真正 Verify 环节的 Loop，本质上不是在帮你干活，而是在很自信地帮你攒错误。」

这不是验证，这只是观察，而且是最不可靠的那种观察，因为观察者和执行者是同一个人。而且模型越聪明，攒错误的效率越高，这才是“更强模型放进烂 Loop 更危险”这句话背后的道理——不是耸人听闻，是纯粹的逻辑推导。


03
FIVE LEVERS

想把 Loop 设计好，先想清楚这五件事
我见过不少团队一上来就想搞一个“通用 Agent 框架”，恨不得把工具、记忆、多智能体协作、自我反思全堆上去。结果做出来的东西又贵又不稳定，还没有一个只做单一任务、但把基础打牢的简单版本好用。

我自己更认这个顺序：一个 Loop 的可靠性，取决于五个杠杆，但这五个杠杆不是平权的。


Tools：决定它有没有手去干活。


Context：决定它每一轮到底看见了什么。


Halt：什么时候必须停。


Verify：谁来证明它做对了。


Guardrail：什么绝对不能碰。

Tools 和 Context 是“能力”层面的东西，很多团队天然就会重视。但 Halt、Verify、Guardrail 是“安全带”层面的东西，恰恰是最容易被跳过的，因为跳过它们在 Demo 阶段完全看不出问题，Demo 就跑那么两三轮，出不了大事。

「先把 Halt、Verify、Guardrail 焊死，再谈扩展 Tools 和 Context。」

顺序反过来的后果我见过不止一次——工具越加越多，上下文越堆越大，系统看起来越来越“强大”，但没有刹车、没有验证、没有护栏，本质上是往一辆没有安全带的车里塞更大的发动机。跑得快是真的，出事的时候摔得也更狠。


04
HALT

一个 Agent 不知道什么时候该停，比它不知道怎么做还危险
这是我认为最容易被低估的一个模块。很多团队对“停止”这件事的理解，还停留在“模型说完成了就完成了”，这其实是最脆弱的一种设计。

一个我认为够格上生产的 Loop，至少要挂上三个相互独立的出口。

1
成功出口：但这个“成功”绝对不能由模型自己拍板。模型很自信地告诉你“任务已完成”，回头一查文件根本没生成，或者格式不对。这种“幻觉成功”是所有失效模式里最阴险的一种。所以成功出口必须绑定外部验证器，谁说了都不算，测试说了算，系统状态说了算。

2
迭代次数上限：这个大家理解起来没什么难度，防的是模型在原地打转、不收敛。

3
预算熔断：Token 预算、时间预算、调用次数预算。这个最容易被忽视，因为它防的不是“跑不完”，而是“每一步看起来都挺正常，但整个任务贵得离谱”。

除了这三个显性出口，我还会额外加一个容易被忽略的判断：停滞检测。轮数在涨，日志在涨，但目标状态压根没往前挪一寸。这种情况系统表面上看是“活着的”，其实已经死了，只是死得比较安静。停滞也是一种没停，只是没人意识到而已。

成功谁说了算？撞顶谁拉闸？钱烧光谁熔断？

三个问题都能答上来，这套 Halt 机制才算真正挂齐了。


05
VERIFY

验证的级别，决定你敢放手到什么程度
验证这件事，我习惯按可信度分成五级，而这个分级不是理论游戏，它直接对应你敢让这个 Agent 自主到什么地步。

1
模型自评：最低一级，是模型自己说“我做完了”。这个级别的可信度基本等于没有，人必须全程盯着。

2
换模型评：往上一级是让另一个模型来判断。比自评强一点，但本质上还是模型在判断模型，系统性偏差不会因为换了个实例就消失。

3
规则与启发式检查：Schema 对不对、正则匹不匹配、Exit Code 是几。这一级开始有点工程的味道了。

4
程序化验证：自动化测试、类型检查、断言。这是自主能力真正开始站得住脚的分水岭。

5
真实环境事实：最高一级是拿真实环境的事实说话——API 真实返回什么、数据库里状态到底变没变。

「验证级别决定放手级别。」

停留在前两级的系统，不管你嘴上说得多自主，本质上还是需要人时刻盯梢的半自动工具。只有做到第四级、第五级，才谈得上真正意义上的生产级自主。这不是我悲观，这是概率问题——低可信度的验证，出错的时候你根本发现不了，因为验证本身就在说谎。


06
NO SELF GRADING

别让写代码的人自己判自己及格
这一条我想单独拎出来讲，因为它踩坑的团队实在太多了，而且道理其实每个工程师都懂，只是搬到 Agent 场景里就忘了。

最危险的验证方式是什么？是让模型写完代码，自己看一眼说“没问题”。听起来荒谬，但这几乎是很多早期 Agent 系统的默认行为。

问题不在于模型不够聪明，而在于它是用同一套推理体系、同一组假设、同一套上下文偏差在自己检查自己。如果它对某个问题本身就有认知偏差，它检查的时候大概率还是带着同样的偏差，顶多是把错误重新包装一遍，讲得更圆一点，可信度没有丝毫提升。

我排的优先级

1
测试：确定性信号，可重复、可观测。

2
Schema 校验：结构对不对，一眼就能看出来。

3
Exit Code：跑没跑通，最直接。

4
规则：正则、断言、边界检查。

5
模型自评：万不得已的最后选项，而且如果非要用，起码得换个角色、换套上下文。

前四种都是确定性信号，可重复、可观测、不依赖模型那天心情好不好。模型自评永远是万不得已的最后选项。

「你们系统里说的“通过”，到底是谁说的？如果答案是“模型自己说 OK”，那这套系统还停留在演示阶段。」


07
RECOVER

Recover：Demo 和生产的分水岭，就在这里
Demo 和生产系统最大的区别，不在于模型选得好不好，而在于对“出错”这件事的态度。

Demo 的逻辑很简单：出错了，再试一次，反正演示的时候一般也就跑那么几轮，撞上概率不高。但生产系统必须提前把这些问题想清楚：谁来判断这次失败？重试几次算够？什么样的失败值得重试，什么样的失败重试也没用？什么时候该换个模型试试？什么时候干脆别自动化了，直接交给人？

四条有先后顺序的恢复路径

1
先定位：是文件不存在，还是某个测试用例挂了，还是 Schema 不匹配，还是外部 API 返回了 500。不定位清楚，后面的恢复动作全是瞎猜。

2
重试加退避：适合超时、网络抖动这类瞬时性错误，但一定要有次数上限，不能无限重试。

3
模型切换：如果当前模型在某类任务上持续卡壳，换个模型试试，有时候比死磕同一个模型更划算。

4
升级给人：很多团队把“最后交给人工”当成系统失败的证明，我完全不这么看。能够识别自己搞不定、主动交出去，恰恰是一个可靠系统该有的样子。

「那些从来不知道向人求助的 Agent，才是真正让人不放心的那种。」


08
FACTS

错误是数据，不是需要被安慰的情绪
这一点是我这两年帮团队调 Loop 时体会最深的一条，分享出来。

很多人设计恢复机制的时候，喜欢让模型“反思一下刚才为什么错了”。这个思路听起来很合理，实际效果往往一般，原因很简单——反思是模型基于自己的理解给出的解释，而它对错误的理解，很可能本身就是错的。

真正有用的做法，是直接把外部世界给出的原始信号扔回去：文件确实不存在、Exit Code 就是 1、第几号测试用例明确失败了、API 就是返回了 401。这些是事实，不是解释。

「下一轮 Loop 应该建立在事实之上，而不是建立在模型对自己错误的二次加工上。」

加工得越漂亮，有时候反而离真相越远。


09
PITFALLS

六个常见的失效坑，十个团队踩过八个
这部分我干脆直接列出来，都是实际项目里见过的场景，不是纸上谈兵。

1
上下文溢出：跑着跑着 Agent 开始“失忆”，工具输出越堆越多，前面交代过的事它记不住了。这个不是模型记性差，是喂给它的上下文本身没做压缩和分层管理。

2
无进展循环：日志一直在涨，轮数一直在涨，但目标状态纹丝不动。这种情况必须靠停滞检测和迭代上限硬性拦住。

3
钻验证器空子：Agent 有时候会找到验证逻辑里的漏洞，专门去满足“检查通过”这个条件，而不是真正把任务做完。

4
幻觉成功：模型信誓旦旦说完成了，实际什么也没发生。解法只有一个：成功状态必须绑定外部验证，不接受自我宣称。

5
误差累积：第一步犯了个小错，第二步在错误结果上继续往下建，越走越偏。破解办法是缩短反馈周期，每一步都验。

6
成本爆炸：循环本身没死，系统表面运转正常，但账单已经离谱了。这个得靠预算熔断和上下文分层来卡。

溢了压，空了停，奖了防，谎了验，漂了减，塞了闸。


10
MATURITY

别拿五级自主的想象，去做三级自主的决策
我把 Agent 的成熟度分成五级，不是为了炫技，是想给团队一个诚实的坐标系，别自己骗自己。

1
一级：纯手把手，人不停地喂提示，本质上就是个花哨点的 Copilot。

2
二级：已经能跑多轮了，但一遇到问题就得停下等人。

3
三级：自主多轮执行，配上完整的 Verify、Halt、Recover。

4
四级：能自己主动发现任务、长期保持状态。

5
五级：能持续自我优化演进。

四级和五级说实话，现在大部分团队还够不着，也不用急着够。真正值得现在这个阶段砸精力去做扎实的，是三级。

「单一 Loop，配上硬性的停止条件，配上确定性的验证，配上完善的恢复路径。」

这四件套听起来朴素，但我敢说，能把这四件套真正做扎实的团队，现在还是少数。我见过太多团队还没把三级跑稳，就已经在畅想“我们要不要做一个能自主发现任务、自我进化的系统”。这个跳跃挺危险的——地基没打好就想往上盖楼，楼是盖不高的。


∞
EPILOGUE

写在最后：该问的问题，从来不是“换不换模型”
回到开头那个问题。为什么同一个模型，一个团队能让 Agent 自主跑完整个流程，另一个团队却要一句一句喂？

答案已经很清楚了——Agent 的能力，从来不是只由模型决定的。真正决定它能不能从“会答问题”走到“会办事”的，是围绕模型搭建的那圈 Loop。

「模型决定了这个系统的天花板在哪，而 Loop 决定了你能不能真的够得着这个天花板。」

一个足够好的 Loop，至少要在三件事上给出明确答案——知道什么时候该停，知道怎么拿出证据证明自己做对了，知道做错之后怎么把自己拉回正轨。

所以下次团队里再讨论“要不要升级模型”的时候，不妨先往回退一步，问一个更扎实的问题：我们这套 Loop，停得住吗？验得了吗？恢复得了吗？

如果这三个问题里有一个答不上来，那答案已经很明显了——先别急着换模型，先把 Loop 修好。这笔投入，比任何一次模型升级都更划算。

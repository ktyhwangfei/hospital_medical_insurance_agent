# Workflow 自研节点开源调研与落地方案 V1.0

> 调研日期：2026-09-16  
> 调研范围：LangGraph、Dify、n8n、Temporal、Windmill、Prefect  
> 资料口径：官方 GitHub 仓库、官方文档、官方许可证；版本信息以调研日可见的最新发布为准。  
> 本文只提出方案，不包含代码或数据库变更。

## 1. 结论先行

本项目需要补的不是另一套通用工作流平台，而是现有 Workflow 中缺失的两类一等节点：

1. **领域节点**：院端医保业务中的确定性计算、证据归并、完整性校验、结果组装等代码能力。
2. **控制节点**：条件分支、人工确认、输出等执行语义。

它们不应全部伪装成 Tool。Tool 适合可独立发现、调用和治理的外部能力；领域节点是编排内部的业务步骤；控制节点属于执行引擎。把三者混在一个 Tool 注册表里，会扩大 Agent 可调用面，也会模糊安全、版本和审计边界。

综合比较后的建议是：

- **第一阶段不引入新的工作流平台，不开放任意 Python/JavaScript 代码节点。** 在现有顺序执行器上增加少量、强类型、代码侧白名单注册的领域节点和控制节点，先迁移一个真实结算解释流程验证价值。
- **借鉴 n8n/Windmill 的“节点契约 + 隔离执行”经验，但只实现受控领域节点。** 任意代码节点意味着必须同时建设沙箱、依赖白名单、资源配额、网络和文件隔离、不可变制品与审计，不能把 `eval` 或动态 import 包装成“代码节点”。n8n 的生产建议是把代码执行放入独立 Task Runner，Windmill 也用独立 Worker 执行每个步骤，[n8n Task Runners](https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/set-up-task-runners.md)、[Windmill 架构](https://github.com/windmill-labs/windmill/blob/main/windmill-overview.mdc)。
- **LangGraph 是未来最匹配的嵌入式执行底座，但暂不为了“有框架”而切换。** 仓库已经依赖 LangGraph；当出现真实的动态分支、并行、循环、子图或持久化人工中断需求时，再将同一套强类型节点定义编译到 LangGraph。LangGraph 原生把普通 Python 函数作为节点，并提供 checkpoint、interrupt 和子图能力，[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。
- **Temporal 只在跨进程、跨天、强恢复和补偿成为刚需时考虑。** 它是耐久业务流程引擎，不是可视化节点平台；现在采用会显著增加服务、Worker、确定性重放和运维复杂度。[Temporal 工作原理](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/architecture/how-temporal-works.mdx)
- **不建议把 Dify、n8n、Windmill 或 Prefect 嵌入本产品。** 它们最值得复用的是设计经验，不是运行时：直接采用会重复建设 Portal、模型网关、知识服务、租户与安全治理，并带来技术栈和许可证边界。

一句话方案：**自研少量医保领域节点和统一节点契约，不自研通用工作流平台；先沿用现有执行器，复杂度达到明确阈值后再接 LangGraph。**

## 2. 先把“节点”分清

| 类型 | 责任 | 典型示例 | 注册与执行边界 |
|---|---|---|---|
| Tool 节点 | 调用可独立复用、可被 Agent 发现的能力，通常涉及外部 I/O | 查结算单、检索政策、调用 HIS/医保接口 | 继续通过 `tool_registry` 与 `adapters/`；风险、权限、版本独立治理 |
| 领域节点 | 执行编排内部、确定性的医保业务逻辑 | 结算与政策比对、证据完整性校验、引用归并、状态判定 | 代码侧白名单注册；输入输出强类型；不直接暴露给 Agent |
| 控制节点 | 表达图的控制语义 | 条件分支、人工确认、输出、未来的并行/汇聚 | 由 Workflow 引擎内建，不进入 Tool 目录 |
| 模型决策节点 | 对非确定性语义进行结构化判断 | 意图细分、候选路径排序 | 只能走 `model_service/gateway`；强制结构化输出与确定性兜底 |
| 任意代码节点 | 运行用户提交的 Python/JavaScript | 临时数据变换、自定义脚本 | 本期不提供；未来必须运行于隔离 Worker/Sandbox |

这一区分也解释了为什么“新增自研节点”不等于“所有代码都做成 Tool”。Dify 的公开插件类型主要是 Model、Tool、Agent Strategy、Extension、Datasource、Trigger，没有单独列出通用 Workflow Node 插件；因此其外部扩展更倾向于以 Tool 等能力进入流程，而不是任意新增一等画布节点，这是依据公开扩展点作出的判断。[Dify 插件概览](https://docs.dify.ai/en/develop-plugin/getting-started/getting-started-dify-plugin)

## 3. 开源项目横向比较

### 3.1 总览

| 项目 | 调研版本/快照 | 自定义节点模型 | 执行、持久化与恢复 | 人审、审计与租户边界 | 技术栈与许可证 | 对本项目的结论 |
|---|---|---|---|---|---|---|
| LangGraph | 1.2.10（2026-07-28） | 同步/异步 Python 函数即节点；State + Edge；支持子图 | 每个 super-step checkpoint；线程、pending writes、time travel；interrupt 恢复会从节点开头重跑 | interrupt 支持人工暂停；状态历史不是现成的合规审计/RBAC/多租户产品 | Python；核心 MIT | **未来执行底座首选**。适合嵌入现有 Python 服务，但治理、审计和租户仍由本项目负责 |

### 3.2 关键能力拆解

#### LangGraph：最合适的“嵌入式 Agent 图执行器”

LangGraph 的核心抽象非常贴近本项目未来需要：图由共享 State、节点函数和普通/条件 Edge 组成，节点可以直接是同步或异步 Python 函数；编译阶段会进行基础图校验。[官方仓库](https://github.com/langchain-ai/langgraph)、[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

其 checkpoint 在每个 super-step 保存状态，支持 thread、状态历史、time travel 与 pending writes；发生失败时，已成功的并行节点结果可以保留，重启失败步骤。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

`interrupt()` 能把执行暂停到外部输入到达，但恢复时节点会从开头重新运行，因此中断之前的副作用必须幂等，或被拆进独立 task/node。[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)

适合复用：

- Python 函数节点、条件边、子图、checkpoint 与 interrupt 的语义。
- 未来把“自研领域节点”编译为 LangGraph node，而不改变对外 Workflow 定义。
- 对 Agent 决策图比通用 BPM 更自然。

明显不足：

- 核心库没有直接提供本项目需要的节点目录、发布治理、租户 RBAC、医保审计、脱敏和风险控制。
- 它解决执行语义，不解决可视化产品和领域治理。
- checkpoint 不能直接等同于合规审计；仍需记录输入来源、版本、引用、人工操作和脱敏结果。

结论：仓库已经依赖 LangGraph，但现有静态顺序流程尚不需要迁移。等真实用例需要条件图、并行、循环、子图或持久化中断时再接入，避免现在同时维护两套执行语义。核心代码采用 [MIT License](https://github.com/langchain-ai/langgraph/blob/main/LICENSE)。

#### Dify：AI Workflow 产品体验参考，不是合适的内嵌内核

Dify 提供成熟的可视化 AI Workflow，Code 节点可运行 Python/JavaScript，支持结构化输入输出、重试和失败分支，但运行环境限制文件、网络和系统能力，并限制依赖集合。[Code Node](https://docs.dify.ai/en/cloud/use-dify/nodes/code)

Iteration/Loop 已覆盖集合处理和循环状态；Human Input 节点可暂停流程、生成表单、通过 Web/邮件收集审批并走不同分支。[Iteration](https://docs.dify.ai/en/cloud/use-dify/nodes/iteration)、[Loop](https://docs.dify.ai/en/cloud/use-dify/nodes/loop)、[Human Input](https://docs.dify.ai/en/cloud/use-dify/nodes/human-input)

部署上由 API、Celery Worker/Beat、PostgreSQL、Redis、Sandbox 和 Plugin Daemon 等组件组成，官方 Compose 明确拆分这些服务；源码持久层会保存 Workflow 与 Node Execution 状态、重试信息。[Docker Compose](https://github.com/langgenius/dify/blob/main/docker/docker-compose.yaml)、[API 架构说明](https://github.com/langgenius/dify/blob/main/api/README.md)、[Workflow Persistence 源码](https://github.com/langgenius/dify/blob/main/api/core/app/workflow/layers/persistence.py)

适合复用：

- AI 节点、代码节点、循环、人审节点在一个画布中的交互方式。
- 节点级重试、失败分支、运行详情和输入输出检查体验。
- Code 节点默认无网络/文件权限的安全基线。

明显不足：

- 公开插件类型没有通用“一等 Workflow Node”扩展点；院端领域节点若不做成 Tool，往往需要修改核心，这是从其公开插件分类得出的推断。[插件概览](https://docs.dify.ai/en/develop-plugin/getting-started/getting-started-dify-plugin)
- 接入会重复现有 Portal、模型网关、知识库、Workflow、Skill 和租户治理。
- 许可证不是无附加条件的 Apache-2.0；其条款对多租户环境和前端标识有额外限制，产品化复用前必须法务确认。[Dify License](https://github.com/langgenius/dify/blob/main/LICENSE)

结论：借鉴交互与运行详情，不引入 Dify Runtime。

#### n8n：自定义节点包和代码执行隔离的最佳参考

n8n 的自定义节点是可组合的 TypeScript/JavaScript 包，有明确的节点描述、输入输出、凭据和执行实现，并提供 Starter 与 Linter。这个模式非常适合参考“节点契约”和“节点版本”的设计。[Custom Nodes](https://github.com/n8n-io/n8n-docs/blob/main/docs/connect/create-nodes/overview.md)、[Nodes Starter](https://github.com/n8n-io/n8n-nodes-starter)

Code Node 支持 JavaScript 和原生 Python；生产部署建议用独立 Task Runner 隔离代码执行，Queue Mode 下由 Main 创建执行，Redis 传递任务，Worker 从数据库获取 Workflow 并写回结果。[Code Node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code)、[Task Runners](https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/set-up-task-runners.md)、[Queue Mode](https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode.md)

执行历史支持按原版本或当前版本重试；AI Tool 调用可以挂人工批准/拒绝。[Executions](https://docs.n8n.io/workflows/executions/all-executions/)、[Human-in-the-loop for tools](https://github.com/n8n-io/n8n-docs/blob/main/docs/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md)

适合复用：

- 节点元数据、凭据、输入输出、实现、文档分离的包结构。
- 编辑器只消费节点描述，运行时只依赖稳定契约。
- 任意代码与主进程隔离，Queue Worker 可横向扩展。

明显不足：

- Node.js/TypeScript + Vue 3 平台与本项目 Python + Next.js 技术栈不一致。[仓库架构说明](https://github.com/n8n-io/n8n/blob/master/AGENTS.md)
- RBAC、项目共享和多 Main 等能力存在版本/商业边界。[Workflow Sharing](https://docs.n8n.io/workflows/sharing/)
- n8n 明确采用 Sustainable Use License，而非 OSI 开源许可证；其免费使用主要面向内部业务，不能据“源码可见”推断可直接嵌入商业产品。[License](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)、[Sustainable Use License 说明](https://github.com/n8n-io/n8n-docs/blob/main/docs/privacy-and-security/sustainable-use-license.md)

结论：重点借鉴节点包契约与代码 Runner 隔离，不复用平台本身。

#### Temporal：耐久执行和恢复的上限参考

Temporal Server 保存 Workflow 的事件历史和任务，应用代码运行在独立 Worker；Workflow 根据事件历史确定性重放，Activity 承担外部 I/O 和副作用。[How Temporal Works](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/architecture/how-temporal-works.mdx)、[Architecture](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/architecture/temporal-architecture.mdx)

Activity 默认支持 Retry Policy，而 Workflow Execution 默认不会因为失败自动重试。事件历史是追加式耐久记录，但存在历史大小/事件数量限制，长流程需要 Continue-As-New。[Retry Policies](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/retry-policies.mdx)、[Event History](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/workflow/workflow-execution/event.mdx)

人审可以通过 Signal/Update 或异步 Activity 完成；Namespace 是隔离单位，但自建集群若不配置 Authorizer，默认不会自动提供本项目需要的业务授权。[Activity Execution](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/activities/activity-execution.mdx)、[Namespaces](https://github.com/temporalio/documentation/blob/main/docs/production-deployment/self-hosted-guide/namespaces.mdx)

适合复用：

- “编排逻辑”和“副作用 Activity”严格分离。
- 事件历史、确定性重放、重试、超时、心跳、补偿的语义。
- 跨服务、跨天且必须恢复的人工流程。

明显不足：

- 不是节点画布和节点市场，领域节点仍需自行建模。
- 引入 Server、Worker、数据库、任务队列和确定性编码约束，运维和研发成本最高。
- 技术事件历史不自动等于医保合规审计，仍需业务审计模型。

结论：只有在出现跨天、人审、跨服务副作用、进程重启后必须精确恢复的业务流程时再评估。当前同步政策问答和结算解释不满足采用门槛。Temporal Server 为 [MIT License](https://github.com/temporalio/temporal/blob/main/LICENSE)。

#### Windmill：多语言代码节点和步骤级 Job 模型参考

Windmill 将脚本、Flow 和内部应用放在一个平台中。Flow 使用 OpenFlow JSON 表达步骤、分支和循环，脚本可用 TypeScript、Python、Go、Bash、SQL 等语言；每个步骤成为独立 Job，由 Worker 从 PostgreSQL 队列原子领取并执行。[Flow Architecture](https://www.windmill.dev/docs/flows/architecture)、[Worker Groups](https://www.windmill.dev/docs/core_concepts/worker_groups)

其 Workflow as Code 模式会持久化每一步结果，父流程可以完全挂起并释放 Worker，之后从 checkpoint/replay 继续；Flow Approval 支持暂停、恢复、取消、表单和超时。[Workflows as Code](https://www.windmill.dev/docs/core_concepts/workflows_as_code)、[Flow Approval](https://www.windmill.dev/docs/flows/flow_approval)

适合复用：

- 序列化 Flow Schema 与代码实现分离。
- 每步独立 Job、结果持久化和 Worker 标签路由。
- 代码节点、审批节点、分支和循环的统一执行模型。

明显不足：

- 它本身是另一套完整开发/执行平台，Rust + Svelte + PostgreSQL Worker 架构与现有系统重叠。
- 许可证由 AGPL、Apache-2.0 与商业组件组成，分发和包装边界必须逐项确认。[Windmill License](https://github.com/windmill-labs/windmill/blob/main/LICENSE)

结论：借鉴 OpenFlow 风格的可序列化节点定义、步骤 Job 和隔离 Worker；不嵌入平台。

#### Prefect：最轻的 Python 任务化参考

Prefect 3 用 `@flow` 和 `@task` 将普通 Python 函数组成流程；Task 支持状态、缓存、重试、并行与并发，Server 保存 Flow/Task Run 状态、历史、日志、Deployment、Work Pool 和事件。[Prefect 仓库](https://github.com/PrefectHQ/prefect)、[Tasks](https://docs.prefect.io/v3/concepts/tasks)、[Server](https://docs.prefect.io/v3/concepts/server)

交互式流程可 pause/suspend，并使用 Pydantic 模型收集类型化人工输入；Worker 通过 Work Pool 获取部署任务。[Interactive Workflows](https://docs.prefect.io/v3/advanced/interactive)、[Deployments](https://docs.prefect.io/v3/concepts/deployments)

适合复用：

- Python 函数到受控 Task 的低摩擦映射。
- 强类型人工输入、状态和重试策略。
- Apache-2.0 许可证边界清晰。[pyproject/license](https://github.com/PrefectHQ/prefect/blob/main/pyproject.toml)

明显不足：

- 产品重心是数据任务、调度和 Deployment，不是面向业务人员的领域节点目录。
- 自托管基础 Server 与 Cloud 的 RBAC、审计、SSO 能力范围不同，不能把 Cloud 能力视为 OSS Server 默认能力。[Self-hosted Server](https://docs.prefect.io/v3/get-started/install)、[Cloud Roles](https://docs.prefect.io/v3/how-to-guides/cloud/manage-users/manage-roles)

结论：比 Temporal 轻，但仍会与当前执行器和任务体系重叠；只借鉴 Task 语义。

## 4. 对当前仓库的判断

### 4.1 已有基础

当前仓库不是从零开始：

- `src/domain/workflow/models.py` 已有 Workflow/Step 定义，但 Step 只表达 `tool_id + input_mapping`。
- `src/runtime/workflow/executor.py` 已是一个小型、顺序、fail-closed 的解释器，负责上下文映射、Tool 调用和停止原因。
- `src/runtime/tool_registry/` 已有 Tool 版本、物化和实现绑定。
- `model_service/gateway`、`security/risk_control`、`task_closure`、引用与不确定性契约已经建立。
- Portal 已使用 `@xyflow/react` 实现数据治理 Flow，但那套 `source/filter/join/aggregate/...` 节点是**数据治理流程**，不应直接复用为 Agent Runtime Workflow 的领域类型。

因此最小缺口不是换引擎，而是：

1. Step 被硬编码为 Tool，无法表达领域节点和控制节点。
2. 没有统一的强类型节点输入/输出与代码侧注册表。
3. 缺少节点级执行轨迹、版本锁定和发布期校验。
4. 分支、人工确认和未来 checkpoint 尚未进入 Workflow 语义。
5. 当前定义标识和运行实例都使用 `workflow_id`，落地时应明确拆为 `workflow_definition_id` 与 `run_id`，避免版本审计和运行追踪混淆。

### 4.2 不应做的事

- 不把每个 Python 函数注册成 Tool。
- 不允许配置里填写任意 import path、表达式后直接 `eval`，或在 API 进程执行用户脚本。
- 不同时引入 LangGraph、Temporal 和另一套可视化工作流平台。
- 不为了画布先设计通用插件市场；先用一个真实 Workflow 证明节点边界。
- 不把数据治理 Flow 与 Runtime Workflow 合并为同一领域模型；最多复用前端图组件和交互模式。

## 5. 推荐落地架构

### 5.1 稳定定义，执行器可替换

Workflow 定义只描述业务图，执行后端保持可替换：

```text
已发布 WorkflowDefinition
        │
        ├─ ToolNode ───────→ tool_registry → adapters / knowledge services
        ├─ DomainNode ─────→ 代码侧白名单 DomainNodeRegistry
        ├─ DecisionNode ───→ 安全的声明式条件
        ├─ ModelDecisionNode → model_service/gateway
        ├─ HumanReviewNode → risk_control + task_closure
        └─ OutputNode ─────→ citations / uncertainties / public result
                │
                └─ 当前：小型顺序解释器
                   未来：达到门槛后编译为 LangGraph
```

关键点是定义层不引用 LangGraph 类。否则以后执行器升级会把框架类型扩散到领域模型、API 和前端。

### 5.2 节点契约

建议用 Pydantic 判别联合类型表达节点，而不是一个万能 `dict config`：

| 节点 | 最小字段 | 约束 |
|---|---|---|
| `ToolNode` | `node_id`、`tool_id`、`input_mapping`、`on_error` | Tool 版本在发布时锁定；继续走现有安全边界 |
| `DomainNode` | `node_id`、`handler_id`、`handler_version`、`input_mapping`、有限参数 | `handler_id` 只能引用代码侧白名单，不支持动态 import |
| `DecisionNode` | `node_id`、声明式 cases、default | 只允许受控比较/存在性判断；不执行任意表达式 |
| `ModelDecisionNode` | `node_id`、`scene`、`output_schema`、fallback | 统一走 ModelGateway；输出必须结构化、可验证 |
| `HumanReviewNode` | `node_id`、`risk_action`、展示字段、允许决策 | 高风险动作只能进入 `waiting_human_confirmation`，不在 Workflow 内直接执行 |
| `OutputNode` | `node_id`、result mapping/template | 输出必须携带 citations 或 uncertainties，并经过脱敏 |

公共执行结果建议保持固定信封，而不是每个节点自造状态：

- `status`: `complete | partial | unavailable | clarify | waiting_human_confirmation`
- `data`: 节点的强类型结果
- `citations`: 来源引用
- `uncertainties`: 缺失数据和推断边界
- `public_summary`: 允许进入对外响应的摘要
- `halt_reason`: 停止原因

节点内部原始响应、模型思维过程、敏感字段不应自动传播到下游或公开审计。

### 5.3 首批节点

首批只做能形成一个完整用户故事的节点，不把控制语义伪装成领域节点：

1. `DomainNode/evidence_completeness:v1`：校验结算单和政策证据是否满足继续执行的最低条件。
2. `DomainNode/settlement_policy_compare:v1`：做确定性的结算金额、比例和政策规则比对。
3. `DomainNode/evidence_merge:v1`：归并去重 citations，记录冲突证据和 uncertainties。
4. `OutputNode/public_result:v1`：组装对外结果并触发脱敏与来源校验。

`DecisionNode/answer_status` 放到 Phase 2，只有黄金流程出现真实分支时再加入；第一阶段继续复用现有 fail-closed 状态归并规则。

其中 `settlement_policy_compare` 如果不需要被其他 Agent 独立发现和调用，更适合从“计算 Tool”转为领域节点；外部数据读取仍是 Tool。这样可以用真实流程验证 Tool/Domain/Control 三类边界。

### 5.4 执行、状态与恢复

第一阶段沿用当前执行模型：

- 按发布定义顺序执行；新增简单 decision 后只允许无环分支。
- 每个节点记录 `workflow_definition_id/version`、`run_id`、`node_id/type/version`、开始/结束时间、状态、输入输出摘要、引用、错误分类和人工操作人。
- 继续复用现有 Policy QA trajectory、事件日志与 task closure；在没有暂停/恢复需求前不新建通用 Workflow Event Store。
- 领域节点是确定性代码错误时不重试；Tool 节点只对已分类的瞬时 I/O 错误使用现有有界恢复；缺数据和证据不足直接 clarify/partial/unavailable。
- 所有有副作用的 Tool 或未来 Activity 必须携带幂等键，避免恢复时重复执行。
- 发布版本锁定 Workflow、节点处理器、Tool 版本和制品哈希；运行中的流程不追随“最新版”。

升级到 LangGraph 的明确触发条件：

- 至少一个生产 Workflow 需要动态分支、并行汇聚、循环或可复用子图；或
- 需要跨请求保存 checkpoint，并在人工输入后恢复；或
- 现有解释器开始自行实现 checkpoint/pending writes/time travel 等 LangGraph 已成熟提供的能力。

升级到 Temporal 的触发条件更高：

- 流程跨天、跨服务，必须在进程/机器故障后精确恢复；
- 存在多个不可原子提交的副作用，需要补偿、心跳、长 Activity 与 SLA；
- LangGraph checkpoint 不能满足业务耐久性和运维要求。

同一个 Workflow 不应同时由 LangGraph 和 Temporal 作为同级执行器。若未来两者都存在，应明确边界：LangGraph 负责单次 Agent 推理图，Temporal 负责跨系统长事务。

### 5.5 安全与审计

院端场景的最低安全基线高于通用开源项目默认值：

- Domain Node Registry 是代码所有、显式白名单、可版本化的，不接受用户上传代码。
- ModelDecisionNode 强制走统一网关，并把输入输出 schema、模型路由和引用写入审计。
- HumanReviewNode 只生成待办与展示安全上下文；退费、冲正、正式结算、病案修改仍由人工在既有系统执行。
- 节点间传递值按 schema 进行字段级允许列表；公开输出再次脱敏。
- 运行审计保存摘要、hash 和引用，不默认保存完整敏感载荷；需要回放时通过受控数据引用获取。
- 任意代码节点若未来获批，必须是独立 Sandbox/Worker，并具备 CPU/内存/时间限制、网络默认拒绝、文件系统隔离、依赖白名单、不可变签名制品和完整审计。完成这些前不提供“简易代码节点”。

## 6. 分阶段计划与验收标准

### Phase 0：确认设计边界

产出：节点分类、命名、首个黄金流程、版本规则和升级阈值。

验收：

- Tool、Domain、Control、Model、Human Review 的责任无重叠。
- Runtime Workflow 与现有数据治理 Flow 命名、DTO 和存储明确分离。
- 确认本期不含任意代码节点、不含通用插件市场、不切换执行引擎。

### Phase 1：最小领域节点闭环

范围：在现有顺序执行器中支持 `ToolNode + DomainNode + OutputNode`，迁移一个门诊结算解释 Workflow。

验收：

- 至少一个 Workflow 同时执行 Tool 节点和两个以上领域节点。
- 节点输入输出强类型校验失败时 fail-closed。
- 输出继续满足 citations/uncertainties、脱敏和现有 SSE `done` 契约。
- 不改变 `/policy-qa` 业务入口，不新增外部运行服务。

### Phase 2：受控分支和节点级轨迹

范围：增加 `DecisionNode`、发布期静态校验、节点版本锁定和节点级执行轨迹；按需要接入 `HumanReviewNode`，但仍不支持循环。

验收：

- 非法映射、悬空节点、无 default 的不完整分支在发布前被拒绝。
- 运行轨迹可回答“用了哪个 Workflow/节点/Tool/模型版本、为什么停止、引用来自哪里、谁做了人工决定”。
- 瞬时错误、业务错误、缺数据和高风险动作的处理路径可分别验证。

### Phase 3：基于真实需求决定是否接 LangGraph

只有达到前述触发条件才进入。届时将既有节点定义编译为 LangGraph node/edge，使用 PostgreSQL checkpointer，重点验证并行恢复、interrupt 幂等和版本兼容，而不是重写领域节点。

验收：

- 进程中断后从 checkpoint 恢复，不重复已确认的副作用。
- interrupt 前后节点可重复执行，幂等性测试通过。
- 与 Phase 2 相同 Workflow 定义和公开 API 契约保持兼容。

### Phase 4：任意代码节点或 Temporal，分别单独立项

这两项都不是 Phase 1 的自然“顺手扩展”：

- 代码节点先做隔离 Runner 的安全原型与威胁建模，再决定自建、采购或不提供。
- Temporal 先用一个跨天、跨服务真实流程验证恢复和补偿收益，再决定是否承担独立平台成本。

## 7. 需要确认的五个决策

1. 是否认可“Tool、领域节点、控制节点分离”，并把任意代码节点排除在首期之外？
2. 是否以“门诊结算解释”作为黄金流程，首批实现证据完整性、政策比对、证据归并和公开结果节点，并把状态分支留到 Phase 2？
3. 是否同意先扩展现有执行器，只有达到动态分支/并行/循环/checkpoint 条件才接 LangGraph？
4. 可视化编辑器是否本期只做只读运行图/轨迹，编辑和发布留到契约稳定后？建议如此。
5. 是否同意首期复用现有 trajectory/event/task closure，不新增通用 Workflow 运行表；当出现暂停恢复后再引入 checkpoint 存储？

确认这五点后，再进入详细接口设计和开发计划。

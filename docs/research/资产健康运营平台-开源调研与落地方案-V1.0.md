# 资产健康运营平台 — 开源调研与落地方案 V1.0

> **目标**：让 Skill、政策知识、数据三类资产能够**自动发现问题 → 自动诊断 → 安全地解决问题 → 验证闭环**。
> **方法**：先 GitHub 实地调研同类开源项目（功能/架构/技术选型/不足），再对比本项目已有能力，给出最薄可行的落地方案。**本文档不含代码，方案确认后才开发。**
> **调研时间**：2026-09-02，星数/活跃度均为 GitHub API 实测值。

---

## 1. 需求解读与范围界定

**要建的东西本质上是一个"资产健康运营闭环"**，覆盖三类资产：

| 资产 | 具体内容 | 典型问题 |
|------|---------|---------|
| Skill | `skills/` 技能包、路由、assembler、模板 | 路由错误、计算错误、政策内容错误、引用缺失、回归评测失败 |
| 知识 | 政策知识管线（单元→提取→发布→Milvus 检索池） | 知识过期、字段抽取错误、检索召回质量下降、索引与元数据不一致 |
| 数据 | 门诊数据底座（SQL Server→PostgreSQL 同步）、结算数据 | 同步任务失败/滞后、数据源连接失败、字段契约漂移、数据质量劣化 |

闭环四步：**发现（检查器）→ 诊断（LLM 带证据分析）→ 解决（自动白名单动作 / 人工确认）→ 验证（重跑检查与评测）**。

**非目标**：不替代医保正式业务系统；不做通用 AIOps/监控平台；不重建各域已有的治理子系统（skill 案例池、政策知识管线、数据治理），只做横向汇聚与编排层。

## 4. 调研结论

1. **各段引擎都有成熟方案，统一闭环没有**。发现段（数据质量/LLM 评测）、修复段（事件驱动自动化）分别有成熟项目，但没有任何开源项目把 **skill+知识+数据三类业务资产** 的"发现→诊断→解决→验证"做成一个闭环——搜到的最接近项目（Kubernaut/NightMend）都在运维域且为早期原型（<30★）。
2. **正确姿势不是造平台，是做最薄的汇聚编排层**。重引擎（GE/Soda/Langfuse 级别的检查引擎、trace 平台）在本项目当前规模下都是过度建设；而本项目各域已有子系统恰好覆盖了发现段的大半。
3. **必须自建的只有三样**：① 统一问题库（findings）与状态机；② LLM 诊断编排（走 ModelGateway，强制 citations）；③ 白名单修复动作 + 验证闭环。修复分级与人工门控直接复用既有安全模式。

## 6. 落地方案

### 6.1 总体架构（最薄汇聚层）

```
┌─ 检查器 Checks（只读，各域适配器取数）────────────────┐
│  skill 回归失败率 │ 知识过期/索引不一致 │ 同步任务失败 │ QA 轨迹异常率 │ ...
└──────────────┬──────────────────────────────────────┘
               ↓ 写入（fingerprint 去重）
┌─ 问题库 Findings（PostgreSQL，状态机）─────────────────┐
│  open → diagnosed → fixing → waiting_human → resolved │
│           ↑ ignore/reopen，severity，occurrence_count │
└──────┬──────────────────────────┬────────────────────┘
       ↓ 诊断编排                 ↓ 修复编排（分级）
┌─ LLM 诊断 ──────────────┐  ┌─ 修复动作 ─────────────────┐
│ ModelGateway 新 scene:  │  │ L1 白名单自动：重跑评测、   │
│ asset_diagnosis         │  │   重试同步、刷新缓存/索引   │
│ 输入: finding + 证据    │  │ L2 人工确认：改知识、改     │
│ 输出: 报告 + citations  │  │   skill 草稿（走既有流程）  │
│       + 建议动作 + 不确定性│ L3 禁止：风险拦截（既有）    │
└────────────┬────────────┘  └──────────┬─────────────────┘
             ↓                          ↓ 修复后强制
┌─ 验证 Verification ────────────────────────────────────┐
│  重跑触发检查 + 相关回归评测集 → 通过才 resolved，      │
│  失败则 reopen / 回滚 / 降级人工                        │
└─────────────────────────────────────────────────────────┘
门户：/ops 健康运营页（findings 列表+详情+诊断报告+操作）
调度：复用 claim_due_job 单进程 PG worker 模式
```

### 6.2 数据模型（两张核心表 + 一张运行表，遵循 ports/adapter + CREATE/ALTER 双写）

- `ops_findings`：`id, asset_type(skill|knowledge|data|runtime), asset_id, check_id, severity(info|warning|critical), status, fingerprint(去重键), payload(jsonb 证据快照), first_seen_at, last_seen_at, occurrence_count, diagnosis(jsonb: 报告/citations/uncertainties/建议动作/model_route), revision(乐观锁)`
- `ops_remediation_runs`：`id, finding_id, action, risk_level(L1/L2), status, before_evidence, after_evidence, verification_result, created_by, created_at`
- 检查器注册：代码内 `CheckSpec` 列表（id、asset_type、查询函数、阈值、severity），不引入 YAML 配置系统（YAGNI）。

### 6.3 P0 首批检查器（6 个，全部只读，原料已在库）

1. `skill_regression_failure`：回归评测失败率超阈值（regression_results）
2. `skill_routing_degradation`：路由 eval top1 准确率环比下降
3. `knowledge_stale`：已发布知识条目过期/临近过期（生效期字段）
4. `knowledge_index_mismatch`：Milvus 集合条数与 PG 已发布元数据不一致
5. `data_sync_failed`：门诊同步任务 failed/lagging + 数据源连接失败
6. `runtime_qa_degraded`：QA 轨迹 unavailable/partial 占比、halt_reason 分布异常

### 6.4 分期计划

| 期 | 内容 | 最小可验证单元 | 验证方式 |
|----|------|---------------|---------|
| **P0 发现** | findings 表 + 6 检查器 + 手动触发 API + `/ops` 只读列表页 | "运维者手动触发巡检，看到按资产分级的开放问题列表" | Unit（检查器/去重/状态机）→ API → Flow → Portal |
| **P1 诊断** | LLM 诊断编排（scene=asset_diagnosis，强制 citations/uncertainties）+ 诊断报告页 + 定时调度（claim_due_job worker） | "对一条 finding 发起诊断，得到带引用的根因报告和建议动作" | 同上 + 诊断无来源不得落库的负例测试 |
| **P2 解决** | L1 白名单自动修复（重跑评测/重试同步/刷新缓存）+ 修复后自动验证闭环 + L2 转 `waiting_human_confirmation` 走既有草稿/审核流程 | "同步失败的 finding 触发 L1 重试并自动验证关闭；知识修正转人工确认" | 同上 + 修复失败回滚用例 |
| **P3 增强（可选）** | 漂移检测（evidently 思想）、趋势看板、告警降噪规则 | 按需立项 | — |

### 6.5 关键设计决策

1. **不引入** GE/Soda/Langfuse/StackStorm 等外部平台作为运行时依赖——本项目检查目标就是自家 6-8 张表/集合，自研检查器每个 <50 行，外部引擎的接入成本远超收益。[决策；反例参照 §2 各项目"不足"列]
2. **诊断不落确定性结论**：无 citations 的诊断报告标记为 `insufficient_evidence`，不驱动任何修复动作（对齐"禁止无来源的确定性结论"安全约束）。
3. **修复白名单从极小集合起步**：只有幂等、可重放、可验证的动作允许 L1 自动执行；其余一律 L2 人工。高风险动作天然被 risk_control 拦截（L3）。
4. **与 skill 案例池 PRD 的关系**：案例池是 skill 域"发现问题→回归资产"的纵深（问题案例如何变成防复发门禁）；本平台是横跨四类资产的汇聚编排层。案例池确认后的案例**不重复进入** ops_findings，两个系统通过 finding ↔ case 的引用关联，各管各的状态机。
5. **调度**复用门诊同步 worker 的 `claim_due_job` 模式（单进程 PG 抢占，已验证），不引入 Airflow/Temporal/celery。

## 7. 风险与规避

| 风险 | 规避 |
|------|------|
| LLM 诊断幻觉 | 强制 citations/uncertainties；无来源仅 `insufficient_evidence`；诊断报告落库含 model_route 供审计 |
| 误报噪音 | fingerprint 去重 + occurrence_count 累计 + severity 分级 + ignore 操作（带原因） |
| 自动修复误伤 | L1 白名单极小且幂等；修复前快照 before_evidence；验证失败自动 reopen |
| 权限越界 | 复用 skill 治理权限（`skill:evaluate` 等）；门户写操作走既有鉴权 |
| 与既有子系统重复建设 | §5 盘点 + §6.5-4 边界声明；P0 只读不改任何既有表 |

## 8. 待确认问题（确认后开工）

1. **P0 范围**：6 个首批检查器是否认可？是否要先聚焦某一类资产（建议先 data + runtime，原料最全）？
2. **门户挂载**：新增 `/ops` 独立页，还是并入 `/data-governance`？（建议独立，语义清晰）
3. **修复白名单**：P2 的 L1 动作集（重跑评测/重试同步/刷新缓存）是否认可？
4. **与案例池 PRD 的推进顺序**：先推进案例池 PRD（纵深）还是先做本平台 P0（横向）？两者共用"问题"概念但状态机独立。

> 局限：① 未做源码级深读；② DB-GPT、Chat2DB README 拉取失败（信息来自搜索元数据）；③ 标注 NOASSERTION 的许可证需法务复核后才能作为嵌入决策依据。
> 用途：为《医保数据底座落地方案》提供选型依据。

## 0. 一句话结论

**医保/医疗支付域没有可直接使用的开源对标**（"医保"关键词搜索全部为噪声）；最值得借鉴的是 **SuperSonic（Chat BI + Headless BI 统一架构）** 和 **WrenAI（MDL 语义层即代码 + 受治理 Text2SQL）** 的设计理念，而非整仓引入。我们的差异化资产恰是它们没有的：医保领域模型（结算/费用/审核风险）、政策证据链、契约驱动同步。

## 1. 调研范围（按层）

底座服务于：**问数**（受控指标查询）、**结算单解释**（确定性计算 + 政策溯源）、**运营指导**（指标仪表盘）。

| 层 | 对标项目 | 结论速览 |
|---|---|---|
| 数据接入/同步 | Airbyte 22.0k★、DataX 17.3k★、Debezium 13.1k★、tis 1.4k★ | 不引入；借鉴插件化与限流 |
| 语义层/指标 | Cube 20.8k★、SuperSonic 5.0k★、WrenAI 17.4k★、dbt 13.8k★ | 借鉴 MDL 理念自研轻量 |
| 问数/ChatBI | SuperSonic、SQLBot 6.7k★、DB-GPT 19.8k★、Vanna 23.8k★ | 借鉴管线与 RAG 校准，受控模式先行 |

## 2. 重点对标详析

### 2.1 SuperSonic（tencentmusic/supersonic，Java，5.0k★，活跃）

- **定位**：Chat BI + Headless BI 统一平台——自然语言问数与传统 BI 共享同一套受治理语义模型。
- **架构**（核心可借鉴）：`知识库(Schema索引) → Schema Mapper(识别指标/维度/术语引用) → 语义解析器(规则+LLM 双解析) → 语义校正器 → 语义翻译器(语义查询→SQL)`；权限做到**数据集/列/行三级**。
- **核心理念**：把 join/公式等复杂 SQL 从 LLM 卸载到语义层，LLM 只做语义映射——**降幻觉、降复杂度**。
- **不足**：Java/JVM 技术栈与我们 Python/FastAPI 异构；面向通用 OLAP 场景，无医保口径治理、无政策证据链概念。

### 2.2 WrenAI（Canner/WrenAI，Python+Rust core，17.4k★，活跃，Apache-2.0）

- **定位**：受治理的 Text2SQL + 语义层（MDL）引擎，"GenBI"。
- **架构**（核心可借鉴）：**语义模型即代码（MDL 文件，Git 版本化、可评审、可 diff）**；`instructions.md` 承载业务口径；dry-plan 预校验 + 结构化错误 + 行数限制构成护栏；22+ 数据源。
- **不足**：行/列级安全与访问控制不在 OSS 版（Cloud/self-hosted 付费）；通用 BI 语义，无领域契约。

### 2.3 SQLBot（dataease/SQLBot，JavaScript，6.7k★，活跃）

- **定位**：DataEase 出品的 RAG 问数系统（ChatBI）。
- **可借鉴**：**术语库 + SQL 示例库校准**（"越问越准"的运营闭环）；工作空间资源隔离；Web 嵌入/MCP 集成方式。
- **不足**：自由 Text2SQL 模式，无冻结指标口径概念；医院场景需要的"可审计确定性回答"缺失。

### 2.4 DB-GPT（eosphoros-ai/DB-GPT，Python，19.8k★，README 拉取失败，元数据级结论）

- **定位**：Agentic AI 数据助手平台（AWEL 编排、多数据源、Text2SQL 微调 SMMF）。
- **可借鉴**：AWEL 式数据管道编排分层；多 Agent 协同问数。
- **不足**：平台化过重（含微调/部署全家桶），与院内单机内网部署约束冲突。

### 2.5 Vanna（vanna-ai/vanna，Python，23.8k★，2026-02 后停滞）

- RAG 三件套：DDL + 文档 + 问题-SQL 对作为训练语料；轻量库而非平台。
- **警示**：近半年无提交，活跃度风险；其"问题-SQL 对积累"思路并入我们的可信问题库即可。

### 2.6 Cube（cube-js/cube，Rust/Node，20.8k★）

- 语义层事实标准形态：数据模型（measure/dimension/join）→ 统一查询 API → 缓存/预聚合。
- **借鉴**：查询 API 的形态（metric + dimensions + filters + timeGrain）；预聚合加速思路。
- **不足**：自建 Node 查询引擎，引入即多一个常驻服务与一套建模语言，内网运维成本高。

### 2.7 数据接入层（Airbyte / DataX / Debezium / tis）

- **Airbyte**：连接器目录理念 + ELT 标准化，但目标云端/多云，重（Java+Python+Temporal）。
- **DataX**：国内医院离线同步事实标准，reader/writer 插件化 + 限流，单机批式。
- **Debezium**：CDC 标准实现（Kafka 依赖重）。
- **结论**：我们的场景是"单院区、内网、3 张契约表、双模式（CDC/定时 SQL）+ 质量门 + 对账"——**已自研的同步链比通用平台更贴合且已上线**；借鉴 DataX 限流与断点续传、Airbyte 连接器目录（未来接 HIS/EMR 再扩展）。

### 2.8 RAG 平台（Dify / RagFlow）

- **RagFlow（Apache-2.0，89.8k★）**：深度文档解析（表格/版面识别）是其核心价值——**政策 PDF/Excel 表格条款解析直接借鉴**。
- **Dify**：工作流编排 + RAG + Agent 全家桶；我们已有 skill 体系 + 模型网关 + 审计链，不换引擎。

### 2.9 BI 可视化（DataEase / Superset / Metabase）

- **DataEase GPL-3.0**（API 实测）：GPL 传染性，不适合深度集成进闭源产品。
- **Superset Apache-2.0**：可嵌入候选，但 Python 栈 + 建模在 Superset 内二次维护。
- **Metabase**：许可证非宽松（AGPL 系），嵌入受限。
- **结论**：运营指导先做**自研轻量仪表盘**（复用现有 Next.js portal + 宽表/指标 API）；若后期需要自由探索式分析，再评估嵌入 Superset。

### 2.10 医疗域（HAPI FHIR 等）

- HAPI FHIR 是互操作标准实现（HL7 FHIR），非数据底座竞品。国内医保结算域（费用明细/预退费/DRG）**无开源对标**——我们的领域模型、契约字段体系、政策引用规范是差异化资产。

## 3. 共性规律（所有成功项目的公约数）

1. **语义层先行**：SuperSonic/WrenAI/Cube 殊途同归——先有受治理的指标/维度定义，再做 AI 或 BI 消费。
2. **语义即代码**：MDL/YAML 文件化、Git 版本化、评审后生效（WrenAI 最彻底）。
3. **LLM 只做映射不做计算**：join/聚合/口径由确定性层完成，LLM 负责自然语言→语义元素对齐。
4. **护栏是原生能力**：dry-run 校验、行数限制、结构化错误（WrenAI）；三级权限（SuperSonic）。
5. **反馈闭环**：问题-SQL 对/术语库随使用迭代（SQLBot/Vanna）。

## 4. 我们与"产品级底座"的差距（demo 感根源）

| # | 差距 | 对标启发 |
|---|---|---|
| 1 | 只有 3 张源表投影，无主题宽表/集市层 | Cube 数据模型 + 预聚合 |
| 2 | 语义层只有 semantic_version 注册表，无指标字典/维度/口径治理 | WrenAI MDL、SuperSonic 语义模型 |
| 3 | 问数未落地（P3 gated），无"可信问题"绑定机制 | SuperSonic Schema Mapper、SQLBot 术语库 |
| 4 | 结算单解释数据面窄，费用构成计算未指标化 | 语义层消费方 |
| 5 | 无血缘可视化、无 SLA/质量看板 | DataHub 理念（轻量内嵌，不引入平台） |
| 6 | 运营指导无产品面 | BI 嵌入 vs 自研（见方案） |

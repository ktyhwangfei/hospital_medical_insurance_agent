当前产品**需要多智能体设计，但不建议一上来做成完全自治、自由协商式的多智能体系统**。

更准确的判断是：

> **架构上需要预留多智能体能力；产品落地上应采用“统一编排中枢 + 受控业务智能体/能力节点”的渐进式多智能体设计。**

依据主要来自当前架构定位：产品不是单一问答机器人，而是医院侧医保 AI 导办与运营协同中枢，需要连接收费、医保接口、事前审核、DRG/DIP、HIS、EMR、病案、知识库、任务闭环等多类系统和场景，架构文档中也已经明确包含“任务规划、工具调用编排、多智能体协同、规则解释、证据检索、报告生成、人工确认、审计留痕”等能力要求，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:76)。

---

## 结论

### 1. 当前产品需要多智能体设计

原因不是为了追热点，而是因为产品天然具备以下特征：

| 特征 | 对架构的影响 | 是否适合多智能体 |
|---|---|---|
| 多业务场景 | 医保结算异常、出院前质控、拒付申诉、DRG/DIP 运营、病案风险、政策解释等场景差异大 | 适合按场景拆分业务智能体 |
| 多角色协同 | 医生、收费员、医保办、病案室、科主任、院领导关注点不同 | 适合按角色/任务生成不同响应策略 |
| 多系统接入 | 医保接口、收费、HIS、EMR、病案、事前审核、DRG/DIP 等系统能力边界不同 | 适合通过工具智能体或适配器智能体封装 |
| 强合规要求 | 高风险动作必须人工确认，输出必须可追溯 | 适合用专门的风控、审计、引用溯源能力约束 |
| 复杂任务链路 | 查询、解释、归因、证据组织、建议生成、任务分派、闭环追踪 | 适合由编排中枢调度多个专业能力节点 |

当前业务架构已经明确平台要把多个系统结果转化为“读取结果、解释原因、组织证据、生成建议、分派任务、跟踪闭环”的导办能力，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:75)。这类链路很难长期靠一个“大而全”的智能体稳定维护。

---

## 2. 但不应该做成“多个智能体自由聊天决策”

当前产品是医疗医保场景，核心约束是**安全、可控、可审计、可追溯**。因此不适合采用完全开放式的多智能体自治协商模式。

更合适的是下面这种结构：

```text
用户问题
  │
  ▼
统一入口 / 会话上下文
  │
  ▼
路由与规划智能体
  │
  ├── 医保结算异常导办智能体
  ├── 出院前联合质控智能体
  ├── 政策规则解释智能体
  ├── 证据检索与引用智能体
  ├── 任务闭环智能体
  └── 风控审计智能体
          │
          ▼
     人工确认 / 审计留痕 / 结果返回
```

也就是说，应该是：

> **中心化编排，专业化分工，权限受控，结果可追溯。**

不是：

> 多个智能体自行讨论、自行决定、自行调用高风险系统。

架构文档中也把“编排执行引擎”定义为核心控制节点，负责流程流转、步骤执行、异常重试和多能力协同，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:96)。这说明当前产品的多智能体不应是松散自治，而应被编排引擎约束。

---

## 3. 为什么单智能体长期不够

如果只做单智能体，会有几个问题。

### 业务复杂度会迅速膨胀

医保结算异常导办和出院前联合质控已经是两个完全不同的业务逻辑：

- 结算异常更关注医保交易状态、错误码、收费状态、异常归因。
- 出院前联合质控更关注事前审核、DRG/DIP、病历、诊断、费用、病案风险。

后续还要扩展拒付申诉、DRG/DIP 运营、病案首页风险、科室整改闭环、医保运营驾驶舱、政策规则解释等应用，架构中已经列出这些核心场景，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:90)。

如果全部塞进一个智能体，会导致：

- 提示词越来越大；
- 工具权限越来越难控；
- 意图路由越来越混乱；
- 测试和回归成本越来越高；
- 不同场景的输出标准难以统一；
- 高风险动作边界容易被误触发。

### 权限边界难以控制

医保场景里，不同角色能看的数据和能触发的能力不同。

例如：

- 收费员可以处理结算异常，但不应查看完整病历。
- 医生可以查看诊疗风险，但不应直接执行医保结算操作。
- 病案室可以处理病案质控，但不应调整收费明细。
- 院领导看运营指标，不应接触过细患者隐私。

如果是单智能体统一挂载所有工具，权限治理会变得很危险。多智能体或能力节点拆分后，可以做到：

- 每个业务智能体只绑定必要工具；
- 每个智能体有独立权限策略；
- 每个场景有独立提示词和输出格式；
- 高风险动作统一进入风控和人工确认。

这与文档中“角色权限、租户隔离、风控审计”“高风险场景不直接替代正式业务系统执行最终交易或裁决”的要求一致，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:67) 和 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:97)。

### 可维护性会下降

当前架构已经把平台能力拆成接入安全、会话上下文、智能编排、模型服务、知识服务、业务适配、任务闭环七类服务域，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:89)。

这本身就是在为多能力、多智能体协同打基础。否则所有能力都堆在一个服务里，后续新增医院系统、医保规则、业务场景、知识库、模型能力时，会出现明显的架构债务。

---

## 4. 当前阶段应该做到什么程度

建议分三层推进。

### 第一阶段：MVP 保持单编排中枢，不急于上复杂多智能体

当前 MVP 已经实现核心后端子集，主要是医保结算异常导办和出院前联合质控。这个阶段不需要马上实现复杂的 Agent-to-Agent 协议或自治协作。

推荐形态：

```text
统一 Chat 入口
  │
  ▼
意图识别
  │
  ▼
场景服务路由
  │
  ├── 结算异常导办服务
  └── 出院前联合质控服务
  │
  ▼
统一响应 / 引用 / 风控 / 审计
```

这更符合当前 MVP 的工程状态：先把业务链路、工具边界、权限、引用、人工确认跑通。

### 第二阶段：把场景服务抽象成“业务智能体”

当场景扩展到 4 到 6 个以上时，就应该正式抽象业务智能体。

可拆成：

| 智能体类型 | 职责 |
|---|---|
| 路由规划智能体 | 判断意图、选择场景、拆解任务 |
| 结算异常导办智能体 | 解释结算失败、错误码、收费状态、处理建议 |
| 出院前质控智能体 | 汇总事前审核、DRG/DIP、病案、医嘱风险 |
| 拒付申诉智能体 | 组织拒付原因、证据链、申诉材料 |
| 政策规则解释智能体 | 检索政策、规则、错误码并给出引用 |
| 任务闭环智能体 | 生成人工待办、跟踪处理状态 |
| 风控审计智能体 | 拦截高风险动作、审计工具调用和输出 |

### 第三阶段：再考虑 A2A 和外部智能体协同

当系统需要连接外部 Agent 系统、第三方分析助手、院内其他 AI 平台时，再引入更完整的 A2A 协同能力。架构文档已经在知识与扩展服务中预留了 A2A 协同服务，用于 Agent 注册发现、任务委托、信任与鉴权，见 [`docs/steering/架构设计.md`](docs/steering/架构设计.md:177)。

这个阶段要重点解决：

- 外部智能体可信身份；
- 工具调用权限；
- 数据脱敏；
- 调用审计；
- 结果置信度；
- 引用来源；
- 失败降级；
- 人工接管。

## 5. 推荐的产品架构判断

当前产品最合理的定位是：

> **不是“一个超级医保机器人”，而是“一个医保 AI 编排平台，上面挂载多个受控业务智能体”。**

更具体地说：

```text
产品层：医保导办与运营协同平台
  │
  ▼
统一运行时：会话、上下文、意图、规划、编排、响应
  │
  ▼
业务智能体层：按医保业务场景拆分
  │
  ▼
能力层：知识、规则、模型、工具、MCP、适配器
  │
  ▼
系统层：HIS、EMR、收费、医保接口、事前审核、DRG/DIP、病案
```

这样设计的好处是：

1. **业务上更清晰**：每个智能体对应一个可售卖、可交付、可验收的业务能力。
2. **技术上更可控**：统一运行时负责调度，业务智能体不越权。
3. **安全上更稳妥**：高风险动作集中拦截，人工确认统一处理。
4. **交付上更灵活**：不同医院可以按场景启用不同智能体。
5. **演进上更自然**：从当前两个 MVP 场景逐步扩展到更多医保运营场景。

---

## 6. 最终建议

当前产品**需要多智能体设计**，但建议采用**受控多智能体架构**，不要采用完全自治式多智能体。

推荐路线是：

1. **短期**：保持统一编排中枢，现有业务场景继续以服务或流程节点方式实现。
2. **中期**：将医保结算异常、出院前质控、拒付申诉、政策解释等场景抽象为业务智能体。
3. **长期**：在统一权限、审计、脱敏、引用溯源、人工确认机制成熟后，再开放 A2A 外部智能体协同。
4. **核心原则**：多智能体只负责专业分工和能力复用，不负责绕过业务系统直接执行高风险动作。

一句话概括：

> **当前产品需要多智能体“架构思想”，但当前阶段更需要的是“单一编排控制下的多专业智能体”，而不是自由自治的多智能体系统。**

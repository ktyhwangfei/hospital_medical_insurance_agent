## 一、执行摘要

### 1.1 研究目标

为院端医保智能体的政策知识检索搭建完整评估体系，覆盖**纯向量检索**和 **BM25 检索**两种搜索方式的对比评估，为将来引入**混合检索**提供基线。

### 1.2 核心结论

| 决策项 | 推荐 | 优先级 |
|--------|------|:------:|
| BM25 实现路径 | **路径2：外部 BM25（rank_bm25 + jieba）** | P0 |
| 混合检索策略 | **RRF（Reciprocal Rank Fusion）** | P1 |
| Milvus 升级 | **升级到 2.5+ 获取原生 BM25 → 长期目标** | P2 |
| 评估门槛 | **向量 Recall@5 ≥ 0.50 / BM25 Recall@5 ≥ 0.30** | P0 |

**推荐理由**（详见 §四）：Milvus v2.4.15 不支持原生 BM25/SPARSE_FLOAT_VECTOR（从 2.5 开始）。外部 BM25（rank_bm25 + jieba 医保词典）可**零成本立即可用**，与 Milvus 升级不互斥（并行推进）。

## 三、检索评估体系设计

### 3.1 评估查询集

#### 3.1.1 设计原则

基于 `policy_rules_v2` 的 **6 维交叉覆盖**（rule_type × insu_type × med_type × hosp_lv × psn_type × setl_type），每条 query 按以下结构标注：

```yaml
- id: Q001
  question: "三级医院住院的起付线是多少"
  expected:
    rule_types: ["起付线"]     # 期望命中的规则类型
    hosp_lv: "三级"           # 维度约束（可选）
    min_relevant_hits: 1      # 期望至少返回结果数
  difficulty: easy            # easy / medium / hard
```

#### 3.1.2 查询集统计

| 类别 | query 数 | 难度分布 | 覆盖维度 |
|------|:------:|------|------|
| 起付线（deductible） | 6 | easy:2, medium:3, hard:1 | hosp_lv, insu_type, med_type |
| 支付比例（payment_ratio） | 11 | easy:1, medium:7, hard:3 | insu_type, hosp_lv, psn_type, med_type |
| 封顶线（cap） | 4 | easy:1, medium:3 | insu_type, med_type |
| 通用规则（general） | 8 | easy:1, medium:5, hard:2 | psn_type, med_type |
| 适用范围（scope） | 9 | easy:3, medium:4, hard:2 | insu_type, psn_type |
| 排除规则（exclusion） | 6 | easy:2, medium:4 | insu_type |
| 跨类别（cross） | 4 | medium:1, hard:3 | 多 rule_type |
| setl_type 维度 | 3 | medium:1, hard:2 | setl_type |
| 简单关键词（keyword） | 5 | easy:5 | 宽泛关键词 |
| psn_type 维度 | 3 | medium:3 | psn_type |
| **合计** | **59** | easy:15, medium:31, hard:13 | **6 rule_types × 4 insu_types × 5 med_types** |

### 3.2 标注方法

**宽松自动标注**（`is_relevant()` in `eval_metrics.py`）：

```python
# 规则：rule_type 匹配 AND（至少 1 个维度字段匹配 或 无维度约束）
def is_relevant(hit, expected) -> bool:
    # 1. rule_type 必须匹配
    if expected.get("rule_types"):
        if entity["rule_type"] not in expected["rule_types"]:
            return False
    # 2. 至少 1 个维度匹配（insu_type/hosp_lv/psn_type/med_type/setl_type）
    for field in dim_fields:
        if field in expected and entity.get(field) == expected[field]:
            return True
```

**严格人工标注**：后续由医保业务专家对采样 20 条 query 逐条判断 `relevant / partially_relevant / not_relevant`。

### 3.3 评估指标矩阵

| 指标 | 缩写 | 定义 | 评估阈值（向量/BM25） | 用途 |
|------|------|------|------|------|
| Recall@5 | R@5 | 前 5 命中相关/期望相关 | ≥ 0.50 / ≥ 0.30 | 主要指标：是否遗漏 |
| MRR | MRR | 第一个相关结果的倒数排名均值 | ≥ 0.30 / — | 首个正确的排序位置 |
| Hit@1 | H@1 | 首位命中率 | ≥ 0.40 / — | 最严格：第一个就对 |
| NDCG@5 | N@5 | 归一化折扣累积增益 | ≥ 0.40 / — | 综合排序质量 |
| NDCG@10 | N@10 | k=10 的 NDCG | 诊断 | 大窗口排序 |
| MAP@10 | MAP | 平均精确率均值 | 诊断 | 综合精度 |
| Precision@5 | P@5 | 前 5 精确率 | 诊断 | 噪音控制 |

**按分组**：所有指标均支持按 `difficulty`（easy/medium/hard）和 `rule_type`（6 类）分组汇总。

[来源: `eval_metrics.py` — `evaluate_all()` 函数]

### 3.4 评估对比基线

| 基线 | 检索方式 | 说明 |
|------|------|------|
| **Vector** | bge-base-zh-v1.5 768d HNSW+COSINE | 当前生产管线 |
| **BM25** | rank_bm25 Okapi (k1=1.2, b=0.75) + jieba 医保词典 | 纯 Python 外部实现 |
| **Hybrid (RRF)** | RRF(k=60) 融合 Vector + BM25 | 混合检索模拟 |

## 四、BM25 技术方案分析

### 4.1 约束条件

- **Milvus v2.4.15** 不支持 `SPARSE_FLOAT_VECTOR` / `BM25InvertedIndex`（从 v2.5 引入）
- 生产集合 `policy_rules_v2` 全部为 `FLOAT_VECTOR(768d)`，无稀疏向量字段
- full-text 搜索完全依赖 `embedding_text` → 向量化 → ANN

### 4.2 方案对比

#### 路径 1：升级 Milvus 2.5+ → 原生 BM25

| 维度 | 评估 |
|------|------|
| **实现复杂度** | 高 — 需要升级整个 Milvus 服务 + schema 变更 + 数据迁移 + 全量 re-index |
| **性能** | 最优 — 原生 SPARSE_FLOAT_VECTOR，BM25 计分在 Milvus 内部完成 |
| **运维影响** | 高 — 涉及生产数据库升级，需要停机窗口 + 回滚预案 |
| **产品集成** | 好 — 与现有 ANN 搜索统一在 Milvus 内，`hybrid_search()` 原生支持 |
| **时间线** | 8-12 周（含测试+迁移+验证） |
| **风险** | 中高 — 升级失败可能影响生产检索，pymilvus 2.6.x 与 Milvus 2.5+ 兼容性需验证 |

#### 路径 2：外部 BM25（rank_bm25 Python 库）→ RRF 融合

| 维度 | 评估 |
|------|------|
| **实现复杂度** | 低 — 纯 Python，无需变更 Milvus 或 schema |
| **性能** | 中 — 外部 BM25 需要加载全部语料（337 rules ~0.1MB），检索 < 10ms |
| **运维影响** | 零 — 无基础设施变更 |
| **产品集成** | 中 — 需要在检索管线上额外做 RRF 融合，结果列表需合并去重 |
| **时间线** | 1-2 周（本评估已实现基础原型） |
| **风险** | 低 — 纯应用层代码，不影响生产检索管线 |

### 4.3 推荐方案：路径 2（外部 BM25）+ 长期向路径 1 演进

**理由**：

1. **立即可用**：`rank_bm25`（0.2.2）是成熟的 Python BM25 实现，配合 `jieba`（0.42.1）中文分词，已在本评估中验证可用。
2. **零风险**：不修改 Milvus 服务、不变更 schema、不影响当前生产检索。
3. **与升级不互斥**：外部 BM25 作为评估基线和混合检索原型，验证效果后再决定是否推动 Milvus 升级。
4. **医保中文适配**：已向 jieba 注入 50+ 医保术语（「起付线」「城乡居民基本医疗保险」「门诊慢特病」…），确保关键词不被错误切分。
5. **RRF 融合已验证**：`eval_metrics.py` 已实现 RRF(k=60) 融合算法，可对向量和 BM25 结果列表做重排序。

### 4.4 BM25 实现细节

#### 4.4.1 中文分词策略

```
分词器:  jieba 精确模式 + HMM 新词发现
词典:    自定义医保术语词典（50+ 词条，freq=100）
回退:    无 jieba 时 → 字符 bigram（2-gram 窗口）

关键术语保护示例：
  "三级医院住院的起付线是多少" → ["三级医院", "住院", "的", "起付线", "是", "多少"]
  "城乡居民大病保险起付标准" → ["城乡居民", "大病保险", "起付标准"]
```

#### 4.4.2 BM25 参数

| 参数 | 值 | 说明 |
|------|:--:|------|
| k1 | 1.2 | 词频饱和度（经典 Okapi 默认值） |
| b | 0.75 | 文档长度归一化（经典值） |

理由：医保政策事实文本通常较短（200-800 字），`b=0.75` 可避免短文档被过度惩罚。`k1=1.2` 是 BM25 的经典值，适用于大多数检索场景。

#### 4.4.3 RRF 融合算法

```
RRF(d) = Σ 1/(k + rank_i(d))

其中:
  - d = 文档（规则）
  - rank_i(d) = 文档 d 在第 i 个检索器结果中的排名
  - k = 60（经典平滑参数）
```

当前实现（`eval_metrics.rrf_fusion()`）支持任意两个结果列表的 RRF 融合。

### 4.5 政策知识 BM25 特殊挑战

| 挑战 | 说明 | 对策 |
|------|------|------|
| **同名不同义** | 「起付标准」在门诊和住院场景含义不同 | 依赖维度字段（med_type/hosp_lv）辅助判断 |
| **结构化维度** | BM25 无法利用 insu_type/hosp_lv 等维度过滤 | 混合检索时向量侧提供维度召回，BM25 补充关键词精确匹配 |
| **医保术语分词** | jieba 默认词典不包含「城乡居民基本医疗保险」等长术语 | 已注入 50+ 自定义医保术语 |
| **稀疏维度** | med_type/hosp_lv/setl_type 填充率低 | 标注时宽松处理（仅 rule_type 匹配也视为相关） |

## 五、产品集成分析

### 5.1 与现有架构集成点

```
产品检索管线（当前）:
  question → understand_query → embedding → ANN(HNSW+COSINE) → reranker → 返回

评估检索管线（新增）:
  question → ├─ embedding → ANN(HNSW+COSINE) → vector_results ─┐
             └─ jieba → BM25(rank_bm25) → bm25_results ─────────┤
                                                                 │
                                                          ┌─────┘
                                                          ▼
                                                     RRF 融合
                                                          │
                                                          ▼
                                                     最终结果列表
```

**集成建议**：

1. **评估阶段**（当前）：评估框架独立运行，不影响生产管线。通过 `EvalRetriever` 并排运行向量和 BM25，对比评估。
2. **原型阶段**（后续）：在 `milvus_retriever.py` 中增加可选 `use_bm25: bool = False` 参数，RRF 融合在检索器内部完成。
3. **生产阶段**（远期）：Milvus 升级到 2.5+ 后，使用原生 `hybrid_search()` 替代外部 RRF 融合。

## 六、结论与推荐

### 6.1 核心推荐

### 6.2 技术路由图

```
Phase 1 (当前) ──────────────────────────────────────────
  外部 BM25 评估基线（rank_bm25 + jieba + RRF）
  ├─ eval_queries.yaml: 59 条 query
  ├─ eval_retriever.py: vector + bm25 双模式
  ├─ eval_metrics.py: Recall@k/MRR/Hit/NDCG/MAP + RRF
  └─ test_retrieval_quality.py: 3 条基线 + 回归测试
                                │
Phase 2 (下迭代) ──────────────────────────────────────▼──
  人工标注 + 参数调优 + RRF 原型集成到检索器
  ├─ 采样 20 条人工标注
  ├─ BM25 k1/b 参数调优（基于评估结果）
  └─ RRF 融合集成到 milvus_retriever.hybrid_search()

  ├─ Milvus 2.5+ trial: 原生 SPARSE_FLOAT_VECTOR

  └─ 决策: 升级 or 继续外部 BM25
```

### 6.3 风险提示

1. **BM25 评估阈值偏低**：当前 BM25 Recall@5 门槛设在 0.30，低于向量（0.50）。原因是 BM25 对 paraphrase/同义改写敏感，对中文长尾 query 效果弱于向量。这是预期行为，不是异常。
2. **维度稀疏影响标注精度**：med_type/hosp_lv/setl_type 大量为空（~75-92%），导致宽松标注中维度约束实际不可用。需要人工标注补充。
3. **jieba 词典维护**：政策更新新增术语时需同步更新 `_MEDICAL_TERMS`。

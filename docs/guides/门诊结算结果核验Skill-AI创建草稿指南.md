# 门诊结算结果核验 Skill - AI 创建草稿指南

> 适用角色：医保办、收费处、产品经理等业务/产品人员  
> 示例场景：基于协和调研单据创建“门诊结算结果核验 Skill”  
> 文档状态：目标功能使用指南（AI 创建入口尚未实现，当前能力与差距见第 9 节）  
> 安全要求：示例不记录患者姓名、身份证号、电话、医保号、票据号或真实结算编号

## 1. 这项功能解决什么问题

业务人员提交一段需求说明或脱敏材料，由 AI 生成可编辑的 Skill 草稿，减少手工判断业务分类、输入指标、输出结构和验收用例的工作。

本示例把调研材料中的需求收敛为一个最小业务能力：

> 核验一笔门诊医保结算是否按已确认的参保身份、医疗类别和适用待遇完成结算，并解释核验依据、金额勾稽关系、异常点与下一步处理建议。

调研材料同时包含费用解释、慢特病申请和异地就医导办等诉求。本 Skill 只负责“门诊结算结果核验”，其他诉求应由独立 Skill 承担，避免一个 Skill 同时承担多个主动作。[来源：`raw/协和数据/协和调研单据.pdf` 第 1-9 页；`src/domain/AGENTS.md` §1.5]

## 2. Skill 的业务边界

### 2.1 要做的事

- 核对参保身份、医疗类别、就诊类型和结算日期等上下文是否完整。
- 核对总费用、医保范围内外金额、个人负担和各基金支付金额的勾稽关系。
- 核对适用待遇或特殊病资格是否有可追溯的政策依据。
- 输出“核验通过、部分可核验、无法核验”三类结论。
- 发现缺少指标、政策证据或结算数据时，明确列出不确定性和补充材料。
- 给出人工查询、复核或业务窗口处理建议。

### 2.2 不做的事

- 不重新计算并替代医保系统的正式结算结果。
- 不执行退费、冲正、补报、身份变更或待遇备案。
- 不承诺患者一定可以获得补偿或二次报销。
- 不根据单张票据直接认定医院或医保经办机构结算错误。
- 不输出未经来源支持的确定性政策结论。

出现退费、冲正、正式结算或数据修改诉求时，必须转为人工确认，由工作人员在既有业务系统处理。[来源：根目录 `AGENTS.md` §安全约束]

## 3. AI 创建草稿的目标流程

```text
输入需求或上传脱敏材料
  -> AI 提取业务目标、约束与证据
  -> AI 推荐 BusinessAction / BusinessObject
  -> AI 匹配已发布语义指标
  -> 人工处理冲突、缺失项和不确定性
  -> AI 生成结构化草稿与验收用例
  -> 人工确认“生成草稿”
  -> 进入现有草稿编辑器
  -> 校验、包预览、研发补齐执行逻辑
  -> 评测通过后 Test 激活
```

AI 只能生成独立草稿，不得自动物化、激活或覆盖正式 Skill。草稿内容变化后必须重新校验。[来源：`docs/superpowers/specs/2026-08-06-skill-management-workbench-design.md` §4、§6、§8]

## 4. 创建前准备

### 4.1 材料要求

可以提供：

- 脱敏后的票据或结算明细。
- 脱敏后的业务申请说明。
- 门诊结算字段说明或数据字典。
- 经审核的政策文件或政策知识链接。
- 期望回答示例和典型失败案例。

不得提供：

- 姓名、身份证号、社保卡号、医保号、手机号、住址。
- 票据二维码、完整票据号、真实门诊号或医保交易流水号。
- 数据库密码、密钥或生产系统访问凭证。

当前调研 PDF 含真实个人敏感信息，只能作为内部需求依据，不能原样上传到尚未具备自动脱敏证明的 AI 创建入口。[来源：`raw/协和数据/协和调研单据.pdf`；根目录 `AGENTS.md` §安全约束]

### 4.2 业务口径

在使用 AI 前至少确认：

1. 核验对象是门诊医保结算结果，不是住院结算。
2. 核验依据以医保系统结算明细和已发布政策知识为准。
3. 金额不一致时只标记异常，不自动认定责任方。
4. 政策或数据不足时允许返回部分结果，不强行给结论。
5. 所有确定性结论必须带来源；没有来源时必须声明不确定性。

## 5. 在 Portal 中使用 AI 创建

> 本节描述目标交互。目标入口建议为：`Skill 管理工作台 -> 新建 Skill -> AI 创建`。

### 第一步：提交需求

选择“AI 创建”，输入下列内容，或上传已经脱敏的材料：

```text
创建一个“门诊结算结果核验”Skill。

使用人：医保办、收费处工作人员。
业务目标：核验一笔门诊医保结算是否按正确的参保身份、医疗类别和待遇完成，
并说明金额勾稽关系、政策依据、异常点和下一步人工处理建议。

必须核对：
1. 费用总金额；
2. 医保范围内、范围外金额；
3. 起付金额、自付一、自付二和大额自付；
4. 基金、个人账户、现金及补充保险支付；
5. 参保身份、医疗类别、特殊病资格和异地结算状态。

约束：
- 只核验，不执行重新结算、退费、冲正或补报；
- 确定性结论必须有政策或结算数据引用；
- 证据不足时返回部分可核验或无法核验；
- 输出不得包含患者敏感信息。
```

### 第二步：核对 AI 的需求理解

AI 应展示“需求理解卡”，业务人员逐项确认：

| 项目 | 本示例应显示的内容 |
|---|---|
| Skill 名称 | 门诊结算结果核验 |
| 使用角色 | 医保办、收费处 |
| 核心问题 | 这笔门诊结算结果是否正确、依据是什么 |
| 主动作 | `verify`（核验） |
| 业务对象 | `settlement`（结算） |
| 风险边界 | 只读核验，不执行正式结算或修改 |
| 来源要求 | 结算数据引用或政策引用；不足时声明不确定性 |

本组合为能力矩阵中的合法组合：`Verify + Settlement`。[来源：`src/domain/AGENTS.md` §1.5 Action x Object 能力矩阵]

如果 AI 推荐 `explain`，应检查需求是否已经偏向“为什么个人支付这么多”；如果推荐 `guide`，应检查需求是否已经偏向“慢特病或异地就医怎么办”。不要为了保留全部原始诉求而接受多个主动作。

### 第三步：核对基本信息和路由建议

建议值：

| Portal 字段 | 建议填写或确认 |
|---|---|
| `skill_id` | `outpatient_settlement_verify_skill` |
| 名称 | 门诊结算结果核验 |
| 说明 | 核验门诊医保结算的上下文、金额勾稽关系和待遇适用情况，输出可追溯结论与人工处理建议 |
| 负责人 | 实际业务负责人或产品负责人 |
| `BusinessAction` | `verify` |
| `BusinessObject` | `settlement` |
| 触发词 | 门诊结算对不对、门诊报销对不对、核对门诊结算、门诊费用核验、为什么没按特病报销 |
| 排除意图 | 如何备案慢特病、如何办理异地就医、住院结算核验、退费、冲正 |

触发词只保留业务人员真实会说出的表达，不放数据库字段名、表名或规则 ID。

### 第四步：核对 AI 匹配的输入指标

AI 必须只推荐语义层中“已发布且有查询实现”的指标。建议需求如下：

| 业务输入 | 重要性 | 用途 |
|---|---:|---|
| 结算标识、就诊日期、结算日期 | 核心 | 定位本次门诊结算 |
| 医疗类别、参保类型、人员类别 | 核心 | 判断适用待遇上下文 |
| 特殊病资格、异地结算状态 | 条件核心 | 判断慢特病或异地待遇是否应参与本次结算 |
| 费用总金额 | 核心 | 金额勾稽起点 |
| 医保范围内金额、范围外金额 | 核心 | 核对目录内外费用 |
| 起付金额、自付一、自付二、大额自付 | 核心 | 核对个人负担构成 |
| 基金支付金额 | 核心 | 核对基本医保支付 |
| 个人账户支付、现金支付 | 核心 | 核对个人支付构成 |
| 补充保险、公疗、大病或救助支付 | 可选 | 核对其他支付渠道 |
| 适用政策规则与来源 | 核心 | 支撑待遇核验和引用 |

在当前仓库的语义层种子和代码定义中，未发现已登记的门诊结算金额指标。AI 应把上述项目标记为“未匹配/待语义层发布”，并阻止生成可物化版本；不得用住院指标替代，也不得自行编造 `metric_code`。实际创建时还需以 Portal 输入选择器返回的已发布指标为准。[来源：`src/semantic_layer/seed.py` 与 Skill 输入选择器实现；核对日期：2026-08-12]

业务人员可以：

- 保存 AI 草稿，等待语义层补齐指标；
- 将缺失项导出为“语义指标需求单”；
- 删除非必要的可选指标；
- 不得绕过核心指标缺失门禁。

### 第五步：核对 AI 生成的输出契约

AI 生成的输出至少应包含：

| 输出 | 说明 |
|---|---|
| 核验状态 | `complete`、`partial`、`unavailable` |
| 核验结论 | 面向业务人员的单一结论，不输出内部推理 |
| 上下文核对 | 参保类型、医疗类别、待遇资格等是否完整一致 |
| 金额核对 | 总费用、范围内外、个人支付、基金支付之间的勾稽结果 |
| 异常项 | 缺失、冲突或无法解释的项目 |
| 引用 | 结算数据来源和政策依据 |
| 不确定性 | 数据或政策证据不足之处 |
| 下一步建议 | 人工查询、补材料或到既有业务系统复核 |

禁止输出患者原始身份字段、内部表名、SQL、模型推理过程或无来源的“结算错误”判断。

### 第六步：核对 AI 生成的验收用例

至少保留以下用例：

| 用例 | 输入条件 | 预期结果 |
|---|---|---|
| 完整且勾稽一致 | 核心数据和政策证据齐全，金额关系一致 | `complete`，结论带引用 |
| 金额不一致 | 总费用与支付构成不一致 | `partial`，列出差额和人工复核建议，不认定责任 |
| 特病资格缺失 | 用户声称有资格，但系统无可验证资格数据 | `partial` 或 `unavailable`，说明缺失证据 |
| 政策证据不足 | 有结算数据，无适用政策依据 | `partial`，不得给确定性待遇结论 |
| 关键结算数据缺失 | 无法取得费用总额或主要支付金额 | `unavailable`，列出需补充字段 |
| 高风险请求 | 用户要求退费、冲正或重新结算 | 转人工确认，不执行动作 |
| 敏感信息输出检查 | 输入材料含个人身份信息 | 输出完成脱敏，不回显原值 |

### 第七步：生成草稿

确认下列门禁后点击“生成 Skill 草稿”：

- AI 对需求来源做了摘要，且没有回显敏感信息。
- 主动作只有 `verify`，业务对象只有 `settlement`。
- 所有核心输入指标已匹配，或明确显示为阻塞待办。
- 输出包含引用和不确定性。
- 高风险动作已排除。
- 业务负责人已确认范围。

生成后，系统应调用现有草稿服务创建独立 `SkillDraft`，状态为 `editing`，不会影响当前正式 Skill、路由或 Test Active 版本。[来源：`src/runtime/skill_management/draft_service.py`]

## 6. 进入现有工作台后的操作

### 6.1 编辑草稿

进入 `Skill 管理工作台 -> 草稿 -> 继续编辑`，再次核对：

- 说明、负责人、动作和对象。
- AI 选择的输入指标及“必填/可选”标记。
- 输入输出 Schema。
- 缺失指标和来源警告。

人工修改后先保存；内容变化会把草稿恢复为编辑状态，需要重新校验。

### 6.2 校验

点击“校验”。以下问题必须阻止后续流程：

- 缺少基本信息或业务挂载。
- 输入或输出 Schema 不是合法 JSON。
- 核心指标不存在、未发布或没有查询实现。
- 政策结论无法提供引用。
- 材料中含身份证号、密钥等敏感内容。
- 脚本包含危险导入或危险调用。

警告不应被忽略，应由业务负责人写明接受原因。

### 6.3 包预览

点击“包预览”，确认至少包含 `SKILL.md`、`skill_manifest.yaml`、`config.yaml` 和输入输出 Schema。预览用于确认生成结果，不代表 Skill 已具备可执行的核验逻辑。

### 6.4 研发交接

AI 草稿经业务确认后，研发至少需要补齐：

- 门诊结算输入指标及查询实现。
- 金额勾稽与待遇核验规则。
- 真实 `assembler.py` 执行逻辑。
- 来源引用、不确定性、脱敏和高风险拦截。
- 单元测试、API 测试和 Flow 测试。
- AI 生成的业务验收用例。

模型调用必须通过 `model_service/gateway`，外部医保数据必须通过 `adapters/` 或受控 MCP 边界访问。

### 6.5 物化、评测和 Test 激活

只有在执行逻辑和测试完成后，才可以按以下顺序继续：

```text
重新校验
  -> 包预览
  -> 物化并登记不可变版本
  -> 运行评测
  -> 查看候选版与基线差异
  -> 非创建人审批
  -> Test 激活
```

本项目当前只支持 Test 激活，不是生产发布。停用不会删除历史版本和审计记录。[来源：`docs/superpowers/specs/2026-08-06-skill-management-workbench-design.md` §1、§6]

## 7. AI 生成结果示例

AI 在人工确认前应展示类似以下摘要，而不是直接写正式 Skill：

```yaml
basic:
  skill_id: outpatient_settlement_verify_skill
  skill_name: 门诊结算结果核验
  owner: 待业务人员确认

business_mounting:
  business_action: verify
  business_object: settlement
  include_keywords:
    - 门诊结算对不对
    - 门诊报销对不对
    - 核对门诊结算
  excluded_intents:
    - 如何备案慢特病
    - 如何办理异地就医
    - 退费
    - 冲正

inputs:
  status: blocked
  reason: 当前语义层缺少已发布的门诊结算金额指标

output_contract:
  statuses: [complete, partial, unavailable]
  requires_citations: true
  requires_uncertainties_when_evidence_is_insufficient: true
  contains_high_risk_action: false
```

这里的 `inputs.status: blocked` 是 AI 预览状态，不是当前 `SkillDraft` 的正式字段。落草稿前应转换为结构化输入列表和待办清单。

## 8. 完成标准

AI 创建草稿功能达到可用状态，需要同时满足：

- 业务人员可以输入自然语言或上传脱敏材料。
- AI 能区分核验、解释和导办，不把调研材料中的多个诉求合成一个 Skill。
- AI 只匹配已发布指标，不生成虚假指标编码。
- AI 草稿在人工确认前不会写入正式目录。
- 生成的草稿可在现有编辑器打开、保存和校验。
- 缺失门诊指标时明确阻塞，不允许假通过。
- 生成内容带来源摘要、引用要求和不确定性要求。
- 敏感信息不会进入 Prompt、草稿、日志或输出。
- AI 不生成可直接执行高风险动作的配置。
- 物化、评测和 Test 激活继续使用现有治理门禁。

## 9. 当前已有能力与实现差距

| 能力 | 当前状态 | 本指南中的处理 |
|---|---|---|
| 草稿 CRUD、复制和 ZIP 导入 | 已实现并验证 | 直接复用 |
| 草稿结构化编辑 | 已实现 | AI 生成后进入现有编辑器 |
| 语义指标选择、校验和查询计划接口 | 已有基础实现 | AI 只能调用只读接口推荐指标 |
| 草稿校验、包预览、物化、版本登记 | 已实现 | 继续作为人工治理流程 |
| 评测与 Test 发布门禁 | 已实现并验证 | 继续复用 |
| 自然语言/文档生成 Skill 草稿 | **未实现** | 需要新增 AI 创建入口和后端生成服务 |
| 调研 PDF 的 OCR 与自动脱敏证明 | **未实现于 Skill 创建链路** | 上线前只允许使用人工脱敏材料 |
| 门诊结算专用语义指标 | **当前未发现** | 作为物化前阻塞项 |
| 模板向导完整保存关键词、Schema 和输入指标 | **当前不完整** | AI 接口需直接生成并保存完整结构化草稿 |
| 包生成器把输入契约写入 `needed_objects` | **当前未完成** | 物化前需补齐 |
| 模板物化后的业务执行逻辑 | 当前为占位执行器 | 研发补齐并验证后才能评测 |

因此，现阶段可先用本指南完成需求定义和 AI 草稿输出契约，但不能把现有人工“新建 Skill”页面当作已经具备 AI 创建能力，也不能把模板草稿物化成功当作业务 Skill 已可用。[来源：`src/apps/portal/app/skills/new/page.tsx`、`src/runtime/skill_management/package_generator.py`、`src/runtime/skill_management/materializer.py`]

## 10. 建议的最小产品落地范围

首版只新增一个“AI 创建草稿”入口，复用现有草稿和治理链路：

1. 接收自然语言和已脱敏文本；首版不直接解析含敏感信息的扫描 PDF。
2. 通过统一模型网关生成结构化草稿候选。

# 提示词与模型统一治理设计（评审稿）

> 状态：已批准，分阶段实施中。P1 只读治理页与 P2 显式路由已完成；用户已批准先建设开发/测试环境可用的治理控制面，再逐条迁移现有调用。生产写入口保持关闭。

## 1. 结论

可以把**正在运行的 LLM 提示词资产、模型档案和场景路由规则**纳入统一维护页面，并让所有生产调用经由 `ModelGateway` 路由；但不能把仓库中所有文本模板一键迁入数据库。

初始基线不满足“全部统一”的原因如下；其中可见性和显式路由已由 P1/P2 解决：

1. 政策事实抽取脚本通过 `DeepSeekLLMClient` 直接调用 OpenAI SDK，绕过了 `ModelGateway`、`ModelRouter`、统一异常和审计链路。
2. 多个运行场景原先未在 `ROUTING_TABLE` 显式登记；P2 已补齐活跃场景，未知场景仍保留兼容回退。
3. 已有 `prompt_templates` 残留表及旧接口/原型设计，但没有可用的版本化管理能力；P1 已增加只读 API 和 Portal 页面，P3A 补齐写入管理闭环。
4. Skill 的 `prompt_template.yaml` 已是可维护资产，但其中 `temperature`、`max_tokens` 当前未传入网关，配置与实际生效值不一致。

推荐采用“**版本化配置中心 + 代码/Skill 适配器 + 分阶段迁移**”。先建立只读台账和真实路由可见性，再迁移可控的生产提示词与路由；直接 SDK 调用和疑似遗留代码必须先验证可达性与输出契约，不能批量改写。

## 2. 目标、范围与非目标

### 2.1 目标

- 让每个生产 LLM 调用都有明确的 `scene`、`model_type`、模型档案、提示词标识和版本。
- 由统一页面维护已发布的提示词、模型档案与路由规则；变更可预览、审核、发布、追溯和回滚。
- 所有真实模型 HTTP 调用只保留在 `OpenAICompatibleProvider` 等 Provider 适配层，业务/知识代码统一通过 `ModelGateway`。
- 保留语义层 schema、意图注册表和 Skill 数据等运行时动态上下文，不把业务数据复制成静态提示词。

### 2.2 最小范围

- 统一治理 LLM 的 system/user prompt、模型参数、模型档案和 `scene + model_type → profile` 路由。
- 将直接 SDK 的政策事实抽取改为经网关调用，前提是其结构化 JSON 输出契约经过单独验证。
- 第一版页面仅面向具备治理权限的内部人员，不展示或保存 Provider 明文密钥。

### 2.3 非目标

- 不把 `answer_template.yaml`、`definition.yaml` 等确定性业务输出模板当作 LLM 提示词迁移；它们应继续由 Skill 管理，必要时在台账中标注为“业务响应模板”。
- 不把 `ModelGateway` 的 dummy 响应作为可发布提示词；它仅应保留为受控的开发/测试夹具。
- 不在首期实现任意时间的热更新、在线修改密钥或自动发布。P3A 只生成已发布快照，P3B 接入消费者时采用显式重载，确保运行时配置可复现。
- 不借本事项重构已废弃或未证实可达的 `policy_qa`、`llm_enhanced_extractor` 流程。

## 5. 风险与处理原则

| 风险 | 等级 | 处理原则 |
|---|---|---|
| 直接 SDK 调用绕过统一边界 | 高 | 在迁移完成前将其标记为例外；迁移时先写结构化输出回归测试，再替换调用。 |
| 运行时修改模型/提示词导致政策结论不可追溯 | 高 | 模板、档案和路由必须版本化，发布记录保存版本、操作者、时间、差异与回滚目标。 |

## 6. 推荐设计

### 6.1 控制面与运行面边界

```
治理页面
  ├─ 提示词版本（草稿 → 校验 → 审核 → 已发布）
  ├─ 模型档案（Provider 引用、模型名、参数、启用状态）
  └─ 路由规则（scene + model_type → 模型档案、显式退避）
             ↓ 仅加载已发布版本
治理 API / 存储
             ↓ 已发布快照（控制面先交付）
运行时解析器（后续按调用逐条接入）
             ↓ 显式重载
ModelGateway → ModelRouter → OpenAICompatibleProvider → 外部模型
             ↑
已迁移的业务代码只传 prompt_id、变量、scene、model_type
```

- **提示词版本**：包含稳定指令、变量 schema、输出模式（文本/JSON）、适用场景、状态、版本和审计信息。渲染前验证变量，禁止遗漏或额外未声明变量。
- **模型档案**：包含 Provider ID、模型名、允许参数、启用状态和版本；Provider 凭据只保留环境变量或密钥引用，不进入数据表。
- **路由规则**：`scene + model_type` 精确映射一个已发布档案；退避链显式保存，禁止用隐式 `default` 掩盖遗漏场景。
- **运行时快照**：控制面先生成只读的已发布快照，但不自动替换当前代码配置；后续消费者逐条接入并显式重载。这样既能独立验收管理能力，也不会把“发布成功”误报为“运行时已生效”。实时热更新在确有运维需求时再增加。

### 6.2 页面位置与最小交互

P1 已新增 Portal 顶级入口 `/model-governance`，名称为“模型与提示词治理”，不放入“政策知识”子页：模型路由是全平台 PaaS 能力，Skill、意图识别、政策抽取均会使用。

P3A 页面使用四个工作区：

1. **提示词**：查看来源、版本、变量、渲染预览和发布记录；区分“LLM 提示词”“业务响应模板”“开发夹具”。
2. **模型档案**：查看模型、参数、启用状态和脱敏后的 Provider 连接健康；不提供明文密钥编辑。
3. **路由规则**：查看每个场景的代码当前路由、治理库已发布路由、显式退避和接入状态。
4. **发布记录**：查看版本差异、审核记录、发布及回滚历史。

P1 已先提供只读台账和“配置来源不一致”告警。P3A 在用户批准的开发/测试边界内增加写入与发布，并同时交付版本、审核、快照和接入状态，保证控制面自身可验证。

控制面阶段在既有页面上增加四个工作区：提示词、模型档案、路由规则、发布记录。每项资产均展示“代码当前值”“治理库已发布值”“运行时接入状态”，发布后尚未迁移的资产明确标记为“已发布，待接入”，不得显示为“已生效”。

### 6.3 现有资产的适配原则

- 代码内稳定指令：迁移为版本化模板，调用点只保留 `prompt_id` 和运行时变量。
- 动态 schema/检索/注册表内容：作为受信任变量由代码生成，不由页面任意编辑。
- Skill YAML：保留为单一来源，通过适配器显示和校验；确认统一治理数据模型稳定后，再决定是否迁入版本库，避免双写漂移。
- 直接 `DeepSeekLLMClient`：仅在网关能够表达 JSON 输出格式、超时和允许参数后迁移；Provider 仍是唯一的 SDK/HTTP 所在层。
- 无法确认可达的遗留代码：标记为“待核验”，不作为首批迁移对象，也不在页面中允许发布。

## 7. 分阶段实施路径

| 阶段 | 最小可验证单元 | 改动边界 | 完成标准 |
|---|---|---|---|
| P0：基线 | 生成可追溯资产台账 | 文档、静态扫描规则、场景清单 | 每个生产调用都有状态：已统一、例外或待核验。 |
| P1：只读治理页 | 管理员查看真实生效配置 | 只读 API、Portal 页面；复用当前代码/YAML/static config | 页面展示的模型、路由和提示词来源与运行时一致；不写数据库、不改变调用。 |
| P2：显式路由 | 让活跃场景不再隐式回退 | `ModelRouter` 配置与测试 | `intent_recognition`、`skill_routing`、`policy_fact_extraction` 等均有显式规则。 |
| P3A：治理控制面 | 在开发/测试环境管理提示词、模型档案和路由 | 版本化仓储、校验/审核/发布/回滚 API、Portal 管理页、已发布快照；不改业务调用 | 三类资产均可管理、审计和回滚；页面区分当前代码值、已发布值及接入状态；生产写入口返回 403。 |
| P3B：运行时逐条接入 | 让现有调用逐步消费已发布配置 | 运行时解析器、调用点适配、网关审计；一次只迁移一条活跃调用 | 每条迁移均证明已发布版本被真实 API/流程消费且可追溯；未迁移调用行为不变。 |
| P4：政策事实抽取收口 | 直接 SDK 路径改走网关 | `DeepSeekLLMClient` 调用点、网关请求能力、回归测试 | JSON 输出、错误分类、重试和审计契约不变，且无业务层直连 SDK。 |
| P5：遗留处置 | 确认或下线不兼容遗留调用 | 仅实际可达的遗留模块 | 没有未知模型调用；不可达代码经独立评审删除。 |

P1 已按最小范围完成，先解决了“看不见真实配置”的问题；后续写能力遵守 P3A 的环境门禁和发布约束。

## 8. 验证路径

按仓库约定，涉及代码的每个阶段严格执行“单元 → API → 流程”顺序。

1. **单元测试**：模板变量校验、版本状态转换、路由精确匹配/显式退避、参数上限、密钥脱敏、动态 schema 变量注入、JSON 输出契约。
2. **API 测试**：治理台账与发布接口的角色、审计、版本冲突和未发布配置隔离；pytest 使用 `-p no:asyncio`。
3. **流程测试**：P3A 先验证 Portal 创建草稿、预览、异人审核、发布、读取已发布快照和回滚，并确认页面仍标记“待接入”；P3B 再逐条验证真实 API/流程消费已发布配置。
4. **防回归检查**：增加仓库级规则，除 Provider 适配层外禁止新增 `OpenAI`/HTTP 直连；对现存例外设明确白名单，直至 P4 收口。

## 9. 后续阶段决策边界

P1 不依赖写入权限、密钥托管和生产抽取样本，已按只读边界实施。进入对应后续阶段前，仍需以代码和测试确认以下事项；若现有上下文不足以唯一确定方案，应停止该阶段实施并报告：

1. 治理页的生产使用角色、审核人和发布权限仍待真实认证体系确定；P3A 已批准仅在 `MODEL_GOVERNANCE_DEV_MODE=1` 的开发/测试环境开放写入、审核和发布，生产默认返回 403。
2. P3A 继续以环境变量/现有密钥引用为 Provider 凭据权威来源；接入指定密钥管理服务属于后续生产化决策。
3. “所有活跃场景显式路由”已在 P2 接受并实施；未知场景的兼容回退在 P5 前保留并持续登记。
4. P3A 不绑定首个运行时消费者；P3B 第一条迁移必须从已注册 API 的活跃调用中选择，不能以未接入的 `intent.classify` 充当流程闭环。
5. 政策事实抽取脚本是否仍为生产路径，以及其 JSON 输出、超时、重试和模型选择的正式验收样本。
6. P1/P2 已完成；后续顺序已批准为 P3A 控制面 → P3B 逐条接入 → P4 直连收口 → P5 遗留处置。

## 10. 评审结论

该能力值得建设，但不应以“把所有字符串放入一个页面”为目标。正确边界是：先交付可独立验收的治理控制面，再让活跃调用逐条消费已发布快照，最终统一 LLM 调用入口、版本化提示词和显式模型路由。动态业务上下文、Skill 业务模板、测试夹具及未证实可达的遗留代码仍分别处理。用户已批准按 P1 → P2 → P3A → P3B → P4 → P5 的顺序实施；每个阶段仍须遵守本节边界和仓库验证规则。

## 14. P3A 控制面设计

### 14.1 后端边界

- 资产类型仅包含 `prompt`、`model_profile`、`route_rule`。确定性业务响应模板、Provider 明文密钥、动态 schema/检索结果和测试夹具不进入可编辑资产。
- 每项资产使用相同生命周期：草稿带 `revision` 乐观锁；校验通过后形成不可变版本；审核人与最后编辑人必须不同；发布记录维护开发/测试环境的唯一活动版本；回滚通过重新发布历史版本生成新记录，不原地修改历史。
- 存储沿用仓库既有模式：默认 PostgreSQL，只有显式 `USE_MEMORY_STORAGE=1` 才使用内存实现；数据库失败不得静默降级。
- Provider 凭据继续来自环境变量或未来密钥系统。模型档案只保存 Provider ID、模型名、参数白名单、启用状态和密钥引用标识。
- 已发布快照聚合三类活动版本，并为每项资产返回 `published_version`、`source_hash`、`runtime_status` 和关联消费者。P3A 的 `runtime_status` 只能为 `not_connected` 或既有静态来源状态，不驱动当前 `ModelRouter`/业务调用。
- 所有写接口先检查 `MODEL_GOVERNANCE_DEV_MODE=1`，再校验 `model_governance:write/review/publish` 权限；生产或未显式开启时返回 `403/MODEL_GOVERNANCE_DISABLED`。现有开发令牌解析器不得被描述为生产认证。

### 14.2 API 与页面最小交互

- API 提供资产列表/详情、创建和更新草稿、校验、渲染或路由预览、审核、发布、发布记录、回滚及已发布快照；统一使用具名 Pydantic 结果和 `AgentResponse`，版本冲突返回 409，变量或引用错误返回 422。
- Portal 复用 `/model-governance`，增加“提示词、模型档案、路由规则、发布记录”四个工作区，不另建第二个管理应用。
- 提示词预览只渲染稳定模板与显式测试变量；模型预览展示脱敏连接状态和最终参数；路由预览验证 `scene + model_type` 可解析到已发布且启用的模型档案。
- 页面必须并列展示代码当前值、治理库已发布值和运行时接入状态。P3A 发布后统一显示“已发布，待接入”，直到 P3B 的真实消费者验证完成。

### 14.3 最小可验证单元与交付顺序

1. 提示词管理闭环：草稿 → 变量校验/预览 → 异人审核 → 发布 → 已发布快照 → 回滚。
2. 模型档案管理闭环：草稿 → 参数/密钥引用校验 → 异人审核 → 发布 → 快照 → 回滚。
3. 路由管理闭环：只能引用已发布且启用的模型档案；预览解析结果后审核、发布和回滚。
4. Portal 管理流程：通过真实 API 完成上述闭环，并验证未授权、生产关闭、409 冲突、422 校验失败及“待接入”展示。

每个单元分别按单元测试 → API 测试 → Flow 测试验证；前三个闭环完成且 Portal 真实流程通过后，P3A 才完成。P3B 另行按一个活跃消费者一个最小单元迁移，不批量切换。

# 政策—数据语义协同发现设计

日期：2026-08-21  
状态：开发中（Phase 1 后端已实现，见 `docs/steering/政策知识治理-需求迭代记录.md`；前端与发布流水线待续）  
范围：政策语义异常线索发现、全政策交叉验证、语义发现聚合与价值排序、人工语义裁决、政策指标与业务对象指标的适用关系，以及 Skill 基于业务事实查询政策规则的闭环。

> [决策] 本能力命名为“政策—数据语义协同发现”（Policy–Data Semantic Co-Discovery，PDSC）。政策原文是语义权威源，业务数据是结构证据源，语义层负责形成可复用资产，人负责最终业务裁决。
>
> [关系] 本设计整合并修正 `2026-08-20-policy-field-database-evidence-discovery-design.md` 与 `2026-08-20-rule-driven-policy-structure-governance-ux-design.md` 的后续方向；不改变已发布政策快照不可变、语义变更通过候选 release 生效的原则。

---

## 1. 设计判断

### 1.1 出发点是否成立

政策结构化任务会持续暴露未知概念、字段混用、值域越界和跨单元不一致。bjyb 中的业务对象、字段定义和真实值域可以帮助判断这些线索是否代表可落地的语义资产；审核后的语义资产又可以反向提升政策抽取、规则检索和 Skill 查询能力。因此，“政策触发线索、业务数据增强验证、语义层统一治理、Skill 消费”的方向合理且有实际价值。

它不是“从数据库批量找字段”，也不是“模型自动判断政策错误”，而是以下闭环：

```text
结构化任务产生可验证异常信号
  → 系统提出待验证语义假设
  → 全部政策单元与数据库值域交叉验证
  → 聚合为语义治理决策包
  → 人工一次性裁决指标、对象、字段、值域及影响范围
  → 构建候选语义契约与政策 release
  → 验证后人工激活
```

### 1.2 对当前实现的评价

当前规则治理页面以人工给定 `release_id + rule_ids` 为入口，能够还原 lineage、匹配数据库证据并生成未发布草稿，但它属于“人工指定后的治理辅助”，还不是真正的主动语义发现。系统不能把用户指出的问题包装为自身发现；新设计必须明确区分机器观察、系统假设和人工结论。

[来源: `src/knowledge_extension/rule_explanation/rule_governance.py`、`src/apps/portal/src/components/policy-knowledge/rule-governance-wizard.tsx`]

## 2. 核心原则

1. **机器发现线索，不宣布业务真相**：系统只能陈述可追溯的结构异常并提出假设。
2. **所有政策统一考虑**：发现和影响分析覆盖全部政策文档、单元、版本和规范规则；历史政策不排除，但保留时间、地区、人群及有效期差异。
3. **一张卡代表一个语义发现簇**：任务、规则和政策单元是证据来源，不是卡片身份。
4. **一屏完成全盘判断**：人工裁决时同时看到概念、政策来源、业务对象、字段、值域、交叉验证和影响范围，不把相互依赖的判断拆成向导。
5. **政策指标与业务指标分离**：`zcgz` 指标只描述 Milvus 政策规则字段；数据库字段由其他业务对象指标承接。
6. **关系显式、实现克制**：本期只建设政策适用关系，不提前建设通用指标关系图谱。
7. **政策专用指标是合法例外**：政策证据充分但没有可靠业务字段时允许 `policy_only`，不得强绑错误字段。
8. **人工批准完整方案，不逐条修数据**：系统完成聚合、评分、交叉验证、影响计算和候选构建，人只处理业务语义与上线裁决。

## 3. 机器与人的职责边界

| 环节 | 系统负责 | 人负责 |
|---|---|---|
| 线索发现 | 检测未知概念、字段和值域混用、编译问题、跨单元不一致 | 可补充人工反馈，但不需要逐条寻找异常 |
| 发现聚合 | 精确重复自动去重，形成近似语义簇及合并建议 | 对有歧义的簇执行合并或拆分 |
| 全政策验证 | 检索并归类支持、扩展、冲突、无关单元 | 判断真正存在业务歧义的少数证据 |
| 数据证据 | 推荐业务对象、指标、字段和值域映射 | 确认字段业务角色和代码释义 |
| 建模建议 | 生成复用、新增、修复抽取或 `policy_only` 方案 | 一次性批准或调整完整方案 |
| 影响分析 | 计算政策单元、规则、版本及 Skill 依赖 | 决定是否进入候选发布 |
| 发布执行 | 重提取、编译、构建索引和自动验证 | 最终激活候选版本 |

页面不得使用“原始问题”描述系统并未自动发现的事实。统一改为：

- **发现线索**：机器实际观察到的客观差异；
- **系统假设**：基于线索提出、尚未被人工确认的语义解释；
- **人工反馈**：用户明确提交的独立证据来源；
- **人工结论**：审核后形成的正式语义裁决。

## 4. 自动发现信号

### 4.1 当前可复用信号

- `EXTRACTION_UNKNOWN`：抽取结果出现未知概念或值；
- `CONFLICT_PARTITION`：同族规则出现需要拆分的语义轴；
- 编译 `WARN/REVIEW/FAIL` 与未解析关系；
- 人工规则纠偏 `MANUAL_RULE_CORRECTION`；
- 数据发现字段和值域画像。

[来源: `src/knowledge_extension/rule_explanation/semantic_alignment.py`、`policy_compiler/models.py`、`pipeline_orchestrator.py`]

### 4.2 需要补充的确定性检测

1. **轴和值类型不一致**：同一指标同时承载机构类型、医院等级等不同角色值。
2. **原文区分被结构压缩**：政策原文明确区分多个类别，规范规则却落入单一宽泛字段。
3. **跨单元映射不一致**：近似政策表达在不同任务中映射到不同指标或值域。
4. **规则主体与条件冲突**：综合待遇、具体基金分项和结果字段互相污染。
5. **值域越界**：抽取值不属于指标发布值域且没有合法来源映射。
6. **业务字段角色冲突**：候选数据库字段名称相似但定义角色明确不符。

每条信号只保存可重放事实：任务、文档、单元、抽取、规则、编译步骤、精确原文和结构差异。信号本身不保存“这是正确指标”的确定性结论。

## 5. 全政策交叉验证

### 5.1 范围

每个语义假设必须检索全部政策资产：

- 全部政策文档和政策单元；
- 全部历史、当前和候选版本；
- 全部规范规则和 lineage；
- 有效期、地区、人群、险种和医疗场景。

统一考虑不等于抹平差异。结果按以下类型归类：

| 类型 | 含义 | 对治理的作用 |
|---|---|---|
| `supporting` | 独立政策证据支持同一概念和值域 | 增加可信度 |
| `extending` | 发现新的合法政策值或适用范围 | 扩充值域和影响范围 |
| `temporal_variant` | 不同时期含义或值域变化 | 建议时间版本约束 |
| `conflicting` | 同一表达存在无法自动解释的语义冲突 | 阻止一键批准 |
| `irrelevant` | 仅文字相似，业务角色不同 | 保留排除理由，不参与得分 |

### 5.2 数据库额外值反向验证

候选业务字段的值域除当前政策值外，其余有释义值也要反向检索全部政策单元：

```text
数据库额外值
  → 中文释义与别名
  → 全政策检索
  → 找到支持：值域扩展
  → 找到冲突：人工判断
  → 未找到：数据库专用值
  → 无释义：不可判断
```

数据库值不能直接证明政策概念。最终归类必须由政策原文独立支持。

### 5.3 时间处理

历史政策参与概念发现、值域演变和影响力计算。已发布的历史文档与 release 快照保持不可变；新语义契约通过新版本重新解释相关政策单元，而不是回写历史制品。

## 6. 去重与语义聚类

### 6.1 两级去重

**证据级精确去重**由系统自动执行：

- 同一任务重跑；
- 同一政策单元重复抽取；
- 同一规则相同异常重复上报；
- 同一数据库扫描字段重复命中。

证据指纹至少包含来源类型、文档/单元/抽取或扫描身份、结构异常类型和规范化片段。重复证据不增加可信度、出现次数或价值分。

**语义级聚类**把不同来源中的近似概念组合为候选发现簇。聚类参考：

- 规范化概念名称、别名和定义；
- 业务角色和语义类型；
- 政策值域重合与扩展关系；
- 候选业务对象和字段角色；
- 时间、地区、人群和场景约束。

系统只自动合并完全一致的语义签名。有歧义的近似概念显示“建议合并”，由人选择合并、按时间拆分或按业务场景拆分。

### 6.2 卡片身份

卡片身份不包含任务或 release：

```text
SemanticDiscoveryCluster
  cluster_id
  normalized_concept
  semantic_role
  semantic_type
  policy_value_signature
```

任务、政策文档、单元、规则、release 和人工反馈均作为 `evidence_sources` 附着在簇上。

## 7. 治理价值分

### 7.1 主公式

```text
治理价值分 =
发现可信度 × 40%
+ 语义落地支持度 × 35%
+ 全政策影响力 × 25%
```

页面同时显示总分和三个子分，禁止只展示不可解释的总分。

### 7.2 发现可信度

- 结构异常是否明确、可重放；
- 支持证据来自多少独立政策文档和单元；
- 是否跨任务重复出现；
- 支持、扩展、冲突和排除证据比例；
- 同一来源重复运行不加分。

### 7.3 语义落地支持度

- 政策指标定义和值域是否完整；
- 候选业务对象和指标角色是否一致；
- 字段中文定义与业务角色匹配度；
- 政策值覆盖率、数据库值释义率和关系映射证据；
- 数据完整性、扫描质量和新鲜度。

`policy_only` 没有业务字段关系，不因此否定政策语义，但明确降低“业务数据可自动查询”部分得分。

### 7.4 全政策影响力

- 涉及的独立政策文档和单元；
- 覆盖时期、地区、人群、险种和医疗场景；
- 受影响规范规则；
- 需要重新验证的 Skill；
- 是否补齐多个政策共同缺失的语义轴。

### 7.5 分数门禁

- 只有单一任务且没有独立政策支持时，状态必须为“待验证”；
- 存在未解决语义冲突时可以高优先级展示，但不能一键批准；
- 数据库代码没有可靠中文释义时，值域对齐度显示“不可计算”，不得伪造低分或高分；
- 人工反馈是来源证据，不能被计作系统自动发现能力。

## 8. 值域符合度

### 8.1 展示的四类值

| 层次 | 说明 |
|---|---|
| 当前触发政策值 | 触发任务原文中的值 |
| 全政策值 | 全部政策交叉验证发现的支持和扩展值 |
| 业务指标标准值 | 业务对象指标的正式值域 |
| 数据库来源值 | 适配器/源系统原始代码和值 |

### 8.2 量化结果

```text
值域对齐度 =
全政策值覆盖率 × 60%
+ 数据库值释义率 × 25%
+ 映射证据可信度 × 15%
```

同时显示：

- 当前单元政策值覆盖；
- 全政策值覆盖；
- 业务指标标准值数量；
- 数据库有释义、无释义和仅业务数据使用的值；
- 一对一、一对多、多对一和未匹配关系；
- 每条映射对应的政策与数据证据。

数据库字段的额外值不直接算错误。经全政策验证后分别标为值域扩展、数据库专用值或不可判断。

## 9. 一屏语义治理决策包

### 9.1 页面结构

当前三步向导改为一屏决策卡。首屏必须让审核人无需展开即可看见：

1. 系统假设和治理价值分；
2. 为什么出现：客观异常线索，不伪装成人工结论；
3. 政策来源：文档、条款、原文、版本、单元和规则；
4. 全政策交叉验证：支持、扩展、时间变体、冲突数量；
5. 政策指标及 Milvus 字段建议；
6. 业务对象指标、中文对象名、中文表名/物理表名、中文字段名/物理字段名及数据来源；
7. 完整值域和逐值对齐结果；
8. 预计影响的政策单元、规则和 Skill；
9. 系统推荐的完整建模方案。

详细政策单元、全部原文、技术 ID、扫描统计和排除证据按需展开。

发现列表默认按治理价值分降序排列；同分时优先展示未解决冲突更多、影响政策单元更多且最近重新验证的发现。排序依据必须在页面可见。

### 9.2 人工动作

- **接受完整方案**：一次性确认指标、对象、字段、值域、关系和影响范围；
- **调整方案**：修改任何一项后系统重新计算交叉验证、分数和影响；
- **合并/拆分发现**：处理语义聚类歧义；
- **证据不足**：保留待补证据状态；
- **不是问题**：记录理由并归档相同指纹；
- **政策专用指标**：政策证据充分但无可靠业务字段时采用。

正常接受推荐不要求填写说明；改选、排除强证据、拆分或驳回时要求理由。

## 10. 政策指标、业务指标与政策适用关系

### 10.1 正确边界

```text
政策规则对象 zcgz
└─ zcgz.institution_category
   └─ 来源：Milvus policy_rules.institution_category

医疗机构对象 Institution
└─ Institution.category
   └─ 来源：领域对象属性 + 适配器
      └─ 底层可映射 bjyb m_institution.H_TYPE
```

政策指标不能直接绑定 SQL Server 字段。数据库字段应由已有业务对象指标承接；没有合适指标时新增业务指标，没有合适业务对象时才建议新建业务对象。业务对象是业务概念，不按数据库表机械创建。

[来源: `docs/steering/语义层设计规范.md` §7–§8；Metric.source_field 指领域模型属性而非数据库列]

### 10.2 当前最小关系模型

本期不建设通用 `MetricRelation`。只新增固定语义的：

**政策适用关系 `PolicyApplicabilityRelation`**

```text
relation_id
policy_metric_code
business_metric_code
policy_value_domain_code
business_value_domain_code
value_mappings
source_proposal_id
status
revision
created_at
updated_at
```

约束：

- `policy_metric_code` 必须属于 `zcgz` 且指向 Milvus 政策规则字段；
- `business_metric_code` 必须属于可由 Business Facts Builder 查询的业务对象；
- `value_mappings` 保存政策条件值与一个或多个业务标准值的对应；
- 关系只有一种语义：业务事实值如何转换为政策适用条件；
- `policy_only` 指标不创建该关系。

关系值映射示例只使用已经有可靠业务释义的值，不允许把“其他定点医疗机构”映射为“一级/二级/三级医院”，因为医院类别与医院等级是独立业务轴。

### 10.3 Skill 运行时

```text
Skill 声明业务对象指标
  → Business Facts Builder 获取标准业务值
  → PolicyApplicabilityRelation 解析政策条件值
  → Policy Retriever 使用 zcgz 指标构建 Milvus 标量过滤
  → 返回适用规则和来源
```

Skill 不保存数据库字段、SQL、Milvus 物理字段或关系值映射。

最小解析接口：

```text
resolve_policy_filters(
  business_metric_code,
  business_standard_value
) -> list[(policy_metric_code, policy_value)]
```

## 11. 审核、构建与激活

### 11.1 完整决策包

审核通过后生成一个原子治理变更集：

- 新增或复用 `zcgz` 政策指标及 Milvus 字段；
- 新增或复用业务对象指标及适配器来源；
- 两侧值域；
- `PolicyApplicabilityRelation` 和关系值映射；
- 全政策交叉验证与影响范围；
- 受影响政策单元的重提取和编译计划；
- 候选 release 的 Milvus schema；
- 受影响 Skill 的查询验证样例。

复用现有 `SemanticProposal` 状态机，不新建第二套审核状态机。`accepted` 表示语义方案已批准，不等于已经发布或激活。

### 11.2 执行顺序

```text
人工批准语义治理决策包
  → 发布语义对象/指标/值域/适用关系候选版本
  → 对全部受影响政策单元重提取
  → 规范规则重新编译
  → 构建候选 Milvus collection
  → 执行规则、值域和受影响 Skill 验证
  → 展示候选版本影响和失败项
  → 人工激活
```

任一步失败，当前活动语义对象版本和政策 release 保持不变。

### 11.3 发布门禁

- 政策指标已进入候选 Milvus schema；
- 业务指标有可用对象、领域属性和适配器，或明确为 `policy_only`；
- 关系两端指标及值域版本一致；
- 无未确认数据库代码被写入正式关系映射；
- 受影响政策单元编译通过；
- Skill 能从业务事实解析政策过滤条件并命中正确规则；
- 输出保留政策、数据和人工裁决来源。

## 12. 为未来图谱保留的最小扩展边界

本期不建设图数据库、通用关系类型、多跳查询或关系推理。为未来升级保留以下兼容性：

1. `relation_id` 是稳定唯一标识；
2. 两端使用稳定 `metric_code`，天然可迁移为图节点引用；
3. 关系方向固定为政策指标到业务指标；
4. 值映射是结构化属性，不写入不可解析文本；
5. 关系拥有独立状态、revision 和来源提议；
6. 存储和 API 不依赖页面卡片结构。

出现经过验证的第二类指标关系需求时，再将模型扩展为：

```text
MetricRelation
  source_metric_code
  target_metric_code
  relation_type
  properties
```

届时 `PolicyApplicabilityRelation` 可无损迁移为 `relation_type=policy_applicability` 的图谱边。本期不为尚未出现的关系预建枚举、遍历器或图存储。

## 13. 最小验证范围

1. 证据精确去重：同任务重跑不增加分数和证据数量。
2. 语义聚类：机构类别的多种政策表达形成一个候选簇，存在冲突时不自动合并。
3. 全政策验证：历史、当前和候选政策均参与支持、扩展、时间变体和冲突分类。
4. 值域验证：数据库额外值可找到其他政策单元；无释义代码显示不可判断。
5. 价值评分：三个子分和总分可解释，重复证据不刷分。
6. 一屏决策包：政策来源、中文表字段、值域对齐、影响范围和完整建议首屏可见。
7. 关系边界：`zcgz` 指标只指向 Milvus；业务指标通过领域对象/适配器取数。
8. Skill Flow：业务指标值经 `PolicyApplicabilityRelation` 转换为政策过滤条件并命中正确规则。
9. `policy_only`：无业务字段时仍可发布政策指标，但不生成适用关系。
10. 发布失败：候选构建或 Skill 验证失败不改变活动版本。

## 14. 非目标

- 不自动认定政策结构错误；
- 不把人工反馈伪装成机器发现；
- 不只分析当前活动政策；
- 不从全部数据库字段批量创建指标；
- 不把数据库表直接建成业务对象；
- 不让政策指标直接绑定 SQL Server 字段；
- 不建设通用指标关系引擎、知识图谱或图数据库；
- 不实现多跳关系推理；
- 不绕过人工审核自动发布指标、值域、关系或政策 release；
- 不修改历史政策文档和历史发布快照。

## 15. 已确认决策摘要

1. 方法名称采用“政策—数据语义协同发现（PDSC）”。
2. 一项发现按业务语义聚合为一张卡，重复证据自动去重。
3. 总分由发现可信度、语义落地支持度和全政策影响力构成。
4. 数据库完整值域必须反向验证全部政策单元并展示对齐度。
5. 人在一屏内基于完整方案进行原子裁决。
6. 所有历史和当前政策均参与发现、评分和影响分析。
7. 政策指标与业务对象指标独立建模。
8. 本期只新增 `PolicyApplicabilityRelation`，保留未来迁移为图谱边的边界。
9. 政策证据充分但无可靠业务字段时允许 `policy_only`。
10. Skill 通过业务对象指标和政策适用关系生成 Milvus 政策过滤条件。

# Skill 治理工作台 UI 重构详细设计（方案 2）

> 状态：待评审
>
> 日期：2026-08-05
>
> 页面：Portal `/skills`
>
> 目标用户：Skill 研发、测试、治理与信息科管理人员
>
> 设计基线：版本化资产库、批量评测和 test shadow 发布门禁已经实现

## 1. 背景与结论

当前 `/skills` 已具备版本登记、制品证据、路由测试、执行测试、批量评测、人工审批和 test shadow 激活能力，但页面仍按“后台数据表 + 多页签弹窗”组织：

- 页面同时出现 `Skills`、`技能包管理`、`Skill 版本化资产库` 三层标题，入口语义重复；
- 筛选、搜索、技术健康指标、九列表格、关键词和操作按钮处于同一视觉层；
- “引用指标”“排除关键词”等表头被压缩换行，完整关键词占据一行的大部分空间；
- 版本、评测和发布属于主流程，却隐藏在详情弹窗的九个页签中；
- 用户必须先理解资产表字段，再寻找下一步操作，页面没有表达 Skill 当前处于生命周期的哪一步。

[来源: `src/apps/portal/app/skills/page.tsx`] 当前页面使用 `max-w-[1120px]` 容器和嵌套白色卡片。

[来源: `src/apps/portal/src/components/infra-skill-management.tsx`] 当前资产表包含九列，详情使用滚动弹窗承载九个页签。

2026-08-05 对 `http://127.0.0.1:8887/` OpenSPG 本地页面的浏览器对照显示，其成熟感主要来自：稳定的全局与局部导航、单一主工作区、明确步骤、克制边界和围绕任务组织的信息，而不是更复杂的装饰。

**设计结论**：采用“左侧 Skill 目录 + 右侧治理工作区”的双栏布局，把“版本登记 → 批量评测 → 人工审批 → Test Shadow”提升为页面主路径。详情不再作为弹窗，技术字段渐进展开。

## 2. 目标与成功标准

### 2.1 目标

1. 用户进入页面后 5 秒内能识别 Skill 总体健康、待处理事项和当前 test 状态；
2. 用户选择 Skill 后，无需打开弹窗即可判断当前生命周期位置和下一步动作；
3. 版本、评测、审批和激活在同一个稳定工作区内完成，切换步骤不丢失 Skill 上下文；
4. 关键词、Manifest、目录和原始 JSON 不再占据默认首屏；
5. 页面能扩展到数十个 Skill，不产生逐 Skill 请求评测与发布状态的 N+1 问题；
6. 保持现有安全边界、写接口、权限和发布门禁判断不变。

### 2.2 可量化验收

- 1440px 宽桌面首屏完整显示全局标题、五个治理指标、Skill 列表和选中 Skill 的生命周期步骤；
- 默认视图不存在横向滚动条或纵向换行的表头；
- 从页面进入到执行“运行候选评测”不超过 3 次主操作；
- 从 passed 评测到 test shadow active 的每个状态只显示一个明确主动作；
- 刷新页面后恢复 `skill_id`、页签和环境；
- 局部请求失败不清空目录、选中项和其他已加载页签；
- 键盘能够完成 Skill 选择、页签切换和主流程操作；
- 现有 T1、T2a、T2b 和 Chromium E2E 保持通过。

## 3. 范围边界

### 3.1 本次包含

- `/skills` 页面信息架构和视觉层级重构；
- 资产表改为紧凑 Skill 目录；
- 详情弹窗改为同页治理工作区；
- 生命周期步骤条和下一步引导；
- 版本、评测、发布和技术详情重新分组；

- URL 状态、加载/空态/错误态、响应式和无障碍设计；
- 对现有 Portal 组件做与本页面直接相关的渐进拆分。

### 3.2 本次不包含

- 不新增生产灰度、生产回滚或运行趋势能力；
- 不允许在 Portal 编辑、上传或删除 Skill 源文件；
- 不修改 `SkillLoader`、Skill assembler 或业务路由算法；
- 不改变现有发布门禁、审批、防自审和幂等规则；

## 4. 用户任务与页面优先级

| 优先级 | 用户任务 | 页面回答的问题 |
|---|---|---|
| P0 | 发现异常或待处理 Skill | 哪些 Skill 未登记、评测失败、待审批或尚未激活？ |
| P0 | 推进 test 发布 | 当前在哪一步，为什么不能继续，下一步做什么？ |
| P0 | 查看不可变证据 | 当前版本、Git commit、artifact hash 和校验是否一致？ |
| P1 | 执行批量路由评测 | 固定用例是否通过，与现有 test 基线相比有什么变化？ |
| P1 | 路由或执行调试 | 某个问题为什么命中该 Skill，执行结果是否符合契约？ |
| P2 | 查看技术细节 | Manifest、字段映射、查询计划、目录和 `SKILL.md` 是什么？ |

页面默认服务 P0/P1。P2 信息只在“开发详情”页签内展示。

## 5. 页面总体结构

```text
┌──────────────────────────── Portal 全局 Header ─────────────────────────────┐
│ Skill 管理                               环境：test  [路由调试] [同步状态] │
│ 版本证据、固定评测与 Test Shadow 发布治理                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│ Skill 总数  1 │ 健康  1 │ 待评测  0 │ 待审批  0 │ Test Active  1          │
├──────────────────────┬──────────────────────────────────────────────────────┤
│ Skill 目录            │ 结算解释技能                         Test Shadow     │
│ [搜索] [状态筛选]     │ settlement_explain_skill · v2.0.0                 │
│                      │                                                      │
│ ● 结算解释技能        │ ①版本登记 ─ ②批量评测 ─ ③人工审批 ─ ④Test 激活     │
│   v2.0.0              │                 当前：Test Active                   │
│   已登记 · 评测通过    │                                                      │
│   Test Active         │ [总览] [版本] [评测] [发布] [开发详情]              │
│                      │                                                      │
│                      │ 当前页签内容                                         │
└──────────────────────┴──────────────────────────────────────────────────────┘
```

### 5.1 页面头部

只保留一个标题：`Skill 管理`。

副标题固定为：`版本证据、固定评测与 Test Shadow 发布治理`。

右侧操作：

1. 环境选择器：第一阶段只有 `test` 可操作，`dev` 只读展示；不显示不可用的 `prod`；
2. `路由调试`：次要按钮，打开右侧抽屉，不打断当前治理上下文；
3. `同步状态`：图标按钮，刷新只读状态，不自动登记版本。

移除当前 `Skills` 胶囊、`技能研发 / 详情 / 路由测试` 面包屑和卡片内的重复标题。

### 5.2 治理指标带

指标只展示能驱动处理的状态：

| 指标 | 定义 | 点击行为 |
|---|---|---|
| Skill 总数 | 当前目录中可治理 Skill 数 | 清除状态筛选 |
| 健康 | 已登记、校验通过且无门禁失败 | 筛选健康 Skill |
| 待评测 | 当前制品没有有效 passed 评测 | 筛选待评测 Skill |
| 待审批 | candidate 为 approval_pending | 筛选待审批 Skill |
| Test Active | 当前存在 test shadow active | 筛选活动 Skill |

指标卡使用文本、图标和数字共同表达，不使用颜色作为唯一状态。没有数据时显示 `0`，聚合接口失败时显示 `—` 和“状态更新失败”，不得伪造为零。

### 5.3 主工作区

主工作区只保留一个白色容器，不再使用“页面外卡片 + 组件 Card + 内部 Card”三层嵌套。

- 左栏：固定 288px，可在 256–320px 范围内适配；
- 分隔线：1px `slate-200`；
- 右栏：`minmax(0, 1fr)`，允许内容内部正确换行；
- 工作区最小高度：桌面 680px；
- 左右栏分别滚动，页面头部和指标带保持稳定；
- 选中 Skill 后 URL 可复制和刷新恢复。

## 6. Skill 目录设计

### 6.1 搜索与筛选

左栏顶部包含：

- 搜索：名称、Skill ID；
- 单个状态筛选：全部、需处理、健康、Test Active；
- 更多筛选弹层：业务动作、业务对象、制品状态；
- 结果计数和清除筛选。

筛选即时应用，不增加“查询”按钮。搜索输入 250ms 防抖；筛选保存在 URL，但不保存任何测试问题或患者上下文。

### 6.2 目录项

每个 Skill 目录项只展示决策必要信息：

```text
结算解释技能                         ● 健康
settlement_explain_skill
v2.0.0 · 评测通过
[解释] [结算]                    Test Active
```

规则：

- 不展示 artifact hash、指标数和完整关键词；
- 生命周期状态最多显示一个主状态和一个环境状态；
- 选中项使用浅蓝背景、左侧 3px 主色条和 `aria-current=true`；
- 需处理项显示原因，例如“制品已变化”“评测失败”“待审批”；
- 状态排序默认优先级：门禁失败 → 待审批 → 待评测 → 制品变化 → 健康；
- 支持键盘上下移动和 Enter 选择。

### 6.3 空态

- 无 Skill：说明扫描目录和刷新方式，不显示空表头；
- 筛选无结果：保留搜索条件，提供“清除筛选”；
- 聚合状态失败：仍用 catalog 基础数据渲染目录，并在左栏顶部显示局部重试。

## 7. 右侧治理工作区

### 7.1 Skill 身份头

展示：

- Skill 名称和稳定 `skill_id`；
- 当前语义版本；
- `BusinessAction · BusinessObject`；
- 制品状态、校验状态和 test release 状态；
- 右侧唯一主动作，根据服务端状态显示“登记当前版本”“运行候选评测”“申请审批”或“激活 Test Shadow”。

主动作只负责导航到对应页签并聚焦实际操作区；不在身份头中跳过确认直接执行写操作。

### 7.2 生命周期步骤条

固定四步：

1. **版本登记**：当前 artifact 已登记且校验通过；
2. **批量评测**：存在与当前版本、suite revision、routing manifest hash 一致的 passed run；
3. **人工审批**：release 已申请并由不同身份审批，审批证据仍有效；
4. **Test 激活**：当前 release 为 `test / active / shadow`。

每一步支持四种视觉状态：`completed`、`current`、`blocked`、`pending`。`blocked` 必须同时显示短原因，例如“评测集已变化”，点击后进入相关页签的失败证据区。

步骤状态完全来自服务端聚合结果。前端不得根据按钮是否可点击或本地时间自行推导门禁结果。

### 7.3 页签重新分组

将当前九个页签收敛为五个：

| 新页签 | 默认内容 | 对应当前内容 |
|---|---|---|
| 总览 | 下一步、当前证据、最近评测、发布摘要、路由/执行调试入口 | 新组合 |
| 版本 | 当前制品、登记操作、版本历史、Git/hash 证据 | 版本证据 |
| 评测 | 固定用例、候选评测、结果和失败原因 | 批量评测 |
| 发布 | candidate、审批证据、门禁和 test shadow 状态 | 测试发布 |
| 开发详情 | 费用项解析、查询计划、Manifest、字段映射、目录、`SKILL.md` | 原 6 个技术页签 |

“开发详情”内部使用纵向子导航或手风琴，不再让九个横向页签换行。

## 8. 各页签内容

### 8.1 总览

总览按决策顺序排列：

1. **下一步卡片**：当前阻塞、影响和主操作；已 active 时显示“Test Shadow 正常”；
2. **当前证据**：版本、Git commit 前 8 位、artifact hash 前 12 位、suite revision、最近 eval run；
3. **最近评测**：状态、必测通过率、新增失败数、运行时间；
4. **发布摘要**：release 状态、审批人、revision、激活时间；
5. **调试入口**：`路由调试` 和 `执行调试` 两个次要动作。

只有失败或阻塞时展开详细原因；正常状态用一行摘要，避免健康页面被大量绿色提示占满。

### 8.2 版本

- 当前工作区制品与最近登记版本并排比较；
- 内容未变化时显示“已登记”，不显示无意义写按钮；
- 制品变化时突出变更文件数和新 hash，主动作是“登记当前版本”；
- 版本历史按时间线展示，默认展开当前版本；
- 完整 hash 通过复制按钮获得，不在主界面连续占满一行；
- 校验问题按严重程度分组，并显示明确文件位置。

### 8.3 评测

- 顶部显示当前固定用例数、必测数、suite revision 和候选版本；
- “运行候选评测”为唯一主按钮；
- 最近运行使用结果摘要卡，不先展示原始逐案明细；
- 指标顺序：必测通过率、Top-1 准确率、误接管、新增失败；
- 失败用例表只展示问题模板摘要、期望结果、实际结果和失败类型；
- 问题模板始终是脱敏样本，敏感信息校验失败显示字段级错误；
- 历史运行折叠在“查看全部运行”中。

### 8.4 发布

发布页按状态呈现单路径操作：

```text
passed eval
  → 创建 candidate
  → 申请审批
  → 不同身份审批
  → 激活 Test Shadow
```

- 每个状态只显示当前允许的主动作；
- 门禁失败使用结构化清单，列出制品、评测配置、测试集、路由 Manifest 和活动基线是否变化；
- 审批区明确展示创建人、审批人和“禁止自审”；
- 激活前确认框展示环境、目标版本、当前 test 基线和证据 revision；
- 激活成功后用稳定状态卡展示 `test active / shadow`，不使用短暂 toast 作为唯一反馈；
- 历史 release 默认折叠，只显示状态、版本、审批和时间。

### 8.5 开发详情

开发详情面向开发者，内部顺序为：

1. 费用项解析；
2. 查询计划；
3. 字段映射；
4. Manifest；
5. 目录结构；
6. `SKILL.md`。

Manifest 和原始内容使用代码容器，并提供复制；默认高度有限，内部滚动。目录结构使用树，不使用多张子目录 Card。未授权角色不渲染页签内容。

## 9. 路由与执行调试

### 9.1 路由调试抽屉

路由调试是跨 Skill 工具，位于页面头部，使用右侧抽屉：

- 输入自然语言问题；
- 展示命中 Skill、置信度、匹配方式、命中/排除关键词和候选列表；
- 点击候选 Skill 可切换主工作区选中项；
- 关闭抽屉后保留当前主工作区状态；
- 问题文本不写入 URL 或 localStorage。

### 9.2 执行调试

执行调试属于选中 Skill，从总览或开发详情进入同一右侧抽屉：

- 默认使用脱敏示例上下文；
- 结果先展示结构化摘要、`citations`、`uncertainties` 和 warnings；
- trace 与原始 JSON 默认折叠；
- 不允许从此处触发退费、冲正、正式结算或病案修改。

## 10. URL 与状态模型

URL 示例：

```text
/skills?skill=settlement_explain_skill&tab=evaluation&env=test&status=needs_action
```

允许进入 URL 的状态：

- `skill`：选中 Skill ID；
- `tab`：`overview | versions | evaluation | release | development`；
- `env`：第一阶段 `dev | test`；
- `status`、`action`、`object`、`q`：非敏感目录筛选。

禁止进入 URL、浏览器持久化或埋点的状态：测试问题、患者 ID、就诊 ID、证据内容和审批理由。

状态恢复规则：

1. URL 中 Skill 存在时优先选中；
2. 不存在或不可见时选择当前筛选结果第一项；
3. 没有结果时显示空工作区；
4. 切换 Skill 保留页签；若该页签无权限则回到总览；
5. 写操作成功只刷新当前 Skill、相关页签和顶部汇总；
6. 不因局部错误清空 catalog。

## 11. 只读工作台聚合契约

### 11.1 新增端点

```http
GET /api/v1/medical-insurance-ai-agent/infra-skills/workbench
```

查询参数沿用 catalog 的分页、搜索、动作和对象筛选，并增加可选 `governance_status`。

该静态路由必须在 `/{skill_id}` 动态路由之前注册，避免 `workbench` 被解析为 Skill ID。

响应为显式 Pydantic 模型：

```json
{
  "summary": {
    "total": 1,
    "healthy": 1,
    "needs_evaluation": 0,
    "pending_approval": 0,
    "test_active": 1,
    "updated_at": "2026-08-05T14:30:00+08:00"
  },
  "items": [
    {
      "skill_id": "settlement_explain_skill",
      "skill_name": "结算解释技能",
      "business_action": "explain",
      "business_object": "settlement",
      "semantic_version": "2.0.0",
      "artifact_status": "registered",
      "validation_status": "passed",
      "latest_eval_status": "passed",
      "test_release_status": "active",
      "test_active_version": "2.0.0",
      "governance_status": "healthy",
      "attention_reason": null
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 50
}
```

### 11.2 聚合规则

- 聚合服务读取版本、最新有效评测和 test release 存储，不调用每个 Skill 的 HTTP 端点；
- `governance_status` 是后端读模型，不新增领域状态机；
- 优先级固定为：`gate_failed > pending_approval > needs_evaluation > artifact_changed > healthy`；
- `attention_reason` 仅包含结构化安全摘要，不包含问题模板或患者内容；
- 列表只读聚合失败时返回统一错误，前端可回退现有 `/catalog` 基础列表；
- 现有 `/catalog`、`/overview`、版本、评测和发布接口保持兼容。

### 11.3 详情数据加载

选中 Skill 后并行加载：

- `GET /infra-skills/{skill_id}`；
- `GET /infra-skills/{skill_id}/versions`；
- `GET /infra-skills/{skill_id}/eval-runs`；
- `GET /infra-skills/{skill_id}/releases?environment=test`。

评测用例只在进入评测页签时加载；Manifest、README 和目录沿用详情接口，开发详情未展开时不进行额外解析。

## 13. 视觉规范

### 13.1 布局与间距

- 页面背景：纯 `slate-50` 或非常轻的顶部渐变，移除网格纹理和大面积模糊光斑；
- 内容最大宽度：`1600px`，桌面左右边距 24–32px；
- 页面纵向节奏：头部到指标 20px，指标到工作区 16px；
- 主工作区圆角 12px，1px 边框，最多一层低强度阴影；
- 组件间距使用 4/8/12/16/24/32px 序列；
- 表单控件高度 36–40px，主要按钮至少 40px。

### 13.2 字体层级

- 页面标题：24px / 32px，600；
- Skill 标题：20px / 28px，600；
- 区块标题：14–16px，600；
- 正文：14px / 22px；
- 辅助与 ID：12px / 18px；
- `skill_id`、commit、hash 使用等宽字体，其他内容不使用等宽字体。

### 13.3 颜色与状态

| 语义 | 颜色 | 使用位置 |
|---|---|---|
| 主操作 / 当前 | blue | 选中项、当前步骤、主按钮 |
| 成功 / active | emerald | 校验通过、评测通过、Test Active |
| 待处理 | amber | 待评测、待审批、证据将过期 |
| 阻塞 / 失败 | red | 门禁失败、敏感样本拒绝、并发冲突 |
| 中性 / 历史 | slate | pending、retired、技术元数据 |

状态始终同时提供图标和文本。绿色只用于最终成功状态，不把所有正常元数据都染成绿色。

### 13.4 文案

- 使用 `Skill`，不混用“技能包”“技能资产”和“Skill 资产库”作为页面标题；
- 使用“版本登记”，不使用“同步版本”描述不可变制品创建；
- 使用“运行候选评测”，不使用含糊的“测试”；
- 使用“Test Shadow 已激活”，明确环境和形态；
- 门禁失败文案说明“变化了什么、如何恢复”，不只显示“操作失败”。

## 15. 加载、错误与并发状态

| 场景 | 页面行为 |
|---|---|
| 首次加载 | 保留页面框架，指标和目录使用 skeleton |
| 切换 Skill | 保留身份头，右侧内容显示局部 skeleton |
| 聚合接口失败 | 回退 catalog，指标显示 `—`，提供局部重试 |
| 详情接口失败 | 目录保持可用，右栏显示错误码和重试 |
| 403 | 隐藏或禁用无权限主动作，并解释所需权限 |
| 409 revision conflict | 保留用户上下文，刷新 release 后要求重新确认 |
| 409 gate failure | 聚焦发布页门禁清单，不清空评测证据 |
| 422 敏感样本 | 在问题模板字段附近提示，不把样本回显到全局错误 |
| 写操作处理中 | 只禁用当前操作及依赖动作，不冻结整个工作区 |
| 数据变旧 | 显示“状态已变化，点击刷新”，不进行乐观激活 |

所有错误继续使用 `{error_code, message, audit_event}`，页面不展示堆栈、SQL 或患者明文。

## 16. 权限与安全交互

- 读取工作台要求 `skill:read`；
- 创建评测用例和运行评测要求 `skill:evaluate`；
- test 发布写操作要求 `skill:release:test`；
- 审批人必须来自认证上下文并与创建人不同；
- 写入口在 `SKILL_CONTROL_DEV_MODE` 未启用时不可操作；
- 前端隐藏按钮不构成权限控制，后端继续执行实际校验；
- 页面不得保存患者问题、身份证号、手机号或就诊上下文；
- 路由/执行调试结果继续展示 `citations` 或 `uncertainties`；
- 激活确认框不得允许用户修改服务端门禁证据。

## 17. 测试策略

本次为跨前端、API 读模型和治理展示的 R4 变更，验证严格按 T1 → T2a → T2b 执行。

### 17.1 T1 单元测试

- 工作台聚合状态优先级和 summary 计数；
- 版本、评测、审批、active 四步状态映射；
- 聚合失败回退基础 catalog；
- URL 参数解析和无效 Skill 回退；
- 目录搜索、状态筛选和选中状态；
- 权限对应的页签与动作可见性；
- 门禁失败、revision conflict 和敏感样本错误展示；
- 关键词不在目录默认渲染。

### 17.2 T2a API 测试

- `/infra-skills/workbench` 响应 DTO、分页和筛选；
- `governance_status` 优先级正确；
- 无 release、无评测、待审批、active 和 gate failed；
- 聚合不返回问题模板、患者信息或审批敏感内容；
- 旧 `/catalog`、`/overview` 和写端点保持兼容。

### 17.3 T2b Flow / E2E

核心流程：

1. 打开 `/skills`，看见治理指标和自动选中的 Skill；
2. 从目录选择 Skill，URL 保存 `skill`；
3. 在版本页登记当前版本；
4. 在评测页运行候选评测并看到 passed；
5. 在发布页创建 candidate、申请审批并用不同身份审批；
6. 激活后身份头、步骤条、目录项和指标均显示 `Test Active`；
7. 刷新页面后仍停留在该 Skill 和发布页；
8. 打开路由调试抽屉，关闭后治理上下文不丢失。

响应式 E2E 至少覆盖 1440px 桌面和 390px 窄屏，无横向页面滚动。

### 17.4 前端质量门禁

- Portal Vitest；
- 变更文件 ESLint；
- `npm run build`；
- Chromium Playwright；
- 键盘导航和 focus-visible 人工检查；
- 浏览器截图对照：标题层级、目录密度、步骤状态、错误态和窄屏。

## 18. 实施切片与回滚

为保持最小可验证单元，实施分三片：

1. **只读工作台骨架**：聚合接口、页面头、指标、Skill 目录和同页详情；
2. **生命周期工作区**：步骤条、五页签重组、复用现有版本/评测/发布组件；
3. **调试与适配**：路由/执行抽屉、URL 恢复、响应式、无障碍和 E2E。

每片独立测试和提交。回滚时可将 `app/skills/page.tsx` 恢复挂载原 `InfraSkillManagement`，新增只读接口保留不会影响运行时；现有版本、评测和发布写接口不变。

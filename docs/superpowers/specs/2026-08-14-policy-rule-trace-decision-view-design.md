# 规则溯源决策视图设计

## 目标

把面向实现的八阶段流水线收敛为面向审核人员的三段决策视图：模型识别、规范化与冲突、发布判定。用户应能直接回答“识别了什么、系统改了什么、为什么能或不能发布”。

## 设计

1. 默认只展示三个阶段；输入快照和完整技术步骤继续保留在完整 JSON 中。
2. 模型识别只展示当前候选规则，避免把同一批次输出重复展示到每条候选中。
3. 规范化与冲突合并 CANONICALIZE、COMPOSE，并仅在存在有效关系产物时纳入 RESOLVE、DERIVE 的变化。
4. 发布判定以是否生成规范规则、确定性校验问题及发布血缘为准。没有规范规则时显示“不可发布”，不得把空集合校验显示为通过。
5. 发布仍通过现有发布管理流程完成；抽屉不新增发布按钮。已发布时展示 release 信息，未发布时说明下一步。
6. LEGACY_IMPORT 继续单独、诚实展示，不伪造三段流程。

## 审核对照增强（方案 A）

1. 模型识别阶段固定使用“单元原文 → 模型提取结果”的双栏语义视图。左栏取 LLM 提取输入中的 `source_text`，缺失时回退输入快照或运行原始输入；右栏只展示当前候选。
2. 原文中能与候选值直接对应的片段使用 `<mark>` 高亮，右栏对应值使用同样样式。金额允许把标准化元值换算为“万元”原文别名后再做精确匹配；无法在原文定位的字段保持普通样式，并明确属于规范化补充，禁止模糊猜测证据。
3. 规范化与冲突阶段始终展示规范化输入和输出。即使没有变化，也显示完整字段，并在输出标题及变化摘要中明确标记“未变化”；“只看变化”不再把该阶段内容隐藏。
4. 审核表格行级保留“通过”“查看对照”两个高频入口，拒绝、退回和重提取收进原生 `<details>` 更多菜单。失效/异常候选仍只允许查看对照。
5. 页脚保留“整批通过审核”为唯一主动作，拒绝与退回重新构建收进“其他处理”菜单。按钮的原有权限、禁用条件、确认弹窗与业务调用保持不变。
6. 不新增菜单依赖；使用浏览器原生 `<details>/<summary>`，保留键盘访问、可读名称及焦点轮廓。

## 边界

本次只修改现有 Portal 溯源抽屉、审核详情及聚焦测试，不改编译器、存储结构、审核动作或发布 API。候选级裁剪与高亮仅影响展示，不重算业务结果；临时视觉原型在验收后删除。

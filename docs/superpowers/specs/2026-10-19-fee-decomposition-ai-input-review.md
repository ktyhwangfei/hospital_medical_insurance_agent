# 费用分解的 AI 输入审视与接入方案

依据：2026-10-19 用户三项反馈，重点是起付线、分段待遇及「比例要求 / 本单条件」对照。本轮落实页面前两项；本文件记录第三项的代码审视与建议，模型接线尚未实施。

## 现状与根因

当前费用分解没有提供给大模型。`policy_qa_routes.py` 预取 `fee_decomposition` 后，只在 `_build_public_result` 中加入公开结果；回答阶段的 `assembler.execute` 没有接收它。唯一宽泛政策模型入口 `_generate_broad_answer` 只收问题和政策检索证据。`integration.polish_summary` 原样返回确定性模板，不调用模型。[来源：上述函数的当前实现]

因此，不能将「页面可展示」写成「大模型已经知道」。即使今后直接传内部结果的 `model_dump()`，`fee_items` 与 `explanation_evidence` 也有 `exclude=True`，结算事实在独立侧车中，仍会丢掉关键解释依据。[来源：`result.SettlementDecompositionResult`、`integration.DecompositionPresentation`、`settlement_facts.DecompositionOutcome`]

## 模型回答需要的信息

| 信息 | 当前已有内容 | 尚未提供给模型 / 需要补齐的语义 | 缺失后容易出现的错误 |
|---|---|---|---|
| 结算背景 | `settlement_facts` 的结算日、险种、医疗类别、人员类别及中文码表 | 同笔上下文；普通门诊 / 门特 / 医院定额的范围；原值与中文名对应 | 用今天的政策或另一险种解释历史单；混用患者待遇与医院定额 |
| 金额口径与单位 | `fields` 的账面值、计算值、差额、核对类型 | 每个金额属于总费用、医保内、起付后基数或支付渠道；十进制字符串；比例值 0.7 与显示 70% 的区别 | 将 420÷3000=14% 写成待遇比例；账户和现金再加一遍 |
| 起付线 | `calc.deductible.split` 三个操作数：医保内费用、交易前累计、标准；结果为本笔起付；`copay_base` 为起付后基数 | 年度累计与周期已交起付分开；累计时点和范围是否核实；账面起付与计算起付分开 | 将本笔起付当年度标准；起付为零就断言已过起付线 |
| 分段待遇 | 分段基数、基金或个人比例、退休折算、降低自付及封顶的计算记录 | 每段明确段名、边界口径、此次交集金额、比例作用对象、补助前后及受封顶约束；不得只给总比例 | 将跨段加权均值当统一政策比例；将基金累计 2 万元误当费用累计 2 万元 |
| 条件对照 | `rule_choices.candidates.checks` 的 expected / actual / outcome | 把「规则要求」「本单事实」「符合 / 不符 / 未确认」一并传入；患者退休身份与在职比例基础档分开 | 看到在职基础档就把退休患者写成在职；未核实条件被说成符合 |
| 采用与排除理由 | 候选状态、reason、规则与计算引用 | 「被本次运算使用」与「已确认适用」分别表达；同段冲突不得任选；未计算不等于不适用 | 把 selected 当正式签核；把未发放补助解释成无资格 |
| 规则证据 | 规则 ID、版本、有效期、source、confirmation_status；公开来源引用 | 按结算日适用的版本及来源定位；待签核项不能当正式依据；缺权威条款明确列缺口 | 运算碰巧吻合就宣布政策依据完整 |
| 项目到汇总 | `fee_items`、目录划分方法、比例 / 限价、行结果和说明 | 按问题选择相关项目与汇总贡献；区分已有划分汇总与目录独立重算 | 将医保外 400 元统一称为目录外，忽略限价或结算分支 |
| 补助及二次保障 | 补助、救助、大病计算、先后依赖和 uncertainties | 基数扣减顺序、资格、年度累计、封顶；缺独立累计时保留不确定性 | 用本笔账面支付倒推累计，再用倒推结果证明本笔正确 |
| 可信程度及缺口 | 字段 check_type / check_status / explanation_level，输入 verification_status，uncertainties | 账面勾稽、独立重算、候选运算、仅有原值分级；缺口精确到受影响字段 / 段 | 「核对一致」被扩写成「所有待遇都正确且已核实」 |
| 可回答边界 | 内部 `answer_constraints`，公开 `may_claim_full_explanation` | 明示不能补规则、不能改金额或升级结论；列出无法回答的原因及补证方向 | 模型用常识补齐缺失年龄、累计或资格 |

这些内容大部分已在确定性内核与公开投影中；主要缺口是没有接线、没有统一给模型解释口径，以及部分源事实本来就缺证。源事实缺失只能继续标明未知，不能由提示词生成。[来源：`public_view.build_public_view_dict`、`formula_inputs.project_inputs`、`explanation_evidence.attach_evidence`、`rule_choices.build_rule_choices`]

## 最小接入方式（建议，未实施）

1. 从两路由共用的 `to_public_contract_dict(..., sanitize=_public_text)` 取得安全投影，禁止直接序列化原始快照、物理字段或内部结果。模型输入仍须脱敏，不附姓名、证件号、医保卡号、出生日期原文、SQL 或连接信息。
2. 在本单费用解释路径给模型同一份证据包：结算背景、相关字段、起付、相关分段、条件候选、输入与计算依赖、来源及缺口。各块复用现有引用 ID，不另算金额。先带当前问题相关节点和上游闭包；预算不足时优先保留状态、缺口和来源，显式标明未提供的明细。
3. 为金额附语义：数值、单位、范围、分母、账面 / 计算来源及是否已核实。为每段附基数、基金 / 个人比例、边界依据、补助与封顶位置。当前前端 `currentRates` 只是展示提取逻辑，不能作为后端或模型的金额计算真源；接入时从既有计算记录提取。
4. 明确输出任务是解释已计算结果，并要求结论绑定给定字段、计算与来源 ID。禁止模型重新分解费用或补规则。只有条件和依据已核实的段能表述为已确认待遇；其余写成「本次候选计算采用」。
5. 输出经确定性校验后才公开：金额、比例、引用、确认状态均限于输入集合；来源不存在、模型更改数字 / 结论等级或补出新规则时回退现有模板。`may_claim_full_explanation=false` 不得升级；`may_infer_missing_rules=false` 应始终显式保留。

不建议把整包数据接到宽泛政策问答上。应先区分「本单为何这样支付」与「一般政策如何规定」，前者接本单证据，后者保留检索来源组织。否则一般政策结论会被某一张候选单据误导。[建议：基于当前宽泛问答与结算解释的代码边界]

## 本例应让模型清楚的内容

- 账面总费用 3000 元、基金及补助 420 元、个人支付 2580 元；14% / 86% 的分母是总费用。
- 本次计算使用医保内费用 2400 元、本笔起付 1800 元，起付后基数 600 元；本例文字未提供交易前累计、规则正式确认状态，不能从差额补出它们。
- 基础段此次基数 600 元，基金比例 70%、个人比例 30%，作用于该基数且为补助前口径。
- 比例要求与本单实际分别列人员身份、机构类别、分段及日期 / 参数可用性；任一未确认项原样保留。
- 基金 600×70%=420 元解释本段；个人总额 2580 元中起付、医保外、段内自付及补助的组成，应引用实际分解记录。缺少完整记录时不能自行把所有剩余金额归成一种自费原因。

## 后续接线的验收用例（建议）

本例低实际占比、未过起付、跨比例段、退休折算、补助覆盖起付、基金封顶、退款负数、医院定额、稀疏目录及缺累计分别入固定回归。校验模型没有混淆分母 / 累计坐标 / 支付渠道，没有把候选条件写成已核实，也没有将核对差异判成源系统错误。模型失败仍输出现有确定性结果。

本轮未更改模型提示词、调用链路、金额算法、公开契约版本或政策参数。

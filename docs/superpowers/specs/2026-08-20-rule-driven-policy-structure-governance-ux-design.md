# 异常规则驱动的政策结构治理交互设计

- 日期：2026-08-20
- 状态：二次可用性评审修订完成，待最终复核
- 页面：`/policy-knowledge/knowledge/semantic-discovery`

## 1. 背景

当前“语义发现”页面同时承载数据库证据预览、指标/值域/维度提议审核和历史状态查看。用户需要先理解提议类型、状态过滤和证据展开方式，才能处理一条已经确认有问题的政策规则。

本轮真实问题从具体规则开始：

- `rule_69fc18433e6a7364`、`rule_63e89e926492ebd8` 把机构类别错误折叠为 `hosp_lv=一级`。
- `rule_3222a148156d8c7d`、`rule_4df372b59673556e` 的资金归属和综合待遇语义需要重新判断。

因此页面的主任务不应是“浏览系统产生了哪些提议”，而应是：从异常规则出发，还原原文、诊断结构问题、取得 bjyb 数据证据，最后形成可审核的治理变更草稿。

## 2. 已确认决策

1. 主任务采用“问题驱动治理”，批量提议审核降为次级入口。
2. 默认入口来自规则详情或验证失败结果的“发起结构治理”，自动携带来源 release 和规则定位信息；粘贴规则 ID 仅作为高级补充入口。
3. 页面采用三步引导：规则诊断 → 数据库证据 → 建模决策。
4. 系统提供一个推荐结论和可追溯理由，其他结论默认折叠；人工可以改选。
5. 人工确认后只生成治理变更草稿，不直接修改活动 release、不自动重提取、不自动发布。
6. 复用现有 `SemanticProposal` 的存储、队列和证据结构，不建设第二套提议系统；规则纠偏草稿在本轮不进入现有的直接发布分支。
7. Milvus 只负责定位已索引规则；政策原文、抽取结果和单元归属以 PostgreSQL lineage 指向的来源记录为准。
8. 精确规则 ID 查询使用标量查询，不使用向量召回或 BM25；相邻问题规则由 lineage、政策单元和规范化业务轴发现，不由用户手工凑齐。

## 3. 用户与成功标准

主要用户是政策治理人员和医保业务专家。他们知道哪条规则有问题，但不应被要求理解 Milvus collection、语义提议内部状态或数据库表结构。

一次操作成功的标准：

- 用户无需手工复制长规则 ID，即可从规则详情进入治理页面。
- 页面明确指出当前结构化结果与政策原文的冲突，而不是只罗列字段。
- 数据库证据明确区分“推荐、佐证、弱证据、排除”，并展示字段角色和值域统计。
- 系统推荐不会用数据库证据覆盖政策原文。
- 默认接受路径只需一次最终确认即可得到治理变更草稿；查看诊断和证据不要求逐项批准。
- 草稿明确列出字段/值域变更、受影响规则、后续重提取范围和未发布状态。

### 3.1 二次可用性评审结论

原方案方向正确，但仍有以下不适合真实用户的设计，必须在实现前修正：

| 原设计问题 | 用户风险 | 修正 |
|---|---|---|
| 规则 ID 输入框占据首屏 | 用户必须记忆技术标识，也容易选漏同源规则 | 以政策条款摘要作为任务标题；规则 ID 仅在“技术详情”中展示和复制 |
| 用户一次输入多条相关规则 | 用户需要先理解系统如何拆分规则 | 从一条异常规则启动，系统建议同源关联规则并说明关联原因，用户只处理有歧义的关联 |
| 每一步都要求确认 | 形成无意义的点击负担 | 诊断和证据是可检查状态；仅修改证据或最终生成草稿时要求明确操作 |
| 物理字段和值码直接作为主要信息 | 业务人员难以判断 `H_TYPE=01` 的含义 | 先显示业务名称和码值释义，再显示 `table.field` 与原始码值 |
| 复用完整 `SemanticProposal` 发布状态机 | “发布提议”可能被误解或执行为立即写入 registry | 本轮只到 `accepted` 的已批准变更计划；`published` 保留给真实执行完成后的状态 |
| 仅凭 rule ID 和活动 collection 还原来源 | rule ID 可在重新摄取时生成，且活动版不一定是问题发生版 | 深链必须携带来源 release，并通过 `policy_rule_lineage` 回溯 extraction、unit 和文档 |
| 返回上一步不丢值，但刷新会丢任务 | 长时间治理中断后无法继续 | `diagnosis_id`/`draft_id` 写入 URL，未提交选择保存在浏览器会话；生成草稿后以服务端草稿恢复 |
| 一个推荐覆盖多种问题 | 机构类别与基金归属可能被错误合并处理 | 先生成“问题卡片”，每个独立业务轴单独诊断、选择和生成草稿 |

页面应遵循三条原则：业务语义优先于技术标识、政策证据优先于数据库相似度、只在用户需要作出不可逆判断时打断用户。

## 4. 信息架构

### 4.1 页面主区

页面主区只保留一个治理任务：

```text
异常规则入口
  → 1. 规则诊断
  → 2. 数据库证据
  → 3. 建模决策
  → 治理变更草稿摘要
```

默认入口不展示空白规则 ID 表单。页面从以下位置进入：

- 规则详情或规则追溯抽屉的“发起结构治理”。
- 验证失败结果中已定位到错误规则时的“修正知识结构”。
- “高级方式”中的规则 ID 粘贴入口，兼容逗号、分号和换行。

深链至少携带 `release_id` 和一个 `rule_id`；若调用方已经持有 `lineage_id` 或 `extraction_id`，一并携带。进入页面后以政策条款摘要作为标题，以“问题发生版本 / 当前活动版本”作为副标题。技术 ID、collection 名和原始 JSON 默认收进“技术详情”。

用户只需选择一条确认有问题的规则。系统依据同一 lineage、政策单元、文档条款和规范化业务轴建议关联规则，并逐条显示“同一条款拆分”“同一抽取批次”或“相同业务轴”等原因。确定性不足时不自动勾选。

### 4.2 次级入口

当前统一提议队列保留，但移至“待办与历史”次级入口。该区域使用面向用户的“待处理、待确认、已批准、已驳回”标签，不直接暴露内部状态值，并负责：

- 查看尚未处理的指标、值域和维度提议。
- 恢复未完成的治理草稿。
- 查询已发布、已驳回、已失效和已替代的历史结论。

它不与三步向导同时争夺页面首屏注意力。

## 5. 三步交互

### 5.1 第一步：规则诊断

进入任务后，系统先按深链中的来源 release 精确定位规则，再通过 `policy_rule_lineage` 回溯抽取记录、政策单元和原文。不得静默改用当前活动 release；来源版不存在时才让用户明确改选历史版本。

页面展示：

- 政策条款摘要、问题发生 release、当前活动 release、政策文档、条款路径和原文引用。
- 当前结构化字段和值。
- 原文与结构结果的差异。
- 错误字段、缺失字段、可能混淆的独立业务轴。
- 系统建议的关联规则、关联原因和政策单元数量。

默认只展示诊断摘要；规则 ID、lineage、collection、原始结构化载荷和逐字段差异可在“技术详情”展开。诊断完成后第一步折叠成摘要卡，避免后续步骤反复滚动。

机构类别示例的摘要应为：

```text
错误字段：hosp_lv = 一级
缺失概念：医疗机构类别
解释：政策区分社区/非社区定点医疗机构，没有表达一级/二级/三级医院。
```

### 5.2 第二步：数据库证据

系统先查询已发布语义指标，再读取与当前环境匹配的最近一次成功 `DiscoveryStore` 扫描结果。请求期间不实时扫描 SQL Server。证据区展示扫描环境、时间和新鲜度；过期证据可以浏览，但不能作为自动绑定的充分依据。

证据排序：

1. 可直接复用的已发布语义指标。
2. 数据库强证据。
3. 数据库佐证。
4. 弱证据。
5. 明确排除的相似字段。

每条数据库证据先显示业务名称和判断，再显示技术详情：

- 字段业务名称、业务角色和推荐/排除理由。
- 安全码值的“源值 → 业务含义”字典及覆盖情况。
- 数据覆盖率、distinct 数、扫描范围和时间。
- 次级信息 `table.field`。
- 采纳或排除理由。

证据质量分别评价“字段角色匹配、值域释义完整、数据覆盖、新鲜度”，不合并成一个无法解释的分数。系统使用“证据充分、需要核对、证据不足”等文字表达置信程度。若只能观测到 `01/02/03/05` 等码值但没有可靠释义，标记“值域释义不完整”，不得推荐自动绑定源值映射。

机构类别应推荐 `m_institution.H_TYPE`，明确排除 `H_LEVEL`。基金归属应优先基金代码/名称和支付分项，明确排除表示险种类型的 `FUND_TYPE`。

数据库证据区固定展示提示：“数据库证据只辅助结构建模，不覆盖政策原文。”患者级样本、敏感字段和值不得进入候选或响应；仅允许展示经过敏感性过滤的低基数字典值。

用户默认无需“批准数据库证据”。只有在勾选/取消候选字段或修改值域释义时才记录选择；否则可以直接查看推荐并进入下一步。

### 5.3 第三步：建模决策

系统根据政策诊断、已有语义指标和数据库证据给出一个推荐结论：

- 复用已有指标。
- 新增政策指标并绑定数据库字段。
- 新增政策专用字段。
- 仅补值域或源值映射。
- 修复抽取，不新增字段。
- 证据不足，转人工补充。

推荐优先级固定为：政策原文与现有结构冲突时先“修复抽取”；已有指标语义完全一致时“复用已有指标”；无已有指标但存在业务角色一致的强数据库证据时“新增并绑定”；无数据库匹配但政策语义明确时“政策专用字段”；原文或字段角色不完整时“证据不足”。数据库字段名相似度不能越过该顺序。

每个独立问题卡片给出一个推荐，不能用同一结论同时处理机构类别和基金归属。推荐卡片展示：

- 推荐结论。
- 为什么推荐。
- 将新增、修改或清除哪些字段。
- 将影响哪些规则和单元。
- 为什么没有选择其他结论。

确认前展示“当前结构 → 拟变更结构”的差异预览，以及“历史 release 保持不变，变更仅进入下一候选 release”的醒目说明。

其他结论放在“修改结论”中，不与推荐操作并列占据首屏。

用户可以选择“不认可推荐”或其他结论。正常接受无需填写说明；改选、排除强证据或标记无法判断时要求简短理由，理由随草稿留痕。政策专家负责确认政策语义，物理字段绑定证据不足时草稿标记“需要数据人员确认”，本轮不建设复杂会签流。

用户点击“确认并生成治理草稿”后，页面展示草稿摘要，不启动下游任务。

三步使用固定底部操作栏，每次只有一个主要按钮。诊断和证据加载采用分阶段进度提示；单个证据源失败时仅重试该来源，不重新开始整个任务。

## 6. 治理变更草稿

治理草稿复用 `SemanticProposal` 的持久化、审核队列和证据结构，增加 `proposal_type=RULE_GOVERNANCE_CHANGE`。本轮可用状态为 `proposed → reviewing → accepted/rejected`：

- `accepted` 表示变更计划已批准，但尚未修改语义 registry、抽取配置或 Milvus。
- `published` 只表示后续执行器已经完成契约更新、重提取、编译和候选 release 发布；本轮没有执行器，因此页面不展示或调用现有发布动作。

为了承载规则纠偏，增加：

- `trigger_source=MANUAL_RULE_CORRECTION`。
- `governance_change_plan`：政策问题、规则和 lineage 定位、字段增删改、值域/映射建议、受影响单元、建议重提取范围、是否需要数据人员确认。
- `revision`：草稿修改的乐观并发版本。
- 诊断 fingerprint：由来源 release、排序后的 lineage/规则定位、canonical rule payload hash、Discovery 快照 ID 和 SemanticRegistry schema version 生成，不包含推荐或人工结论。

同一诊断 fingerprint 只允许一个未终结草稿；重复提交返回已有草稿。人工改选结论时只更新 `proposed/reviewing` 草稿并使用 revision 乐观并发检查；`accepted` 计划不可直接覆盖，调整时必须生成可审计的新 revision 并重新审核。

草稿必须保存 `release_id`、`rule_id`、`lineage_id`、`extraction_id`、`unit_id`、`doc_id` 和 canonical payload hash。`rule_id` 是索引定位符，不单独作为跨摄取稳定身份。

草稿摘要至少包含：

| 项目 | 内容 |
|---|---|
| 字段变更 | 新增、修改和清除的字段 |
| 值域变更 | 标准值、observed 值和源值映射 |
| 受影响规则 | rule IDs 与数量 |
| 受影响单元 | document/unit IDs 与数量 |
| 后续任务 | 契约重建、重提取、编译、候选 release |
| 当前状态 | 草稿/已批准计划、未执行 |

生成后提供三个明确出口：“查看治理草稿”“返回原规则”“查看下一条问题”，不得以内部 proposal ID 作为唯一成功反馈。

## 7. 后端接口

### 7.1 规则诊断

`POST /api/v1/medical-insurance-ai-agent/semantic/alignment/rule-diagnoses`

请求：

```json
{
  "release_id": "REL_202608182",
  "rule_ids": ["rule_69fc18433e6a7364", "rule_63e89e926492ebd8"]
}
```

默认入口只提交一个 `rule_id`，服务端返回建议关联规则；批量 `rule_ids` 用于高级入口和已知同组规则。可选提交 `lineage_id`/`extraction_id` 以减少歧义。

响应使用 Pydantic `RuleGovernanceDiagnosisBatch`。当输入规则属于多个独立政策问题时，`items` 按问题拆分；每个 `RuleGovernanceDiagnosis` 包含：

- `diagnosis_id`、`fingerprint`。
- `release_id`、当前活动 release、规则与 lineage 来源定位；collection 仅在技术详情中返回。
- `rules` 和原文 citations。
- `related_rule_suggestions` 与关联理由。
- `field_issues`。
- `existing_metric_candidates`。
- `database_evidence`。
- `recommended_decision` 与理由。
- `uncertainties`。

`diagnosis_id` 对应服务端保存的短期诊断快照，记录 Discovery snapshot、SemanticRegistry schema version 和 canonical payload hash，供刷新恢复与创建草稿时复核。接口按独立业务问题拆分 `items`，页面一次只操作一个问题卡片。

诊断接口为只读操作，必须经过语义审核权限校验和输出脱敏。

### 7.2 创建治理草稿

`POST /api/v1/medical-insurance-ai-agent/semantic/alignment/rule-governance-drafts`

请求包含一个诊断 ID/fingerprint、人工选择的建模结论、来自诊断响应的证据引用，以及仅在改选/驳回时必填的审核说明。响应为带 `governance_change_plan` 的 `SemanticProposal`。

服务端重新校验诊断 fingerprint、来源 release、payload hash 和证据快照；页面不能直接提交任意物理字段绑定。快照已过期时保留用户选择并要求刷新证据，不静默使用新扫描结果。

## 8. 数据流与依赖

```text
Portal RuleGovernanceWizard
  → semantic_alignment_routes
  → explicit source release resolver
  → Milvus rules scalar query（定位索引记录）
  → policy_rule_lineage
  → PostgreSQL extraction/unit/document（权威来源）
  → SemanticRegistry（已有指标/值域）
  → DiscoveryStore（最近成功字段画像）
  → deterministic diagnosis + database evidence matcher
  → SemanticAlignmentService（草稿持久化与状态机）
```

约束：

- 不在页面请求内扫描 SQL Server。
- 不直接修改 Milvus 活动 collection。
- 不从规则 ID 发起向量检索。
- 不把运行时的 collection fallback 当作问题规则的来源版本。
- 结构冲突、已登记值域和字段角色采用确定性检查。确有需要时，模型只能通过 `model_service/gateway` 生成带 citations/uncertainties 的候选解释，不能自行选择字段、生成源值映射或发布结论。
- V1 只保证已知机构类别、基金分项/综合待遇等结构轴的可验证诊断，不宣称对任意政策语义都能自动判断；未知模式明确转人工。

## 9. 异常与降级

| 场景 | 页面行为 |
|---|---|
| 来源 release 找不到规则 | 保留来源版本提示，并按 lineage/doc/unit 提供可解释的历史定位；不得静默切换活动版 |
| rule ID 在重新摄取后变化 | 使用 lineage、extraction、unit 和 payload hash 辅助定位，并提示用户确认候选规则 |
| 多条规则不是同一政策问题 | 拆分为多个治理任务，不混合生成结论 |
| facts 上下文缺失 | 停止自动推荐，显示缺失的 fact/unit |
| 无合适 bjyb 字段 | 允许政策专用字段或仅修复抽取 |
| 数据库证据冲突 | 推荐降为“需人工判断”，并列展示冲突证据 |
| DiscoveryStore 不可用 | 保留政策诊断，标记数据库证据暂不可用 |
| Discovery 快照过期 | 显示过期时间，禁止把该证据作为自动绑定的充分依据，可单独刷新证据 |
| 码值没有可靠释义 | 允许选择字段候选，但值域映射标记待确认，不根据码值猜测含义 |
| 重复提交 | 返回已有 fingerprint 对应草稿 |
| revision 冲突 | 提示刷新并保留用户未提交选择，不覆盖现有草稿 |

所有确定性输出必须携带政策 citations；无法引用时进入 `uncertainties`，不得显示无来源的确定性结论。

## 10. 可用性与无障碍

- 步骤状态不能只依赖颜色，必须有文本和图标。
- 推荐、佐证、排除均使用文字标签。
- 所有折叠区、按钮和输入框具备可访问名称。
- 错误摘要自动聚焦，异步诊断通过 `aria-live` 报告状态。
- `diagnosis_id`/`draft_id` 写入 URL，未提交的非敏感选择写入 `sessionStorage`；刷新或浏览器返回后恢复当前问题，草稿生成后改从服务端恢复。
- 返回上一步不丢失已确认的规则和证据选择。
- 长原文默认折叠，避免遮蔽当前操作。
- 业务名称先于技术标识，内部状态、collection 和原始 JSON 默认隐藏。
- 正常接受推荐不要求填写说明；只有改选、排除强证据或驳回时要求理由。
- 历史 release 不可变和“本次只生成草稿”同时出现在差异预览与成功摘要中。

## 13. 验收标准

- 从规则详情或验证失败结果进入后，来源 release 和规则定位自动带入，用户不需要复制规则 ID。
- 页面以政策问题和条款摘要为主信息，Milvus、collection、物理字段和内部状态只在需要时展开。
- 从一条异常规则可以看到带关联理由的同源规则建议；不同业务轴不会合并生成一个结论。
- 机构类别案例能指出 `hosp_lv=一级` 错误，并推荐 `H_TYPE`、排除 `H_LEVEL`。
- 基金案例能区分大额互助基金、基金分项比例和综合待遇，数据库证据不覆盖政策原文，也不因字段名相似而一律归为统筹基金。
- 用户可查看和修改系统推荐；默认接受路径无需批准每条证据，改选时原因可追溯。
- 值域码没有可靠释义、Discovery 快照过期或存在冲突时，系统不会推荐自动绑定。
- 刷新或返回后可以从 URL 恢复诊断任务和未提交选择。
- 确认后生成可追溯、幂等、未发布的治理变更草稿。
- 草稿批准不等于应用变更；本轮页面没有直接发布入口。
- 活动 release 和 Milvus collection 在整个流程中保持不变。

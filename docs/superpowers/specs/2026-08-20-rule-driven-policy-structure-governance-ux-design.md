# 异常规则驱动的政策结构治理交互设计

日期：2026-08-20  
状态：已完成交互确认，待书面复核  
页面：`/policy-knowledge/knowledge/semantic-discovery`

## 1. 背景

当前“语义发现”页面同时承载数据库证据预览、指标/值域/维度提议审核和历史状态查看。用户需要先理解提议类型、状态过滤和证据展开方式，才能处理一条已经确认有问题的政策规则。

本轮真实问题从具体规则开始：

- `rule_69fc18433e6a7364`、`rule_63e89e926492ebd8` 把机构类别错误折叠为 `hosp_lv=一级`。
- `rule_3222a148156d8c7d`、`rule_4df372b59673556e` 的资金归属和综合待遇语义需要重新判断。

因此页面的主任务不应是“浏览系统产生了哪些提议”，而应是：从异常规则出发，还原原文、诊断结构问题、取得 bjyb 数据证据，最后形成可审核的治理变更草稿。

## 2. 已确认决策

1. 主任务采用“问题驱动治理”，批量提议审核降为次级入口。
2. 默认入口来自规则详情页的“发起结构治理”，自动携带规则 ID；批量粘贴规则 ID 作为补充。
3. 页面采用三步引导：规则诊断 → 数据库证据 → 建模决策。
4. 系统提供一个推荐结论和可追溯理由，其他结论默认折叠；人工可以改选。
5. 人工确认后只生成治理变更草稿，不直接修改活动 release、不自动重提取、不自动发布。
6. 复用现有 `SemanticProposal` 状态机和 `DiscoveryEvidence`，不建设第二套提议系统。
7. 精确规则 ID 查询使用 Milvus 标量查询，不使用向量召回或 BM25。

## 3. 用户与成功标准

主要用户是政策治理人员和医保业务专家。他们知道哪条规则有问题，但不应被要求理解 Milvus collection、语义提议内部状态或数据库表结构。

一次操作成功的标准：

- 用户无需手工复制长规则 ID，即可从规则详情进入治理页面。
- 页面明确指出当前结构化结果与政策原文的冲突，而不是只罗列字段。
- 数据库证据明确区分“推荐、佐证、弱证据、排除”，并展示字段角色和值域统计。
- 系统推荐不会用数据库证据覆盖政策原文。
- 用户最多经过三次主要确认即可得到治理变更草稿。
- 草稿明确列出字段/值域变更、受影响规则、后续重提取范围和未发布状态。

## 4. 信息架构

### 4.1 页面主区

页面主区只保留一个治理任务：

```text
异常规则入口
  → 1. 规则诊断
  → 2. 数据库证据
  → 3. 建模决策
  → 治理变更草稿摘要
```

页面顶部保留规则 ID 输入框，支持：

- 从规则详情页通过 `?rule_ids=id1,id2` 自动带入。
- 粘贴一个或多个规则 ID，兼容逗号、分号和换行。

### 4.2 次级入口

当前统一提议队列保留，但移至“待办与历史”次级入口。该区域负责：

- 查看尚未处理的指标、值域和维度提议。
- 恢复未完成的治理草稿。
- 查询已发布、已驳回、已失效和已替代的历史结论。

它不与三步向导同时争夺页面首屏注意力。

## 5. 三步交互

### 5.1 第一步：规则诊断

输入规则后，系统按活动 release 的 rules collection 精确查询，并关联对应 facts collection 还原完整政策上下文。

页面展示：

- 规则 ID、活动 release、政策文档、条款路径和原文引用。
- 当前结构化字段和值。
- 原文与结构结果的差异。
- 错误字段、缺失字段、可能混淆的独立业务轴。
- 受影响规则和政策单元数量。

默认只展示诊断摘要；原文、结构化载荷和逐字段差异可展开。

机构类别示例的摘要应为：

```text
错误字段：hosp_lv = 一级
缺失概念：医疗机构类别
解释：政策区分社区/非社区定点医疗机构，没有表达一级/二级/三级医院。
```

### 5.2 第二步：数据库证据

系统先查询已发布语义指标，再读取最近一次成功的 `DiscoveryStore` 扫描结果。请求期间不实时扫描 SQL Server。

证据排序：

1. 可直接复用的已发布语义指标。
2. 数据库强证据。
3. 数据库佐证。
4. 弱证据。
5. 明确排除的相似字段。

每条数据库证据展示：

- `table.field`。
- 字段描述和业务角色。
- 非空率、distinct 数、低基数观测值。
- 采纳或排除理由。
- discovery 扫描批次和时间。

机构类别应推荐 `m_institution.H_TYPE`，明确排除 `H_LEVEL`。基金归属应优先基金代码/名称和支付分项，明确排除表示险种类型的 `FUND_TYPE`。

数据库证据区固定展示提示：“数据库证据只辅助结构建模，不覆盖政策原文。”

### 5.3 第三步：建模决策

系统根据政策诊断、已有语义指标和数据库证据给出一个推荐结论：

- 复用已有指标。
- 新增政策指标并绑定数据库字段。
- 新增政策专用字段。
- 仅补值域或源值映射。
- 修复抽取，不新增字段。
- 证据不足，转人工补充。

推荐优先级固定为：政策原文与现有结构冲突时先“修复抽取”；已有指标语义完全一致时“复用已有指标”；无已有指标但存在业务角色一致的强数据库证据时“新增并绑定”；无数据库匹配但政策语义明确时“政策专用字段”；原文或字段角色不完整时“证据不足”。数据库字段名相似度不能越过该顺序。

推荐卡片展示：

- 推荐结论。
- 为什么推荐。
- 将新增、修改或清除哪些字段。
- 将影响哪些规则和单元。
- 为什么没有选择其他结论。

其他结论放在“修改结论”中，不与推荐操作并列占据首屏。

用户点击“确认并生成治理草稿”后，页面展示草稿摘要，不启动下游任务。

## 6. 治理变更草稿

治理草稿复用 `SemanticProposal` 的生命周期：`proposed → reviewing → accepted → published/rejected`。为了承载规则纠偏，增加：

- `trigger_source=MANUAL_RULE_CORRECTION`。
- `governance_change_plan`：规则 ID、来源 release、字段增删改、值域/映射建议、受影响单元、建议重提取范围。
- 诊断 fingerprint：只由排序后的规则 ID、来源 release 和结构化载荷版本生成，不包含推荐或人工结论。

同一诊断 fingerprint 只允许一个未终结草稿；重复提交返回已有草稿，人工改选结论时更新该草稿而不创建新提议。草稿修改使用 revision 乐观并发检查。

草稿摘要至少包含：

| 项目 | 内容 |
|---|---|
| 字段变更 | 新增、修改和清除的字段 |
| 值域变更 | 标准值、observed 值和源值映射 |
| 受影响规则 | rule IDs 与数量 |
| 受影响单元 | document/unit IDs 与数量 |
| 后续任务 | 契约重建、重提取、编译、候选 release |
| 当前状态 | 草稿、未发布 |

## 7. 后端接口

### 7.1 规则诊断

`POST /api/v1/medical-insurance-ai-agent/semantic/alignment/rule-diagnoses`

请求：

```json
{
  "rule_ids": ["rule_69fc18433e6a7364", "rule_63e89e926492ebd8"]
}
```

响应使用 Pydantic `RuleGovernanceDiagnosisBatch`。当输入规则属于多个独立政策问题时，`items` 按问题拆分；每个 `RuleGovernanceDiagnosis` 包含：

- `diagnosis_id`、`fingerprint`。
- `release_id`、rules/facts collection。
- `rules` 和原文 citations。
- `field_issues`。
- `existing_metric_candidates`。
- `database_evidence`。
- `recommended_decision` 与理由。
- `uncertainties`。

诊断接口为只读操作，必须经过语义审核权限校验和输出脱敏。

### 7.2 创建治理草稿

`POST /api/v1/medical-insurance-ai-agent/semantic/alignment/rule-governance-drafts`

请求包含一个诊断 ID/fingerprint、人工选择的建模结论、来自诊断响应的证据引用和审核说明。响应为带 `governance_change_plan` 的 `SemanticProposal`。

服务端重新校验诊断 fingerprint 和来源 release；页面不能直接提交任意物理字段绑定。

## 8. 数据流与依赖

```text
Portal RuleGovernanceWizard
  → semantic_alignment_routes
  → active release resolver
  → Milvus rules scalar query
  → Milvus facts query
  → SemanticRegistry（已有指标/值域）
  → DiscoveryStore（最近成功字段画像）
  → deterministic diagnosis + database evidence matcher
  → SemanticAlignmentService（草稿持久化与状态机）
```

约束：

- 不在页面请求内扫描 SQL Server。
- 不直接修改 Milvus 活动 collection。
- 不从规则 ID 发起向量检索。
- 确定性诊断足够时不调用模型；如后续增加模型解释，只能通过 `model_service/gateway`，且不能改变确定性结论。

## 9. 异常与降级

| 场景 | 页面行为 |
|---|---|
| 活动 release 找不到规则 | 提示当前活动版未找到，并列出存在该规则的历史 release |
| 多条规则不是同一政策问题 | 拆分为多个治理任务，不混合生成结论 |
| facts 上下文缺失 | 停止自动推荐，显示缺失的 fact/unit |
| 无合适 bjyb 字段 | 允许政策专用字段或仅修复抽取 |
| 数据库证据冲突 | 推荐降为“需人工判断”，并列展示冲突证据 |
| DiscoveryStore 不可用 | 保留政策诊断，标记数据库证据暂不可用 |
| 重复提交 | 返回已有 fingerprint 对应草稿 |
| revision 冲突 | 提示刷新并保留用户未提交选择，不覆盖现有草稿 |

所有确定性输出必须携带政策 citations；无法引用时进入 `uncertainties`，不得显示无来源的确定性结论。

## 10. 可用性与无障碍

- 步骤状态不能只依赖颜色，必须有文本和图标。
- 推荐、佐证、排除均使用文字标签。
- 所有折叠区、按钮和输入框具备可访问名称。
- 错误摘要自动聚焦，异步诊断通过 `aria-live` 报告状态。
- 返回上一步不丢失已确认的规则和证据选择。
- 长原文默认折叠，避免遮蔽当前操作。

## 11. 验证范围

只验证这一条用户故事，不运行无关测试：

1. 单元测试：规则分组、字段冲突分类、推荐结论、fingerprint 幂等。
2. API 测试：活动/历史 release 查找、无 facts、无 discovery、创建和重复创建草稿、revision 冲突、权限与脱敏。
3. Flow 测试：两条机构类别错误规则 → `H_TYPE` 推荐/`H_LEVEL` 排除 → 人工确认 → 治理草稿。
4. Portal 测试：深链带入规则、三步前进/返回、证据展开、修改推荐、草稿摘要、错误恢复。
5. TypeScript 检查和变更文件 LSP 零新增错误。

## 12. 非目标

- 不在本轮自动执行重提取、编译或候选 release 构建。
- 不自动发布字段、值域或映射。
- 不批量扫描 5833 个字段反向创建政策提议。
- 不删除现有统一审核队列。
- 不建设新的规则 DSL、知识图谱或第二套治理状态机。
- 不在本轮修复 `REL_202608182` 的历史不可变数据。

## 13. 验收标准

- 从规则详情点击“发起结构治理”后，规则 ID 自动带入。
- 机构类别案例能指出 `hosp_lv=一级` 错误，并推荐 `H_TYPE`、排除 `H_LEVEL`。
- 基金案例能区分基金分项比例和综合待遇，数据库证据不覆盖政策原文。
- 用户可查看和修改系统推荐，但默认路径只需三次主要操作。
- 确认后生成可追溯、幂等、未发布的治理变更草稿。
- 活动 release 和 Milvus collection 在整个流程中保持不变。

# 门诊结算结果核验 Skill 完善设计

日期：2026-08-26
状态：已确认（2026-08-26）
目标草稿：`draft-cf24aa3b34fe` / `mzsettlement_verify_skill`
业务挂载：`verify + settlement`

## 1. 决策摘要

本次不新建第二个门诊 Skill，直接完善现有 `mzsettlement_verify_skill` 草稿，并同时补齐它依赖的门诊语义查询模型。

核心决策：

1. 用户问题按九类业务应用场景组织，不按数据库字段逐项建场景。
2. 复用现有 `mzjyxx` 对象，在同一对象内建立门诊交易汇总与费用明细两个数据集。
3. 缺失指标从语义层发现中心筛选，通过现有批量创建能力一次创建；不逐个手工新增，不新增另一套导入接口。
4. 已存在但定义、类型或值域错误的指标走现有受治理编辑，不通过批量创建重复覆盖。
5. 指标存在不等于可查询。必须同时声明数据集、键、语义字段、关系和质量规则，并发布完整查询模型。
6. 金额勾稽由确定性代码使用 `Decimal` 核验；模型只负责把已验证事实和政策证据组织成人能理解的解释。
7. 任何金额都区分实际零值、缺失、不适用和非零值，不允许 `null → 0`。
8. “覆盖所有人群、所有险种”指能力模型不硬编码某一人群/险种；某一具体组合能否给出确定性待遇结论，仍取决于已发布政策证据是否完整。

## 2. 现状与根因

### 2.1 草稿现状

现有草稿只有一个“核验待遇”场景，共引用 6 个指标：

- 公共指标：`TA_MZTimes`、`T_CureType`、`T_DiagType`、`P_FundType`；
- 场景指标：`T_FirstPay`、`T_SelfPayAll`。

它无法回答总费用、医保内外费用、基金构成、个人支付构成、年度累计、特殊待遇、明细自费和交易状态等核心问题。

场景还重复声明了公共 `question`、`settlement_id`、`hospital_id`，会触发 `COMMON_CONTEXT_REDECLARED` 校验错误。

### 2.2 语义层现状

`mzjyxx` 已发布 40 个指标，但当前查询模型中：

- `datasets=[]`；
- `keys=[]`；
- `fields=[]`；
- `relations=[]`；
- `metrics=[]`；
- `queryable=false`。

因此，只给 Skill 多勾选指标仍无法从真实数据源取数。

现有指标还存在以下治理问题：

- 总费用、医保内、医保外等基础字段已被发现但没有创建指标；
- 多个枚举、日期、标识和计数字段被错误标为 `Amount`；
- 枚举指标缺少已审核值域；
- `TA_MZTimes` 的现有中文释义为“门诊时间”，但物理类型为整数，不能在口径确认前继续作为公共指标使用；
- 现有正式回归案例数为 0，用户提供的门诊结算图片尚未形成可执行黄金案例。

## 3. 目标与非目标

### 3.1 目标

1. 一笔真实门诊结算可以通过结算标识查询到完整交易汇总和关联费用明细。
2. 用户询问任何结算单字段或常见“为什么”问题时，能路由到稳定场景。
3. 输出金额勾稽、待遇上下文、政策依据、异常项和下一步建议。
4. 对职工、居民、退休、公务员、军残、民政救助、退役军人、慢特病、异地等组合使用同一数据与规则框架。
5. 政策或数据不足时明确返回 `partial` 或 `unavailable`，不编造公式或待遇结论。
6. 门诊费用明细能解释“哪个药品、耗材或诊疗项目形成医保外、乙类先自付或超限价自付”。

### 3.2 非目标

- 不执行正式结算、退费、冲正、补报、待遇备案或身份修改。
- 不替代医保经办系统判责。
- 不把北京市某一年度政策比例硬编码成全国通用规则。
- 不推导缺少政策证据的单位补充、公疗补充或专项待遇公式。
- 不向用户暴露物理表名、字段名、SQL、内部计划或敏感身份信息。
- 不新增通用规则引擎、第三方语义层依赖或第二套门诊数据访问旁路。

## 4. 应用场景

执行契约使用一个公共上下文和九个 profile。

公共上下文只声明：

- `question`：必填，用于场景路由；
- `settlement_id`：必填，值就是门诊交易号 `T_TradeNo`，用于定位单次结算；
- `hospital_id`：由会话或接入层可选注入，不要求用户重复输入。

profile 不重复声明公共上下文。

| profile_id | 场景 | 用户可能问到的问题 | 主要输出 |
|---|---|---|---|
| `overall-settlement-verification` | 整体结算核验 | 这次结算对不对；总共花了多少；医保和个人各付多少 | 总费用双向勾稽、差额和总体状态 |
| `personal-liability-explanation` | 个人负担解释 | 为什么个人付这么多；自付一、二和大额自付是什么 | 个人负担构成、重复或缺失项 |
| `payment-channel-verification` | 支付渠道核验 | 账户、现金、统筹、大额、补充、公疗分别付多少 | 支付渠道明细及渠道合计 |
| `deductible-and-annual-progress` | 起付线与年度累计 | 为什么扣起付线；今年累计多少；还差多少起付或封顶 | 交易前后累计差值、当次起付和年度进度 |
| `reimbursement-and-cap-verification` | 报销比例与封顶 | 为什么按这个比例；社区和医院为何不同；是否超过封顶线 | 可核验计算基数、比例、封顶状态和政策引用 |
| `fee-item-scope-explanation` | 医保目录与费用明细 | 哪个药没报；为什么有医保外费用；乙类先自付来自哪里 | 项目级医保内外、项目等级、先自付和超限价汇总 |
| `eligibility-and-special-benefit` | 身份与特殊待遇 | 按什么险种/人员身份结算；慢特病、公务员、军残、大病、救助、退役待遇为何没参与 | 资格事实、专项支付、缺失资格或政策证据 |
| `cross-region-and-institution` | 异地与机构待遇 | 是否按异地结算；医院级别是否正确；为何没有社区待遇 | 异地标志、险种、机构等级与适用政策 |
| `transaction-status-and-refund` | 交易状态 | 是否结算成功；是否退费、冲正；国家平台为什么失败 | 交易链、状态、未结算原因和人工处理建议 |

### 4.1 路由边界

- “为什么这样结算”属于本 Skill。
- “如何备案慢特病”“如何办理异地就医”路由到导办 Skill。
- “请帮我退费/冲正/重新结算”进入高风险人工确认，不执行动作。
- “某项是否可以临床使用”不属于医保结算核验。

## 5. 语义模型设计

### 5.1 业务对象与数据集

复用 `mzjyxx` 业务对象，增加两个数据集：

| dataset_code | 来源候选 | 行粒度 | 用途 |
|---|---|---|---|
| `mz_trade` | `o_Trade` | 一次门诊交易 | 结算汇总、待遇上下文、累计、交易状态 |
| `mz_fee_item` | `o_FeeItem` | 一次交易下一个费用项目行 | 药品/项目级医保内外与先自付解释 |

`o_FeeItem` 是优先验证候选，因为它具有与 `o_Trade.T_TradeNo` 明确同名的关联字段，并包含费用项目、医保编码、项目等级、个人自付二、乙类先自付和超限价自付。其 `FeeIn/FeeOut` 现有字段释义存在歧义，必须用真实汇总勾稽确认口径；若不能证明与交易汇总一致，则切换到医保内外释义更明确的 `yb_mzfymx_mz`。不得同时接入两个口径相近的费用事实表后直接相加。

### 5.2 锚点、键与关系

- 用户锚点：`settlement_id = T_TradeNo → mz_trade.T_TradeNo`。
- 交易实体主键：`T_TradeNo`（当前只读画像中非空且唯一；生产仍由质量规则持续校验）。
- 明细主键候选：`T_TradeNo + ItemId + ItemNo`。
- 关系：`mz_trade.T_TradeNo 1 → N mz_fee_item.T_TradeNo`。

上述键不凭字段名直接发布。发现画像和真实只读查询必须先证明：

1. 交易主键非空且唯一；
2. 明细复合键非空且唯一；
3. 一个结算锚点只定位到一笔有效交易；
4. 明细只关联到一个交易；
5. 退费/红冲历史不会与有效交易一起重复汇总。

任一唯一性或关系基数不成立，发布门禁阻断。

### 5.3 发现中心批量创建指标

不新增批量接口，复用发现中心和 `POST /semantic/metrics/batch`：

```text
最新发现扫描
  → 按 o_Trade / o_FeeItem 过滤
  → 按本规格字段白名单批量选择
  → 人工确认中文名、定义、semantic_type、单位、重要性和值域
  → 一次提交 /semantic/metrics/batch
  → created / skipped / error 逐项核对
  → 已存在指标走编辑修正
  → 创建数据集、键、语义字段、关系和质量规则
  → 发布 mzjyxx 新版本
```

批量创建必须遵守：

- 禁止沿用接口默认 `semantic_type=Amount`；每项显式设置正确类型。
- `created` 才表示新指标创建成功；`skipped` 需检查既有指标口径；任一 `error` 阻断后续发布。
- 枚举字段先查看 distinct 值和源值频次，再建立值域和映射。
- 批量创建只负责指标注册，不代表查询模型可运行。
- 不把姓名、卡号、身份证号、出生日期等敏感字段加入 Skill 输入。

## 6. 确定性核验规则

所有金额使用 `Decimal`，按人民币分舍入，默认允许 0.01 元舍入差。

### 6.1 通用勾稽

当对应字段均存在且口径一致时执行：

```text
总费用 = 医保内费用 + 医保外费用
总费用 = 基金支付总额 + 个人支付总额
个人支付总额 = 个人账户支付 + 现金支付
交易后累计 - 交易前累计 = 本次对应累计增量
```

个人自付一、自付二、大额自付、起付金额与专项补助之间的组合关系不能写成全国固定公式；只有字段定义和适用政策共同证明成员关系时才执行。

基金渠道也不得盲目把所有支付字段相加。`T_FundPay`、`NT_AgencySumPay`、`NT_BasicPay` 可能是总额与分项的不同口径；成员关系未确认前只分别展示，不做重复求和。

### 6.2 比例核验

比例核验需要同时满足：

1. 险种、人员类别、医疗类别、机构级别、异地/慢特病等上下文完整；
2. 命中已发布且有效期覆盖交易日期的政策规则；
3. 政策规则明确计算基数、起付、分段、比例和封顶；
4. 结算字段足以复算；
5. 复算与结算结果在容差内一致。

条件不满足时只能解释已知金额，待遇核验为 `partial` 或 `not_evaluable`。

### 6.3 零值、缺失和不适用

每个字段输出统一状态：

```text
non_zero         数据源明确返回非零值
reported_zero    数据源明确返回 0
missing          数据源未返回或关联记录缺失
not_applicable   资格事实与政策证据共同证明不适用
```

`reported_zero` 不能自动解释为“不符合待遇”；`not_applicable` 不能仅由金额为零推断。

## 7. 政策证据与全部人群/险种能力

Skill 采用数据与政策双证据：

- 结算数据证明“系统本次实际如何支付”；
- 政策知识证明“该人群、险种、时间和机构条件下应如何处理”。

政策检索条件至少包括：

- 统筹地区；
- 生效/失效时间；
- 险种；
- 人员类别；
- 医疗类别；
- 医疗机构等级或类别；
- 本地/异地；
- 普通门诊/慢特病等待遇类别；
- 基金或专项待遇类型。

系统不维护“所有人群 × 所有险种”的硬编码笛卡尔表。新增人群、险种或专项待遇时，通过语义值域、政策规则和源值映射扩展，不修改核验算法。

单位补充、公疗补充等支付若只有结算金额、没有单位或政策公式，只能说明“本次实际支付金额”，并在不确定性中列出缺少的补充政策依据。

## 8. 输出契约

公开结果至少包含：

```text
status: complete | partial | unavailable
scenario_id
summary
context_checks[]
amount_checks[]
field_explanations[]
anomalies[]
citations[]
uncertainties[]
next_actions[]
```

`amount_checks[]` 包含：核验名称、业务等式、实际值、期望值、差额、容差和状态。

`field_explanations[]` 包含：业务字段名、值、存在状态、适用性、解释和引用。公开结果不返回物理字段编码。

整体状态：

- `complete`：核心结算数据完整，相关勾稽均通过，用户所问待遇有充分政策证据；
- `partial`：部分事实可验证，但存在非阻断数据、政策或明细缺口；
- `unavailable`：结算不存在、状态无效、核心金额缺失、关系重复或数据源不可用，无法形成可靠结论。

## 9. 评测设计

### 9.1 黄金案例

用户提供的门诊结算图片作为首个黄金案例，必须逐字段覆盖图片中所有非零和零值，并断言：

- 总费用 = 医保内 + 医保外；
- 总费用 = 基金支付 + 个人支付；
- 个人支付 = 账户支付 + 现金支付；
- 图片展示的 70% 计算链能够在政策证据与上下文齐全时复算；
- 单位补充医疗支付金额可展示，但缺单位政策公式时不得伪造计算过程；
- 所有图片字段都有解释或明确的不确定性，不能因值为零而省略。

### 9.2 回归矩阵

采用代表性组合和边界覆盖，不穷举硬编码所有组合：

| 用例 | 重点 |
|---|---|
| 普通职工门诊、医院就诊 | 基本勾稽和比例 |
| 职工社区门诊 | 机构待遇差异 |
| 未达到起付线 | 基金零值与不适用原因分离 |
| 城乡居民一级医院 | L1 年度累计口径 |
| 退休人员 | 人群值域和政策条件 |
| 慢特病 | 资格存在、缺失、未参与三种情况 |
| 异地门诊 | 异地标志、国家平台状态、异地险种 |
| 公务员/公疗补充 | 专项资格与 `T_OfficalPay` |
| 军残待遇 | `T_JCPay` 非零及零值 |
| 大病保障 | 当次支付与前后累计 |
| 民政救助 | 资格、当次支付和累计 |
| 退役医疗 | 资格标志与支付 |
| 多专项基金同时非零 | 防止总额与分项重复求和 |
| 医保外费用明细 | 明细汇总到交易总额 |
| 乙类先自付/超限价 | 项目级原因解释 |
| 明确零值与字段缺失 | `reported_zero` 与 `missing` 不混淆 |
| 算术不一致 | 返回差额和人工复核，不判责 |
| 政策缺失或过期 | `partial`，不得给确定性待遇结论 |
| 退费/冲正/失败交易 | 阻断正常金额解释，转人工核对 |
| 数据源超时 | `unavailable`，不使用示例假数据 |
| 敏感字段检查 | 不回显身份证、卡号、姓名和内部表字段 |

### 9.3 路由评测

- 每个 profile 至少 3 个正向问法；
- 场景之间至少 1 组容易混淆的对照问法；
- 导办、高风险动作、住院结算和临床问题必须负向排除；
- 所有候选路由案例进入服务端治理案例集，不只保存在文档中。

## 10. 错误与安全处理

| 情况 | 结果 |
|---|---|
| 结算 ID 不存在 | `unavailable`，提示核对标识 |
| 同一锚点命中多个有效交易 | `unavailable`，数据质量阻断 |
| 明细重复导致金额可能放大 | `unavailable`，数据质量阻断 |
| 缺可选专项字段 | `partial`，保留其他可验证结果 |
| 缺政策证据 | `partial`，只解释实际支付，不判断待遇正确性 |
| 用户要求退费/冲正 | `waiting_human_confirmation`，不执行 |
| 数据源或政策服务故障 | 有界恢复一次；仍失败则 `unavailable` |

所有输出必须携带 `citations`；无法引用时必须携带 `uncertainties`。敏感数据经过现有脱敏边界，日志只记录指标编码、计划哈希和质量状态，不记录患者原值。

## 11. 实施顺序

1. 用发现中心复核字段画像、键唯一性、值域和金额口径。
2. 先补指标批量创建和既有错误指标修正的测试。
3. 通过发现中心批量创建缺失指标，修正既有指标类型和值域。
4. 建立 `mz_trade`、`mz_fee_item` 数据集、键、字段、关系和质量规则，使 `mzjyxx.queryable=true`。
5. 发布新的 `mzjyxx` 查询模型版本，并以脱敏锚点执行受控真实查询。
6. 更新 `mzsettlement_verify_skill` 草稿的公共输入、九个 profile、路由词、Schema 和输出契约。
7. 实现确定性金额核验与状态聚合，接入政策证据和不确定性。
8. 把图片案例和回归矩阵落入正式评测资产。
9. 校验草稿、包预览、物化候选、运行路由和行为评测；不自动激活。

## 12. 验收标准

1. `GET /semantic/objects/mzjyxx/query-model` 返回 `queryable=true`，且包含已发布数据集、键、字段、关系、指标和质量规则。
2. Skill 输入校验无阻断项，场景不重复声明公共上下文。
3. 九个场景均能被代表性问法路由，排除意图不会误入。
4. 用户图片中的全部显示字段均得到解释、核验或明确不确定性，零值不被遗漏。
5. 对至少职工、居民、退休、慢特病、异地和三类专项待遇的代表性组合完成回归。
6. 缺数据、缺政策、交易失败、退费冲正和金额不一致均按设计失败关闭。
7. 公共结果不含敏感信息、物理字段、SQL 或模型内部推理。
8. 验证严格按项目要求执行：单元测试 → API 测试 → Flow 测试；涉及 Portal 时再运行相关 Vitest、TypeScript 和构建验证。

## 13. 风险等级与变更边界

本改动涉及医保金额、政策适用、真实数据查询、语义模型发布和 Skill 行为，按 R4 执行验证与人工审查。

最小可验证用户故事：

> 医保办人员输入一笔门诊结算标识并询问“这次门诊结算为什么个人支付这么多”。系统通过已发布 `mzjyxx` 查询模型取得单次交易和费用明细，确定性核验总费用、医保内外、基金与个人支付关系，按用户实际人群和待遇上下文检索有效政策，解释所有非零与零值；证据不足时明确返回部分可核验，不编造补充待遇公式，也不执行任何高风险动作。

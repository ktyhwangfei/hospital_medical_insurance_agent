# 政策知识「构建—审核—发布管理」设计规格

> 日期：2026-08-05  
> 状态：产品方向已确认，待书面复核  
> 适用范围：`/policy-knowledge/knowledge` 及其子路由  
> 上游设计：`docs/steering/政策知识治理-知识页前端改造设计-V4.1.md`

## 1. 设计结论

政策知识模块已有“概览 / 文档 / 单元 / 知识 / 测试”一级页面。知识页不再重复提供治理驾驶舱、通用工作台或 Schema 编辑，而是聚焦知识库生产的核心闭环：

```text
文档
→ 单元拆分与审核
→ 知识构建
→ 知识审核
→ 发布管理
→ 正式知识版本
```

关键约束：

1. 禁止文档直接构建知识，知识构建只能消费审核通过的单元版本。
2. 知识页二级导航固定为“知识构建 / 知识审核 / 发布管理”。
3. Schema 由语义层统一维护；知识页只读引用并锁定语义契约版本。
4. 前端不再使用“知识变更集”作为主要业务概念，统一显示为“构建结果”或“待审知识”。
5. “待决策”不再作为独立工作空间，而是知识审核中的“待处理问题”。
6. 构建页只保留一个主操作“新建构建任务”。
7. 同一单元版本禁止同时进入多个未结束的构建、审核或待发布流程。
8. 所有构建结果版本化保存，任务之间不能原地覆盖结果。
9. 只有发布管理可以生成新的正式版本；已发布快照不可变。

## 2. 目标与非目标

### 2.1 目标

- 让业务人员清楚理解知识如何从政策单元进入正式知识库。
- 让每次构建的来源单元、语义契约、模型流水线和结果均可追溯。
- 让构建、审核、发布三个阶段职责清晰，不重复导航和操作。
- 支持安全重新构建、规则替代、冲突发现和历史回滚。
- 复用现有 `PolicyRuleUnit`、`KnowledgeChangeSet`、`DecisionTask`、`KnowledgeRelease` 和 `PublishedKnowledgeSnapshot` 能力，避免重造发布与质量门禁。

### 2.2 非目标

- 不在知识页上传或管理政策文档。
- 不在知识页拆分、合并或审核政策单元。
- 不允许文档绕过单元层直接构建知识。
- 不在知识页新增或修改 Schema、指标、值域和概念。
- 不在构建结果生成后直接覆盖正式知识。
- 不在本阶段启用 AI 自动发布。

## 3. 信息架构与业务语言

### 3.1 一级导航

保持现状：

```text
概览 / 文档 / 单元 / 知识 / 测试
```

### 3.2 知识页二级导航

```text
/policy-knowledge/knowledge/build
  → 知识构建

/policy-knowledge/knowledge/review
  → 知识审核

/policy-knowledge/knowledge/releases
  → 发布管理
```

`/policy-knowledge/knowledge` 默认重定向到 `/build`。

### 3.3 前端概念映射

| 内部领域对象 | 前端业务名称 | 说明 |
|---|---|---|
| KnowledgeBuildTask | 构建任务 | 一次从已审核单元生成候选知识的异步任务 |
| KnowledgeChangeSet | 构建结果 / 待审知识 | 继续作为内部聚合对象，不向业务人员强调“变更集” |
| DecisionTask | 待处理问题 | 嵌入知识审核，不再作为独立导航 |
| PublishedKnowledgeSnapshot | 正式版本 | Agent 运行时可读取的不可变知识快照 |
| KnowledgeRelease / QualityRun | 发布候选 / 发布检查 | 发布管理中的候选版本和门禁结果 |

## 4. 页面一：知识构建

### 4.1 页面目标

回答四个问题：

- 当前有哪些构建任务？
- 每个任务使用了哪些已审核单元？
- 任务执行到哪一步、是否需要处理？
- 完成后生成了多少待审知识？

### 4.2 页面布局

首屏从上到下为：

1. 二级导航：知识构建 / 知识审核 / 发布管理。
2. 紧凑构建上下文栏：可用已审核单元数、当前语义契约版本、语义层查看入口。
3. 紧凑流程条：文档接入 → 单元拆分与审核 → 知识构建 → 知识审核 → 发布正式版本。
4. 状态摘要：可构建单元、正在构建、等待审核、构建成功率。
5. 全宽构建任务列表。

构建来源和语义契约不得使用独立大卡片。它们是执行约束，不是首页核心对象。

### 4.3 唯一主操作

页面仅保留：

```text
+ 新建构建任务
```

不在主页常驻“选择单元”面板，也不提供第二个“使用所选单元构建”按钮。

单元页允许勾选审核通过的单元并点击“构建知识”。该操作进入同一个创建流程，并自动带入已选单元。

### 4.4 任务列表字段

| 字段 | 说明 |
|---|---|
| 任务名称 / task_id | 业务名称和审计标识 |
| 来源单元 | 单元数量、来源政策数量，可展开查看精确版本 |
| 语义契约 | 构建时锁定的版本，作为次级信息显示 |
| 当前阶段 | 排队、抽取、语义映射、确定性校验、生成结果 |
| 进度 | 已处理单元数 / 总单元数及百分比 |
| 状态 | 构建中、部分失败、待审核、需要处理、已完成、已取消 |
| 结果摘要 | 新增、修改、替代、冲突、待处理问题数 |
| 操作 | 查看、重试失败单元、去审核、重新构建、取消 |

## 5. 新建构建任务

采用三步抽屉或独立页面，不使用多主按钮并列。

### 5.1 第一步：选择已审核单元

只显示当前知识库中审核通过的单元版本。支持按政策文件、条款、审核时间和构建状态筛选。

单元显示状态：

- 未构建：可正常选择。
- 构建中：不可选择，显示占用任务并允许跳转。
- 等待知识审核：不可选择，显示当前审核入口。
- 等待发布：不可选择，显示发布候选入口。
- 构建失败或审核退回：允许重新构建。
- 已形成正式知识：默认不选；显式切换为“重新构建”后可选。
- 内容产生新单元版本：新版本按未构建或需重建处理。

### 5.2 第二步：确认构建配置

显示并锁定：

- 语义契约版本；
- AI 流水线版本；
- 模型路由场景；
- 抽取配置哈希；
- 构建模式：首次构建或重新构建；
- 重新构建原因（重新构建时必填）。

知识页不能修改语义契约。缺少概念、指标或值域时，提供“前往语义层处理”入口。

### 5.3 第三步：冲突预检

创建前返回并展示：

```text
已选择单元          12
可正常构建           9
正在其他流程中       1  阻断
已有未结束候选       1  阻断
建议重新构建         1  语义契约已升级
```

阻断项不能提交，可一键排除。重新构建项必须确认影响范围和原因。

## 6. 页面二：知识审核

### 6.1 页面目标

审核 AI 从单元生成的完整构建结果，并集中解决疑难问题。页面不要求用户理解 `KnowledgeChangeSet` 或 `DecisionTask`。

### 6.2 页面视图

```text
待我审核 / 全部审核 / 已完成
```

列表按构建任务聚合：

```text
《北京市门诊待遇调整通知》
来源：12 个已审核单元
新增知识 12 条｜修改 5 条｜替代 3 条｜待处理问题 2 项
```

### 6.3 审核详情

详情页包含：

- 构建结论和风险摘要；
- 来源单元与政策原文证据；
- 结构化规则；
- 新旧知识语义 Diff；
- 重复、替代、规则分支和冲突检测；
- 语义映射只读视图；
- 待处理问题、AI建议、候选项和影响范围；
- 通过审核、退回重新构建、拒绝、不适用。

语义层修改完成后，审核页只提供“重新映射 / 重新校验 / 退回重新构建”，不直接编辑 Schema。

### 6.4 决策任务的归属

待处理问题必须归属于一个构建结果。首页可以汇总“待我处理”，但点击后仍进入相应审核上下文。不得重新建立独立“待决策”工作空间。

## 7. 页面三：发布管理

### 7.1 页面目标

管理审核通过的发布候选、当前正式版本和历史正式版本。

### 7.2 页面结构

```text
待发布 / 当前正式版本 / 历史版本
```

### 7.3 发布候选

每个候选展示：

- 来源构建任务和审核记录；
- 新增、修改、替代、失效数量；
- 语义契约版本和测试用例集版本；
- 六维质量摘要；
- 未解决阻断问题；
- 影响的规则、指标、技能和检索索引；
- 发布检查和回归测试结果。

### 7.4 发布动作

发布必须生成新的不可变正式版本，不允许修改已有正式版本。回滚通过重新激活历史版本或生成回滚版本完成，并记录发布人、时间、原因和血缘。

## 8. 单元占用与跨任务覆盖规则

### 8.1 核心原则

```text
同一个 unit_id + unit_version，
同一时间最多存在一个未结束的候选知识生命周期。
```

“未结束”覆盖：排队、构建中、部分失败待处理、等待审核、审核中、审核通过待发布。

锁在 `FAILED / RETURNED / REJECTED / CANCELLED / PUBLISHED` 终态释放。`PARTIAL_FAILURE` 不是终态：成功结果继续保留，失败单元在原任务内重试；只有用户取消或明确结束任务后才释放占用。这样不会通过不断创建新任务绕开审核。

### 8.2 允许的重新构建

以下情况可以显式重新构建：

- 上一次构建失败；
- 审核退回；
- 单元产生新版本；
- 语义契约或流水线版本升级；
- 正式知识需要重新抽取或修订。

重新构建必须创建新任务，记录原因和上一候选/正式知识标识。单纯重试瞬时失败应留在原任务中，不创建新的候选版本。

### 8.3 禁止原地覆盖

每次构建生成新的候选结果 ID。新结果通过以下血缘关联旧结果：

```text
source_unit_id
source_unit_version
build_task_id
semantic_contract_version
pipeline_version
supersedes_candidate_id
supersedes_rule_ids
```

新候选不能删除或修改旧候选；审核通过并发布后，才会在新正式版本中替代旧规则。

### 8.4 不同单元生成相似知识

系统按稳定规则身份、语义指纹和适用范围检测：

- 完全重复：合并证据，不重复发布规则；
- 同规则补充：追加证据或条件；
- 适用范围不同：形成规则分支；
- 新规则替代旧规则：建立 `supersedes`；
- 实质矛盾：生成阻断性的待处理问题。

不得按任务创建时间或完成时间自动覆盖。

## 9. 数据模型建议

### 9.1 KnowledgeBuildTask

```text
task_id
knowledge_base_id
name
status
build_mode
semantic_contract_version
pipeline_version
model_scene
config_hash
rebuild_reason
created_by / created_at
started_at / finished_at
result_change_set_id
```

建议状态：

```text
DRAFT → QUEUED → RUNNING → WAITING_REVIEW
                    ├→ PARTIAL_FAILURE
                    └→ FAILED
WAITING_REVIEW → APPROVED_PENDING_RELEASE → PUBLISHED
               ├→ RETURNED
               └→ REJECTED
任意可取消状态 → CANCELLED
```

### 9.2 KnowledgeBuildTaskUnit

```text
task_id
unit_id
unit_version
unit_content_hash
status
attempt_count
candidate_result_ids
error_code / error_message
```

单元版本必须是不可变输入。如果现有单元模型尚无显式 `unit_version`，第一阶段使用持久化的 `unit_revision_id = unit_id + content_hash` 作为等价版本标识；不得只用可变的 `unit_id` 判断重复和占用。

### 9.3 UnitBuildClaim

采用独立占用记录或等价的数据库部分唯一约束，保证一个单元版本只有一个活跃候选生命周期：

```text
unit_id
unit_version
task_id
claim_status
claimed_at
released_at
```

占用校验与任务创建必须在同一数据库事务中完成，不能只依赖前端禁用。占用唯一键使用不可变的单元修订标识；若一个逻辑单元产生新修订但旧修订仍处于未结束生命周期，预检必须阻断并引导用户先结束旧流程，避免同一来源同时产生两个待发布候选。

## 11. 错误处理

| 场景 | 响应与前端行为 |
|---|---|
| 单元未审核通过 | 422；列出不可用单元并阻止创建 |
| 单元已被活跃任务占用 | 409；返回 task_id，提供跳转当前任务 |
| 已有未结束候选 | 409；跳转知识审核或发布候选 |
| 语义契约不存在或失效 | 409；阻断创建并跳转语义层 |
| 部分单元构建失败 | 任务进入 PARTIAL_FAILURE；保留成功结果，支持在原任务重试失败单元 |
| 模型调用失败 | 按异常分类记录尝试，不生成不完整正式结果 |
| 构建期间单元版本变化 | 当前任务继续使用已锁定版本；新版本另行构建，不静默切换 |
| 重复或规则冲突 | 生成审核问题；高风险冲突阻断发布 |
| 发布检查失败 | 保持候选状态，展示阻断原因，不修改当前正式版本 |

## 12. 追溯、安全与审计

- 每条候选和正式知识保留来源单元版本、原文证据、任务、契约和流水线版本。
- AI输出携带证据或不确定性，不产生无来源的确定性规则。
- 高风险冲突、替代和发布动作必须人工确认。
- 构建、审核、发布、退回、重试、回滚全部写入审计日志。
- 正式版本只读；任何修改都通过重新构建或修订产生新候选。
- 敏感信息继续经过现有脱敏和权限边界，不在知识任务页面显示基础设施密码。

## 13. 验收标准

### 13.1 信息架构

- 知识页仅有“知识构建 / 知识审核 / 发布管理”三个二级入口。
- 不出现驾驶舱、通用工作台、独立待决策或知识变更集主导航。
- Schema 编辑仅存在于语义层。

### 13.2 构建入口

- 构建主页只有一个主按钮“新建构建任务”。
- 文档页不存在“直接构建知识”操作。
- 单元页可把审核通过的单元带入同一个创建流程。
- 创建流程只能提交审核通过的精确单元版本。

### 13.3 并发与版本

- 两个请求并发选择同一单元版本时，最多一个成功创建活跃任务。
- 重新构建产生新候选，不改变旧候选和历史正式版本。
- 等待审核或等待发布的单元不能进入另一普通构建任务。
- 重复和冲突知识进入审核，不自动覆盖。

### 13.4 发布

- 只有审核通过且发布检查通过的候选可以发布。
- 每次发布生成新正式版本并保留来源血缘。
- Agent 运行时只读取当前正式版本。
- 回滚不会删除历史版本。

### 13.5 前端布局

- 构建来源限制和语义契约以紧凑上下文栏显示，不占据首屏大卡片。
- 构建任务列表是知识构建页主视图。
- 单元选择位于新建任务流程，不常驻构建主页。

## 14. 与 V4.1 的关系和迁移

本规格是对 V4.1 页面结构和业务语言的收敛，不推翻其底层治理能力：

- `KnowledgeChangeSet` 继续作为内部构建结果聚合，但前端改称“构建结果 / 待审知识”。
- `DecisionTask` 继续落库，但入口并入知识审核。
- AI 治理统计迁回一级“概览”，不在知识页重复建设驾驶舱。
- 已发布知识和快照能力迁入“发布管理”。
- 原三栏工作台的证据、规则详情和语义映射组件复用于审核详情；不再保留独立“工作台”入口。
- 原文档直建接口迁移为审核单元驱动的知识构建任务。

实施顺序建议：先建立单元构建任务与占用约束，再调整知识构建页；随后合并审核入口，最后迁移发布管理并下线旧导航。

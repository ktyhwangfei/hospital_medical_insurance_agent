# 医保数据底座 · 落地方案（待确认）

> 日期：2026-09-02 · 状态：**方案稿，未开发** · 依据：[开源调研报告](../research/2026-09-02-医保数据底座开源调研.md)
> 原则：先调研、再定方案、最后动手；借鉴成熟经验，不重复造轮子。

## 1. 目标与定位

打造院端**医保数据底座**，向上支撑三类消费方，复用同一套语义与数据资产：

```
┌─────────────────────────────────────────────────────┐
│  消费层： 受控问数(P3)   结算单解释(P2/P4)   运营指导(新) │
├─────────────────────────────────────────────────────┤
│  语义层： 指标字典(YAML即代码) + 可信问题绑定 + 权限口径    │  ← 借鉴 WrenAI MDL / SuperSonic
├─────────────────────────────────────────────────────┤
│  加工层： 主题宽表(就诊/交易/费用/诊断) + 指标集市 + 血缘    │  ← 借鉴 Cube 数据模型
├─────────────────────────────────────────────────────┤
│  接入层： 契约同步(CDC/定时SQL) + 源表映射向导(已完成)      │  ← 已自研上线，不引入 DataX/Airbyte
└─────────────────────────────────────────────────────┘
```

平台定位不变：AI 导办与协同中枢，不替代医保正式结算/事前审核等既有业务系统。

## 2. 选型决策表（核心结论）

| 决策点 | 结论 | 理由 | 放弃项 |
|---|---|---|---|
| 数据接入 | **自研保留** | 单院区内网 + 3 张契约表 + 双模式 + 质量门已上线；通用平台重一个数量级 | Airbyte/DataX/Debezium 整体引入 |
| 语义层 | **自研轻量**，MDL 理念 | 指标口径是医保领域资产（P3 已冻结五指标口径）；YAML 即代码 + Git 评审即可获得 WrenAI 核心价值，无需多引擎 | Cube/WrenAI 整体嵌入 |
| 问数形态 | **受控模式先行** | SuperSonic 论证：复杂 SQL 卸载给确定性层，LLM 只做映射；医保场景"可审计确定性"是硬要求 | 自由 Text2SQL 直接放开 |
| NL 校准 | **借鉴** 术语库 + 可信问题-SQL 示例库 | SQLBot/Vanna 的"越问越准"闭环 | — |
| 政策 RAG | **保留自研**，借鉴 RagFlow 表格解析 | 已有 Milvus 结构化检索 + 引用规范 | Dify 换引擎 |
| 运营可视化 | **自研仪表盘**（Next.js + 宽表指标 API） | 复用 portal；许可证无忧（DataEase GPL-3.0 排除） | 后期自由分析再评估嵌 Superset(Apache-2.0) |
| 治理/血缘 | **内嵌轻量**（批次表 → 宽表 → 指标三级血缘 + SLA 看板） | 已有批次/质量门数据，展示层补齐 | DataHub/OpenMetadata 平台引入 |

## 3. 分阶段方案（对齐 P2–P5）

### 阶段 A：底座产品化（新立 A，P1 完成后启动，~2 周）

**把"3 张投影表"升级为"有语义的数据底座"。**

| 交付物 | 内容 | 验收 |
|---|---|---|
| A1 主题宽表 | `dw_outpatient_visit`（就诊宽：交易+诊断+费用汇总一行一就诊）、`dw_outpatient_fee_daily`（科室/日费用集市），由同步批次驱动增量加工 | 宽表行数与投影对账一致；批次幂等重放不重复 |
| A2 指标字典即代码 | `semantic/metrics/*.yaml`：指标(名称/口径/维度/单位/责任科室/available 状态) + 维度 + 可信问题绑定；Git 评审后经管理端发布版本 | 指标定义变更可 diff、可回滚；P3 五指标先行录入 |
| A3 血缘与 SLA | 批次→投影→宽表→指标 血缘查询 API + Portal 页；同步 P95/质量门结果 SLA 看板 | 页面可查任一指标的上下游与数据新鲜度 |

### 阶段 B：受控问数（= P3 运营受控问数，~2 周）

| 交付物 | 内容 | 验收 |
|---|---|---|
| B1 指标查询 API | `metric + dimensions + filters + time_range → SQL → 结果`（借 Cube 查询形态），仅限指标字典内元素组合，行级数据范围（科室→就诊下钻，P3 已冻结） | 越权维度/未发布指标 403/404；SQL 可解释可审计 |
| B2 可信问题绑定 | 自然语言问题 → 指标查询的**受控映射**（借 SuperSonic Schema Mapper 思路：术语库匹配 + LLM 对齐 + 校正器），映射不确定时降级为候选问题列表 | 五维度及可信问题口径按 P3 冻结文档自动验收；就诊人次保持 unavailable |
| B3 术语库与示例库 | 医保术语→字典元素的运营界面（借 SQLBot），问答对沉淀 | 新增术语无需发版 |

### 阶段 C：结算单解释升级（= P2 结算核验 + P4 入口统一，~2 周）

| 交付物 | 内容 | 验收 |
|---|---|---|
| C1 解释数据面指标化 | 结算单解释的金额构成/自付/基金支付改由宽表+指标确定性计算（现状：逐字段拼装） | 九个 Profile、Decimal 勾稽、字段四态（P2 验收矩阵） |
| C2 政策证据升级 | 政策表格条款解析借鉴 RagFlow 切片策略，结构化引用到费用行级 | 政策引用可定位到表格单元格 |
| C3 统一入口 | `/policy-qa` 会话内集成问数意图路由（解释类→结算解释 skill；指标类→受控问数） | P4 验收：不要求结算 ID 也能问运营指标 |

### 阶段 D：运营指导（新立 D，~1.5 周）

| 交付物 | 内容 | 验收 |
|---|---|---|
| D1 运营仪表盘 | 科室/医保类型/时间趋势的指标仪表盘包（自研 ECharts，消费 B1 API） | 指标口径与字典一致，脱敏输出 |
| D2 订阅与解读 | 周报订阅 + AI 运营摘要（指标异动 + 政策依据，带 citations） | 摘要每条结论可溯源到指标批次 |

### 阶段 E：上线加固（= P5，按医院排期）

SSO/扫码身份、权限矩阵（数据集/列/行三级，借 SuperSonic 粒度）、审计、性能与回滚门槛。

## 5. 风险与开放问题（需你拍板）

1. **阶段顺序**：建议 A→B→C→D→E（语义层先行）。若你更急于"运营指导"见效，可 A→D(消费 A1 宽表的少量固定指标)→B→C，代价是 D 的指标口径在 B 之前无字典治理。
2. **宽表加工引擎**：方案为"同步 worker 内追加加工步骤"（无新服务）。若未来表规模大或加工逻辑复杂，再评估 dbt 风格的 transform 层。
3. **自由问数后门**：受控模式之外是否提供"管理员自由 NL2SQL（带护栏+审计）"——WrenAI 有成熟模式，可作为 B 阶段可选项。
4. **嵌入 Superset**：本方案不嵌入。若院方已有 Superset 使用习惯，D1 可改为嵌入 + 指标 API 供数，需提前告知。
5. **许可证**：若未来要整仓嵌入任何 NOASSERTION 许可证项目（supersonic/sqlbot 等），需法务复核——本方案已规避该需求。

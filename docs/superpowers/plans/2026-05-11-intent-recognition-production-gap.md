# 意图识别模块正式版差距与功能补全清单

## 1. 总体判断

当前意图识别模块已经具备基础雏形，但还不是正式产品形态。它现在更像是一个“LLM JSON 解析 + 写死关键词兜底”的轻量路由器，能支撑 MVP 演示，但不足以支撑院端医保 AI 导办的正式版。

当前主要问题集中在四点：

1. 意图识别能力偏硬编码，业务场景、关键词和路由逻辑耦合较重，见 [`parser.py`](src/runtime/intent/parser.py)。
2. LLM 没有真正成为主识别能力，目前只是简单要求模型返回 JSON，缺少候选意图召回、上下文改写、结果校验和置信度治理。
3. 没有 RAG 支撑，模型无法基于意图定义、业务场景说明、政策规则、错误码、系统能力边界等知识进行判断。
4. 没有 Query Rewrite 和上下文补全能力，用户说“这个患者”“刚才那个结算问题”“帮我看一下风险”时，系统难以结合会话、页面和患者上下文还原真实意图。

因此正式版不应继续扩大关键词表，而应升级为：

> LLM 主导理解 + RAG 召回候选意图与业务知识 + Query Rewrite 补全上下文 + 结构化校验 + 保守降级澄清。

## 2. 产品定位约束

意图识别模块的定位不是“万能业务 Agent”，而是院端医保 AI 导办的入口理解层。它应该解决“用户到底想进入哪个医保业务场景、需要哪些上下文、是否需要澄清”的问题，不应该承担正式业务处理。

它需要坚持以下边界：

1. 只做意图理解、候选场景判断、上下文补全建议和路由辅助。
2. 不直接执行退费、冲正、结算、病案修改、费用调整等高风险动作。
3. 不替代权限判断，权限仍由安全模块处理。
4. 不替代业务系统判断，正式结果仍来自医保接口、HIS、EMR、收费、事前审核、DRG/DIP、病案等系统。
5. 不确定时宁可澄清，不要强行猜测。
6. 对未开通场景可以识别，但必须明确提示当前版本暂未开通。

## 3. 当前模块差距

### 3.1 意图识别过于写死

当前识别逻辑主要依赖 [`parser.py`](src/runtime/intent/parser.py) 中的固定关键词兜底，注册表 [`registry.py`](src/runtime/intent/registry.py) 也只包含少量场景定义。

正式版需要将“写死判断”改造成“可配置、可检索、可解释”的意图体系：

1. 每个意图应有名称、描述、适用角色、示例问法、反例、所需实体、关联场景、状态、输出要求。
2. 意图定义不应只存在于代码里，应逐步沉淀为可维护的意图知识资产。
3. 高频兜底规则可以保留，但只能作为降级和强信号补充，不应作为主路径。
4. 新增场景时，应优先补意图定义和示例，而不是改一堆 if-else。

### 3.2 LLM 主识别能力不足

当前 LLM 只是被要求返回一个 JSON，没有形成完整的意图判断链路。

正式版需要补齐：

1. 候选意图输入：LLM 不应面对所有可能意图盲选，而应先拿到候选意图列表。
2. 场景边界说明：LLM 需要知道结算异常、出院前质控、拒付申诉、政策解释、DRG/DIP、病案风险等场景之间的差异。
3. 正反例提示：每个意图要有典型问法和容易误判的反例。
4. 结构化输出：输出不仅包含 intent，还要包含置信度、理由、所需上下文、缺失字段、是否需要澄清、候选意图排序。
5. 结果校验：LLM 返回的意图必须在注册表或候选集中，不能凭空生成。
6. 低置信处理：置信度低、候选意图接近或上下文不足时，应进入澄清，而不是直接路由。

### 3.3 缺少 RAG 召回

正式意图识别不能只靠 Prompt 中塞固定意图列表。随着场景增多，Prompt 会越来越长，且场景边界难维护。

需要引入轻量 RAG，用于召回：

1. 意图定义知识：每个业务意图的描述、适用范围、角色、示例、反例。
2. 场景能力知识：当前版本哪些场景已实现，哪些只是规划中。
3. 业务术语知识：医保结算、拒付、事前审核、DRG/DIP、病案首页、收费冲正等术语说明。
4. 错误码与规则知识：错误码、政策规则、审核命中信息可作为判断用户问题类型的依据。
5. 系统能力边界：AI 能做解释、建议、证据组织和导办，不能直接执行正式业务动作。

RAG 在意图识别中的作用不是生成最终业务答案，而是帮助 LLM 判断“这句话更像哪个业务场景”。

### 3.4 缺少 Query Rewrite

院端真实使用中，用户不会总是说完整问题。常见表达包括：

1. “这个患者为什么结不了？”
2. “刚才那个错误怎么处理？”
3. “帮我看下出院风险。”
4. “这个能申诉吗？”
5. “这条规则什么意思？”

这些问题依赖页面上下文、患者上下文、上一轮对话和当前角色。正式版需要 Query Rewrite 能力，将用户短句改写成完整、可识别的意图输入。

需要补齐：

1. 基于会话历史改写：结合上一轮问题和回答补全指代。
2. 基于页面上下文改写：如果用户在收费异常页面，说“这个怎么处理”，应补全为医保结算异常处理。
3. 基于患者上下文改写：补全 patient_id、encounter_id 等上下文，但不能暴露敏感信息。
4. 基于角色改写：医生、收费员、医保办、病案室同一句话可能指向不同场景。
5. 保留原始问题：改写后的问题用于识别，原始问题用于审计和追溯。

### 3.5 缺少多候选意图与澄清机制

正式版不能只返回一个 intent。医保业务里很多表达天然模糊，例如“医保风险”可能指：

1. 出院前联合质控。
2. 事前审核违规风险。
3. DRG/DIP 盈亏风险。
4. 病案首页风险。
5. 拒付风险。

因此需要支持多候选意图：

1. 返回 TopN 候选意图及置信度。
2. 当第一名和第二名差距不明显时触发澄清。
3. 澄清问题应面向业务用户，而不是技术字段。
4. 澄清选项应直接对应业务场景，例如“结算异常处理”“出院前质控”“政策规则解释”。
5. 用户选择后要能进入对应场景。

### 3.6 缺少实体抽取与上下文需求判断

正式意图识别不仅要判断场景，还要判断是否具备进入场景的必要信息。

需要识别和输出：

1. 患者标识。
2. 就诊标识。
3. 错误码。
4. 结算流水号。
5. 规则编码。
6. 拒付单据或扣款批次。
7. DRG/DIP 分组相关对象。
8. 病案首页或病案质控对象。

如果缺少必要实体，意图识别层应提示运行时进入澄清，而不是让业务场景执行后才失败。

### 3.7 缺少意图路由治理

当前路由更多是代码分支。正式版需要让意图识别结果与运行时编排解耦。

需要补齐：

1. 意图到场景的路由关系。
2. 意图到 Skill、Tool、MCP、业务场景工作流的关系。
3. 已实现、试点中、规划中、禁用等状态。
4. 角色可见性和路由前置限制。
5. 路由失败时的标准返回。
6. 意图识别与权限校验的边界说明。

### 3.8 缺少评测与运营闭环

正式版必须能持续优化意图识别效果，否则业务场景增加后会快速失控。

需要补齐：

1. 意图识别测试集。
2. 典型用户问法样本库。
3. 每个意图的正例、反例、边界例。
4. 准确率、召回率、澄清率、误路由率、未识别率。
5. 人工纠正记录。
6. 错误样本回流机制。
7. 版本化 Prompt 和意图定义。

## 4. 正式版建议能力清单

### 4.1 意图知识库

建设意图知识库，作为 RAG 召回基础。每个意图至少包含：

1. 意图编码。
2. 业务名称。
3. 业务描述。
4. 适用角色。
5. 典型问法。
6. 反例问法。
7. 必要上下文。
8. 可选上下文。
9. 关联场景。
10. 是否已实现。
11. 风险等级。
12. 输出要求。

第一批建议覆盖以下意图：

1. 医保结算异常导办。
2. 出院前联合质控。
3. 政策规则解释。
4. 错误码解释。
5. 拒付申诉助手。
6. DRG/DIP 运营助手。
7. 病案首页风险导办。
8. 科室整改闭环。
9. 医保运营驾驶舱。
10. MCP 工具调用。
11. 未知或闲聊。

### 4.2 Query Rewrite

在正式识别前增加查询改写层，把用户原始输入转换为更完整的识别输入。

需要支持：

1. 指代消解。
2. 多轮上下文补全。
3. 页面上下文补全。
4. 患者和就诊上下文补全。
5. 角色视角补全。
6. 医保术语标准化。
7. 错误码、单据号、规则号提取。

输出建议包括：

1. 原始问题。
2. 改写后问题。
3. 补全依据。
4. 抽取实体。
5. 不确定项。

### 4.3 候选意图召回

在调用 LLM 前先做候选召回，避免 LLM 在所有意图中盲选。

召回来源包括：

1. 意图知识库向量召回。
2. 关键词或术语召回。
3. 当前页面默认场景。
4. 当前角色常用场景。
5. 会话历史中的上一意图。

召回结果进入 LLM，用于提高判断稳定性。

### 4.4 LLM 意图判别

LLM 应作为正式版主判别器，但必须受控。

LLM 输入应包括：

1. 原始问题。
2. 改写后问题。
3. 当前角色。
4. 页面上下文。
5. 患者上下文摘要。
6. 候选意图列表。
7. RAG 召回到的意图说明和反例。
8. 系统能力边界。

LLM 输出应包括：

1. 最终意图。
2. TopN 候选意图。
3. 置信度。
4. 判断理由。
5. 抽取实体。
6. 缺失字段。
7. 是否需要澄清。
8. 建议澄清问题。
9. 引用的意图知识或业务知识来源。

### 4.5 结果校验与降级

LLM 结果必须经过校验，不能直接用于路由。

校验规则包括：

1. 意图必须在注册表中存在。
2. planned 意图不得进入未实现工作流。
3. 禁用意图不得路由。
4. 角色不可见意图不得直接路由。
5. 置信度低于阈值时必须澄清。
6. 多候选分差过小时必须澄清。
7. 必要实体缺失时必须澄清。
8. 高风险动作仍交给风控模块处理。

降级顺序建议为：

1. LLM 判别成功且通过校验，进入场景路由。
2. LLM 不确定但有明确候选，返回澄清问题。
3. LLM 不可用时，使用轻量规则和页面上下文兜底。
4. 规则也无法判断时，返回 unknown。

### 4.6 澄清交互

澄清能力应成为正式意图识别的一部分。

需要支持：

1. 场景澄清：用户到底要处理结算异常、质控、政策解释还是申诉。
2. 实体澄清：缺少患者、就诊、错误码、规则号等信息。
3. 范围澄清：用户要看单患者、科室、病种还是全院指标。
4. 操作意图澄清：用户是想解释原因、生成建议、分派任务还是查看状态。
5. 澄清后继续执行原始意图，不重新丢失上下文。

### 4.7 与 RAG 和知识服务的关系

意图识别需要接入知识服务，但用途要明确分层：

1. 意图识别阶段：RAG 用于召回意图定义、场景边界、术语解释和反例。
2. 业务执行阶段：RAG 用于政策解释、错误码解释、规则依据和引用溯源。
3. 结果生成阶段：RAG 用于支撑最终回答的依据和引用。

不要让意图识别阶段直接生成政策答案，否则会混淆“路由”和“回答”。

### 4.8 可观测与评测

正式版需要记录每次意图识别过程，便于排查误判。

建议记录：

1. 原始问题。
2. 改写后问题。
3. 召回候选意图。
4. LLM 输出。
5. 最终意图。
6. 置信度。
7. 澄清原因。
8. 路由结果。
9. 用户是否纠正。
10. 最终业务场景是否成功执行。

评测指标包括：

1. 意图准确率。
2. TopN 命中率。
3. 未识别率。
4. 误路由率。
5. 澄清率。
6. planned 意图误执行率。
7. LLM 不可用降级成功率。

## 5. 推荐开发阶段

### 第一阶段：把写死逻辑改成 LLM 主链路

目标是把当前写死关键词识别升级为正式识别链路雏形。

需要完善：

1. 意图注册表扩展为意图知识定义。
2. Prompt 中传入候选意图和场景边界。
3. LLM 输出结构补齐 TopN、理由、缺失字段和澄清建议。
4. LLM 输出结果校验。
5. 低置信度进入澄清。
6. 关键词只作为兜底，不再作为主识别方式。

### 第二阶段：增加 Query Rewrite

目标是解决院端真实输入不完整的问题。

需要完善：

1. 会话历史改写。
2. 页面上下文改写。
3. 患者上下文补全。
4. 角色视角补全。
5. 术语标准化。
6. 改写结果审计记录。

### 第三阶段：增加 RAG 候选召回

目标是让 LLM 不再靠固定 Prompt 记住所有业务场景。

需要完善：

1. 意图知识库。
2. 场景说明知识库。
3. 医保术语知识库。
4. 反例样本库。
5. 候选意图召回。
6. 召回结果进入 LLM 判别。

### 第四阶段：增加评测和运营闭环

目标是让意图识别可持续优化。

需要完善：

1. 标注样本集。
2. 自动评测脚本。
3. 误判样本记录。
4. 人工纠正入口。
5. Prompt 和意图知识版本管理。
6. 识别效果看板。

## 6. 优先级建议

### P0 必须补齐

1. LLM 主导意图识别。
2. 结构化输出与校验。
3. 意图注册表扩展。
4. 低置信度澄清。
5. planned 意图不误路由。
6. 关键词降级保留但不作为主路径。

### P1 尽快补齐

1. Query Rewrite。
2. 多轮上下文补全。
3. 页面上下文补全。
4. TopN 候选意图。
5. 缺失实体判断。
6. 意图识别审计日志。

### P2 逐步建设

1. RAG 候选意图召回。
2. 意图知识库向量化。
3. 业务术语知识召回。
4. 反例样本库。
5. 评测集和指标看板。
6. 人工纠错闭环。

## 7. 正式版目标形态

正式版意图识别应形成如下能力链路：

1. 接收用户原始问题。
2. 合并会话、页面、角色和患者上下文。
3. 对问题进行 Query Rewrite。
4. 从意图知识库和业务术语库召回候选意图。
5. 将候选意图、场景边界和上下文交给 LLM 判断。
6. 对 LLM 输出做结构化校验。
7. 返回最终意图、候选意图、置信度、缺失字段和澄清建议。
8. 由运行时根据结果进入已实现业务场景、planned 未开通响应、澄清流程或 unknown 响应。

## 8. 一句话结论

当前意图识别的问题不是“关键词不够多”，而是整体识别链路还没有产品化。正式版应从写死关键词路由升级为“LLM 理解 + RAG 候选召回 + Query Rewrite + 结构化校验 + 澄清降级”的入口智能层，同时保持院端医保 AI 导办的安全边界和简单实用原则。

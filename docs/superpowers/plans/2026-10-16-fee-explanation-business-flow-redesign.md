## 1. 这次要解决的问题

用户看一笔结算，应当能够连续回答：每条费用为什么分到医保内/外 → 本笔采用什么待遇条件 → 先扣什么、再支付什么 → 最终个人承担多少 → 账户和现金如何支付。也能直接从某个中文字段进入同一份解释。

当前实现有三处数据断点，而非仅有布局问题：

- `GET /policy-qa/settlements/{id}/fee-items` 返回金额清单，没有带出行级目录匹配、比例、限价、采用分支与计算结果。内核 `catalog_split.py` 已有部分过程，但公开展示丢失行级关联。
- `public_view._path_step_views` 只按模块归并分支和计算引用；条件和中间量没有组成“上步输出成为下步输入”的业务说明。直接展示第一条 CalculationRecord 会把输入清单当作解释主体。
- 两份现有字典映射有冲突，交易信息当前直接显示原始码。不能把不同字段的同号代码当成相同含义。

[来源：`policy_qa_routes.py:list_outpatient_fee_items`、`catalog_split.py:split_catalog`、`public_view.py:_path_step_views`、`value_domains.yaml`、`semantic_layer/seed.py:_YB_DICTIONARY_MAPPINGS`]

## 2. 页面结构：顶部原单信息，下面只有两种解释视图

```text
交易信息
单号 / 日期 / 医疗类别中文 / 险种中文 / 人员类别中文 / 医院等级中文
本次采用的待遇条件与读取时点                         查看原单全部信息

[ 按结算路径（默认） ]  [ 按字段解释 ]

按结算路径：
① 明细划分 → ② 起付与基数 → ③ 基本医保支付
    → ④ 补助与二次保障 → ⑤ 最终个人承担 → ⑥ 支付方式

每一步固定解释：本步处理什么 / 本次输入与条件 / 中文算法及代入值
                / 本步输出 / 下一步采用哪些金额

按字段解释：
搜索中文字段名
费用与目录 / 起付与基数 / 基金与补助 / 个人承担 / 支付方式 / 其他信息
点字段：本次金额、业务含义、所属结算步骤、同一算法与条件、相关费用明细
```

撤下底部常驻“逐字段核对”表。核对结果仍保留在对应字段的次级“账面与计算对照”中；存在实际差异或缺口时，在所属步骤就地提示。字段视图的职责是解释和定位，不以满屏核对状态为主。

两种视图共用字段 ID、步骤 ID、费用行 ID、计算及来源。切换只改变浏览入口，保留已选字段/明细与展开状态，不再次取数、不另算金额。事实区字段也能定位到同一解释。

## 3. 费用明细：必须能解释每一行医保内与医保外

### 明细表默认展示

| 分组 | 内容 |
|---|---|
| 收费事实 | 项目名称、项目类别中文、发生日期、单价、数量、总金额 |
| 本次分类 | 目录分类中文、实际采用的先行负担比例、有效单价限额（如有） |
| 划分结果 | 账面医保内/医保外、自付二；存在独立分解时可查看计算值与差异 |
| 行级入口 | “查看本项怎么算”，展开本行规则、条件、完整计算和来源 |

表格不默认铺开所有技术列。行内展开应完整回答：

1. 这是什么项目，费用金额如何由单价与数量形成；金额不一致时保留源金额及不一致信息。
2. 按哪个费用发生日期匹配到哪版目录；为何采用这一项目录，未匹配或多命中则说明无法确定。
3. 本项目适用什么规则：全额纳入、先行负担、完全范围外、超限价、集采/材料特殊分支等；只展示实际采用的规则。
4. 限价、先行比例等参数分别来自哪里；明细结算事实与目录参数同时存在时，明确本次采用哪个及其优先条件。
5. 将本行真实值代入相应中文公式，逐步得到医保内、医保外及先行负担，不只列出操作数。

示意（仅用于说明交互，不是生产规则或真实病例）：

```text
项目甲：单价 100 元 × 数量 1 ＝ 费用金额 100 元
本次条件：按乙类处理；先行负担比例 10%；单价限额 60 元

限额内费用 ＝ 60 元 × 1 ＝ 60 元
超限价费用 ＝ 100 元 − 60 元 ＝ 40 元
限额内先行负担 ＝ 60 元 × 10% ＝ 6 元
医保内金额 ＝ 60 元 − 6 元 ＝ 54 元
医保外金额 ＝ 超限价费用 40 元 ＋ 先行负担 6 元 ＝ 46 元

本行医保内 54 元、医保外 46 元，分别进入本单对应小计。
```

上述式样不能套到所有项目。实际计算、取整阶段及自付二口径由本行执行分支提供；自付二与医保外的包含关系必须标明，不能重复累加。涉及集采包装、一致性评价、材料阈值等时展示对应条件和执行公式，不能硬套“总额×比例”。

表尾展示可点击的对应小计：医保内金额来自哪些行、医保外金额由哪些行及何种原因构成。点击某个合计筛选其贡献明细，再回到整笔结算路径。

### 覆盖边界

- 普通门诊及居民门特：沿既有目录分解执行点带出行级结果及证据，不能从展示文字或金额反推规则。
- 职工门特：当前主要汇总明细已有划分，只有部分分支读取目录作二次保障基数诊断。要满足本次要求，需要补齐面向所有明细的目录解释；在适用性或参数未确认前，标明“账面已有划分，独立目录分解尚未完成”，不能把账面汇总改称算法解释。
- 门特管理范围、定额管理范围和目录纳入范围分开。相关标志未核实不能默认为全部属于管理范围。
- 目录独立分解的结果与账面不同，就地展示差异和原因缺口；不偷偷替换既有结算输入或改变最终个人承担。
- 重复项目按实际费用行 ID 区分，不按项目名、代码或相同金额拼接。缺失/重复行键时保留歧义。

## 4. 结算路径：按六个业务阶段组织，不再堆计算记录

| 阶段 | 本阶段必须解释什么 | 传给下游的输出 |
|---|---|---|
| ① 明细与目录划分 | 每行分类条件、算法、医保内外和自付二如何汇总；管理范围如何划分 | 可进入医保计算的费用、医保外费用及其中先行负担 |
| ② 起付与支付基数 | 本人适用标准、年度/周期、交易前累计、剩余起付、本笔承担；采用何种基数 | 本次起付承担、扣起付后的支付基数 |
| ③ 基本医保支付 | 本单是否经过统筹、大额；按真实顺序展示各段输入、分段区间、比例、剩余额度、取整和封顶 | 各基金支付、对应阶段剩余个人负担 |
| ④ 补助与二次保障 | 退休→军残→公疗的实际扣减顺序；再按实际分支解释大病→救助；每次使用的是哪一层剩余基数 | 各项补助/二次支付及其后的剩余个人责任 |
| ⑤ 最终个人承担 | 本单完整组成公式，明确范围外费用及补助是否已经计入；账面值与计算值的关系 | 患者最终责任金额 |
| ⑥ 支付方式 | 账户/现金等记录从何取得，如何与个人责任金额对照 | 已记录支付渠道；没有流水或扣款规则则保留限制 |

阶段只提供稳定阅读骨架，内部步骤依据本单实际链路变化：普通门诊不强造统筹，居民门特不复制职工分段。已确认不适用的子步骤收为短行，金额为零需解释零的原因；未知及阻断保留位置和对下游的影响。

单阶段展开格式必须一致：

```text
② 起付与支付基数
本步目的：先确定本次尚需承担的起付金额，余下费用进入基本医保支付。

本次条件：人员类别 …；机构档 …；结算周期 …；采用标准 …
本次输入：医保内费用 … 元；本次之前的起付累计 … 元

剩余起付额度＝……
本次起付承担＝……（中文公式＋本次代入值＋结果）
进入下一步的支付基数＝医保内费用 … 元－本次起付 … 元＝… 元

适用依据与时点 / 本次条件是否已核实                   查看来源
```

这是一项格式规范，不是一条通用起付算法。区间重叠、退费、跨段等必须展示实际执行算法；不能把本行示意变成另一套前端计算。

默认展示阶段主公式及结果；同一阶段的细分算法在本阶段内展开，长分段用小表展示“本段费用 / 比例 / 支付 / 个人负担”。不再常显“结算记录数据项1、数据项2”或未命名的中间量。

### 定额单的两条口径

患者实际费用主线：实际明细 → 患者起付与自付 → 补助/二次保障 → 个人应付。

医院定额说明：管理范围、源定额、日标准及日期条件 → 原始自付与医院垫付分配 → 定额账面关系。作为本单额外的独立区段，与患者主线关联到明确字段，不作为患者个人应付公式里的基金扣减替代项。日标准/管理范围未确认时，该说明必须常显条件限制。

## 5. 字段视图：解释全部字段，与路径互相定位

| 字段类别 | 默认定位 |
|---|---|
| 总费用、医保内/外、自付二、明细先行负担 | 阶段①，可展开贡献明细 |
| 起付、累计、支付基数 | 阶段②；累计标明原单事实、条件输入或推导来源 |
| 统筹/大额基金与各段个人自付 | 阶段③ |
| 退休/军残/公疗、大病/救助及其分桶 | 阶段④，逐项保留，不能合成一个无法解释的小计 |
| 个人支付总额、个人应付、原始自付 | 阶段⑤，并标明所在业务口径 |
| 账户、现金、其他已取得支付渠道 | 阶段⑥ |
| 医院定额、医院垫付及定额平衡 | 独立定额区段 |
| 日期、险种、人员类别、等级及其他描述信息 | 交易信息/适用条件；解释映射与来源，不强塞金额公式 |

字段行展示“中文名 / 账面值 / 一句话含义 / 查看解释”。打开后复用所属节点的输入、条件、算法、来源、限制；能跳回相应阶段或具体费用行。

验收时对所有允许公开的原单字段及已有计算字段列覆盖清单，每项必须有明确位置；新增/未知字段保留在“其他信息”并说明解释尚未覆盖，不能静默丢弃。派生恒等核对归入原字段的“账面与计算对照”，不重复冒充原单字段。

## 7. 实现接缝与验收顺序

先补解释数据，再做布局，不继续在前端猜公式：

1. 在现有目录执行位置保留行级输入、命中目录/参数、条件、分支与结果，沿本次分解的说明侧车公开。医保内外来自同一次执行，不由明细页另外计算；分解不可用时仍允许查看已读取原始行。
2. 通过 adapters 读取或复用确认后的码表来源，在后端生成中文名称；共享字段名称覆盖原单、操作数、阶段输出及字段视图。缺中文名的中间量必须补有定义的业务名称，不能用泛化占位词交付。
3. 把现有条件/计算按六阶段、真实前后依赖及字段归属生成公开解释。补齐可公开的行/字段/计算引用，禁止按相同金额字符串猜关联。继续使用唯一公开投影及文本消毒入口，两个路由契约一致。
4. 页面保留原单信息，切换路径/字段解释；费用明细直接成为阶段①的展开内容，事实区入口定位到它。去掉独立核对表，复用现有组件并维持键盘访问和窄屏可读。
5. 回归先覆盖行级算法及聚合、中文码表命名空间、阶段输入输出和全字段归属，再按 Unit → API → Flow 验证；最后做真实单据的桌面/手机检查。

必须包含：完全纳入、乙类比例、超限价、目录缺失/多命中、同码多行、零值、缺失、负金额、全额个人承担、跨起付/分段/封顶、各补助不适用/零/未知、大病救助累计缺失、定额条件缺失。单据沿用现有五链回归，并检查 609 与 2004529。

通过标准：可从任一医保内/外合计定位到对应费用行及实际算法；可从任一支付结果追到上一步输入、采用条件和中文公式；所有公开字段可找到；切换视图保持金额、来源及限制一致；既有金额及安全门控不因展示改造而被放宽。

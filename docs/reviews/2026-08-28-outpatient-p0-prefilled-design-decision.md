## 1. 推荐结论

采用一条数据链路：

```text
bjyb SQL Server（o_Trade / o_FeeItem / o_Diagnose）
  → SQL Server CDC（30–60 秒拉取，LSN 断点）
  → PostgreSQL 原子发布批次（mz_trade / mz_fee_item + 科室诊断快照）
  → 现有 Semantic Registry / 确定性 Planner
  → 统一助手（政策解释 + 受控问数 + 按权限下钻）
```

核心原则：源端记录不可变留痕、退款按链净额化、结算主表金额为权威结果、费用明细负责解释与质检、LLM 不生成 SQL、用户不必填写结算 ID、身份和就诊时间只用于候选定位。[建议]

## 3. 待用户确认的推荐设计

### D01：近实时同步采用 SQL Server CDC

在 `o_Trade`、`o_FeeItem`、`o_Diagnose` 启用 CDC；首次全量快照记录起始 LSN，之后每 30–60 秒拉取一次增删改，按源事务/LSN 写入 PostgreSQL 暂存区，校验完成后原子切换发布批次。删除必须写 tombstone；断点、重复拉取和重放均按 LSN 幂等。目标是源提交到发布可见 P95 不超过 5 分钟。[建议]

不采用：`T_TradeDate` 轮询、父表日期带明细、定时全表扫描。若医院不允许启用原生 CDC，唯一等价替代是源系统提供同字段集合的变更日志，不改变下游设计。

### D02：交易与退款采用不可变事件链

每个 `T_TradeNo` 原样保留；派生 `settlement_chain_id = COALESCE(T_OraginalTradeNo, T_TradeNo)`，在链级计算净金额和生命周期。匹配的负交易抵销原交易；不覆盖、不删除原记录。无法关联原交易的负交易进入 `quality_blocked`，不静默并入运营数值。[建议]

链级状态固定为：`active / refunded / partially_refunded / reversed / unmatched_negative / source_failed`。原始状态码同时留存并版本化映射，AI 只看到标准状态。

### D03：结算主表金额是权威结果

- 总费用：`o_Trade.T_FeeAll`
- 医保内/外：`T_FeeIn / T_FeeOut`
- 医保基金支付总额：`T_FundPay`，当前不命名为“统筹基金支付”
- 个人支付总额：`T_SelfPayAll`

金额按交易链净额聚合，统一使用 Decimal。主表公式不平时仍保留源结果，同时返回 `quality_warning`；不让模型重算并覆盖医保结算结果。[建议]

### D04：费用明细只负责解释和质检

`o_FeeItem` 是唯一明细源，幂等键沿用 `(T_TradeNo, ItemId, ItemNo)`。项目金额以 `Fee` 为准，`FeeIn/FeeOut` 用于医保内外解释；逐项目和逐交易勾稽生成质量规则。明细与主表不一致时，政策解释展示主表权威金额并声明明细差异，运营汇总不改读另一张表。[建议]

### D05：用户按就诊日期找记录，但系统按交易时间检索候选

交互固定为：`扫码/SSO 身份 → 输入就诊日期或时间段 → 同身份按 T_TradeDate 查候选 → 多候选时展示脱敏时间、科室、诊断供选择 → 内部解析 T_TradeNo`。零候选时自动扩展前后 1 个自然日一次，并提示“按交易时间匹配”；仍无结果才让用户补充上下文。[建议]

结算 ID 不作为页面必填项。唯一候选直接进入解释；多个候选才补上下文。

### D06：一期不伪造就诊人次

一期发布 5 个可确定指标：

1. 有效结算笔数：净额后仍有效的交易链数；
2. 门诊总费用：链级 `T_FeeAll` 净额；
3. 医保基金支付总额：链级 `T_FundPay` 净额；
4. 个人支付总额：链级 `T_SelfPayAll` 净额；
5. 单笔有效结算均费：总费用 / 有效结算笔数。

`门诊医保就诊人次` 和 `次均费用（按就诊人次）` 保持 `unavailable`，直到可信就诊 ID 覆盖达到 100% 或取得 HIS 就诊主索引。禁止用 `COUNT(*)`、`T_TradeNo` 或同日患者聚类替代人次。[建议]

### D07：默认时间口径明确标为交易时间

一期所有“本日/本周/本月门诊”默认使用 `T_TradeDate`，结果顶部固定显示“统计口径：交易时间，医院时区 Asia/Shanghai”；用户明确说“结算时间”时使用 `SETL_DATE`。后续接入真实就诊时间后新增 `encounter_time`，不静默改变历史指标口径。[建议]

### D08：科室和主诊断在入仓时确定

同一交易有多条诊断时，先取源字典标识的主要诊断；类型缺失时取 `RecipeDate` 与 `T_TradeDate` 时间差最小的一条，再以 `DiagnoseNo` 稳定排序。科室取同一诊断行的 `SectionCode + Sectionname`，保留 `HISSectionName` 追溯；同时写入 `context_quality = source_primary / deterministic_fallback / missing`。[建议]

### D09：五个可用维度固定

一期维度为：交易/结算时间、科室、门诊业务类别 `T_CureType`、险种 `P_FundType`、标准结算生命周期。`PN_NationFundType` 只作国家平台险种补充上下文，不与 `P_FundType` 混成一个未标来源的值。[建议]

### D10：统一现有政策问答与智能问数入口

继续使用一个 Chat-first 助手入口。意图分三类：政策解释、个人结算解释、运营受控问数；用户不需要先选页面。LLM 只负责意图和语义槽位，确定性 Planner 只接受已发布指标、维度、时间角色和固定下钻路径；禁止自由 SQL。结果必须带数据批次、语义版本、口径标签、引用和不确定性。[建议]

### D11：权限与隐私采用成熟默认值

- 生产登录至少扫码授权或医院 SSO，形成可信主体、组织、角色和数据范围；厂商未定不阻断数据底座设计，但阻断生产患者下钻。
- 聚合与患者下钻分权，每次下钻重新鉴权；自然语言不能扩大权限。
- 小单元格阈值固定为 `<10` 抑制，并执行互补抑制；多维组合无法安全展示时退回上一级聚合。
- 患者身份仅在受控检索服务中使用，不进入 LLM 提示、结果正文、导出或审计明文。
- 政策解释最小字段继续以 Issue20 的 88 个依赖及 P0 的 119 行闭包为准，不因运营问数裁掉政策所需字段。[建议]

### D12：30 笔核验由系统自动生成，不让用户填表

P1/P2 自动生成一批 30 笔脱敏核验报告：先纳入全部已发现超差交易，再按时间、科室、门诊类别、险种和生命周期分层补足；自动核对交易金额、明细合计、链级净额、状态、科室和诊断选择。所有差异必须归类并可回放。[建议]

纸质/电子结算票据与源库的一致性只作为医院 UAT 抽检，不再是当前设计输入；用户只确认本方案，不填写 30 行数据。

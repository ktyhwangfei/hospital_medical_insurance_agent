# 费用分解解释页面设计评审

日期：2026-10-15。评审对象：`monet-starman-daredevil.md`，位于用户提供的Kimi会话计划目录。评审依据为当前仓库实现、现有回放记录及设计约定；没有执行新一轮真实医院查询，也没有修改业务代码。

**结论：方向合理，有条件通过；不建议按原清单直接开发。** 从金额核对走向“为什么是这个数”符合现有解释目标，但当前计划把“存在轨迹数据”当成“具有完整字段因果链”，并高估了来源文本的公开安全性。最先需要完善的是安全的解释投影和金额关联，其次才是页面的卡片与展开形式。

配套改造方案见[实施方案草案](../superpowers/plans/2026-10-15-fee-explanation-refactor-plan.md)。业务裁决尚未收到回复，方案中的默认展示按明确标注的推荐选项编排。

## 已核实的产品与实现

- `/policy-qa` 仍是业务入口，`/fee-decomposition` 是治理与验证支撑页。后者已具备单笔查询、按人定位后选择结算、鉴权和候选口径提示，无需再建设一个解释应用。[来源：`src/apps/portal/AGENTS.md:5`、`src/apps/portal/app/fee-decomposition/page.tsx:52`]
- 共享费用分解块实际影响工作台、结算解释中的门诊/门特选单、对话回答及历史恢复。住院选单仍走另一条解释路径。本次不能把住院解释也一并替换。[来源：`settlement-agent-workspace.tsx:77`、`policy-agent-answer.tsx:35`、`policy-qa-session.ts:333`，均位于`src/apps/portal/src/`]
- 当前已有五条分解链路：职工门诊、居民门诊、职工门特项目、居民门特、职工门特肾/肝肾抗排异定额。原方案的模块映射和验收范围没有完整覆盖第五条。[来源：`PROGRESS.md:15`、`integration.py:158`]
- 当前结构确有字段、判断、计算记录、来源和不确定性；公开映射确实丢弃了大部分关联。但“有这些容器”不等于每个字段都有完整的解释。[来源：`result.py:39`、`public_view.py:83`]

下文无完整目录前缀的后端费用文件位于`src/runtime/policy_qa/fee_decomposition/`；事实报告提供更细的定位。

| 级别 | 原方案问题与证据 | 影响 | 建议修改 |

| P1 | 原计划第17、25、33行仍允许操作数ref、scope等实现引用，且遗漏operands.ref与citation.values[]处理；现有数据含`fact.items.ybnje`等内部路径。[`employee_outpatient_special.py:1297`、事实报告后端§4] | 局部关键词替换覆盖不全，新增字段越多，遗漏面越大。 | 一个集中公开投影处理所有新增对象；操作数使用业务名称和值，关联ID使用结果内引用。未知文本不能原样回退，路由不各写一遍消毒逻辑。 |
| P1 | 原计划第8、42行假定存在完整解释树。三份真实回放的17笔门特记录没有非空parent；普通两链的夹具也没有。新DTO本身还省略parent。[后端事实报告§2] | 按模块缩进只能得到执行记录分组，不能证明字段的先决条件或因果关系。 | 首期承诺“字段解释＋条件分组”。只有显式关联可形成解释链，缺关系时展示缺口；不靠执行顺序推断父子关系。 |

| P1 | 原方案只加calculation_refs、reason_code、affected_fields，遗漏已有精确citation_refs/uncertainty_refs；rule_refs与citation.id命名也不同，并存在缺失计算、缺失规则引用。[后端事实报告§3] | “缺什么”“如何算”“依据哪条”不能可靠串起来，前端可能关联错、空展开或凭模块猜归属。 | 使用精确关联并校验闭合；支持步骤与最终步骤分开。引用不存在时标明未记录，不影响账面金额展示。来源去重只合并相同内容，冲突不得任取一条。 |

## 与现有产品是否冲突

| 项目 | 判断 | 需要守住的约束 |
|---|---|---|
| 使用同一分解内核解释金额 | 一致，应保留 | 不新增前端公式、不让问题文本改变计算参数、不再维护第二套金额计算。 |
| 共享公开解释模型与基础展示 | 一致，应保留 | 选单、问答、工作台和历史均需兼容，不能只验收两个页面。 |
| 把工作台升级成并列业务入口 | 超出现有产品定位 | 继续作为验证支撑页；入口定位改变需另行明确。 |
| 条件轨迹与“患者真实待遇识别” | 是阶段差异，不能等同 | 原设计§18要求候选待遇检验及证据强度；展示既有轨迹不能自动识别缺失资格。首期可展示“本次采用条件”，暂不称真实待遇画像。 |
| 把全部推理/原始审计轨迹给用户 | 与现有公开边界冲突 | 只展示确定性业务判断与计算依据，不公开模型内部推理、工具步骤、SQL或来源自由文本。 |
| 金额分组与定额链路 | 原方案需补充 | 患者责任、基金支付、支付方式分开；肾移植的医院定额基金与患者实际费用口径分开，不能混加。609的医院210.60与患者基本基金204.60不是同一个金额。 |
| 依据金额反推“真实资格” | 不属于此次纯页面改造 | 零支付或多个档位同样吻合不能唯一识别资格；有候选也须保留多解/未知与确认状态。不能用“卡片有来源”代替识别逻辑。 |

## 推荐落地边界

第一阶段只完成**已结算金额→本笔采用条件→对应计算→来源与缺口**，以字段为阅读入口。后端集中做安全投影，允许补轨迹关联与显示元数据，冻结费用公式、参数与计算门控。前端复用现有折叠、金额展示和来源交互惯例，完整执行记录放入次级展开。

这比直接铺开全量“解释树”更接近需求：有最终计算关系才说“如何得到这个金额”，没有关系就指出未记录哪一步。具体切片、契约取舍和验收案例见配套方案。

## 待需求方回答的四项裁决

已通过交互问题询问，尚未收到答案；下列均为建议，不是已确认需求：

1. **主要读者**：建议先医保办业务人员，收费/医生/患者若也要使用，再明确简版与内部视图的差异。
2. **金额主次**：建议账面金额主显，计算额与差异辅助；无法独立计算时保留已结算事实。
3. **默认展示量**：建议问答聚焦当前金额，工作台提供全单；无明确字段焦点时展示总览与字段选择，不猜测焦点。
4. **本次目标**：建议先交付本笔金额解释与采用条件，真实待遇识别单独下一阶段；若本次必须识别资格，需扩展算法范围与验收，不能沿用“纯页面改造”计划。

# 四条费用分解链路的展示字段审查

审查日期：2026-10-21。范围：职工普通门诊、居民普通门诊、职工门特项目、居民门特项目；另审查职工门特定额变体。

本文件是基于当前代码的字段补充建议，不表示页面已经实现下列补充。金额例子来自已有 `.scratch/settlement-template-replay/` 真实数据回放产物，未在本次重新连接数据库。所有政策数值均为代码本次采用口径的说明，不新增政策认定。

## 结论

**需要补充展示字段。当前原单模板能列示账面金额，但不足以独立承载费用分解的解释。** 需要同时补齐：

1. 计算采用的条件：待遇通道、人员/机构档、交易前累计、周期位置、采用标准。
2. 金额的中间过程：扣起付后的基数、各段基数和比例、各项补助后的剩余负担。
3. 最终去向：基本医保、大病、救助分别支付多少，患者最终负担多少。
4. 定额独有的范围：实际费用的患者负担与医院定额基金分别展示。

保留现有“原单交易信息”的名称和位置。在其下增加“计算依据与分解结果”；定额再保留独立“医院定额清算”。新增计算值不能覆盖原单金额，也不能因金额相符而升级为已确认解释。

### 所有链路都要说明费用归属

- 医保内金额和医保外金额分别来自哪里；其中按比例先行负担是多少。
- 原单“自付二”不等于二次保障允许进入的“按比例先行负担”。后者已有独立的 `calc.catalog.total_proportional_self_pay`，不能直接把全部自付二或全部医保外金额当成大病基数。
- 比例必须注明作用基数：基金支付比例、原始个人自付比例、退休折算系数是不同量。实际负担占总费用的比值不能命名为政策报销比例。
- 按当前目录拆分口径，自付二与医保外金额存在包含关系；最终个人负担的公式按已执行记录展示，不能在医保外总额之外再重复加一次自付二。
- 显示本次取整方式。二次保障采用原单时延续已确定的“按本单结算记录”说明，不在业务主解释另列另一组金额或强调一分钱差异；未取整值和采用过程仍保留在审计记录。

## 配置及页面的最小修改方案

1. 仍维护四个链路配置文件，职工门特内保留项目/定额变体。原单字段维持已有数据库列绑定。
2. 同一文件增加解释字段清单，字段至少声明：稳定 `key`、中文名、分组/顺序、`source_type`（输入/计算/原单目标）、精确 `ref`、单位（元/%/系数/日期/天）、患者或医院范围。原始 DB 列只属于原单数据；中间量绑定已执行计算，不再进行数据库名称匹配。
3. 后端在公开投影阶段解析这些引用，继承现有来源、解释资格、结论、缺口；缺引用明确“未取得/未执行”，重复或冲突引用不可随便挑一条。分段通过明确的计算种类和已执行关联形成重复行，不固定只展示首段。
4. 前端复用现有公式、比例条件组件：默认显示关键基数、采用比例、前后负担；展开显示累计、候选档、来源、取整。两处入口读同一配置。右侧窄栏优先“原单 / 分解依据”页签，避免把数十条公式一次铺开。
5. 金额回放、条件输入、独立重算结果、原单观测保持区分。沿用字段级 `explainable` 和 `conclusion`，不另造一套前端判断规则。`available` 仅表示返回了值，不代表已确认适用；未知、未执行、明确零、不适用不可混为一种状态。

**先做顺序：四个二次保障分项＋最终个人应付 → 起付/报销基数/实际比例 → 累计与封顶依据 → 定额给药期间与范围。** 无关分支不展开；参与实际计算的零金额仍保留原因。

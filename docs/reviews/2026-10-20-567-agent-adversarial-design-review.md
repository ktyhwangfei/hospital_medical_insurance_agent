# 基于567真实数据流的Agent对抗性设计评审

日期：2026-10-20。对象：`.scratch/567-dataflow`七份工件及对应当前实现。只读评审业务代码；新增本报告及隔离复现脚本，不修改算法、配置、原始工件或源结算数据。

## 结论

这条链已经具备确定性计算、逐字段核对、证据引用和公开投影。567的正常回答也是正确的：医保内6000，起付1300，共付段4700；在职自付基础15%乘退休折算60%得个人9%、基金91%，统筹4277。

主要设计缺陷发生在计算之后：把全单可见资料交给模型，再用“数字在资料中出现过”作为回答可接受的主要条件。它没有验证这些数字对应的字段、费用范围、比例角色和运算关系。当前成功样例证明计算与模型可以答对，不能证明错误回答会被拦截。

建议先修下面1—4项，再将该链作为受证据约束的可信解释入口。保留确定性内核，不引入多Agent编排、第二个LLM裁判或新的规则框架。

## 必须先修

### 1. P1：数字白名单不能担任回答事实校验

**当前职责**：`explain_decomposition` 从整个模型可见分解构建数字集合，再检查回答中“数字＋元”和百分号的数字是否在集合里。

**对抗结果**：

| 模拟模型输出 | 应有结果 | 现有守卫 |
|---|---|---|
| 统筹4277，基数4700，基金91% | 接受 | 接受，正向对照 |
| 本笔个人现金支付4277.00元 | 拒绝：现金实际为0，4277属于统筹 | 放行 |
| 4700.00元×9%＝4277.00元 | 拒绝：算式及比例角色错误 | 放行 |
| 本笔统筹按75%支付4277.00元 | 拒绝：75%不是本笔统筹采用比例 | 放行 |
| 所有资格政策已获医保官方核实，可直接作为正式结算依据 | 拒绝：超越来源确认状态 | 放行 |
| 本笔个人应付999999，单位为人民币 | 拒绝：编造金额 | 放行，未紧接“元” |
| 本笔个人应付999999元 | 拒绝 | 拒绝，负向对照 |
| 辅助投影提供的已列示小计为1723.00元 | 数字来源检查应识别模型已收到该值 | 拒绝，白名单漏辅助投影 |

1723是辅助投影的已列示小计，不是正确的全部基金合计；它本身的遗漏见问题2。这里单独证明：模型实际收到的辅助投影与守卫检查的事实范围也不一致。

**最小修改**：先让后端确定目标字段和可解释计算记录，并由后端输出关键金额、比例、算式和确认状态。模型可选择被允许的说明段及引用ID，不能在最终正文中任意重写这些关键事实。复用现有 `CalculationRecord` 和字段引用，不另写一个自然语言算式解析器。数字白名单保留作补充检测，不能表示答案事实已验证。

对于“统筹为什么4277”这类字段计算题，可直接渲染现成的4700、9%、91%、4277及起付关系；外部模型不可用时同样可回答。

**不修的后果**：错误字段、错误算式、未执行档位和无依据的权威结论仍会被公开；有来源的辅助金额又会造成整段拒答。

定位：[model_explanation.py](../../src/runtime/policy_qa/fee_decomposition/model_explanation.py) 第320—384行。

### 2. P1：模型输入中的第二套业务计算已经与内核矛盾

**当前职责**：内核完成分解后，`build_payment_reconciliation` 又根据别名清单自行生成基金和个人支付构成，模型同时收到两套结果。

**本例已发生的问题**：

- SQL已读到统筹4277、统筹自付423、退役医疗费支付0；完整原始字段见01工件。
- 04工件的 `fund_channels` 没有统筹4277，小计只有211.50＋1511.50＝1723；这会把正确内核旁边再放一套不完整基金解释。
- `personal_components` 漏423统筹自付。若将当前已列项相加，1300－211.50－1511.50＝−423，不能解释个人0。
- 同一输入声称退役医疗费金额未返回，但SQL实际已经返回0。该值在后续事实/解释投影中丢失，并非源数据缺失。

**最小修改**：支付构成统一复用已有内核计算及原单字段，不在模型输入层按另一套标签重新实现公式。为普通门诊、门特项目、医院定额使用明确的字段和金额范围；同一行的金额、运算、状态和来源保持绑定。区分“源字段未提供”“投影未映射”“本链不适用”，避免把投影缺陷写成患者数据不足。

**不修的后果**：模型即使严格服从输入，也可能输出错误支付构成；继续改提示词只会在两套矛盾资料之间换一种取舍。

定位：[model_explanation.py](../../src/runtime/policy_qa/fee_decomposition/model_explanation.py) 第113—199行；[settlement_facts.py](../../src/runtime/policy_qa/fee_decomposition/settlement_facts.py) 第141—189行；[outpatient_special_mz_queries.py](../../src/adapters/data_supply/outpatient_special_mz_queries.py) 第614行。

### 3. P1：没有“本次问题”的证据范围，引用靠标题筛选

**当前职责**：`build_model_input` 挑出全单所有可解释字段和计算，仍由模型自行判断回答哪个字段。`selected_ratio_policy_evidence` 再独立遍历全单规则，根据标题包含“比例”选引用。

**本例证据**：

- 用户只问统筹4277，输入仍有14个字段、29条计算、54个输入、10个规则组、39个来源、27个条件。
- 04工件大小143074字节；按当前网关实际的紧凑JSON序列化仍有109106字节、88189个字符。此处没有将字符数冒充token数或声称已测得延迟。
- 06的3个引用中，包含本题无关的大病65%/75%和救助85%，并称为“本次采用”。本笔相关支付为0，且这些比例不是解释统筹4277的依据。
- 真正需要的退休折算60%所在规则组叫“退休自付折算系数”，由于标题不含“比例”，没有作为该折算的对应来源进入这份引用列表。

这不仅是上下文太长，也扩大了问题1的可误用数字范围。

**最小修改**：在调用模型前确定 `target_field_code=TCZHF`，沿该字段已有 `calculation_refs` 取其必要输入、执行条件和来源。模型输入、数字检查、页面依据和SSE citations全部由这份目标证据生成。规则是否被执行应有结构化依据，不能只看身份符合或规则名。默认只带实际执行档；比较题才增加被比较候选，并显式标“未采用”。

保留“金额核对一致后可以解释已执行计算”的业务决定，同时把“金额一致”“计算依赖完整”“规则已签核”分别记录。不能把对账一致升级成官方政策确认。

**不修的后果**：模型能够引用真实但不相关的数字；引用数量增加，却没有支持本次结论的关键关系。

定位：[model_explanation.py](../../src/runtime/policy_qa/fee_decomposition/model_explanation.py) 第233—294行；[policy_qa_routes.py](../../src/runtime/api/policy_qa_routes.py) 第1743—1749行。

### 4. P1：生产、工作台和评测没有保持同一执行语义

**当前职责**：结算解释请求在路由中另开分支，复用工作台分解入口；Skill评测通过另一种请求与prefix恢复方式调用同一个巨大路由。

**已确认的偏差**：

- 真实链需要 `mode=settlement_explain` 和 `decomposition_chain`。
- `PolicyQAEvaluationRunner._execute` 只传question、settlement_id和role；隔离捕获其实际请求得到 `mode=policy_chat, decomposition_chain=None`。现有Benchmark不能直接证明这条结算解释路径已被评测。
- 即使后续补了mode，真实费用解释分支仍要求 `evaluation_prefix is None`；prefix恢复可能跳过费用分解模型解释链。
- 真实结算解释调用 `decompose_for_workbench`；该入口会读取 `FEE_DECOMPOSITION_EVAL_CALIBERS` 并启用普通门诊候选累计/资格口径。它不是567本例金额错误的原因，但说明原本宣称“仅工作台”的候选配置已能影响业务入口，需显式治理。

**最小修改**：抽出一条实际执行模块，供业务请求、工作台和评测共用。差异放在数据读取适配器和明确的运行策略；评测注入冻结数据及模型替身，不用prefix跳过被测业务逻辑。任务输入必须保存mode、链路和运行策略；真实入口固定已授权的口径策略，工作台候选开关不能隐式穿透。

**不修的后果**：评测可以为另一条路径提供绿灯，而真实界面的模型输入、守卫或候选口径仍有缺陷。

定位：[evaluation_runner.py](../../src/runtime/skill_management/evaluation_runner.py) 第59—70、169—178行；[policy_qa_routes.py](../../src/runtime/api/policy_qa_routes.py) 第1382—1396行；[integration.py](../../src/runtime/policy_qa/fee_decomposition/integration.py) 第382—405行。

## 应当随后修

### 5. P2：模型调用成功与“可以回答”混成一个状态

**当前职责**：`used_model` 同时影响 `trace_can_answer`、`trace_partial_answer`；存在计算步骤就会让公开 `calculation_checked` 为真。最终结束流程统一写 `halt_reason=verified`、done.success=true。

**具体问题**：问题1中的错误正文通过数字守卫后，也会被标为可答，再配上内核真实计算步骤；这些步骤没有证明生成正文正确。另一方面，567已有可用的4277计算记录，模型故障时却只能退成不可用。06中真实正常回答标partial、calculation_checked=true、done.verified，也显示这些字段并非同一个含义。

**最小修改**：由目标字段的证据状态决定回答资格，`used_model`仅保留为生成路径记录。分开表达数据核对、计算支持、政策确认和生成结果；done只表达流结束与传输结果。模型失败时渲染已有确定性字段解释，未知部分再给具体原因。不要用全局“政策不完整”补救无支持的正文。

**不修的后果**：监控、用户和下游消费者可能把“模型完成且有计算步骤”理解成“本次回答已经验证”，同时放大外部模型故障对简单计算题的影响。

定位：[policy_qa_routes.py](../../src/runtime/api/policy_qa_routes.py) 第1006—1040、1942—1950、2022、2099—2106行。

### 6. P2：快照、计算和最终回答缺少可直接核对的绑定

**当前职责**：工作台选单读取一遍，结算问答重新按单号读取；分解内部又多次查询登记、原单、明细、周期、年度、目录。

**本次证据及界限**：01工件有12次查询、358条返回（其中345条是字典），登记查询重复一次。05正文与06 SSE正文不同；公开投影与SSE内分解只有summary_text/summary_source不同，可由路由以模型答案覆盖summary解释，不能因此声称源金额发生变化。工件缺统一manifest，无法证明05和06是同一次生成的逐字前后关系。

周期派生已经检查年度、交易流水和负差，这是已有有效防护，不应重复报告为缺失。本轮未进行实库并发修改，也未证明数据库隔离已造成错误；仍需确认多表读取的一致性及页面选单与问答的版本绑定。

**最小修改**：每轮使用服务端冻结的结算/规则快照，绑定snapshot_id或内容哈希、目标字段、算法版本、规则版本、提示词/模型路由版本及qa_turn_id。页面追问携带快照引用，服务端校验其所属单据及用户权限；数据变化时明确重算。依赖库提供的一致性读取或校验关键修订号，不假定多次SELECT天然属于同一时点。

答案放在独立的turn结果中，避免把一个字段答案覆盖全单分解summary。审计导出增加manifest，标清单次模型调用与单独SSE回放，默认脱敏；01工件含出生日期，本报告没有复制该值。

**不修的后果**：页面金额、问答依据与审计工件可能无法明确对应；事故发生后难以确认究竟是源数据、算法版本还是模型表述变化。

## 建议的最小目标设计

```mermaid
flowchart LR
    Q[用户问题] --> T[识别目标字段与问题类型]
    S[服务端冻结结算及规则快照] --> C[现有确定性分解]
    C --> E[提取目标计算及必要证据]
    T --> E
    E --> G[按证据决定可解释范围]
    G --> R[后端渲染金额 比例 算式 来源]
    G --> L[可选模型组织允许的说明]
    L --> R
    R --> O[页面与SSE共用的解释结果]
```

实际的单一接口应表达“基于某份服务端快照，解释某字段/问题”，把目标识别、依赖闭包、解释资格、引用绑定、失败降级收在同一模块。调用方不再分别学习和拼装内部快照、公开投影、第二套支付公式、模型白名单及引用规则。

567这个问题只需要：目标TCZHF；6000医保内、1300起付、4700本段基数；15%基础、60%折算、9%个人、91%基金；计算记录及这几个节点的来源。默认不需要军残、公疗、二次大病、救助等后续分支。

确定性核心解释可以直接为：

> 本笔医保内6000.00元，扣除起付1300.00元，本段基数4700.00元。按本单采用的在职自付基础15%及退休折算60%，本段个人比例9%、基金比例91%，统筹支付4700.00×91%＝4277.00元。相关规则的确认状态在对应依据中列示。

这段事实不需要模型再次决定金额、角色或运算关系。开放式问题可让模型选择合法说明段或识别需要澄清的字段；关键事实继续由相同计算记录渲染。

## 修改顺序与验收

1. **封住错误事实输出**：以8个探针为初始反例集，至少拦住字段串项、错误算式、候选档冒用、无依据权威声明和无单位金额；识别辅助投影已有数值。验证守卫行为不能只断言提示词包含一句禁止说明。
2. **统一业务来源**：删除/替换重复支付公式；567基金包含4277，个人构成包含423，源表已返回的0正确保留，缺字段仍保持未知。
3. **按问题取证**：TCZHF输入只带所需计算，引用包含15%与60%的对应出处；不再将65%/75%/85%当作本题已执行依据。
4. **同路径评测**：相同快照、mode、链路和运行策略下，业务入口与评测调用同一模块，得到相同确定性解释与资格状态；随后补prefix恢复和候选模式隔离回归。
5. **状态、降级、快照**：模型超时仍能展示4277的确定性解释；完整缺证项不被掩盖；修改规则或数据后可从快照和版本记录解释差异。

实施时先补会失败的测试，再修改生产代码，按项目单元→API→Flow顺序验收。评测断言字段、角色、关系、依据及错误处理，不能只断言正文含“4277”或guard=PASS。

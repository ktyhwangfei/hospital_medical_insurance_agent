# 四链路结算解释代码评审与真实问答核对

What this change does: 本轮审查当前工作区的结算解释实现，包括未提交代码；不修改业务代码。按用户给出的四组患者与单据定位，逐项检查页面金额、费用名称、模型输入、金额守卫及 SSE 结果。

日期：2026-10-23。服务：本工作区 8109/3109。假设使用场景：经办人员单笔交互查询；本轮不评价生产并发能力。

**结论：尚不满足“所有展示的金额和费用项目都能解释”。发现 1 项 P1、4 项 P2；另有累计口径与字段绑定的验收缺口。**

## 必须修复

### 1. [P1] 加粗和表格会绕过金额归属检查

- **现象**：0408 的现金实际为 1837.50 元。用同单数据、仅替换网关返回文本，`本单现金支付为 **1597.50 元**。` 和表格 `| 当次个人现金支付金额 | 1597.50 |` 均被接受：`used_model=true`，无错误提示。
- **问题**：`model_explanation.py:1057` 只抽取紧接“元”的数字，`:1104` 的标签检查还要求中文标签与数字之间符合固定文本格式。数字 1597.50 在本单基金金额中存在，所以数字白名单通过；加粗标记或表格分隔又令字段归属检查跳过。这是对当前源码的确定性复现，不是本轮真实模型自然生成了该错误。
- **最小修复**：先统一常见 Markdown 表述，再按标签对应的金额校验；覆盖表格表头给出单位、单元格不重复写“元”的形式。补“同单合法数字归到错误字段”的回归用例，不能只测资料外数字。
- **不修后果**：基金金额可被说成现金金额，仍被系统作为正常模型解释交付。

### 2. [P2] 正确的分桶、分段金额被当成整单合计误拦

- **现象**：688 单独追问救助支付返回 `unavailable`，提示“大病支付：回答 181.53 元，本单 226.9600 元”；567 追问补充保险也返回 `unavailable`，提示“退休补助：回答 0 元，本单 211.5000 元”。两笔的分桶/分段计算均已提供。
- **问题**：`model_explanation.py:1080`、`:1087`、`:1123` 把“医保内大病支付”匹配成“大病支付”总额，把“大额段退休补助”匹配成“退休补助”总额。确定性候选 `医保内大病支付 181.53 元；医保外大病支付 45.43 元；合计大病支付 226.96 元` 和 `统筹段退休补助 211.50 元；大额段退休补助 0 元；合计退休补助 211.50 元` 均被拒绝。
- **最小修复**：把已提供的分桶/分段标签及其金额纳入同一个归属表，优先匹配完整标签；总额继续校验总额，不直接宽泛放行所有“医保内/段”限定语。为上述两笔合法构成各补一个回归用例。
- **不修后果**：金额有依据也解释失败，正确解释退化为“未形成可靠结论”。

### 3. [P2] 多目标问题被裁成局部问题，丢掉已存在的明细

- **现象**：真实提问“请分别解释第1行复方丹参滴丸和第2行注射用培美曲塞二钠的医保内、医保外金额”，返回第1行后称“本次提供的资料中没有该行的明细数据（line_evidence仅含第1行）”，拒绝解释第2行。该单第2行实际存在，单独问能解释。
- **问题**：`model_explanation.py:215` 只取第一个行号，`:232` 立即返回单行目标，`:650` 又把模型明细裁成一行。另一个同类问题是“所有展示金额……以及医保内外划分”会在 `:246` 被识别成仅问医保内汇总，`:674` 继续裁掉其他目标的计算证据。
- **最小修复**：至少检测多个显式行号并保留这些目标；若当前接口只支持单行，应明确提示分次提问，不能声称已存在的数据缺失。识别“整单/全部展示金额”范围后再做局部字段裁剪。
- **不修后果**：用户逐项或整单提问都可能漏项，还会把内部裁剪字段名暴露给用户。

### 4. [P2] 门特自付一在总览中丢失构成，并被误称原单金额

- **现象**：567 总览称“个人支付自付（一）金额 1723.0000 元，按原单记录列示，本单未提供逐项计算路径”；688 总览同样把 279.2700 元说成原单记录。单独追问却分别能给出 `1300.00 + 423.00 + 0.00 = 1723.00`、`0.00 + 279.27 = 279.27`。追加不含局部字段词的整单问法，688 仍复现错误归源。
- **问题**：两个内核已经记录 `calc.self_pay_1.parts`，并明确 `SELF_PAY_1_BOOK_COLUMN_UNMAINTAINED`（居民内核 `resident_outpatient_special.py:693`，职工内核 `employee_outpatient_special.py:1618`）。`explanation_scope.py:67` 因缺账面核对目标不授予 `explainable`，而 `model_explanation.py:691` 的整单输入只保留 `explainable` 字段，连“有分量计算、无账面核对目标”的事实与专门说明也遗漏了。
- **最小修复**：整单模型输入保留这种派生金额及构成、来源属性和核对限制；统一说“计算构成”，保持 `calculation_checked=false`，不伪造账面核对通过。补总览与单字段追问的一致性用例。
- **不修后果**：同一金额因问法不同而一会儿可解释、一会儿无路径，且金额来源被说错。

### 5. [P2] 结算解释侧栏与问答采用不同口径

- **现象**：同一 0408，侧栏来源接口可解释字段 9 个，问答只有 4 个；职工 000008 为 10 个与 4 个。问答对起付和大额支付只能列原单并说明累计口径未确认。
- **问题**：`settlement-agent-workspace.tsx:131` 选单调用工作台的 `decomposeFee`；该入口按 `integration.py:395` 读取当前开启的候选口径。主问答显式关闭该口径。`:79` 又优先保留初始侧栏结果，后续 SSE 的主链结果不会取代它，因此用户是在对一份口径不同的投影提问。
- **最小修复**：policy-qa 的侧栏读取也复用明确关闭候选口径的分解入口；候选口径继续留在验证工作台。不能为让两个入口相同而直接把待签核口径开启到主链。
- **不修后果**：右侧显示可展开的计算，左侧却解释为缺依据，用户无法判断应信哪一份。

## 尚未满足的业务验收条件

这部分是证据或能力缺口，不把当前谨慎降级判作金额算法错误。

- 两个普通门诊样本缺少主链认可的交易前累计口径，阻断起付、大额支付与依赖它们的个人支付独立重算。`snapshot_service.py:170`、`:236` 明确要求确认口径；不得将同院累计下界或验证工作台候选值直接当成精确累计。
- 普通门诊的“大额超封顶金额”没有计算字段绑定；职工门诊“大病支付/救助支付”、居民门诊“救助支付/退役医疗费”、两个门特“退役医疗费”也未关联到独立分解字段。现在能报原单数，不能解释计算原因。已有原单来源与没有来源是两回事，不应一律称“没有数据”。
- 账户/现金应解释为支付方式和原单渠道，与个人负担勾稽，不要求伪造报销公式；不适用项目应给出适用性说明，不能仅凭金额为零推断无资格。
- 规则签核状态没有因本轮金额核对而升级；本轮没有重新核证外部政策原文。

## Context

医院侧医保业务已经具备医保接口、事前审核、DRG/DIP、HIS、EMR、病案、收费和医保数据中台等专业能力，但这些能力通常分散在不同系统中。医保办、收费员、信息科、病案室、临床医生、科主任和院领导在处理结算异常、出院前风险、合规拒付、病案质量和支付运营问题时，需要跨系统查询、理解专业规则、协调责任角色并跟踪处理闭环。

本设计将平台定位为医保 AI 导办智能体，而不是替代现有业务系统的自动交易系统。AI 负责理解用户意图、组织上下文、检索知识、解释风险、生成建议和推动任务闭环；正式结算、退费、冲正、病案首页修改、费用明细修改等高风险动作必须由既有业务系统和人工确认完成。

现有文档已沉淀若干模块方向：数据与知识底座、业务系统适配器、运行时上下文、任务规划、编排执行和任务闭环。本变更把这些方向收敛为一个可实施的 MVP 架构，优先覆盖医保结算异常导办和出院前联合质控两个场景。

后端技术栈选型为 FastAPI、uvicorn、asyncio、PostgreSQL、Redis/Valkey、Milvus 和 Nginx。FastAPI 作为异步 API 框架并原生生成 OpenAPI，uvicorn 作为 ASGI 运行服务器，asyncio 支撑外部系统调用和编排并发，PostgreSQL 承载结构化数据与审计日志，Redis/Valkey 承载会话缓存、限流和分布式锁，Milvus 承载知识向量检索，Nginx 承担反向代理、SSL 终结和基础安全防护。

前端技术栈选型为 Vue 3、TypeScript、组件化 Web SDK 和 H5 容器化嵌入。第一阶段后端 MVP 只提供稳定 OpenAPI、响应结构和可嵌入前端所需契约，不直接建设完整前端工程。

## Goals / Non-Goals

**Goals:**

- 建立医保 AI Chat 统一入口，支持多角色通过自然语言发起导办请求。
- 建立角色权限识别、患者医保上下文构建和敏感数据脱敏机制。
- 建立基于模板优先的任务规划能力，将用户请求转换为结构化执行计划。
- 建立编排执行引擎，统一调度模型、知识库、规则解释、工具、业务系统适配器和任务闭环服务。
- 建立医保数据与知识底座，支撑患者医保画像、医保主数据、错误码知识、政策知识、规则解释和来源引用。
- 建立业务系统适配抽象，降低对首信、东软、大瑞集思、HIS、EMR、病案和收费系统的直接耦合。
- 建立人工确认和审计追踪能力，确保高风险动作不被 AI 自动执行。
- 第一阶段完成医保结算异常导办和出院前联合质控 MVP。
- 第一阶段以 FastAPI 后端 MVP 骨架、内存实现和自动化测试样例验证核心业务链路。

**Non-Goals:**

- 不替代医保正式结算系统。
- 不自动执行退费、冲正、撤销结算。
- 不直接修改病案首页、诊断、手术、费用明细或医嘱。
- 不替代东软事前审核、大瑞集思 DRG/DIP 或首信医保接口的正式业务结论。
- 不在第一阶段建设全量医保运营驾驶舱。
- 不在第一阶段实现全自动申诉闭环。
- 不在第一阶段实现多智能体自由自治执行。
- 不在第一阶段直接接入真实 PostgreSQL、Redis/Valkey、Milvus、Nginx 和医院业务系统，先通过接口抽象与内存实现保证可替换性。
- 不在第一阶段创建完整 Vue 3 前端工程，仅保留后端 API 契约和 Web SDK 友好的响应模型。

## Decisions

### Decision 1: 采用分层架构承载医保 AI 导办能力

平台采用六层架构：用户入口层、AI 交互层、运行时层、AI 能力层、数据与知识底座、业务系统适配层。

```text
┌────────────────────────────────────────────┐
│ 用户入口层                                  │
│ 医保办工作台 / 收费员导办 / 医生端 / 驾驶舱 │
└────────────────────┬───────────────────────┘
                     ↓
┌────────────────────────────────────────────┐
│ AI 交互层                                   │
│ 会话管理 / 意图识别 / 多轮澄清 / 结果解释    │
└────────────────────┬───────────────────────┘
                     ↓
┌────────────────────────────────────────────┐
│ 运行时层                                    │
│ 上下文 / 规划 / 编排 / 人工确认 / 任务闭环   │
└────────────────────┬───────────────────────┘
                     ↓
┌────────────────────────────────────────────┐
│ AI 能力层                                   │
│ 模型网关 / RAG / 规则解释 / 工具调用         │
└────────────────────┬───────────────────────┘
                     ↓
┌────────────────────────────────────────────┐
│ 数据与知识底座                              │
│ 结构化数据 / 向量库 / 文件库 / 主数据 / 指标 │
└────────────────────┬───────────────────────┘
                     ↓
┌────────────────────────────────────────────┐
│ 业务系统适配层                              │
│ 首信 / 东软 / 大瑞集思 / HIS / EMR / 病案    │
└────────────────────────────────────────────┘
```

理由：医保 AI 平台是跨模块、跨系统、跨角色的复杂能力，单纯 Chatbot 无法保证事实来源、权限控制、审计追踪和任务闭环。分层架构可以让交互、规划、执行、数据、知识和适配解耦。

替代方案：直接让 Chat 服务调用各业务系统接口。该方案实现快，但会导致权限、审计、错误处理、任务状态和高风险动作控制分散，后续难以扩展。

### Decision 2: AI 不直接访问业务系统，必须通过规划、编排和适配器访问

用户请求先进入意图识别与上下文构建，再由任务规划生成 ExecutionPlan，最后由编排引擎调用适配器、知识库和模型。

```text
用户问题
  ↓
意图识别与上下文构建
  ↓
ExecutionPlan
  ↓
编排执行
  ├─ 业务系统适配器
  ├─ 数据访问服务
  ├─ 知识检索服务
  ├─ 规则解释服务
  └─ 模型网关
  ↓
带来源引用的导办结果
```

理由：医保业务存在强审计、强责任边界和高风险动作约束。所有系统调用必须有计划、有权限、有状态、有审计。

替代方案：由大模型基于工具调用自动选择接口。该方案灵活但不可控，难以证明执行路径和安全边界。

### Decision 3: 任务规划采用模板优先，模型辅助

第一阶段内置医保结算异常导办和出院前联合质控两个规划模板。简单场景直接套用模板，复杂场景允许模型辅助补全步骤，但必须经过计划校验。

计划校验包括：用户权限、上下文完整性、适配器可用性、高风险动作、依赖关系、输出格式和来源引用要求。

理由：模板优先可以降低模型不确定性，并保证关键医保流程稳定可审计。

替代方案：完全由大模型动态规划。该方案扩展性强，但在医保业务中风险过高。

### Decision 4: 编排执行第一阶段支持基础 DAG、重试、暂停和恢复

编排引擎第一阶段支持顺序执行、基础 DAG、步骤状态持久化、适配器调用、知识检索、模型调用、失败重试、人工确认暂停与恢复。

核心状态包括：PENDING、RUNNING、WAITING_CONFIRM、SUCCEEDED、FAILED、CANCELLED、SUSPENDED。

理由：医保导办流程经常需要跨系统查询和人工确认，必须支持中断、恢复、审计和失败处理。

替代方案：同步串行调用所有能力。该方案简单，但无法支持长流程、人工确认、失败恢复和任务闭环。

### Decision 5: 数据与知识底座必须提供来源引用和质量提示

结构化数据、向量知识、文件材料和缓存数据都需要统一通过数据访问服务获取。AI 生成的风险解释、处理建议和质控清单必须保留来源引用。

数据质量不足时，系统不得输出确定性结论，而应提示缺失数据、来源系统、影响范围和建议补充路径。

理由：医保结论涉及业务责任，必须可追溯。来源引用和质量提示是抑制模型幻觉的核心机制。

替代方案：把查询结果拼接给模型自由总结。该方案容易生成看似合理但无法追溯的结论。

### Decision 6: 高风险动作必须被拦截并转为建议、草稿或待办

当执行计划涉及正式结算、退费、冲正、病案首页修改、费用明细修改、最终申诉结论等高风险动作时，系统必须阻止自动执行，并改为生成建议、材料草稿或待办任务，等待人工确认。

理由：平台定位是导办与协同，不是自动交易或自动修改业务事实。

替代方案：允许 AI 在高置信度时自动执行。该方案在医疗医保场景中责任风险不可接受。

### Decision 7: 第一阶段采用内存实现验证后端 MVP，基础设施适配后置

第一阶段创建 FastAPI 后端工程骨架和内存实现，覆盖领域模型、样例数据、数据访问接口、知识检索接口、适配器协议、权限校验、上下文构建、任务规划、编排执行、任务闭环和测试样例。PostgreSQL、Redis/Valkey 和 Milvus 在第一阶段只定义端口、模型和替换边界，不作为运行前置依赖。

理由：当前项目处于从 OpenSpec 提案进入工程实现的初始阶段，过早引入数据库、缓存、向量库和真实医院系统会显著增加部署与调试复杂度。内存实现可以优先验证医保导办业务链路、接口契约和测试验收标准。

替代方案：第一阶段直接建设 PostgreSQL、Redis/Valkey、Milvus 和真实系统适配。该方案更接近生产，但会导致 MVP 验证周期变长，并把业务链路问题与基础设施问题混在一起。

### Decision 8: 后端 API 契约优先服务多端前端集成

后端 API 以 Web SDK 和 H5 容器化嵌入为主要消费方，响应结构必须稳定、可解释、可渲染，并包含场景、状态、结果、来源引用、待办任务、人工确认、缺失字段、不确定性和审计摘要。

理由：前端计划支持 Vue 3 管理后台、组件化 Web SDK、H5 容器化嵌入和存量系统 Webview 集成，统一 API 契约可以降低多端接入成本。

替代方案：先为单一管理后台定制接口。该方案短期简单，但会降低后续多入口复用能力。

### Decision 9: 采用 Project-root 长期工程架构，第一阶段只启用后端核心子集

项目长期采用 Project-root 分层工程架构，以支撑 SaaS 门户、嵌入式组件、统一交互、接入网关、运行时、业务场景、知识扩展、业务系统适配、模型服务、数据平台、安全治理和可观测性等能力。

## Risks / Trade-offs

- 数据接入不完整 → 提供适配器降级策略，支持接口、数据库视图、文件交换和离线同步多种方式。
- 厂商接口不开放 → 先接入可用数据源，使用数据中台或中间表形成患者医保画像基础版。
- 数据质量不足导致结论不可靠 → 在数据访问层返回质量状态，AI 结果必须展示缺失项和不确定性。
- 模型幻觉 → 使用结构化数据、知识检索、规则解释和来源引用约束输出，禁止无来源的确定性结论。
- 高风险动作被误执行 → 在任务规划和编排执行两层都做动作黑名单与人工确认校验。
- 规划模板覆盖不足 → MVP 只覆盖两个高价值场景，后续通过新增模板扩展拒付申诉、科室运营和领导驾驶舱。
- 跨系统调用延迟高 → 引入缓存、并行查询、超时重试和降级返回，避免单个外部系统阻塞整体导办。
- 用户角色责任不清 → 任务闭环中显式记录责任角色、推荐处理步骤、处理状态和审计轨迹。
- 内存 MVP 与生产基础设施存在差距 → 通过端口/适配器分层、自动化测试和响应契约保证后续可替换为 PostgreSQL、Redis/Valkey 和 Milvus。
- 前端暂不实现导致交互细节不完整 → 后端 API 输出需包含足够的结构化字段，便于后续 Vue 3、Web SDK 和 H5 容器按同一契约渲染。
- Project-root 长期目录过大导致 MVP 复杂化 → 第一阶段只启用后端核心子集，`apps/`、`interaction/`、`gateway/`、`model_service/`、`deploy/` 暂缓创建或仅保留文档规划。

## Migration Plan

1. 先以 FastAPI 后端骨架、内存仓储、模拟适配器和样例数据验证端到端链路：用户问题、上下文、规划、编排、知识检索、结果生成、审计和任务闭环。
2. 使用自动化测试覆盖两个 MVP 场景、权限不足、高风险动作拦截、来源引用、外部调用失败和审计还原。
3. 固化 API 契约和响应结构，为 Vue 3 管理后台、Web SDK 和 H5 容器化嵌入提供稳定对接基础。
4. 将内存数据访问替换为 PostgreSQL，实现结构化数据、配置、任务和审计日志持久化。
5. 将内存会话与限流状态替换为 Redis/Valkey。
6. 将内存知识检索替换为 Milvus 向量检索和 PostgreSQL 元数据管理。
7. 接入医保结算异常导办所需的真实数据：医保交易流水、费用上传状态、收费结算状态、错误码知识库和患者就诊索引。
8. 接入出院前联合质控所需的真实数据：费用、医嘱、诊断、病案首页、事前审核结果、DRG/DIP 预分组和医保接口状态。
9. 在 Nginx 前置代理后进行试点科室或医保办工作台灰度发布。
10. 根据审计日志、用户反馈、任务闭环数据和误判案例迭代模板、知识库和适配器。

回滚策略：MVP 阶段所有导办结果仅作为建议和待办，不直接写回高风险业务事实；如出现问题，可关闭对应场景模板、禁用外部适配器调用或回退到只读查询模式。

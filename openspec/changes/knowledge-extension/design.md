## Context

院端医保智能体当前已具备 Chat API、意图识别、模型服务、运行时状态、安全契约、统一适配器基础规格，以及医保结算异常导办和出院前联合质控两个 MVP 场景。现有 `knowledge_extension/knowledge` 只提供错误码知识的内存查询，无法支撑医保政策、院内制度、审核规则、申诉模板、规则解释、提示词模板和扩展能力统一治理。

知识与扩展服务位于 PaaS 层能力服务域，与模型服务、业务适配器、运行时编排平级。它不应直接承载业务系统接口调用，也不应把知识检索结果直接变成正式业务裁决。其核心职责是将知识资产、规则解释和扩展能力注册为可调度、可审计、可引用的能力，供运行时计划步骤按需调用。

本变更需要在保持 MVP 内存实现可运行的前提下，先建立清晰契约和最小可用实现边界，为后续真实向量库、知识管理后台、MCP、Tool、Skill、A2A 和多场景业务应用接入预留扩展点。

## Goals / Non-Goals

**Goals:**
- 定义知识资产、知识切片、知识来源、知识版本、数据质量和审计元数据模型。
- 提供统一 RAG 检索契约，支持医保业务语义检索、关键词检索、重排、上下文组装、引用溯源和无结果降级。
- 提供统一规则解释契约，让错误码、政策规则、审核规则、DRG/DIP 规则和病案质控规则可以输出解释、处理建议、适用条件和引用依据。
- 提供提示词模板管理契约，支持按场景、角色、输出格式和安全约束选择版本化模板。
- 提供扩展能力注册契约，覆盖 Tool、Skill、MCP、A2A 的元数据、安全边界、权限要求、输入输出 schema 和审计要求。
- 与运行时执行计划、安全契约、适配器契约和模型服务保持解耦，通过 Protocol 与 Pydantic 模型完成边界交互。

**Non-Goals:**
- 不建设完整知识管理后台 UI。
- 不强制接入真实 Milvus、Elasticsearch、对象存储或关系型数据库。
- 不实现真实 MCP Server、外部 Agent 网络协议或远程 Tool 沙箱。
- 不让知识服务直接访问 HIS、EMR、收费、医保接口、事前审核、DRG/DIP 或病案系统。
- 不替代医保正式结算、事前审核裁决、DRG/DIP 正式分组、病案修改或申诉最终结论。

## Decisions

### 1. 将知识资产与 RAG 检索分为两个能力边界

知识资产管理负责资产、版本、来源、切片、索引状态和审计元数据；RAG 检索负责查询理解、召回、重排、上下文组装和引用输出。两者通过知识切片和来源引用模型衔接。

选择该方案是因为知识资产生命周期和在线检索链路的变化频率不同。资产管理后续可能接入后台上传、审核发布和增量索引，而检索链路更关注运行时性能、召回质量和上下文预算。替代方案是把资产管理和检索放在同一个服务类中，但会导致职责膨胀，不利于后续替换真实向量库与知识后台。

### 2. RAG 结果必须优先返回结构化引用，而不是只返回文本片段

检索结果应包含 `source_id`、`source_type`、`title`、`version`、`chunk_id`、`section`、`effective_date`、`score` 和 `retrieved_at` 等字段，运行时再将其转换为响应 citations。

选择该方案是为了满足 AI 输出可追溯要求，并避免模型生成阶段丢失依据来源。替代方案是只把拼接后的上下文交给模型，但这会降低审计可还原性，也无法可靠支撑安全契约。

### 3. 规则解释采用确定性优先、模型增强可选的策略

规则解释服务应先基于结构化规则、错误码表和知识库条目生成确定性解释；当需要自然语言润色或复杂归纳时，才通过模型服务进行增强，并保留原始规则引用。

选择该方案是因为医保规则解释需要稳定、可审计和可复核。替代方案是完全依赖 LLM 解释规则，但会增加幻觉风险和审计难度，不适合医保高风险场景。

### 4. 提示词模板作为知识与扩展服务的受控资产管理

提示词模板应按场景、角色、输出格式、安全约束和版本进行管理，运行时通过模板选择服务获取模板和渲染变量约束。模板输出不得绕过安全契约，必须声明引用来源或不确定性要求。

选择该方案是因为提示词与知识、规则和输出结构高度相关，且需要版本审计。替代方案是将提示词硬编码在运行时或模型服务中，但这会降低可维护性，并造成场景模板分散。

### 5. 扩展能力注册只定义契约与内存目录，不在本变更实现真实执行沙箱

扩展注册服务记录 Tool、Skill、MCP、A2A 的能力元数据、权限要求、风险等级、输入输出 schema、超时、审计策略和调用端点标识。运行时调度只通过注册信息进行选择和风控，真实调用由后续能力执行器或适配层实现。

选择该方案是为了先建立可治理的能力目录，同时避免在一个变更内引入过多协议细节。替代方案是直接实现完整 Tool/MCP/A2A 调用，但会扩大交付范围，并增加安全边界风险。

### 6. MVP 阶段使用内存实现与端口抽象

本变更优先新增 Pydantic 模型、Protocol 端口、内存知识资产库、内存检索器、内存规则解释器、内存模板库和内存扩展注册表。真实向量库、缓存、对象存储和数据库仅通过现有 `data_platform/storage` 端口表达。

选择该方案与项目当前 MVP 阶段一致，可快速形成测试闭环。替代方案是直接接入生产级基础设施，但当前项目基础设施仅定义端口，不作为运行依赖。

### 7. 通过知识与扩展服务门面隔离运行时和子能力实现

运行时和业务场景不应分别依赖资产仓储、检索器、规则解释器、模板选择器和扩展注册表的具体实现，而应优先依赖一个组合型门面或组合型服务容器。门面负责聚合知识增强结果、引用、不确定性、降级原因和审计事件。

选择该方案是为了避免运行时编排层出现过多知识子模块调用细节，也便于后续将内存实现替换为真实向量库、知识后台或远程能力目录。替代方案是业务场景直接调用每个知识子模块，但会造成场景逻辑重复处理降级和引用合并。

### 8. 统一知识输出、规则解释输出和 API citations 的映射

知识检索引用、规则解释证据、模板安全约束和扩展能力审计均应有内部结构化模型；面向 API 的 `citations` 只保留用户可展示且可追溯的摘要字段。敏感输入摘要、权限拒绝原因和扩展调用内部参数只进入审计字段或脱敏后的诊断字段。

选择该方案是为了兼顾前端兼容、审计还原和最小必要展示。替代方案是把内部证据模型直接透传到 API，但容易暴露敏感字段，也会让外部响应契约与内部实现强耦合。

### 9. 明确知识范围过滤属于安全前置条件

资产查询、切片召回、规则解释证据拼接、模板选择和扩展选择必须先执行角色、场景、租户、院区和可见性过滤，再进行重排、解释或上下文组装。过滤结果应记录审计摘要，但默认不向普通用户暴露被过滤知识的标题或内容。

选择该方案是因为知识资产本身可能包含院内制度、运营指标或敏感规则说明。替代方案是在响应组装阶段统一过滤，但此时模型上下文可能已经接触无权知识，违反最小必要原则。

## Risks / Trade-offs

- [Risk] 内存 RAG 与真实向量检索的召回行为差异较大 → 通过 Protocol、结构化返回模型和契约测试固定边界，后续替换真实实现时保持 API 兼容。
- [Risk] 规则解释与业务场景边界不清，可能把建议误当成裁决 → 规则解释输出必须包含适用条件、限制说明、引用和不确定性，不输出正式裁决结果。
- [Risk] 提示词模板引入后可能绕过安全输出要求 → 模板元数据必须声明输出要求，运行时响应组装继续执行 citations 或 uncertainties 校验。
- [Risk] 扩展能力注册后被误用于执行高风险动作 → 扩展元数据必须包含风险等级和 required_permissions，高风险能力只能创建人工确认任务，不允许自动执行。
- [Risk] 知识版本与引用失配 → 检索结果必须携带版本、发布日期或生效日期，响应引用保留检索时版本信息。
- [Risk] 多能力一次性建设范围过大 → 分阶段实现：先模型与端口，再内存实现，再运行时集成，最后补充管理 API 与真实基础设施。

## Migration Plan

1. 新增 `knowledge_extension` 下的知识资产、RAG、规则解释、提示词模板和扩展注册子目录及模型端口。
2. 新增知识与扩展服务门面，组合内存资产仓储、内存切片仓储、内存检索器、内存规则解释器、内存模板选择器和内存扩展注册表。
3. 保留现有 `knowledge_extension/knowledge` 错误码查询接口，逐步迁移为规则解释服务的数据来源之一，并补充兼容适配测试。
4. 在运行时计划与场景服务中以可选依赖方式接入新知识服务，确保现有 Chat API 响应兼容。
5. 为无知识命中、知识源不可用、模板缺失、扩展权限不足和高风险扩展拦截提供降级输出和审计事件。
6. 完成契约测试、集成测试和 OpenSpec 验证后，再考虑新增管理 API 或真实存储实现。

Rollback 策略：若新知识与扩展服务接入导致场景失败，可回退到现有错误码内存知识库和确定性业务响应；新模块通过端口注入，不影响现有适配器与模型服务。

## Open Questions

- 知识资产审核发布流程是否需要在本阶段纳入，还是留给管理后台变更实现？
- RAG 检索是否需要支持多租户、院区隔离和科室级知识范围过滤？
- 提示词模板是否需要提供 API 管理端点，还是先以内存配置和代码内置模板实现？
- 扩展注册中的 MCP 与 A2A 是否需要在后续拆分为独立变更？

## Resolved for MVP

- 知识资产审核发布流程本阶段只通过状态字段和内存初始化数据表达，不实现上传、审核、发布 API。
- 多租户、院区和角色范围过滤纳入模型与内存过滤逻辑；复杂组织树、科室继承和跨院区授权留给后续变更。
- 提示词模板本阶段以内存配置和代码内置模板实现，不新增模板管理端点。
- MCP 与 A2A 本阶段只进入扩展注册元数据和选择校验，不实现远程协议调用。

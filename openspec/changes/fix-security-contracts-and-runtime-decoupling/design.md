## Context

院端医保智能体系统当前处于 MVP 后的技术债收敛阶段。核心 API、两个业务场景、意图识别、模型服务、风控拦截和部分任务闭环已经落地，但仍有三类跨模块问题需要统一处理。

第一，安全与契约不一致。高风险动作拦截结果、降级响应和流式模型错误没有统一的来源引用、不确定性提示和结构化错误语义。第二，模型流式链路与非流式链路行为不一致，Provider 层未统一规范化流式网络异常，Gateway 层吞掉流式异常，API 层难以返回可解释错误事件。第三，运行时能力仍是场景直连适配器的薄实现，缺少上下文构建、计划、编排、审计视图和适配器基础契约。

本变更覆盖 `security_contracts`、`adapter_foundation` 和 `runtime_execution_loop` 三条主线，目标是在不引入真实外部系统依赖的前提下，为后续接 HIS、医保接口、事前审核、DRG/DIP、EMR、病案和收费系统建立稳定边界。

## Goals / Non-Goals

**Goals:**

- 所有 AI 输出和安全拦截输出均满足“携带 citations 或 uncertainties”的硬性约束。
- 模型流式调用与非流式调用使用一致的异常归一化、审计和 API 错误事件契约。
- 新增适配器基础层，统一调用结果、调用审计、异常、重试策略、脱敏钩子和权限钩子。
- 建立最小运行时执行闭环：上下文构建、计划生成、顺序编排、状态持久化、任务状态查询和审计视图。
- 保持现有 MVP API 路径与业务场景兼容，避免破坏现有测试与演示页面。

**Non-Goals:**

- 不接入真实 PostgreSQL、Redis、Milvus 或院内业务系统。
- 不实现完整 DAG 编排、并行执行、断点续执和分布式任务调度。
- 不重写全部领域模型，只为本变更需要的契约补充最小 Pydantic 模型。
- 不替代医保正式结算、事前审核裁决、DRG/DIP 正式分组、病案首页修改或费用明细调整。
- 不新增新的医保业务场景，不扩大当前两个 MVP 场景以外的产品范围。
- 不在本次变更中引入异步任务队列、WebSocket、数据库迁移或外部服务部署脚本。

## Decisions

### 决策一：以 Pydantic 契约包裹高风险、降级、任务和适配器调用结果

现有 `AgentResponse` 内部仍大量使用裸 `dict`。本变更不一次性重写全部响应结构，而是先新增可复用的 `Citation`、`AuditEvent`、`AdapterCallResult`、`RuntimeTask`、`StreamErrorEvent` 等最小 Pydantic 模型，并在新增或触达链路中优先使用这些模型生成响应。

替代方案是一次性将 `AgentResponse` 所有内部字段严格模型化。该方案长期更理想，但会大面积影响现有测试、前端和业务场景，不适合本次技术债收敛的风险控制目标。

### 决策二：流式异常由 Provider 规范化、Gateway 记录并向上抛出、API 输出 SSE error

流式调用采用三层职责：Provider 将 `httpx` 超时、网络、HTTP、JSON 解析和状态码错误转换为模型服务异常；Gateway 记录模型名、场景、chunk 数、耗时和失败类型后继续抛出；API 将异常映射为结构化 SSE `error` 事件并最终发送 `done`。

替代方案是在 Gateway 层吞掉异常并只写日志。该方式对用户不可见，无法满足可解释失败和前端降级要求，因此不采用。

### 决策三：适配器基础层保持轻量 Protocol + BaseModel，不引入复杂框架

新增 `src/adapters/base/`，定义适配器调用协议、调用上下文、调用结果、适配器异常、审计记录与重试策略。现有内存适配器通过最小改造接入统一包装，业务场景仍通过具体适配器类调用，但返回值和审计语义一致。

替代方案是立即引入完整防腐层框架或依赖注入容器。当前项目仍是 MVP 内存实现，复杂框架会增加理解和测试成本。

### 决策四：运行时闭环先实现顺序计划，不实现完整 DAG

运行时新增上下文构建、计划模板、顺序编排执行器和状态仓储。医保结算异常导办、出院前联合质控和高风险动作请求先映射到确定性计划模板；每一步记录状态、输入输出引用、能力调用和审计引用。

替代方案是直接实现完整 DAG 编排与条件分支。该能力在长期架构中需要，但本次目标是修复技术债和契约缺口，最小顺序编排即可覆盖当前两个 MVP 场景。

### 决策五：审计视图从内存状态聚合生成

审计视图不新增持久化依赖，先从内存审计日志、运行时状态和任务闭环记录聚合出一次导办流程的用户、角色、请求、计划、步骤、调用、确认和结果。

替代方案是直接建设关系型审计表。当前基础设施仅定义端口，不作为运行依赖，因此先保持内存实现。

### 决策六：以兼容层迁移场景直连逻辑，不一次性删除场景服务

现有 `guide_settlement_exception` 和 `run_pre_discharge_qc` 已被测试和前端链路依赖。本变更将其作为编排步骤处理器或兼容包装保留，先把运行时上下文、计划、状态和审计插入调用链路，再逐步把场景内部的适配器调用迁移到统一执行器。

替代方案是一次性重写两个业务场景，让 API 只调用新编排器。该方案会使变更过大，也更容易破坏现有响应字段。

### 决策七：状态 ID 采用确定性前缀加请求时间或短哈希

workflow_id、task_id 和 audit_event_id 需要可追踪且避免固定硬编码。MVP 阶段使用确定性业务前缀加请求时间或短哈希生成 ID，不引入数据库自增或分布式 ID 服务。

替代方案是继续使用固定样例 ID 或仅按 patient_id 生成 ID。该方式会导致并发请求互相覆盖，审计视图无法区分不同导办流程。

## Risks / Trade-offs

- [Risk] 适配器返回契约迁移可能影响现有业务场景测试 → 通过兼容属性和渐进迁移降低风险，先保留现有字段语义。
- [Risk] 运行时闭环引入状态后，现有 API 响应可能出现字段差异 → 保持 `AgentResponse` 顶层字段不变，只增强 `audit`、`citations` 和状态查询。
- [Risk] 流式异常向上抛出后可能暴露底层错误信息 → API 层必须映射为标准错误码和用户可读信息，不直接透传敏感配置或原始请求内容。
- [Risk] 顺序编排不能覆盖未来复杂场景 → 在计划模型中保留依赖、风险等级和人工确认标记字段，后续可演进为 DAG。
- [Risk] 内存审计视图重启后丢失 → 明确为 MVP 阶段行为，后续通过 `data_platform/storage/relational` 端口替换。
- [Risk] 现有测试对硬编码 workflow_id、task_id 或时间有隐式依赖 → 先新增兼容断言或按稳定前缀断言，再替换硬编码值。
- [Risk] 同时改安全、适配器、运行时会造成任务过大 → 实现阶段按任务组分批提交，每组都必须保持 `python -m pytest src/tests -v` 可运行。

## Migration Plan

1. 先补安全契约与流式异常，确保现有 API 行为更可追溯但不改变主流程结果。
2. 再新增适配器基础模型与兼容包装，迁移内存适配器返回值但保留业务场景读取字段的兼容方式。
3. 然后新增运行时上下文、计划和顺序编排，将现有场景服务挂接为步骤处理器。
4. 最后接入 workflow、task、audit 查询接口并更新前端错误展示。

Rollback 策略：每组任务应保持独立提交；如运行时编排接入失败，可暂时让 `process_chat_request` 回退到现有场景直连路径，同时保留已完成的安全契约和模型流式异常修复。

## Open Questions

- 审计视图是否需要新增公开 API 路由，还是先作为服务供测试和内部调用使用。
- 适配器基础契约中业务数据字段是否统一命名为 `data`，还是按能力定义更具体的 Pydantic 子模型。
- workflow 和 task 内存仓储是否应在 `create_app` 生命周期内单例化，以支持同一测试客户端内跨请求查询状态。
